# 07 · Своя тема: контракт, подсказки, демо

Этот раздел - для автора темы: дизайнера, верстальщика или AI-агента, который делает тему не для одного сайта, а для многих. Здесь - как описать в `theme.yaml`, из чего состоят страницы темы, как написать подсказки для человека без опыта, как собрать демо, проверить тему и упаковать её. Как устроены сами шаблоны, модули и стили, - в [04 · Тема и дизайн](04-theme.md). Тема уже сделана на версии 0.2 - сразу переходите к разделу [«Перенос темы с 0.2 на 0.3»](#migrate-0-3).

> **Команды в разделе написаны для Docker** и запускаются из папки сайта, на котором вы делаете тему (`cd ~/sites/моя-тема`), поэтому путь к сайту в них - точка. Поставили движок без Docker - замените всё до имени образа (`ghcr.io/fmstm/heron:…`) включительно словом `heron` ([подробнее](00-install.md#without-docker)).

## Что тема рассказывает о себе <a id="what-a-theme-says"></a>

Шаблоны и стили объясняют движку, как страница выглядит. Но тот, кто будет вести сайт на вашей теме, шаблоны не читает. Чтобы он справился сам, тема рассказывает о себе ещё три вещи:

- **контракт** - какие типы страниц она умеет, какие блоки ждёт на каждом и из каких полей состоит каждый блок. Пишется в `theme.yaml`;
- **подсказки** - что писать в каждое поле, как это скажется на сайте и в поиске, хороший пример и частые ошибки. Тоже в `theme.yaml`, на каждом языке темы;
- **демо** - страницы, на которых видно всё, что тема умеет. Это контент сайта, из которого тему упаковывают.

Из этих трёх частей движок сам строит всё остальное: вопросы команд `page add` и `category add`, формы студии в браузере, справку темы, описание для агента (`describe --json`) и проверку `check`. Писать что-то отдельно для каждого из них не нужно: поменяли `theme.yaml` - поменялось везде.

## С чего начать <a id="start"></a>

Тему делают внутри обычного сайта: папка `theme/` - сама тема, а страницы в `content/` станут её демо. Поэтому первый шаг - сайт:

```bash
mkdir -p ~/sites && cd ~/sites
docker run --rm -it -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod new моя-тема
cd моя-тема
```

Языки сайта выберите те, на которых будут демо-страницы, например `ru, en`. В новом сайте уже лежит стартовая тема - белая, полностью описанная, с демо. Дальше два пути:

- **с копии стартовой** - проще всего и подходит почти всегда. Меняйте стили (переменные в начале `assets/site.css`), шаблоны и модули, добавляйте свои типы страниц. Контракт и демо уже есть - их нужно только поддерживать вместе с темой;
- **с нуля** - очистите `theme/` и положите своё. Минимум, который собирается: `theme.yaml`, `base.html`, шаблон на каждый тип в `templates/` (`home.html`, `page.html`, `404.html`) и модули, которые вызывают шаблоны.

В обоих случаях держите запущенным просмотр - он пересобирает сайт после каждого сохранения - и открывайте <http://localhost:8000>:

```bash
docker run --rm -it -p 127.0.0.1:8000:8000 -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod serve .
```

## Паспорт: `theme.yaml` <a id="passport"></a>

Вверху `theme.yaml` - сведения о самой теме:

```yaml
name: workshop                 # имя темы латиницей: под ним она живёт в архиве и каталоге
title: Мастерская              # название для людей
version: "1.0"                 # версия вашей темы
heron: ">=0.3"                 # с какими версиями движка тема работает; не та - E012
languages: [ru, en]            # на каких языках написаны подсказки темы
requires: [contact.phone]      # что тема берёт из site.yaml; не заполнено - E011
images:
  ratios: ["1:1", "16:9"]      # пропорции, которые могут попросить шаблоны
```

Ниже - два больших раздела: `types` (типы страниц) и `modules` (блоки). О них дальше. Остальные ключи паспорта (`links`, `forms`, `images` целиком) описаны в [04 · Тема и дизайн](04-theme.md) и в [`20` §6](../spec/20-data-contract.md#theme-yaml).

## Типы страниц <a id="types"></a>

Тип страницы - это вид страницы со своим шаблоном и своим набором блоков: главная, услуга, статья, контакты. Каждый тип рисуется файлом `templates/<тип>.html`. Пример типа «услуга» целиком:

```yaml
types:
  service:
    uses: [intro, "includes:list", "how:steps", "faq:faq"]
    jsonld: [Service]
    hint_ru: Услуга - что входит, как проходит работа, вопросы
    hint_en: A service - what is included, how the work goes, questions
    help_ru: Одна страница - одна услуга; в поиске она отвечает на запрос «услуга + город»
    help_en: One page - one service; in search it answers the query "service + city"
    sections:
      intro:
        required: true
        hint_ru: Вводный абзац - кому нужна услуга и что человек получит
        hint_en: The intro paragraph - who needs the service and what they get
        fields:
          - {name: text, type: markdown, required: true, md: body, hint_ru: Один-два абзаца о пользе, hint_en: One or two paragraphs about the benefit}
      includes:
        required: true
        hint_ru: Что входит в услугу - список с жирным зачином
        hint_en: What the service includes - a list with a bold start
      how: {hint_ru: Как проходит работа - нумерованные шаги, hint_en: How the work goes - numbered steps}
      faq: {hint_ru: "Вопросы о цене, сроках и гарантии", hint_en: "Questions about price, time and warranty"}
```

Что здесь что:

- **`uses`** - секции страницы этого типа по порядку. Это договор с контентом: `page add` положит в новую страницу заготовки ровно этих секций и спросит их в этом порядке. После двоеточия - форма, которую тема ждёт у секции: `"how:steps"` - нумерованные шаги. `"*"` - «любые блоки»: человек может добавить секцию любой формы. Все формы - [`20` §4.4](../spec/20-data-contract.md#section-forms);
- **`jsonld`** - разметка schema.org страниц этого типа: `Service`, `Article`, `FAQPage`. Её поля человек заполнит в группе «Разметка»;
- **`sections.<якорь>`** - описание секции из `uses`: `required` (обязательна ли), подсказки и, если у секции нет своей формы, её поля (`fields`). Так описан `intro` - вводный блок до первого заголовка `##`. Секция, которой нет в `uses`, - ошибка `E008`. Запись `"*"` в `sections` - подсказка к «любым блокам»;
- **`template`** - если тип рисуется не файлом `templates/<тип>.html`, а другим.

### Категории: `children_type` и `views` <a id="views"></a>

Категория (раздел) - это папка со своей страницей `_index.md`: «Услуги», «Статьи». Если страница вашего типа бывает категорией, скажите движку две вещи:

```yaml
types:
  page:
    uses: [intro, "*"]
    hint_ru: Обычная страница
    hint_en: An ordinary page
    children_type: service       # тип страниц внутри категории этого типа
    views:                       # как категория показывает свои страницы
      key: view                  # строка view: list во фронтматтере _index.md
      default: cards             # вид, когда строки нет
      hint_ru: Как категория показывает свои страницы
      hint_en: How a category shows its pages
      options:
        cards: {hint_ru: Карточки сеткой - для разделов на 3-12 страниц, hint_en: Cards in a grid - for sections of 3-12 pages}
        list: {hint_ru: Список строками - для длинных разделов, hint_en: A list of rows - for long sections}
```

- **`children_type`** - тип страниц внутри такой категории. `category add` запишет его в `_index.md` новой категории, а `page add --category services` сам выберет этот тип для новой страницы;
- **`views`** - виды, которыми категория показывает свои страницы. Перечень придумываете вы - ровно те виды, которые рисуют ваши шаблоны: карточки, список, таблица, плитка. Движок проверяет только, что `default` есть среди `options`. Человек выбирает вид вопросом `category add`, флагом `--view` или в студии, а в файл ложится строка `view: list`.

Шаблон читает вид сам. В стартовой теме модуль `children` делает так:

```jinja
<ul class="{{ 'rows' if page.meta.get('view') == 'list' else 'cards' }}">
```

### Модули: блоки и их поля <a id="modules"></a>

Модуль - это файл `modules/<имя>.html`, который рисует один блок. В `theme.yaml` модули можно просто перечислить, как в 0.2: `modules: [prose, list, faq]`. Но тогда движок не знает, из чего блок состоит, и человеку нечего подсказать. Поэтому модуль описывают:

```yaml
modules:
  faq:
    scope: section               # section - рисует секцию, page - берёт данные из страницы
    kinds: [faq]                 # какие формы секций рисует модуль
    schemaorg: FAQPage           # разметка, которую даёт блок
    hint_ru: Вопросы и ответы - вопрос заголовком, ответ под ним
    hint_en: Questions and answers - the question as a heading, the answer under it
    help_ru: Вопрос - заголовок третьего уровня, ответ - текст под ним; в поиске блок размечается как FAQPage
    help_en: A question is a third-level heading, the answer is the text under it; in search it is marked up as FAQPage
    fields:
      - name: items
        type: list
        required: true
        md: groups               # группы ### в markdown
        hint_ru: Пары вопрос - ответ
        hint_en: Question - answer pairs
        fields:
          - {name: q, type: text, required: true, md: heading, max_length: 120, schemaorg: Question.name, hint_ru: Вопрос, hint_en: The question}
          - {name: a, type: markdown, required: true, md: content, schemaorg: Answer.text, hint_ru: Ответ, hint_en: The answer}
  breadcrumbs:
    scope: page
    schemaorg: BreadcrumbList
    fields: []                   # заполнять нечего: крошки строятся сами
    hint_ru: Хлебные крошки - путь от главной до страницы
    hint_en: Breadcrumbs - the path from the home page to the page
```

- **`scope`** - `section` (по умолчанию): модуль рисует секцию и вызывается как `mod.faq('faq')`; `page`: модуль берёт данные из страницы и сайта (`mod.breadcrumbs()`, `mod.children()`), полей у него нет - пишите `fields: []`;
- **`kinds`** - формы секций, которые рисует модуль: один модуль может рисовать несколько похожих форм, как `list` в стартовой теме рисует и `list`, и `alert-list`. Не задано - форма с именем модуля;
- **`schemaorg`** - тип разметки, которую даёт блок;
- **`fields`** - поля блока, ниже;
- **`example_<язык>`** - образец markdown блока. Его покажут `describe <имя>` и справка темы, если блока нет на демо-страницах.

### Поля <a id="fields"></a>

Поле описывает одно значение, которое человек вписывает в блок. Главное правило: **поле описывает настоящий markdown**, а не придуманную вами модель данных. Ключ `md` говорит, где значение лежит в файле: `heading` - текст заголовка `###`, `content` - всё под ним, `items` - пункты списка `- …`, `bold` - жирный зачин пункта, `body` - всё содержимое секции, `first-paragraph` - первый абзац вводного блока. По этому месту консоль и студия находят значение в файле и пишут его обратно - на то же место, не трогая остального. Весь словарь мест - [`21` «Контракт темы»](../spec/21-engine.md#theme-contract).

| Ключ | Что это |
|---|---|
| `name` | имя поля: строчная латиница, цифры и `_`, с буквы |
| `type` | `text` - строка, `markdown` - текст с разметкой, `list` - список, `image` - картинка из `media/`, `link` - ссылка, `number` - число, `date` - дата ГГГГ-ММ-ДД, `enum` - выбор из списка, `ref` - другая страница сайта, `flag` - да или нет |
| `required` | обязательно ли: пустое поле - ошибка у поля в консоли и в студии |
| `md` | где значение лежит в markdown - место из словаря |
| `min_length`, `max_length` | длина текста в знаках |
| `min_items`, `max_items` | сколько пунктов в списке |
| `ratio`, `min_width` | у картинки: пропорция (`"16:9"`) и наименьшая ширина в пикселях |
| `values` | у `enum`: допустимые значения, обязательно |
| `ref` | у `ref`: на страницы какого типа ссылается поле |
| `schemaorg` | свойство разметки, в которое уходит значение: `Question.name` |
| `item` или `fields` | у списка: тип каждого пункта или поля каждого пункта - одно из двух |

Например, галерея стартовой темы - список картинок, у каждой файл и подпись:

```yaml
    fields:
      - name: items
        type: list
        required: true
        min_items: 1
        md: items
        hint_ru: Картинки галереи
        hint_en: The pictures of the gallery
        fields:
          - {name: image, type: image, required: true, md: image, min_width: 800, schemaorg: ImageObject.contentUrl, hint_ru: Файл картинки в media/, hint_en: The picture file in media/}
          - {name: alt, type: text, required: true, md: alt, max_length: 125, schemaorg: ImageObject.caption, hint_ru: Подпись - что на картинке, hint_en: The caption - what is in the picture}
```

Ограничения проверяются сразу, у самого поля: слишком длинный вопрос, картинка уже 800 пикселей, пустой обязательный пункт - консоль спросит ещё раз, студия покажет ошибку, `check` назовёт файл.

**Служебные поля писать не нужно.** `title`, `h1`, `description`, адрес (`slug`), категорию, меню, обложку, картинку для соцсетей, `noindex`, пометку «перевод не готов», заголовок и якорь каждого блока описывает сам движок - одинаково для всех тем, с подсказками на ru и en.

## Подсказки: для человека без опыта <a id="hints"></a>

Тот, кто будет вести сайт на вашей теме, часто впервые видит и HERON, и markdown, и слово «сниппет». Подсказки - единственное, что стоит между ним и пустым полем. Их увидят в четырёх местах: в консоли у каждого вопроса `page add`, в студии при наведении на поле и по кнопке `?`, в справке темы и в выводе `describe` - его читает и AI-агент.

- **`hint`** - одна строка, которую видно сразу: что это за поле. «Вопрос», «Первый абзац - главная польза одним-двумя предложениями».
- **`help`** - подробная справка по `?`: что это, на что влияет на сайте и в поиске, хороший пример, частые ошибки. Несколько строк - удобно блоком `|-`.
- **`example`** - у модуля: образец markdown, который можно скопировать.

Подсказки пишутся на каждом языке темы с суффиксом языка: `hint_ru`, `hint_en`, `help_uk`. Ключ без суффикса (`hint`) - для языков, у которых своего текста нет. Языки темы - список `languages`. `hint` обязателен у каждого типа, секции из `sections`, модуля из описания, поля и вида: не хватает хотя бы одного - `check` остановится с `E008` и перечислит пути, например `types.service.sections.how (en)`.

Как писать хорошо:

- пишите словами того, кто ведёт сайт, а не того, кто делал тему: «Что входит в услугу», а не «items блока list»;
- в `help` - четыре части: что это; что увидит посетитель и что поймёт поисковик; пример хорошего заполнения; частые ошибки;
- называйте ограничения прямо: «до 60 знаков», «картинка от 1200 px в ширину», «три-пять пунктов»;
- хороший образец - `theme.yaml` стартовой темы: у каждого её блока `help` написан именно так.

## Описание целиком: `describe` <a id="describe"></a>

Посмотреть, что получилось, - командой `describe`. Без имени она коротко покажет всё описание вместе со служебными полями движка и значениями по умолчанию из `site.yaml`. С именем типа или блока - его одного с подробной справкой и образцом markdown. С `--json` - то же одним объектом для агента и программ:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod describe
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod describe service
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod describe --json --lang en
```

`--lang` выбирает язык подсказок. Форма вывода `--json` - [`21` §10](../spec/21-engine.md#heron-describe).

## Демо темы <a id="demo"></a>

Демо - это не украшение, а образец подачи: какие страницы нужны сайту такой тематики, какие блоки на них и в каком порядке. Вы продумываете эту структуру один раз, а тот, кто ставит тему, получает её готовой и заменяет тексты своими. Поэтому у каждой темы демо обязательно, и оно показывает всё, что объявил `theme.yaml`:

- **каждый тип страницы** - хотя бы одна страница этого типа из файла: главная (`index.md`), обычная страница, 404 (`404.md`) и каждый ваш тип;
- **каждый блок** - модуль хоть раз нарисовал что-то на какой-нибудь странице, в том числе модули страницы (`breadcrumbs`, `children`);
- **каждый вид категории** - страница категории со страницами внутри, у которой стоит `view: <вид>`; вид по умолчанию - на категории без этой строки.

**Где лежит демо.** Это обычный контент сайта, на котором вы делаете тему: `content/<язык>/…`, картинки - в `media/`, справочники - в `data/`. При упаковке всё это едет в архив рядом с темой, а `theme get` раскладывает страницы демо в сайт, куда тему ставят, - только туда, где страницы ещё нет. Языка, на котором у демо нет страниц, сайт получает страницы основного языка.

**Как демо проверяется.** Движок по-настоящему собирает страницы шаблонами темы и записывает, какой модуль что нарисовал. Чего не хватает, называет списком - ошибкой `E037`:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check . --theme
```

```
E037 theme/theme.yaml: демо темы workshop показывает не всё, что объявил theme.yaml (1 пропуск):
    тип service: нет ни одной демо-страницы
```

Обычная проверка `check .` демо не требует: на своём сайте человек вправе удалить ненужные демо-страницы. У темы без описания полей неполное демо - только предупреждение.

**Как написать хорошее демо.** Пишите правдоподобные тексты вашей ниши, а не «Lorem ipsum»: по ним человек поймёт, что и где писать. Пусть страница объясняет сама себя - как «Блоки» стартовой темы: рядом с блоком одной фразой, для чего он. Демо на всех языках, на которых написаны подсказки.

## Справка темы <a id="theme-ref"></a>

Справка темы собирается из `theme.yaml` и демо сама, руками её не пишут: типы страниц с секциями, каждый блок с подсказкой и полями, рядом - живой пример из демо и его исходный markdown, виды категорий со строкой, которая их включает, разметка schema.org, переменные стилей и строки интерфейса. Поменяли контракт или демо - поменялась и справка.

- в просмотре и черновой сборке - страница `/_heron/theme/` (на других языках сайта - `/_heron/theme/<язык>/`), с живыми примерами в стилях темы. В боевую сборку, карту сайта и поиск она не попадает;
- в студии - вкладка «Справка темы»;
- в терминале - текстом, примеры там - исходный markdown и файл, где он лежит:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod docs theme-ref .
```

Прочитайте справку глазами новичка: понятно ли из подсказок, что писать в каждое поле? Если нет - допишите `help`.

## Строгий CSP <a id="csp"></a>

Сайт на HERON отдаётся с правилом безопасности браузера `script-src 'self'`. Тема обязана жить по нему - правила и как переделать старую тему, в [04 · Тема и дизайн](04-theme.md#strict-csp). Коротко: никаких скриптов прямо в HTML и обработчиков `onclick=` - только файлы из `assets/`; шрифты, картинки и скрипты - со своего сайта, а не с чужих серверов.

## Проверка <a id="check"></a>

После каждого шага:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check . --theme
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build . --env prod --strict
```

- `check --theme` - описание темы полное (`E008` - чего-то не хватает или оно неверно), демо показывает всё (`E037`), шаблоны не меняют данные (`E033`), нет встроенных скриптов (предупреждение);
- `build --env prod --strict` - каждая страница рисуется без ошибок и предупреждений.

## Упаковка и публикация <a id="pack"></a>

Готовую тему упаковывают в архив вместе с демо:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod theme pack . --out theme.tar.gz
```

Перед записью `theme pack` делает ту же проверку демо, что `check --theme`: не хватает демо - `E037`, и архива нет. В архиве - `heron-theme.yaml` (имя темы и версии движка, с которыми она совместима), папка `theme/` и папка `demo/` - страницы из `content/`, картинки из `media/`, справочники из `data/`. Кода в архиве быть не может: файлы `.py`, `.sh`, `.exe`, папки `plugins` и `.git`, ссылки на другие файлы - `theme get` такой архив не поставит (`E032`).

Как передать тему:

- **файлом** - пришлите `theme.tar.gz`, его ставят командой `theme get ./theme.tar.gz .`;
- **ссылкой** - выложите архив по https: `theme get https://example.com/theme.tar.gz .`. Допишите в конец ссылки `#sha256=<хеш архива>` - движок сверит, что скачал именно ваш файл;
- **в каталог** - чтобы тему ставили по имени (`theme get workshop .`), её добавляют в каталог тем - файл `catalog.json` репозитория [FMSTM/heron-themes](https://github.com/FMSTM/heron-themes): имя, название, описание, https-адрес архива и его sha256. Предложите запись туда обычным запросом на изменение (pull request).

Хеш архива печатает команда `sha256sum theme.tar.gz` (на macOS - `shasum -a 256 theme.tar.gz`). Поставить тему файлом и ссылкой - команды целиком (их запускают в папке сайта, куда ставят тему):

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod theme get ./theme.tar.gz .
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod theme get "https://example.com/theme.tar.gz#sha256=<хеш>" .
```

## Пример целиком: тип «услуга» <a id="example"></a>

Добавим в копию стартовой темы тип `service` с полями, подсказками и демо - от начала до упаковки.

1. **Контракт.** Допишите в `types` файла `theme/theme.yaml` тип `service` из примера в разделе [«Типы страниц»](#types). Блоки `list`, `steps` и `faq` в стартовой теме уже описаны, их поля писать заново не нужно.
2. **Шаблон.** Скопируйте `theme/templates/page.html` в `theme/templates/service.html` и расставьте блоки по местам: `{{ mod.list('includes') }}`, `{{ mod.steps('how') }}`, `{{ mod.faq('faq') }}`.
3. **Проверка описания.** `describe service` покажет тип с вашими подсказками, а `check .` назовёт подсказку, которой не хватает на каком-то языке.
4. **Демо: категория и страница.** Создайте раздел услуг и одну услугу в нём - сразу на всех языках сайта:

```bash
docker run --rm -it -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod category add services . --children-type service
docker run --rm -it -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod page add roofing . --category services
```

5. **Тексты демо.** Движок задаст вопросы по полям типа - с вашими подсказками. Впишите правдоподобную услугу: вводный абзац, три-пять пунктов «что входит», шаги, два-три вопроса. Переведите на остальные языки - иначе страница получит пометку `translation: pending`. Добавьте пункт `services` в меню (`nav.main` в `site.yaml`).
6. **Проверка демо.** `check . --theme` больше не говорит «тип service: нет ни одной демо-страницы». Откройте `localhost:8000/_heron/theme/` - тип `service` появился в справке.
7. **Упаковка.** `theme pack . --out theme.tar.gz` - архив готов.

Команды шагов 3, 6 и 7 целиком:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod describe service
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check . --theme
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod theme pack . --out theme.tar.gz
```

## Перенос темы с 0.2 на 0.3 <a id="migrate-0-3"></a>

Этот раздел можно читать отдельно от остального. Он для того, кто уже сделал тему на движке 0.2 и переводит её на 0.3. Тема 0.2 на движке 0.3 собирается и дальше, но `check` предупредит «нет описания полей», `page add` и студия покажут человеку только SEO-блок, без полей блоков и подсказок, а справка темы будет почти пустой. Чтобы тема работала в полную силу, пройдите по списку.

1. **Обновите движок и проверьте его версию** - первые две команды в конце раздела. Версия должна быть `0.3` или новее. Показывает `0.2` - значит, 0.3 ещё не вышла в стабильную версию: берите образ `:beta` вместо `:prod` во всех командах.
2. **Поднимите версию движка в `theme.yaml`:** `heron: ">=0.3"`. Если там стояло `">=0.2,<0.3"`, движок 0.3 тему не соберёт (`E012`). Поднимите и `version` своей темы.
3. **Назовите языки подсказок:** `languages: [ru, en]` - те, на которых вы напишете подсказки.
4. **Опишите каждый тип.** У каждого типа в `types` - `hint_<язык>` на каждом языке и `help_<язык>`; у каждой секции из `uses`, которую человек заполняет, - запись в `sections` с `required` и подсказкой; у `intro` и других секций без формы - `fields` ([«Типы страниц»](#types)).
5. **Опишите каждый модуль.** Список `modules: [prose, list, …]` превратите в описание: у модуля `scope`, `kinds`, `schemaorg` (если блок даёт разметку), подсказки, `example_<язык>` и `fields` с местом `md` у каждого поля ([«Модули»](#modules), [«Поля»](#fields)). У модулей страницы (`breadcrumbs`, `children`) - `scope: page` и `fields: []`. Не путайте: ключ `fields` верхнего уровня `theme.yaml` - про поля движка, а не про блоки; свои поля туда не пишут (`E023`).
6. **Категории.** Если тип бывает категорией - `children_type` и `views` с видами, которые рисуют ваши шаблоны; шаблон читает вид из `page.meta.get('view')` ([«Категории»](#views)).
7. **Демо.** В `content/` сайта темы - хотя бы одна страница каждого типа (включая `404.md` файлом), каждый блок хоть раз и каждый вид категории на категории со страницами внутри ([«Демо темы»](#demo)). Модуль, который не рисует ни одна страница, уберите из `modules` или покажите на демо. Создавать страницы удобно командами `category add` и `page add` - они кладут файлы сразу на всех языках сайта.
8. **Старые команды в текстах.** Если демо или документация темы советуют `page <тип> <ключ>` или `--folder`, замените на `page add <ключ> --type <тип> --category <путь>`: старая форма в 0.3 убрана (`E038`).
9. **Строгий CSP.** Никаких встроенных `<script>` с кодом и обработчиков `onclick=`, `onload=` в шаблонах - код в `assets/*.js`, данные - атрибутами `data-*`; шрифты, картинки и скрипты - из `assets/`, а не с чужих серверов ([«Строгий CSP»](04-theme.md#strict-csp)).
10. **Проверьте и упакуйте.** `check . --theme` - ни одного `E008` и `E037`; `describe` - всё описание на месте; `localhost:8000/_heron/theme/` в просмотре - справка читается как инструкция для новичка; `build . --env prod --strict` - без ошибок; `theme pack . --out theme.tar.gz` - архив готов.

Команды списка целиком, по порядку:

```bash
docker pull ghcr.io/fmstm/heron:prod
docker run --rm ghcr.io/fmstm/heron:prod --version
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check . --theme
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod describe
docker run --rm -it -p 127.0.0.1:8000:8000 -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod serve .
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build . --env prod --strict
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod theme pack . --out theme.tar.gz
```

Образец полностью описанной темы - стартовая: её `theme.yaml` лежит в `theme/` любого нового сайта (`new`), а все ключи контракта - в [`21` «Контракт темы»](../spec/21-engine.md#theme-contract).
