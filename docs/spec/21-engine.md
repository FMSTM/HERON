## 1. Что делает движок

Читает папку сайта — `site.yaml`, `content/`, `data/`, `img/`, `static/` и тему — и отдаёт готовый статический сайт в `dist/`.

Одна команда, один проход, никакого состояния между запусками. Собрать дважды подряд — получить побайтово одинаковый результат.

Движок живёт в образе `heron:<версия>` и в pip-пакете, а не в папке сайта. Первым делом он сверяет свою версию с требованием `heron:` из `site.yaml` и отказывается собирать несовместимый сайт (`E012`).

Сборка идёт **без сети**. Ни один этап не ходит наружу: всё, что нужно сайту, лежит в папке сайта.

## 2. Стек

Python 3.12. Зависимости минимальны — каждая должна быть оправдана, потому что сопровождать это будет начинающий разработчик.

| Пакет | Зачем |
|---|---|
| `markdown-it-py` | парсинг markdown, поддержка `{#id}` через `attrs` |
| `PyYAML` | фронтматтер и конфиги |
| `Jinja2` | шаблоны |
| `Pillow` | ресайз и конвертация картинок |
| `pydantic` | валидация фронтматтера и `site.yaml` со внятными сообщениями |
| `click` | CLI |

Пакетный менеджер — `uv`. Линтер и форматтер — `ruff`. Тесты — `pytest`.

## 3. Состав кода

Три уровня: контракты, ядро, модули. Деление не косметическое — по нему проходит граница плагинов: модуль и плагин пишутся против одних и тех же хуков.

```
heron/
├── cli.py                команды new, init, check, serve, build
├── contracts/
│   ├── site.py           pydantic-схема site.yaml, включая требование версии
│   ├── theme.py          схема theme.yaml
│   ├── frontmatter.py    схема фронтматтера
│   └── version.py        сверка версии движка с site.yaml
├── core/
│   ├── models.py         Site, Page, Section, Nav
│   ├── parser/
│   │   ├── frontmatter.py
│   │   ├── sections.py   нарезка по заголовкам с якорями
│   │   └── blocks.py     разбор структурированных секций: facts, faq, steps
│   ├── tree.py           обход content/, построение дерева страниц и URL
│   ├── data.py           загрузка data/ в пространство имён шаблонов
│   ├── links.py          резолв связей: treats, procedures, related, каталоги, языки
│   ├── render/
│   │   ├── env.py        окружение Jinja2, макросы mod.*
│   │   └── pages.py      рендеринг страниц
│   ├── media.py          обработка картинок
│   ├── resolver.py       поиск темы и плагинов: локальные → пакеты → git
│   ├── hooks.py          реестр точек расширения и их вызов
│   ├── report.py         отчёт check, сводка предупреждений
│   └── errors.py         типы ошибок и коды
├── modules/              то же, что плагины, только поставляются в ядре
│   ├── sitemap.py
│   ├── robots.py
│   ├── llms.py
│   ├── jsonld.py
│   ├── redirects.py
│   └── feed.py
└── scaffold/             образцы файлов для new и init
```

Границы соблюдаются строго: **ядро не знает предметную область ни одного сайта.** Имя клиента, домен, телефон, слаг конкретной страницы в коде ядра — ошибка. Проверяется pre-commit-хуком репозитория ядра, а не памятью разработчика.

Всё специфичное живёт в папке сайта: `content/`, `data/`, `site.yaml` и тема.

## 4. Конвейер сборки

Восемь этапов, строго по порядку. Каждый может остановить сборку.

**1. Загрузка конфигов.** Сверка версии движка с ключом `heron:` из `site.yaml`, затем сам `site.yaml` и `theme.yaml` найденной темы. Валидация pydantic. Версия не подходит, тема не найдена или тип страницы не имеет шаблона — остановка.

**2. Обход дерева.** Рекурсивный проход `content/<lang>/`. Для каждого файла определяется URL, тип (из `_index.md` папки или по умолчанию), язык. Формируется плоский список страниц.

**3. Парсинг.** Для каждой страницы: фронтматтер → модель, тело → секции, структурированные секции → данные. Ошибки собираются, не прерывая проход — чтобы разработчик увидел все сразу, а не по одной за прогон.

**4. Резолв связей.** Дочерние страницы каталогов, поля `treats` / `procedures` / `related`, языковые соответствия, меню, хлебные крошки, обратные ссылки. Ссылка на несуществующую страницу — остановка.

**5. Обработка картинок.** Варианты под брейкпоинты, WebP и AVIF, вычисление размеров. Результат в `dist/img/`, оригиналы не трогаются. Кэш по хешу файла: неизменённая картинка не переобрабатывается.

**6. Рендеринг.** Каждая страница через `types/<тип>.html`. Плюс `404.html`.

**7. Генерация служебного.** sitemap, robots, llms.txt, redirects, feed. JSON-LD встраивается на шаге 6.

**8. Копирование.** `static/` в `dist/` как есть, `theme/assets/` в `dist/assets/`.

После — сводка: сколько страниц по языкам и типам, сколько предупреждений, список долгов по контенту.

## 5. Парсер секций

Сердце системы, поэтому подробно.

Тело файла разбирается `markdown-it-py` с включённым плагином атрибутов. Секция — заголовок, у которого есть якорь `{#id}`, и всё содержимое до следующего заголовка **того же уровня с якорем** либо до конца файла.

Правила:

- заголовки без якоря секцию не начинают и принадлежат текущей
- текст до первой секции доступен как `intro`
- идентификатор: `[a-z0-9-]+`. Иное — ошибка
- дубликат идентификатора в файле — ошибка
- у секции сохраняются: `id`, `title` (текст заголовка), `level`, `html` (отрендеренное содержимое без заголовка), `raw` (исходный markdown)

Тема сама решает, показывать ли заголовок секции: `mod.prose('what')` выводит и заголовок и текст, а `mod.facts('quick-facts')` заголовок игнорирует, потому что рисует рамку с фактами.

### Структурированные секции

Разбираются из того же markdown, без особого синтаксиса:

**facts** — строки вида `Ключ | Значение`. Результат: список пар. Строка без разделителя внутри такой секции — предупреждение.

**faq** — заголовки `###` внутри секции становятся вопросами, содержимое под каждым — ответом. Результат: список пар вопрос/ответ.

**steps** — нумерованный список. Жирный текст в начале пункта до точки становится заголовком шага, остальное — телом.

**list** — маркированный список, элементы как есть.

**timeline** — строки `Период | Событие`, как facts, но рендерится шкалой.

**table** — обычная markdown-таблица, первая строка — заголовки.

Разбор структурированной секции ошибается мягко: не распознал формат — отдаёт содержимое как прозу и пишет предупреждение. Валить сборку из-за пропущенной палочки в таблице нельзя.

## 6. Модель страницы

```python
class Page:
    lang: str
    path: str              # относительный путь в content/<lang>/
    url: str               # /services/consulting/
    type: str
    title: str
    h1: str
    description: str
    image: str | None
    og_image: str
    order: int
    updated: date
    published: bool
    noindex: bool
    redirect_from: list[str]
    sections: dict[str, Section]
    extra: dict              # прочие поля фронтматтера: treats, procedures, date…
    # заполняется на этапе резолва
    parent: Page | None
    children: list[Page]
    translations: dict[str, Page]
    breadcrumbs: list[Page]
    related: dict[str, list[Page]]
```

## 7. Рендеринг

Jinja2, `autoescape` включён, `StrictUndefined` — обращение к несуществующей переменной валит сборку, а не выводит пустоту. Это ловит опечатки в теме на этапе сборки.

Шаблону доступны: `page`, `site` (весь `site.yaml`), `data` (содержимое `data/`), `nav`, `t` (строки интерфейса темы), `mod` (макросы модулей).

### Макросы модулей

`mod.<модуль>(<id секции>)`. Логика одинаковая для всех:

1. секции с таким id нет → вернуть пустую строку, ничего не рендерить
2. секция есть → отрендерить `theme/modules/<модуль>.html`, передав ей данные секции

Модули без аргумента (`mod.call()`, `mod.author()`, `mod.breadcrumbs()`) берут данные из `site` и `page`, а не из секций.

Пустая строка вместо блока — принципиально: заголовок без содержимого хуже отсутствующего блока.

### Строки интерфейса

Тексты, принадлежащие теме, а не контенту («Записатися», «Читати далі», «Питання та відповіді»), живут в `theme/i18n/<lang>.yaml` и доступны как `t.book_now`. Иначе они окажутся зашиты в шаблоны и тема перестанет быть переносимой между языками.

## 8. Картинки

Для каждой картинки, на которую ссылается контент:

- варианты по ширине: 400, 800, 1200, 1600 — но не больше исходной
- форматы: AVIF, WebP, исходный как запасной
- `srcset` и `sizes` проставляются модулем
- `width` и `height` обязательны в разметке — иначе прыгает вёрстка и растёт CLS
- `loading="lazy"` на всё, кроме картинки первого экрана
- кэш в `.heron-cache/` по хешу исходника

`og_image` не обрабатывается: соцсети ждут JPEG или PNG 1200×630 по фиксированному адресу.

Картинка, на которую есть ссылка, но которой нет на диске — остановка сборки. Битая картинка в проде дороже, чем упавшая сборка.

## 9. Генераторы

### sitemap

`sitemap.xml` — индекс, плюс `sitemap-uk.xml`, `sitemap-ru.xml`, `sitemap-en.xml`.

Включаются страницы с `published: true` и `noindex: false`. `lastmod` из `updated`. Внутри каждой записи — `xhtml:link` на языковые версии.

Служебных типов записей в sitemap нет по определению: в системе нет сущностей без URL. Мусор вида `cpt_layouts` со старого сайта здесь невозможен архитектурно.

### robots.txt

Из `seo.robots_extra` плюс обязательная строка `Sitemap:` с абсолютным адресом. Собирается, а не лежит файлом: положенный руками, он через полгода начинает врать.

### llms.txt

По формату llmstxt.org: заголовок сайта, краткое описание, разделы со списком страниц и однострочными описаниями из `description`. Строится из того же дерева, что и меню.

При `seo.llms_txt: true` дополнительно `llms-full.txt` — весь текст сайта одним файлом.

### JSON-LD

Встраивается в `<head>` каждой страницы, тип зависит от типа страницы:

Типы разметки объявляет **тема**, ключом `types.<тип>.jsonld` в `theme.yaml`: у сайта услуг, магазина и справочника соответствие разное, и ядро его знать не обязано.

Ядро строит то, что действительно знает само:

| Что | Откуда берётся |
|---|---|
| `@type`, объявленный темой | `theme.yaml` |
| `name`, `description`, `url`, `inLanguage`, `dateModified` | страница |
| поля организации и прочие реквизиты | блок `schema` в `site.yaml` |
| уточнения по конкретной странице | блок `schema` во фронтматтере |
| `BreadcrumbList` | построенные крошки, везде кроме главной |
| `FAQPage` | секция, разобранная как `faq` |

Слияние трёхуровневое: сайт, затем страница. Данные организации живут в `site.yaml` и не дублируются в контенте.

### redirects

Собирает все `redirect_from` со всех страниц в `dist/redirects.map` формата nginx:

```
/old/address/  /new/address/;
```

Проверки на этапе сборки: старый URL не совпадает ни с одним существующим, один старый URL не ведёт в два места, цепочек нет.

## 10. CLI

Шесть команд — это вся поверхность движка для человека. Внутрь него заходить не нужно.

```
heron new <имя>                        создать папку сайта с нуля
heron init                             дополнить существующую папку недостающим
heron check [--strict]                 отчёт без сборки
heron serve [--port 8000]              локальный просмотр с пересборкой
heron build [--drafts] [--strict]      собрать в dist/
heron build --image <tag>              собрать и упаковать в образ nginx
heron page <тип> <слаг> [--lang uk]    заготовка md со всеми секциями типа
```

`--drafts` включает `published: false`. `--strict` превращает предупреждения в ошибки — режим для CI.

`heron new` неинтерактивен и детерминирован: одинаковый вызов даёт одинаковую папку. Вопросов о хостинге не задаёт — кладёт и структуру, и `Dockerfile`, и `compose.yml`, и `build.sh` всегда. Выбор «папка или образ» делается позже, флагом сборки, а не при создании. Флаги на редкие случаи: `--lang`, `--theme`, `--no-docker`.

`heron init` — тот же набор, но для папки, которая уже есть: смотрит, что в ней лежит, дописывает недостающее, ничего не перезаписывает без `--force` и печатает, что нашёл и что добавил.

`heron page` создаёт файл со всеми секциями типа, комментариями «что сюда писать» и заполненным фронтматтером. Раньше эта команда называлась `new`; переименована, чтобы `new` означало «новый сайт».

Полное описание команд, генерируемых файлов и режима `--image` — `23-distribution.md`.

## 11. Ошибки и предупреждения

Разделение жёсткое: ошибка останавливает сборку, предупреждение попадает в отчёт.

**Останавливают сборку:**

| Код | Условие |
|---|---|
| `E001` | битый YAML во фронтматтере |
| `E002` | нет `title`, `h1` или `description` |
| `E003` | дубликат идентификатора секции в файле |
| `E004` | два файла дают один URL |
| `E005` | недопустимый слаг |
| `E006` | `treats`, `procedures` или `related` ссылается на несуществующую страницу |
| `E007` | картинки нет на диске |
| `E008` | у типа страницы нет шаблона в теме |
| `E009` | `redirect_from` совпадает с существующим URL |
| `E010` | обращение к несуществующей переменной в шаблоне |
| `E011` | `site.yaml` не проходит валидацию |
| `E012` | версия движка не удовлетворяет требованию `heron:` из `site.yaml` |
| `E013` | тема не найдена ни локально, ни среди установленных пакетов |
| `E014` | плагин из `plugins:` не установлен или упал при загрузке |
| `E015` | сырой HTML в markdown при `build.allow_raw_html: false` |
| `E016` | недопустимый идентификатор секции |

Сообщение об ошибке обязано содержать путь к файлу, номер строки, что не так и что сделать. `Ошибка в шаблоне` без адреса — не сообщение.

**Предупреждения:**

`title` длиннее 60 знаков · `description` длиннее 155 · картинка без `alt` · страница без `image` в каталоге · секция в файле, которую тема не использует · отсутствие опциональной секции.

Последнее собирается в сводку долгов:

```
Не заполнено:
  contra  — 6 страниц: mikrodyskektomiya, spondylodez, …
  price   — 6 страниц
  risks   — 6 страниц
```

Это тот самый список к заказчику, который иначе теряется. Он печатается после каждой сборки, а не вспоминается раз в квартал.

## 12. Отчёт `heron check`

Без сборки, читает контент и тему и печатает:

- страницы по языкам и типам, что переведено, а что нет
- заполненность секций по каждому типу
- секции в файлах, которые тема не использует — ловит опечатку в якоре
- модули темы, которые не использует ни один тип
- внутренние ссылки: битые, и страницы, на которые никто не ссылается
- страницы без ссылки на запись — нарушение правила перелинковки
- длины `title` и `description`
- карта редиректов и её конфликты

Гоняется в CI на каждый push. Это замена схемы валидации, от которой мы отказались ради простоты входа: контроль остаётся, но не требует писать и поддерживать схемы.

## 13. Производительность

Сайт на 40 страниц в трёх языках — это 120 страниц. Полная сборка без кэша картинок должна укладываться в 10 секунд, с кэшем — в 2. Если не укладывается, проблема в обработке картинок, а не в рендеринге.

Инкрементальная сборка на первом этапе не нужна и не делается. `heron serve` пересобирает всё при изменении файла — на таком объёме это незаметно.

## 14. Тесты

Обязательные, без них работа не принимается:

- парсер секций: якоря, вложенные заголовки, дубликаты, текст до первой секции
- структурированные секции: facts, faq, steps, timeline на валидных и битых данных
- построение URL из путей, включая `_index.md` и языковые префиксы
- резолв связей, включая ссылку в никуда
- **каждый URL из карты редиректов отдаёт 301 на адрес, который существует и отвечает 200.** Это единственное, что защищает индекс при переезде
- каждая собранная страница содержит ровно один `<h1>`
- все внутренние ссылки в собранном HTML ведут на существующие файлы
- `hreflang` симметричен: если A ссылается на B, то B ссылается на A
- sitemap не содержит страниц с `noindex` и содержит все остальные
- две сборки подряд дают побайтово одинаковый результат

Отдельно, за пределами unit-тестов: прогон собранного сайта через Lighthouse в CI с порогами из `docs/design/01-brief.md` — LCP менее 2 секунд, CLS менее 0.05.

## 15. Точки расширения

Модули из `heron/modules/` и внешние плагины пишутся против одного набора хуков. Разница только в поставке: модуль лежит в ядре, плагин ставится пакетом и объявляется в `site.yaml`.

| Хук | Когда вызывается | Зачем |
|---|---|---|
| `on_config` | после загрузки `site.yaml` и `theme.yaml` | дописать или провалидировать конфиг |
| `block:<имя>` | при разборе структурированной секции | свой тип секции сверх встроенных |
| `on_page_parsed` | после парсинга каждой страницы | правка модели страницы |
| `on_tree_built` | после обхода `content/` | свои связи и группировки |
| `filter` / `global` | при сборке окружения Jinja2 | свои функции для темы |
| `on_page_rendered` | после рендера страницы | постобработка HTML |
| `on_build_finished` | после копирования `static/` | свои генераторы: ещё один sitemap, экспорт, фид |

Больше на старте не заводим: API, придуманный под будущее, всегда придуман неправильно.

**Хуки действуют только на этапе сборки.** Плагина, который «принимает форму», не существует — в момент POST движок уже отработал и вышел. Всё, что живёт в рантайме, — это `heron-relay`, отдельный сервис (см. `23-distribution.md`).

Источники плагинов и порядок разрешения — `core/resolver.py`: локальная папка `plugins/` сайта → установленный пакет (entry point группы `heron.plugins`) → git-ссылка. Локальный сильнее.
