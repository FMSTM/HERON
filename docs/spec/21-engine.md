## 1. Что делает движок

Читает папку сайта — `site.yaml`, `content/`, `data/`, `media/`, `static/` и тему — и отдаёт готовый статический сайт в `dist/`.

Одна команда, один проход, никакого состояния между запусками. Собрать дважды подряд — получить побайтово одинаковый результат.

Движок живёт в образе `heron:<версия>` и в pip-пакете, а не в папке сайта. Первым делом он сверяет свою версию с требованием `heron:` из `site.yaml` и отказывается собирать несовместимый сайт (`E012`).

Сборка идёт **без сети**. Ни один этап не ходит наружу: всё, что нужно сайту, лежит в папке сайта.

## 2. Стек

Python 3.12. Зависимости минимальны — каждая должна быть оправдана, потому что сопровождать это будет начинающий разработчик.

| Пакет | Зачем |
|---|---|
| `markdown-it-py` | парсинг markdown, поддержка `{#id}` через `attrs` |
| `PyYAML` | фронтматтер и конфиги |
| `Jinja2` | шаблоны |
| `Pillow` | ресайз и конвертация картинок |
| `pydantic` | валидация фронтматтера и `site.yaml` со внятными сообщениями |
| `click` | CLI |

Пакетный менеджер — `uv`. Линтер и форматтер — `ruff`. Тесты — `pytest`.

## 3. Состав кода

Три уровня: контракты, ядро, модули. Деление не косметическое — по нему проходит граница плагинов: модуль и плагин пишутся против одних и тех же хуков.

```
heron/
├── cli.py                команды new, init, check, serve, build
├── contracts/
│   ├── site.py           pydantic-схема site.yaml, включая требование версии
│   ├── theme.py          схема theme.yaml
│   ├── frontmatter.py    схема фронтматтера
│   └── version.py        сверка версии движка с site.yaml
├── core/
│   ├── models.py         Site, Page, Section, Nav
│   ├── parser/
│   │   ├── frontmatter.py
│   │   ├── sections.py   нарезка по заголовкам с якорями
│   │   └── blocks.py     разбор структурированных секций: facts, faq, steps
│   ├── tree.py           обход content/, построение дерева страниц и URL
│   ├── data.py           загрузка data/ в пространство имён шаблонов
│   ├── links.py          резолв связей: каталоги, языки, поля, объявленные темой
│   ├── render/
│   │   ├── env.py        окружение Jinja2, макросы mod.*
│   │   └── pages.py      рендеринг страниц
│   ├── media.py          обработка картинок
│   ├── resolver.py       поиск темы и плагинов: локальные → пакеты → git
│   ├── hooks.py          реестр точек расширения и их вызов
│   ├── report.py         отчёт check, сводка предупреждений
│   └── errors.py         типы ошибок и коды
├── modules/              то же, что плагины, только поставляются в ядре
│   ├── sitemap.py
│   ├── robots.py
│   ├── llms.py
│   ├── jsonld.py
│   ├── redirects.py
│   └── feed.py
└── scaffold/             образцы файлов для new и init
```

Границы соблюдаются строго: **ядро не знает предметную область ни одного сайта.** Имя клиента, домен, телефон, слаг конкретной страницы в коде ядра — ошибка. Проверяется pre-commit-хуком репозитория ядра, а не памятью разработчика.

Всё специфичное живёт в папке сайта: `content/`, `data/`, `site.yaml` и тема.

## 4. Конвейер сборки

Восемь этапов, строго по порядку. Каждый может остановить сборку.

**1. Загрузка конфигов.** Сверка версии движка с ключом `heron:` из `site.yaml`, затем сам `site.yaml` и `theme.yaml` найденной темы. Валидация pydantic. Версия не подходит, тема не найдена или тип страницы не имеет шаблона — остановка.

**2. Обход дерева.** Рекурсивный проход `content/<lang>/`. Для каждого файла определяется URL, тип (из `_index.md` папки или по умолчанию), язык. Формируется плоский список страниц.

Адрес и ключ строятся порознь:

- **ключ** — путь папок плюс имя файла без расширения. Он не смотрит на
  слаг никогда: склеить их значит запретить языкам разные адреса, а
  переименование адреса сделать разрывом связи между переводами
- **адрес** — та же цепочка сегментов, но каждый заменён слагом своего
  раздела, если раздел его объявил, и своим `slug`, если объявила сама
  страница

Слаги разделов собираются отдельным проходом по `_index.md` до обхода
файлов: дочернюю страницу движок встречает раньше, чем индекс её раздела,
а адрес ребёнка зависит от того, как назвал себя родитель.

#### Границы файлов

Сборка читает только исходники сайта, пишет только в папку сборки и кэш,
удаляет только то, чем владеет. Путь сначала нормализуется, затем
разрешается файловой системой со всеми символическими ссылками, и только
результат сравнивается с корнем (`heron/core/paths.py`). Строковая
проверка на `../` не применяется: символическая ссылка точек не содержит.

| Операция | Где разрешено | Нарушение |
|---|---|---|
| чтение страниц и данных | внутри `content/`, `data/` | файл-ссылка наружу — `E024` |
| чтение ресурсов | внутри `media/` (`img/`) | `media/../x`, ссылка наружу — `E024` со страницей, где объявлен путь |
| копирование `static/`, `assets/` темы | внутри своей папки; ссылка внутрь той же папки допустима | ссылка или папка-ссылка наружу — `E024` |
| шаблоны темы (`include`, `extends`) | внутри темы | шаблон-ссылка наружу — `E024` |
| запись результата | внутри папки сборки | имя с `..`, папка-ссылка наружу — `E024` |
| удаление | файлы манифеста прошлой сборки — только по настоящему пути внутри `dist/`; записи кэша — только внутри кэша | папка в `dist/` или каталог кэша, подменённые ссылкой наружу, пропускаются; запись кэша — ссылка наружу при чтении или записи — `E024` |
| корень кэша | `.heron-cache/` и `.heron-cache/renditions/` — настоящие папки рядом со сборкой; ссылка выше них (вся папка сайта — ссылкой) допустима | корень или `renditions/` — ссылка, в том числе битая, — `E024` до любой записи и уборки |
| готовая нарезка | берётся из кэша, только если это обычный файл (тип по самому пути, без перехода по ссылкам) | ссылка или другой не-файл на месте нарезки убирается — сама запись, не цель — и нарезка кодируется заново; папка на её месте — `E024`, dist не меняется |
| сами папки | `content/`, `data/`, `media/`, `static/`, `plugins/` — внутри сайта; `assets/`, `i18n/`, `templates/`, `modules/` и файлы строк `i18n/<язык>.yaml` — внутри темы | папка или файл строк — ссылка наружу — `E024` |
| плагины из `plugins:` | имя — `^[a-z0-9][a-z0-9_-]*$`, без повторов; папка `plugins/<имя>/` и её `__init__.py` — настоящие, не ссылки | имя вне правила — `E011` (схема) или `E014` (резолвер, вызванный напрямую); сама `plugins/`, папка плагина или `__init__.py` — ссылка наружу — `E024`; проверка до исполнения кода плагина, и при `build`, и при `check` |
| запись в папку сайта (`new`, `init`, `setup`, `theme get`) | `site.yaml`, `content/`, тема, `.heron/`, `.gitignore`, резервные копии в `.heron-cache/setup/` — итоговый путь внутри папки сайта; ссылка на другое место того же сайта допустима | файл или любая папка по пути к нему — ссылка наружу, в том числе битая, — `E024`; анкета проверяет все свои цели до первой записи, внешние файлы не меняются |
| обход папок | папка-ссылка внутрь той же папки даёт свои пути рядом с исходными (`latest/` → `v2/`); петля по цепочке предков отсекается | папка или файл исходников не читается (права, диск) — `E030`, а не тихо неполная сборка |

Папки не пересекаются: папка сборки (`--out`) не может быть корнем сайта,
содержать его, совпадать с `content/`, `data/`, `media/`, `static/` или
темой и лежать внутри них; кэш не пересекается ни с ними, ни со сборкой.
Нарушение — `E024` до начала работы. `dist/` внутри папки сайта — норма.

Здесь же выясняется дата обновления, источник задаёт `build.updated_from`
(`manual` по умолчанию, `git`, `file`). Приоритет один и тот же при любом
источнике: `updated` из фронтматтера перебивает автоматику всегда.

Режим `git` спрашивает историю **двумя** вызовами на всю сборку, а не двумя
на файл: один обход истории отдаёт даты по всем путям сразу, второй —
список незакоммиченных файлов. На сайте в несколько сотен страниц разница
между этим и `git log -1` на каждый файл — секунды против минут. Берётся
время коммитера (`%cI`) с его поясом: момент, когда правка попала в
историю, а значит и на сайт не раньше. Время автора бывает старше на
недели (ребейз, черри-пик). После разрешения дат `dates.check` ищет даты
позже момента сборки и обновления раньше публикации — предупреждения
вида «даты», при `--strict` ошибки (`20` §4.2). Переименования не отслеживаются:
для сайта переименование файла — это смена адреса, страница действительно
изменилась.

История недоступна — не репозиторий, гита нет в образе, история обрезана
(`clone --depth 1`) — сборка не падает: движок откатывается на время файлов
и говорит об этом **одним** предупреждением на сборку. Предупреждение с
путём файла остаётся там, где оно про конкретный файл: его нет в истории
или в нём незакоммиченные правки. Иначе сборка из копии без `.git` дала бы
двести одинаковых строк и забила бы сводку.

Дата приводится к календарной дате в UTC, без времени: результат не должен
зависеть от часового пояса машины, на которой запущена сборка.

**3. Парсинг.** Для каждой страницы: фронтматтер → модель, тело → секции, структурированные секции → данные. Ошибки собираются, не прерывая проход — чтобы разработчик увидел все сразу, а не по одной за прогон.

**4. Резолв связей.** Дочерние страницы каталогов, поля связей, объявленные темой в `links`, языковые соответствия, меню, хлебные крошки, обратные ссылки. Ссылка на несуществующую страницу — остановка.

Внутренние ссылки текста приводятся к языку страницы не приклеиванием префикса, а через страницу: написанный путь разбирается сначала как ключ, потом как адрес в языке страницы, потом как адрес языка по умолчанию (полное правило и пример — `20` §2). У найденной страницы берётся версия языка текущей страницы, и подставляется её адрес. Обрабатываются страницы всех языков, включая основной: ссылка-ключ на раздел со слагом и там отличается от адреса. Перевода нет — предупреждение, и ссылка ведёт на версию языка по умолчанию: читатель попадает на существующую страницу, а не в 404.

Отдельно проверяются ссылки, написанные руками в тексте: каждая вида
`/…/` обязана разрешаться в существующую страницу по тому же правилу.
Не разрешается — предупреждение с путём файла, номером строки и самой
ссылкой. Это предупреждение, а не ошибка: битая ссылка внутри текста не
повод не выкладывать остальной сайт. Но и молчать нельзя — адрес раздела
задаётся слагом, и переименование раздела оставляет написанные адресом
ссылки указывать в никуда до первого нажатия. Пропускаются внешние
адреса, якоря, пути к `/media/`, `/static/`, `/assets/` и к файлам с
расширением.

**Большие разделы.** Пагинации у движка нет, и это решение, а не пробел. Раздел со ста и более детьми — это **одна** страница каталога: `page.children` отдаёт теме всех детей сразу, отсортированных по `order`, затем по `h1`. Адресов вида `/faq/page/2/` движок не создаёт, поэтому вопросов с их каноникалом, `prev`/`next` и попаданием в карту сайта не возникает: в sitemap попадают раздел и каждый ребёнок, по одной записи.

Как показать длинный список удобно — забота темы: сгруппировать детей по полю (`groupby` в Jinja), вывести оглавление с якорями, свернуть группы в `<details>`. Все ссылки при этом обязаны быть в HTML (`20` §10): подгрузка списка скриптом прячет страницы от поисковика. Сто ссылок на странице каталога — нормальный размер; если раздел вырастет до тысяч, его делят на подразделы папками — у каждого свой `_index.md`, свой адрес и своя запись в карте.

Проверено на разделе из 120 страниц (`tests/test_large_section.py`).

**5. План картинок.** Для каждого мастера — имена и размеры всех нарезок, которые тема может попросить (пропорции × ширины × форматы, запасной формат — одна ширина `fallback_width`). Ничего не кодируется: шаблонам нужны только имена и `width`/`height`, а их даёт геометрия мастера. Оригиналы не трогаются.

**После рендера и генераторов — нарезка.** Движок ищет ссылки на `media/` во всём собранном тексте: страницах, картах, разметке, файлах плагинов, стилях темы и статике. Кодируется и кладётся в сборку только пересечение этих ссылок с планом. Мастер целиком кладётся, только если на него есть ссылка (`media_url(src)`, og:image) или он объявлен «сырым»: картинка из текста страницы, `og_image`, `twitter_image`, `video_poster`, `seo.og_default_image`. Файлы, которые движок не режет (видео, PDF, svg, `as_is`), копируются как раньше.

Нарезки живут **в кэше**, адресованном содержимым мастера, а в сборку попадают жёсткой ссылкой (подробно — «Кэш нарезок» ниже). Ссылки на `media/` в markdown — от корня сайта: `media/x.svg`, `./media/x.svg` и `/media/x.svg` в картинке и в ссылке выводятся как `/media/x.svg` на любой глубине страницы.

Кодирование раскидывается по ядрам, задача — мастер, а не отдельная нарезка: дробить мельче значит декодировать исходник семьсот раз вместо девяноста пяти. Число процессов — `build.workers`, ноль означает по числу ядер. Прогресс тикает в порядке исходного списка, а не готовности: иначе лог перестаёт читаться, а смотрят в него как раз на долгой сборке.

Замер на сайте с 95 мастерами и 2062 нарезками, четыре ядра: холодная сборка 157 с, повторная — 4 с, из них картинки 0.3 с.

**6. Рендеринг.** Каждая страница через `templates/<тип>.html` темы (или шаблон, названный в `types.<тип>.template`). Страница 404 основного языка дополнительно кладётся в корень как `404.html` (`20` §2, «Страница 404»).

**7. Генерация служебного.** sitemap, robots, llms.txt, redirects, feed. JSON-LD встраивается на шаге 6.

**8. Запись результата.** Этапы 6–7, `static/`, `theme/assets/`, нарезки и файлы плагинов только *заявляют* выходные файлы; пишет один шаг — и только после того, как сборка признана удачной (ошибок нет, а в строгом режиме нет и предупреждений; отчёт, разметка и `nginx -t` проверены до записи).

#### Запись результата

- **Владельцы.** У каждого пути сборки один владелец: страница, генератор (sitemap, robots, llms, карты, конфиг nginx, лента), `static/`, ресурс темы, медиа, плагин. Два владельца у одного пути — `E026` с обоими именами; файл и папка с одним именем (`about` и `about/index.html`) — тоже `E026`. Единственная разрешённая подмена — генерированный файл файлом из `static/`, перечисленный в `build.overrides` (`20` §5).
- **Неудача не трогает прошлую версию.** Ошибка или предупреждение в строгом режиме — в `dist/` не записано ничего.
- **Применение.** Новое готовится во временной `dist/.heron-staging/` (та же файловая система) и ставится на место переименованием. Удаляются только устаревшие файлы, которыми владела прошлая сборка, — их список в `dist/.heron-manifest.json` (наружу его не отдаёт nginx: скрытые файлы — 404). Чужие файлы в `dist/` не трогаются; чужой файл на месте нужного пути — `E026`. Перед первым переименованием манифест атомарно переписывается списком «прошлое ∪ новое» (журнал): если применение оборвётся посреди (кончился диск), в `dist/` может остаться смесь версий, но все появившиеся файлы уже числятся своими — следующая удачная сборка уберёт лишнее своё и не тронет чужое. По окончании манифест — точный список новой сборки.
- **Чужой файл.** Обычный файл на нужном пути, которого нет в манифесте, — `E026` до любого изменения `dist/` (те же байты — не спор). Папка, собранная прошлой версией движка без манифеста (в ней лежит `.heron-nginx.conf`), считается своей — один раз, до первого манифеста.
- **Проверяется итог.** `nginx -t` гоняется на том содержимом `.heron-nginx.conf`, которое ляжет в сборку, — в том числе подменённом статикой через `build.overrides`.
- **Служебные имена.** `.heron-manifest.json` и `.heron-staging/` в корне сборки пишет только движок: файл с таким путём из `static/` или плагина — `E026`.
- **Одна сборка за раз.** Применение идёт под блокировкой файла `.<папка сборки>.heron-lock` рядом с папкой сборки: две сборки в одну папку одновременно применяются по очереди, а не вперемешку.
- **Неизменившееся не переписывается.** Файл с теми же байтами остаётся с прежним временем (ETag и кэш браузеров живут), нарезка — с той же жёсткой ссылкой на кэш. Общий с кэшем или с прошлой версией inode не правится на месте никогда: заменяется запись каталога, не данные.
- **Что инкрементально, а что нет.** Дорогое — кодирование картинок — берётся из кэша и не повторяется (§8, «Кэш нарезок»). HTML рендерится весь при каждой сборке: зависимости страниц (меню, каталоги, связи, переводы, карты) не отслеживаются, и это не инкрементальный рендер. Зато результат повторной сборки совпадает с холодной побайтово при одинаковых входах и `SOURCE_DATE_EPOCH`, а в `dist/` записываются только изменившиеся файлы.
- **Время сборки.** Метка сборки (`env.stamp`) берёт время из `SOURCE_DATE_EPOCH`, если он задан, — так сборки воспроизводимы.

После — сводка: сколько страниц по языкам и типам, сколько предупреждений, список долгов по контенту.

Предупреждения группируются по виду: `картинки`, `связи`, `ссылки`, `меню`,
`переводы`, `языки`, `прочее`. Сверху то, что ломает страницу для посетителя,
снизу то, что заметит только редактор. В каждой группе шесть примеров, полный
список пишется в `<рядом с dist>/.heron-cache/warnings.txt`. Без группировки
сотня однотипных замечаний про переводы прятала десяток важных про картинки,
которых нет на диске.

Ход сборки виден в терминале: этап, время с его начала, счётчик и полоска
внутри длинных этапов — нарезки картинок, рендера, записи файлов. В не-терминал
(CI, докер без `-t`, перенаправление в файл) перерисовывать нечего, поэтому
этап объявляется сразу, как начался, длинные этапы отмечаются раз в две
секунды, в конце пишется итог. Каждая строка выталкивается из буфера сразу:
иначе весь лог доезжает до человека одной пачкой в конце и сборка неотличима
от зависшей.

## 5. Парсер секций

Сердце системы, поэтому подробно.

Тело файла разбирается `markdown-it-py` с включённым плагином атрибутов. Секция — заголовок, у которого есть якорь `{#id}`, и всё содержимое до следующего заголовка **того же уровня с якорем** либо до конца файла.

Правила:

- заголовки без якоря секцию не начинают и принадлежат текущей
- текст до первой секции доступен как `intro`
- идентификатор: `[a-z0-9-]+`. Иное — ошибка
- дубликат идентификатора в файле — ошибка
- у секции сохраняются: `id`, `title` (текст заголовка), `level`, `html` (отрендеренное содержимое без заголовка), `raw` (исходный markdown)
- и разобранные части: `lead` (абзацы до основного узла), `body` (сам узел), `note` с `note_title` (абзацы после), `callout` (цитата) и `links`
- вводный блок отдаётся тремя полями: `lead` — первый абзац, `promise` — второй, `intro` — весь текст целиком. Третий абзац и далее — предупреждение: в шаблоне для них места нет

Тема сама решает, показывать ли заголовок секции: `mod.prose('what')` выводит и заголовок и текст, а `mod.facts('quick-facts')` заголовок игнорирует, потому что рисует рамку с фактами.

### Формы секций

Каждая секция после разбора получает поле `kind` — одну из тринадцати форм: `prose`, `list`, `alert-list`, `checklist`, `two-lists`, `steps`, `table`, `facts`, `faq`, `timeline`, `callout`, `gallery`, `tabs` — и `data` с разобранными данными этой формы. Таблица форм, признаки, порядок распознавания и форма данных — `20` §4.4, это единственное место, где они описаны. Список форм в коде — `heron.contracts.theme.KINDS`, порядок автоопределения — `heron.core.parser.blocks.AUTO_ORDER`.

Разбор ошибается мягко: класс задан, а содержимое не подходит, — секция отдаётся прозой и пишется предупреждение. Валить сборку из-за пропущенной палочки в таблице нельзя.

Модель секции:

```python
class Section:
    id: str                # якорь из {#anchor}
    title: str             # текст заголовка
    level: int
    classes: list[str]     # классы из якоря: alert, timeline, …
    raw: str               # исходный markdown без заголовка
    html: str              # отрендеренное содержимое без заголовка
    kind: str              # форма: prose, list, … — см. 20 §4.4
    data: Any              # разобранные данные формы; в шаблоне модуля — items
    lead: str              # абзацы до основного узла
    note: str              # абзацы после
    note_title: str        # жирный зачин примечания
    callout: str           # цитата, где бы она ни стояла
    links: list[dict]      # ссылки секции {title, href}
    body: Any              # свойство: data, а для прозы — html
```

## 6. Модель страницы

Поля фронтматтера живут в `page.meta` — по одному атрибуту на каждую строку таблицы `20` §4.2, плюс поля темы, которые ядро не трактует (`page.meta.<поле>`, а все разом — `page.meta.extra`). Сама страница добавляет то, что движок выяснил при обходе и резолве:

```python
class Page:
    lang: str                      # код языка
    source: str                    # путь файла от content/: ru/services/x.md
    key: str                       # ключ: services/x; у главной — пустая строка, в шаблонах и nav — "/"
    meta: PageMeta                 # фронтматтер, см. 20 §4.2
    url: str                       # адрес с префиксом языка и слагами: /ru/rukovodstva/x/
    type: str                      # тип страницы, правило выбора — 20 §4.2
    sections: dict[str, Section]   # секции по якорю
    intro: Section | None          # текст до первой секции
    auto_updated: date | None      # дата из git или файла, если updated не задан руками
    links: list[tuple[int, str]]   # ссылки текста как написаны: строка и адрес

    # заполняется на этапе резолва
    parent: Page | None
    children: list[Page]
    translations: dict[str, Page]  # версии на других языках, по ключу
    breadcrumbs: list[Page]
    related: dict[str, list[Page]] # связи, объявленные темой, и обратные

    # вычисляемые
    title: str                     # meta.title
    h1: str                        # meta.h1
    updated: date | None           # meta.updated, иначе auto_updated
    nav_title: str                 # meta.nav_title, иначе имя файла
    video: Video | None            # разобранные meta.video*
    slug: str                      # последний сегмент url
    name: str                      # имя файла без расширения
    is_index: bool                 # _index.md или главная
```

`Site.page(key, lang)` находит страницу по ключу на языке; в шаблоне то же самое — `page_of(key)`.

## 7. Рендеринг

Jinja2, `autoescape` включён, `StrictUndefined` — обращение к несуществующей переменной валит сборку, а не выводит пустоту. Это ловит опечатки в теме на этапе сборки.

Тема — недоверенный код: её ставят из каталога, по ссылке или архивом. Поэтому шаблоны собираются в неизменяемой песочнице Jinja (`ImmutableSandboxedEnvironment`): служебные атрибуты Python (`__globals__`, `__class__` и подобные) закрыты, списки и словари из шаблона не меняются (`.append`, `.update`). Сверх песочницы закрыты методы самого pydantic `BaseModel` у `site` и `theme` (`parse_file`, `model_construct` и т. п. — поля и собственные методы схем доступны), любые атрибуты путей и методы `env`, которые строят окружение заново. Обращение к закрытому — `E033` с именем шаблона. Фильтры и функции плагинов сайта (`plugins/`) — код самого сайта, на них песочница не распространяется.

Шаблону доступны: `page`, `site` (весь `site.yaml`), `data` (содержимое `data/`), `nav`, `t` (строки интерфейса темы), `mod` (макросы модулей), `lang` и `languages`, `hreflang`, `page_of(key)` (страница по ключу на текущем языке, главная — `'/'`), `picture`, `media_url`, `absolute`, `jsonld()`, `env` (окружение сборки: `env.indexable`, `env.analytics`, метка сборки).

### Макросы модулей

`mod.<модуль>(<id секции>)`. Логика одинаковая для всех:

1. секции с таким id нет → вернуть пустую строку, ничего не рендерить
2. секция есть → отрендерить `theme/modules/<модуль>.html`, передав ей данные секции

Модули без аргумента (`mod.call()`, `mod.author()`, `mod.breadcrumbs()`) берут данные из `site` и `page`, а не из секций.

Пустая строка вместо блока — принципиально: заголовок без содержимого хуже отсутствующего блока.

### Строки интерфейса

Тексты, принадлежащие теме, а не контенту («Book now» / «Записаться», «Read more» / «Читать далее»), живут в `theme/i18n/<lang>.yaml` и доступны как `t.book_now`. Иначе они окажутся зашиты в шаблоны и тема перестанет быть переносимой между языками.

## 8. Картинки

Для каждой картинки, на которую ссылается контент:

- варианты по ширине: 400, 800, 1200, 1600 — но не больше исходной
- форматы: AVIF и WebP на всех ширинах; исходный (PNG/JPEG) — запасной для `<img src>`, одной шириной `images.fallback_width` (800), не больше ширины кадра. Другие ширины исходного формата режутся, только если их попросили через `media_url(src, ratio, width)`
- режется только то, на что есть ссылка в собранном сайте: пропорция, которую ни один шаблон не попросил, в сборку не попадает
- `srcset` и `sizes` проставляются модулем
- `width` и `height` обязательны в разметке — иначе прыгает вёрстка и растёт CLS
- `loading="lazy"` на всё, кроме картинки первого экрана
- нарезки хранятся в кэше, а в сборку попадают жёсткой ссылкой

`og_image` не обрабатывается: соцсети ждут JPEG или PNG 1200×630 по фиксированному адресу.

Картинка, на которую есть ссылка, но которой нет на диске — остановка сборки. Битая картинка в проде дороже, чем упавшая сборка.

### Кэш нарезок

Кодирование — самая дорогая часть сборки: 95 мастеров при трёх пропорциях, четырёх ширинах и трёх форматах дают больше двух тысяч файлов и минуты работы процессора. Правка одной строки в CSS не должна их стоить.

**Где лежит.** Рядом с папкой сборки, не внутри неё (`<родитель --out>/.heron-cache/`):

```
.heron-cache/
├── renditions/v5-<настройки кодировщика>/
│   └── <sha256 мастера>/
│       ├── shape.json             ширина, высота, есть ли прозрачность
│       ├── crop-16x9-800.webp     нарезка: способ, пропорция, ширина, формат
│       └── .used                  когда запись последний раз нужна была сборке
└── warnings.txt                   полный список предупреждений последней сборки
```

**Поворот по EXIF.** Мастер читается так, как его показывает браузер: тег Orientation (2–8) применяется до определения размеров, кадрирования и кодирования, в нарезку тег не идёт. Версия формата кэша — `v5`: записи `v4` повёрнутых фотографий были нарезаны без поворота, сборка их не берёт, уборка снимает.

**Идентичность — содержимое и параметры.** Папка записи — sha256 байтов мастера, имя файла — параметры преобразования; настройки кодировщика (качество, скорость) — в имени папки версии. Имя файла в сборке (`media/photo-16x9-800.webp`) берётся от сайта, байты — из записи по хешу. Поэтому «файл с таким именем уже есть» ничего не значит: изменённый мастер — другая запись, два сайта с одинаковым `media/photo.jpg` и разным содержимым не смешиваются, а с одинаковым — делят запись честно.

**Общий кэш и конкурентные сборки.** Несколько сайтов, собираемых в одну папку (`--out out/a`, `--out out/b`), делят `out/.heron-cache`. Файлы пишутся во временный файл рядом и ставятся `os.replace`: две сборки, режущие одно и то же, пишут одинаковые байты и никогда не видят недописанного файла.

**Как попадает в сборку.** Жёсткой ссылкой (§4, «Запись результата»); не вышло — копией. Общий inode не правится на месте никогда: и сборка, и кэш меняют только записи каталога.

**Что считается изменением.** Мастер — по содержимому. Состав нарезок — по спеку темы (`widths`, `ratios`, `formats`, `crop`, `fallback_width`): новая ширина кодируется, уже закодированные ширины и пропорции переиспользуются. Мастер, который уже видели, не декодируется ради плана: размеры и прозрачность — в `shape.json`.

**Уборка.** Кэш общий, поэтому «не нужно этой сборке» — не повод удалять. Сборка держит разделяемую блокировку кэша от плана картинок до записи результата; уборке нужна исключительная, и пока кто-то собирает, она откладывается до следующей сборки. Сборка отмечает нужные ей записи (`.used`); раз в сутки под исключительной блокировкой удаляются записи, которыми не пользовалась ни одна сборка 30 дней, и записи прошлых форматов. Нарезка, уже стоящая в сборке, удалением записи не задевается. Кэш прежнего формата (`media.json`, `media/` по путям сайта — он и смешивал сайты) удаляется при первой сборке.

**Кэш можно удалять в любой момент.** Он влияет только на скорость: первая сборка после удаления будет холодной. Именно поэтому он в `.gitignore` и именно поэтому прод и CI не обязаны его иметь.

**Одинаковые имена нарезок.** `media/photo.jpg` и `media/photo.png` дают одни и те же имена (`photo-16x9-800.webp`) — `E027`: переименуйте один из мастеров. Адреса нарезок существующих сайтов от этого правила не меняются.

### Сколько процессов

Кодирование независимо и упирается в процессор, поэтому раскидывается по ядрам. Задача — мастер, а не отдельная нарезка: дробить мельче значит декодировать исходник семьсот раз вместо девяноста пяти.

`build.workers` в `site.yaml`, ноль — по числу ядер машины. Ставят руками там, где ядра делят с другими задачами: в CI сборка сайта не одна на машине, и забрать все ядра значит замедлить соседей.

Прогресс тикает в порядке исходного списка, а не готовности. Иначе лог перестаёт читаться, а смотрят в него как раз на долгой сборке.

Число процессов выбирают по порядку: флаг `--workers N` у `heron build` и `heron serve` (0–64), переменная `HERON_WORKERS`, `build.workers`. Значение переменной вне 0–64 — `E011` с подсказкой; флаг вне диапазона отвергает сам `click`.

**Сбой пула не валит сборку.** В окружениях с ограниченным обменом между процессами (песочница macOS, контейнер без семафоров, часть CI) пул не создаётся или умирает. Тогда движок один раз предупреждает (`pool_fallback`) и кодирует остаток последовательно; нарезки, уже лежащие в кэше (`_reusable`), не кодируются повторно, результат побайтно тот же, что при `workers=1`. Сбоем пула считаются только `BrokenProcessPool` и отказ при создании пула или `submit` (`OSError` с `errno` `EPERM`/`ENOSYS`/`EACCES`, `NotImplementedError` об отсутствии семафоров). Ошибки воркера — `HeronError`, `PIL.*`, `ValueError`, а также `OSError` диска — пробрасываются как есть, фолбэк в них не включается.

### Скорость кодировщиков

У webp и avif выставлены явные регуляторы скорости — не умолчания библиотеки. Умолчание может смениться с обновлением зависимости и сделать сборку впятеро медленнее без единой строчки в нашем коде.

Замер avif на наборе из 95 мастеров, 800px, quality 82:

| speed | время на вариант | размер | к выбранному |
|---|---|---|---|
| 0 | 5.33 с | 43.0K | −5.7% |
| 4 | 0.69 с | 44.4K | −2.6% |
| **6** | **0.13 с** | **45.6K** | — |
| 8 | 0.05 с | 47.3K | +3.6% |
| 10 | 0.02 с | 57.1K | +25.0% |

Выбрана шестёрка: четвёрка стоит впятеро дороже по времени ради двух с половиной процентов размера, десятка экономит время ценой четверти веса. У webp тем же способом выбран `method=4`: самый медленный режим давал 7 секунд на вариант вместо 0.1 при выигрыше около двух процентов.

## 9. Генераторы

### sitemap

Состав зависит от числа языков в `site.languages`:

- **один язык** — `sitemap.xml` и есть список адресов (`<urlset>`). Индекс над единственным файлом ничего не добавляет, кроме лишнего запроса;
- **два и больше** — `sitemap.xml` становится индексом, рядом лежит `sitemap-<lang>.xml` на каждый язык из `languages`, у которого есть индексируемые страницы. Языка, которого нет в списке, нет и в карте.

Включаются страницы с `published: true` и `noindex: false`, кроме страницы 404. `lastmod` из `updated`, полной датой с поясом (`20` §4.2). У записи, у которой есть версии хотя бы на двух языках, — `xhtml:link` на все версии плюс `x-default`, если есть версия языка по умолчанию. Тот же набор выводится в `<head>` (переменная шаблона `hreflang`); полные правила — `20` §3.

Служебных типов записей в sitemap нет по определению: в системе нет сущностей без URL. Служебные записи, какие оставляют в картах сайта плагины CMS, здесь невозможны архитектурно.

### robots.txt

Из `seo.robots_extra` плюс обязательная строка `Sitemap:` с абсолютным адресом. Собирается, а не лежит файлом: положенный руками, он через полгода начинает врать.

### llms.txt

По формату llmstxt.org: заголовок сайта, краткое описание, разделы со списком страниц и однострочными описаниями из `description`. Строится из того же дерева, что и меню, и по той же политике, что карта сайта: страница с `noindex` (или вне карты) не попадает ни в общий список, ни в список детей своего каталога.

При `seo.llms_txt: true` дополнительно `llms-full.txt` — весь текст сайта одним файлом.

**Одноязычный сайт** языковых файлов не получает: `/llms.txt` сразу содержит полный перечень страниц (с блоком `seo.llms_note` этого языка), `/llms-full.txt` — полные тексты, и они ссылаются друг на друга. Оглавление из одной ссылки заставило бы модель сделать лишний шаг ради того же содержимого.

**На многоязычном сайте файл собирается на каждый язык**, а не только на основной:

- `/llms.txt` — корневой: название сайта, описание и список языковых версий. Перечня страниц в нём нет, это оглавление;
- `/llms-<язык>.txt` — полный перечень страниц своего языка. В шапке ссылки на остальные версии и на корневой файл, чтобы модель, попавшая сразу на русский, знала о существовании других;
- `/llms-full-<язык>.txt` — то же с полным текстом, при `seo.llms_txt: true`.

**Навигация замкнута: тупиков в наборе нет.** Из любого файла можно дойти до любого другого:

| Файл | Куда ведёт из шапки |
|---|---|
| `/llms.txt` | на краткую и на полную версию каждого языка |
| `/llms-<язык>.txt` | на корневой, на краткие версии других языков, на свою полную |
| `/llms-full-<язык>.txt` | на корневой, на полные версии других языков, на свою краткую |

Ссылка между краткой и полной версией одного языка — не про языки, поэтому она есть и на одноязычном сайте, где блока «другие языки» нет вовсе. Полные файлы отключены (`seo.llms_txt: false`) — ссылок на них нет нигде.

Подписи строк — на языке самого файла, для корневого — на языке сайта по умолчанию. Языку, которого нет в наборе подписей, достаётся английская: она понятна и модели, и человеку, а выдуманный перевод — никому.

Языки не смешиваются в одном файле намеренно: модель отвечает на языке того текста, который прочла, а близкие языки — украинский с русским — она путает чаще всего. Раздельные файлы дают ей выбрать нужный, перекрёстные ссылки — найти остальные.

Формат llmstxt.org языковых версий не описывает, поэтому конвенция своя: файл читает модель, ей достаточно внятной строки человеческим текстом.

Язык, у которого нет ничего, кроме заглушки, в список не попадает: ссылка на пустой файл хуже её отсутствия — модель уйдёт по ней и вернётся ни с чем.

**Сведения о сайте.** `seo.llms_note` даёт на каждый язык кусок markdown, который вставляется дословно:

- в `/llms-<язык>.txt` — после краткого описания, до перечня страниц;
- в `/llms-full-<язык>.txt` — после заголовка, до текстов страниц;
- в `/llms.txt` — текст языка сайта по умолчанию.

Порядок именно такой: сначала «что это за сайт», потом «как с ним иметь дело», потом содержимое. Читателю нужен ответ раньше оглавления — за ответом он и пришёл.

Блок не ищется в готовом тексте и никуда не «вставляется» постфактум: файл собирается списком строк, и место блока задано в момент сборки. Поиск по готовому файлу спотыкался бы о тексты страниц, где встречаются и заголовки, и цитаты, похожие на шапку.

Содержимое блока — факты о сайте, а не указания читающей модели. Текст с чужого сайта потребитель вправе считать данными, а не инструкциями; попытка управлять через него чужим агентом бесполезна и выглядит как внедрение инструкций.

### JSON-LD

Встраивается в `<head>` каждой страницы, тип зависит от типа страницы:

Типы разметки объявляет **тема**, ключом `types.<тип>.jsonld` в `theme.yaml`: у сайта услуг, магазина и справочника соответствие разное, и ядро его знать не обязано.

Ядро строит то, что действительно знает само:

| Что | Откуда берётся |
|---|---|
| `@type`, объявленный темой | `theme.yaml` |
| `name`, `description`, `url`, `inLanguage` | страница |
| `datePublished` | поле `date`, полночь UTC: `2026-03-14T00:00:00+00:00` |
| `dateModified` | `updated` или `build.updated_from`; из git — время коммита с поясом |
| поля организации и прочие реквизиты | блок `schema` в `site.yaml` |
| уточнения по конкретной странице | блок `schema` во фронтматтере |
| `BreadcrumbList` | построенные крошки, везде кроме главной |
| `FAQPage` | секция, разобранная как `faq` |

Слияние трёхуровневое: сайт, затем страница. Данные организации живут в `site.yaml` и не дублируются в контенте.

### redirects

Собирает все `redirect_from` со всех страниц в `dist/redirects.map` формата nginx:

```
/old/address/  /new/address/;
```

Старые адреса сначала нормализуются: percent-encoding раскрывается, текст приводится к NFC, регистр сохраняется, завершающий слеш добавляется всем, кроме файлов (`20` §2, «Старые адреса»). Пример с кириллицей: `/%D0%BA%D1%80%D0%B5%D0%B4%D0%B8%D1%82` и `/кредит/` дают одну строку карты `/кредит/  /credits/;`, и 301 срабатывает на обе формы, со слешем и без. Адрес, который после декодирования не текст (слаг обрезан посреди буквы), остаётся в percent-форме и сверяется с `$request_uri`.

Проверки на этапе сборки — по нормализованной форме: старый URL не совпадает ни с одним существующим, один старый URL не ведёт в два места, цепочек нет (`E009`).

Рядом — список 410 из ключа `gone` в `site.yaml` (`20` §5): точные адреса, префиксы `/wp/*` и адреса с параметром `/?p=*`. Пересечение со страницей или с `redirect_from` — `E022`. Копия списка — `dist/gone.map`.

Обе карты движок вписывает в конфиг nginx, который собирает вместе с сайтом (`dist/.heron-nginx.conf`): точный адрес — `location = "/старый/"` (и вариант без слеша), префикс — `location ^~ "/wp/"`, запись с параметром — регулярная карта `map "$uri?$args"`, битый percent-адрес — регулярная карта по `$request_uri` (регистр `%xx` не важен, регистр букв важен). Строковые карты не используются: nginx сравнивает их без учёта регистра, а адреса движка регистр различают. Ответ уходит без обращения к файлам. Адреса 301 и 410 сверяются между собой, со страницами и со служебными адресами в форме без завершающего слеша — сервер отвечает на обе (`/a.html` и `/a.html/` — один адрес; совпадение — `E009` или `E022`). Управляющие символы в старом адресе (`%0A`, `%00`) — тоже `E009`/`E022`. Префикс `gone`, совпадающий со служебным (`/media/`, `/assets/`, `/.well-known/`, языковой `/<lang>/`), и 301/410 на служебных страницах 404 — `E022`.

### feed

`dist/feed.xml` в формате Atom — только если в `site.yaml` задан `seo.feed`: тип страниц, которые идут в ленту. Берутся опубликованные и индексируемые страницы этого типа на языке по умолчанию, не больше `seo.feed_limit` (20). Порядок — по дате публикации (`date`), у страниц без неё — по дате обновления, новые сверху. У записи есть `<published>`, если задана `date`, и `<updated>` — полной датой с поясом, как в разметке.

## 10. CLI

Эти команды — вся поверхность движка для человека. Внутрь него заходить не нужно.

```
heron new [путь] [--notes ru|en] [--name …] [--domain …] [--lang en,ru] [-y] [-v]
                                             создать сайт с нуля; путь по умолчанию — «.»
heron init [путь] [--force] [--notes ru|en] [--name …] [--domain …] [--lang …] [-y] [-v]
                                             достроить папку под написанное в site.yaml
heron check [путь] [--strict] [--drafts] [--json]  отчёт без сборки; --json — коды, файлы, строки для агента
heron serve [путь] [--port 8000] [--host Х] [--workers N]  локальный просмотр с пересборкой
heron build [путь] [--out папка] [--env prod] [--strict] [--drafts] [--workers N]   собрать
heron page <тип> <слаг> [путь] [--lang ru] [--folder раздел]          заготовка страницы
heron docs [тема | template <файл>] [--search текст] [--export папка]  документация этой версии
heron setup [путь] [--answers файл|-] [--dump] [--port 8000] [--host Х]  конфигуратор-анкета
heron theme get <starter|имя|https-ссылка|архив> [путь]   поставить тему с её демо-страницами
heron theme list | heron theme pack [путь] [--out файл]   каталог; своя тема с контентом в архив
heron schema [--setup]                       JSON Schema site.yaml (или ответов анкеты)
heron recipe                                 Dockerfile образа nginx для собранного dist/
```

- `--drafts` включает `published: false`; `--strict` превращает предупреждения в ошибки — режим для CI;
- `--env prod` — боевая сборка: индексация и счётчики. Без него — дев: `robots.txt` с `Disallow: /`, `noindex`, без счётчиков. Пустой сайт и пустой основной язык допустимы только в деве (`E017`, `E021`);
- `heron new` создаёт сайт в новой папке или в текущей (`.`). Папка может быть под git: `.git`, `.gitignore`, `.gitattributes`, `.gitmodules`, `.github`, `.gitlab`, `.DS_Store`, `.editorconfig`, `README`, `LICENSE` не мешают и не перезаписываются. Любой другой файл — отказ с перечнем того, что мешает, и советом `heron init`;
- **в терминале `new` задаёт вопросы**: язык пояснений, название, домен, языки сайта, основной язык (последний — только если языков больше одного). У каждого вопроса есть значение по умолчанию, неверный ответ переспрашивается, в конце — сводка и подтверждение; отказ ничего не создаёт. **Без терминала** (агент, CI, `docker run` без `-it`) вопросов нет: значения из флагов `--name`, `--domain`, `--lang` (через запятую, первый — основной) или по умолчанию, и об этом печатается строка. `-y` отключает вопросы и в терминале. Ответы ложатся в `site.yaml`, под каждый язык сразу создаются `content/<язык>/index.md` и `404.md` с полным SEO-блоком: стартовый сайт собирается `--env prod --strict` без единого предупреждения. Дальше `site.yaml` — единственный источник правды, `heron init` достраивает папки под написанное;
- `--notes ru|en` — язык пояснений: комментарии во всех файлах скелета (`site.yaml`, `theme.yaml`, SEO-блок страниц), записки `heron-readme.md` и сообщения на экране: шаги и итог `new`, `init`, `page`, `check`, `build`, ошибки. Подробный отчёт сборки (сводка предупреждений) пока только по-русски. Порядок: флаг → переменная окружения `HERON_NOTES` → `build.notes` из `site.yaml` → `en`. `new` записывает выбор в `build.notes`, поэтому `init` и `page` без флага держат язык, на котором сайт заведён. Языки самого сайта от него не зависят;
- `heron init` смотрит, что в папке есть, дописывает недостающее, ничего не перезаписывает без `--force` и печатает, что нашёл и что добавил. **Нет `site.yaml` — сайт только заводится**: в терминале те же вопросы, что у `new`, с теми же флагами; языками по умолчанию предлагаются папки, которые уже лежат в `content/`. Есть `site.yaml` — вопросов нет, источник правды он;
- `new` в папке, где уже есть `site.yaml`, не перечисляет «мешающие файлы», а говорит, что сайт здесь уже есть, — на языке этого сайта (`build.notes`) — и предлагает `init`, `check`, `build` или как начать заново;
- **название по умолчанию** — имя репозитория из `origin` в `.git/config`, иначе имя папки. В контейнере папка всегда `/site`, поэтому без репозитория там предлагается `my-site`;
- `new` и `init` печатают сводку по смыслу (конфиг, контент по языкам, тема, папки, записки, что не тронуто) и блок «Что дальше» с готовыми командами под эту папку; полный список файлов — `-v`;
- **пути — относительно текущей папки.** В образе (`HERON_IN_CONTAINER=1`) видна только смонтированная папка `/site`; путь с компьютера человека, которого внутри нет, даёт объяснение про монтирование и совет передать `.` или имя вложенной папки;
- **трейсбек наружу не выходит.** Ошибка движка печатается по форме: код и название, где, подробно, что сделать. Нет прав на запись — совет про `--user $(id -u):$(id -g)`. Непредвиденная ошибка — её вид, текст и совет повторить с `--debug` (или `HERON_DEBUG=1`), который отдаёт трейсбек целиком;
- `heron page` создаёт файл с полным SEO-блоком и всеми секциями типа из `theme.yaml`;
- `heron new` кладёт белую тему (светлая и тёмная, переключатель языков и вида) и её демонстрационные страницы в каждый язык: главная, `blocks.md` (все тринадцать форм), `themes.md`, `docs.md`, 404, меню `["/", blocks, themes, docs]`, картинки `media/demo/`. Тексты — на русском и английском, другие языки получают английские. Флага «без демо» нет: демонстрационные страницы — часть темы. `heron init` дописывает их новому языку, только если в основном языке ещё лежит `blocks.md`;
- `heron docs` — документация ровно этой версии движка, из пакета: без аргументов — оглавление, с темой — файл целиком в markdown, `template <файл>` — образец, `--search` — строки с контекстом, `--export <папка>` — всё папкой с теми же путями, что в репозитории. В пакет и образ едет только текст (около 400 КБ, сжатым — около 130 КБ), картинки бренда — нет; тест следит, чтобы каждый файл документации был доступен как тема.

Упаковки в образ среди команд движка нет: образ nginx с сайтом собирает **хост** — `scripts/site.sh <сайт> image <окружение>` из репозитория движка (`23-distribution.md` §5).

### heron page

`heron page <тип> <слаг> [--lang L] [--folder F] [путь]` кладёт заготовку в `content/<lang>/<folder>/<слаг>.md`.

- `--lang` должен быть в `site.languages`, иначе `E005` (подсказка — список языков). Без него берётся `site.default_lang`.
- `--folder` — путь внутри `content/<lang>/`. Ведущие `./` и `/` и хвостовой `/` снимаются. Путь с `..`, абсолютный, или с частью, начинающейся с точки (`.git`), даёт `E024`, файл не создаётся.
- Если `content/<lang>` или промежуточная папка — символическая ссылка наружу сайта, команда падает с `E024` и ничего не пишет.
- Существующий файл не перезаписывается (`E004`).

### heron setup

Анкета вместо ручного `site.yaml`. Без флагов поднимает локальную страницу (адрес и порт — как у `heron serve`: в образе слушает `0.0.0.0`, порт публикуется только на петлю машины `-p 127.0.0.1:8000:8000`). Граница доступа — ключ, который движок печатает в терминале в адресе страницы после `#` (`http://localhost:8000/#ключ`): в саму страницу он не вшит, и без него `/api/*` (чтение ответов, загрузка темы, запись) отвечает 403. Клиент, который дотянулся до порта, но не видел терминала, получает только пустую страницу. Заголовок `Host` дополнительно обязан быть локальным — это защита от подмены DNS, а не граница доступа. `--answers файл` применяет те же ответы без браузера — для агента и CI, `-` читает stdin; `--dump` печатает записанные ответы в YAML: поправить и подать обратно. Схема ответов — `heron schema --setup`.

Анкета открывается только в папке сайта: нет `site.yaml` — отказ с советом перейти в папку сайта или создать его (`heron new`). Изменённое поле помечено «было: X» с кнопкой «вернуть» — сравнение с тем, что сейчас записано в `site.yaml`.

Группы анкеты:

1. **сайт и домены** — `site.name`, рабочий домен, служебный домен → `site.domains.dev`. Рабочий домен — тот, с которым собирается прод: `site.domains.prod`, если он задан, иначе `site.domain`; поменяли его — меняются оба, остальные окружения `site.domains` не трогаются;
2. **языки** — справочник языков, выбранные — вкладками, основной — из выбранных;
3. **о ком сайт** — «кто вы»: человек или организация и вид организации (`heron/setup/vocab.yaml`), затем сфера деятельности и специализация по классификатору `heron/setup/classifier.yaml` (у специализации бывает точный тип schema.org: стоматология → `Dentist`; компания с ним — `["Corporation", "Dentist"]`; человеку — `hasOccupation`); поля на каждом языке сайта (имя, название, должность, «чем занимаетесь»), адрес блоком (страна справочником с телефонным кодом, город, регион, индекс, улица, дом), конструктор контактов `тип · назначение · значение`. Сфера и специализация ложатся подписями в `organization.field_of_work` и `organization.specialization` (с хвостами языков), в разметку — `knowsAbout`;
4. **поиск** — хвост заголовка разделителем и текстом (`seo.title_suffix`: анкета и `--answers` всегда ставят пробелы вокруг разделителя, текст без разделителя получает « — »), `seo.og_default_image`, `seo.allow_prices`;
5. **ИИ-ассистенты** — `seo.llms_note` вкладками по языкам сайта;
6. **аналитика** — `analytics.ga4`, `gtm`, `metrika` (в сборку только при `--env prod`);
7. **публикация** — `publish:`: «пока не знаю», GitHub (репозиторий, ветка, версия, окружение, `auto` — автоматическая сборка и публикация образа), Docker Hub, статика (на сервер или GitHub Pages — с веткой); при сборке образа — таблица dev/prod: домен, индексация, адрес образа; помощники `publish.helpers` — скрипт сборки, скрипт публикации, `.gitignore`, каждый включается отдельно. При «пока не знаю» в `publish:` остаются только выключенные помощники и движок, если он не `prod`, — повторное открытие анкеты их не возвращает;
8. **ключи и модули** — в разработке, полей нет;
9. **тема** — текущая, из каталога (белая — `starter`), по ссылке, своим архивом.

Как ответы ложатся в `site.yaml`:

- каждый факт — в одно место: название и описание — `organization`, адрес — `contact`, каналы связи — `contact.channels` (`{type, purpose, value}`), первый телефон и первая почта — ещё и `contact.phone`/`contact.email` (их зовут подвал темы и подстановки разметки); языковые значения — хвостом `_<язык>` (`city_de`). Узел разметки `schema.entity` пишется подстановками (`"{{ contact.phone }}"`), а не копиями: телефон меняется в одном месте;
- пропущенный вопрос убирает ключ — пустого значения в разметке не бывает; уровень цен попадает в разметку только при `seo.allow_prices: true`;
- ключи, которыми анкета не ведает (`gone`, `forms`, `nginx`, свои блоки), остаются как были. Узел `schema.entity` сливается в три стороны: база — что анкета записала бы для прежнего конфига; ответ не менялся — ключ остаётся как в файле (поля руками — `geo`, `openingHours`, `medicalSpecialty`, `founder`…, точный `@type`, свой `@id`), менялся — берётся новый, ответ убран — ключ убирается; прежний `site.yaml` — в `.heron-cache/setup/site.yaml.<время>`; две копии в одну секунду получают `-2`, `-3`: файл создаётся исключительно, существующая копия не перезаписывается. Комментарии в `site.yaml` анкета не сохраняет — пишет свою шапку;
- итог проверяется той же схемой, что и сборка; не прошёл — ничего не записано;
- после записи структура следует за конфигом: новый язык получает папку, главную и 404 (`heron init`).

Файлы рядом с `site.yaml` (каждый с отметкой `heron setup`; файл без отметки не перезаписывается, свой файл, ставший ненужным при смене способа, убирается):

| Способ | Файлы |
|---|---|
| помощник | `.heron/scripts/build.sh` — итоговая сборка образом HERON по той же политике, что `scripts/site.sh` и `site-image.yml`: без сети, корень образа только на чтение, без capabilities, не от рута; папка сайта — только на чтение, на запись — только `dist/`, `.heron-cache/` и `.dist.heron-lock` |
| помощник | `.heron/scripts/publish.sh` — публикация выбранным способом (`git push`, образ в Docker Hub, `rsync`); `.gitignore` |
| GitHub | с `auto` — `.github/workflows/image.yml` (зовёт `site-image.yml` той же ветки HERON; путь задаёт GitHub) |
| Docker Hub | скрипт публикации: сборка, `heron recipe` → образ nginx, `docker push` (вход — `docker login` на компьютере) |
| статика | скрипт публикации (`rsync` на сервер) или `.github/workflows/pages.yml` (GitHub Pages; сборка — та же политика запуска) |

Сборочной логики в папке сайта по-прежнему нет: скрипты и workflow — короткие вызовы образа HERON; Dockerfile и `.env` в папку сайта не кладутся. Скрипты лежат в скрытой папке `.heron/` (внутри — `scripts/`, место и для другого служебного): движок её не читает, в `dist/` она не попадает. Прежние `scripts/*.sh` с отметкой анкеты убираются при следующем сохранении.

**Ключи и модули** пока в разработке: в анкете полей нет, в `site.yaml` и git ключи не пишутся никогда. Docker Hub берёт вход из `docker login`, workflow GitHub — короткоживущий токен сборки.

В разметку контакты идут так: `telephone`/`email` — подстановкой основных, `contactPoint` — по каналу с назначением (`contactType`: main → customer service, support → technical support, sales, marketing, booking → reservations, press), `sameAs` — публичные профили (`t.me/…`, `wa.me/…`, соцсети). Состав `contactPoint` и `sameAs` анкета переписывает при каждом сохранении.

Движок для сборки сайта — `publish.engine`: канал (`prod`, `beta`), версия или канал с digest — `prod@sha256:<digest>`. С digest `site-image.yml` берёт рецепт с ветки канала, а образ движка — ровно этот.

Значения публикации уходят в команды оболочки и в YAML, поэтому проверяются при чтении ответов: ветка `publish.branch` — буквы, цифры и `. _ - + /` по правилам git (без `..`, `//`, начального `-`, хвоста `.lock`); сервер — `user@host` без начального `-`; папка на сервере — абсолютный путь из букв, цифр и `. _ - + ~ @` без `..` (её разбирает ещё и оболочка на сервере). В скриптах значения дополнительно взяты в кавычки, в workflow ветка записана строкой. `site-image.yml` получает свои входные значения переменными окружения и проверяет их до первого шага сборки.

### heron theme

Архив темы: `heron-theme.yaml` (имя, совместимые версии HERON), `theme/`, `demo/` — демонстрационные страницы темы: `content/<язык>/`, `media/`, `data/`. Источники: `starter` — встроенная стартовая (без сети), имя — каталог `HERON_THEMES_URL` (по умолчанию `catalog.json` репозитория `FMSTM/heron-themes`: имя → https-адрес и sha256), https-ссылка (`#sha256=<хеш>` в конце сверяется), файл `.zip` или `.tar.gz`.

Распаковка недоверчивая: абсолютные пути, `..`, ссылки и устройства, `plugins/`, `.py`, `.sh` и подобное — отказ `E032`. Запрет файлов кода сам по себе тему не обезвреживает: шаблоны поставленной темы собираются в песочнице (§7); предел 200 МБ на архив, 50 МБ на файл, 5000 файлов. Битый или усечённый архив (zip или tar.gz), в том числе повреждённые сжатые данные, — тоже `E032` («the archive is damaged or truncated»), а не `BadZipFile`/`EOFError`; анкета отвечает на такой архив `400 {"ok": false, "error": …}`. Тема проверяется схемой `theme.yaml` до установки; прежняя уезжает в `.heron-cache/setup/theme.<время>` (в ту же секунду — `theme.<время>-2`). Путь к архиву у `theme get` — от текущей папки, а нет там файла — от папки сайта. Это доверенный путь из терминала: абсолютный тоже разрешён. В анкете (`--answers`, сервер) источник `file` без загрузки (`upload`) принимает только путь внутри сайта, от его корня (`themes/t.tar.gz`); абсолютный путь, `..` или ссылка наружу — `E024`, тема и резервные копии не тронуты, содержимое файла не читается. Архив для `--answers` кладут в папку сайта или ставят темой `heron theme get`. Демонстрационные страницы темы кладутся в каждый язык сайта и только туда, где файла нет: страница сайта не перезаписывается никогда. Нет страниц на языке сайта — берутся страницы основного языка, иначе первые. `heron theme pack` собирает архив из темы сайта и его контента.

## 11. Ошибки и предупреждения

Разделение жёсткое: ошибка останавливает сборку, предупреждение попадает в отчёт.

**Останавливают сборку:**

| Код | Условие |
|---|---|
| `E001` | битый YAML во фронтматтере |
| `E002` | нет `title`, `h1` или `description`, или поле фронтматтера не того типа (дата не дата, `order` не число) |
| `E003` | дубликат идентификатора секции в файле |
| `E004` | два файла дают один URL |
| `E005` | недопустимый слаг |
| `E006` | поле связи ссылается на несуществующую страницу |
| `E007` | картинки нет на диске |
| `E008` | у типа страницы нет шаблона в теме |
| `E009` | `redirect_from` совпадает с существующим URL |
| `E010` | обращение к несуществующей переменной в шаблоне |
| `E011` | `site.yaml` не проходит валидацию |
| `E012` | версия движка не удовлетворяет требованию `heron:` из `site.yaml` |
| `E013` | тема не найдена ни локально, ни среди установленных пакетов |
| `E014` | плагин из `plugins:` не установлен, упал при загрузке или назван недопустимым именем |
| `E015` | сырой HTML в markdown при `build.allow_raw_html: false` |
| `E016` | недопустимый идентификатор секции |
| `E017` | сборка прода без единой страницы |
| `E018` | папка ресурсов сайта задвоена: `media` и старая `img` либо `media` и `static/media` |
| `E019` | у локального видео нет постера |
| `E020` | разметка schema.org не собирается: не JSON, нет объявленного темой типа, в сквозном узле объявлены, но пусты адрес или координаты, есть поля про деньги при `seo.allow_prices: false` |
| `E021` | сборка прода, в которой пуст язык по умолчанию: корень сайта ответил бы 404 |
| `E022` | запись `gone` закрывает адрес существующей страницы или пересекается с `redirect_from` |
| `E023` | `fields` в `theme.yaml` называет поля, которых движок не знает: свои поля фронтматтера туда не пишут, либо нужен более новый движок |
| `E024` | путь выходит за пределы разрешённых папок: `..` в пути к файлу, символическая ссылка наружу из `content/`, `data/`, `media/`, `static/` или темы, имя результата вне папки сборки; папки сборки, кэша и исходников пересекаются; `.heron-cache` или его `renditions/` — ссылка (§4, «Границы файлов») |
| `E025` | атрибут заголовка вне разрешённого набора (`#id`, `.class`, `lang`, `dir`, `title`, `data-*`): `onclick=`, `style=` и подобное (`20` §4) |
| `E026` | два источника дают один файл сборки (страница, генератор, `static/`, тема, медиа, плагин), файл и папка с одним именем, чужой файл в папке сборки на месте нужного пути; подмена генерированного файла статикой — только через `build.overrides` (§4, «Запись результата») |
| `E027` | два мастера дают одинаковые имена нарезок: `photo.jpg` и `photo.png` в одной папке (§8, «Кэш нарезок») |
| `E028` | сборка прода, в которой у языка нет главной (`content/<язык>/index.md`): `/` или `/<язык>/` ответил бы 404. На деве и в `check` — предупреждение |
| `E029` | два файла одного языка дают один ключ страницы (`a.md` со своим `slug` и раздел `a/_index.md`): ключ связывает переводы и ссылки |
| `E030` | папка или файл исходников не читается — нет прав, сбой диска: сборка остановлена, а не прошла без части страниц (§4, «Границы файлов») |
| `E031` | `heron serve` не может занять адрес и порт: порт занят другой программой или адрес не принадлежит машине |
| `E032` | тема не ставится: архив вне правил (пути, ссылки, код, размер) или битый/усечённый, каталог недоступен, sha256 не совпал, `theme.yaml` не прошёл проверку |
| `E033` | шаблон темы обращается к закрытому песочницей: служебные атрибуты Python, изменение данных сайта, методы `BaseModel`, пути (§7) |
| `E034` | файл сборки, который движок обязан проверить до записи, пуст, не читается или не UTF-8: подмена `.heron-nginx.conf` из `static/` по `build.overrides`. Ошибка и без `--strict`, `dist/` не меняется |
| `E035` | рядом с папкой сборки нельзя создать `.heron-cache` или файл блокировки `.<dist>.heron-lock`: папка над `--out` не доступна для записи. `dist/` не тронут; движок называет путь и причину системы, а не общее «нет прав» |

Сообщение об ошибке обязано содержать путь к файлу, номер строки, что не так и что сделать. `Ошибка в шаблоне` без адреса — не сообщение.

**Предупреждения:**

`title` длиннее 60 знаков · `description` длиннее 155 · картинка без `alt` · страница без `image` в каталоге · секция в файле, которую тема не использует · отсутствие опциональной секции.

Последнее собирается в сводку долгов:

```
Не заполнено:
  contra  — 6 страниц: design, audit-basic, …
  price   — 6 страниц
  risks   — 6 страниц
```

Это тот самый список к заказчику, который иначе теряется. Он печатается после каждой сборки, а не вспоминается раз в квартал.

## 12. Отчёт `heron check`

Без сборки, читает контент и тему и печатает:

- страницы по языкам и типам, что переведено, а что нет
- заполненность секций по каждому типу
- секции в файлах, которые тема не использует — ловит опечатку в якоре
- модули темы, которые не использует ни один тип
- внутренние ссылки: битые, и страницы, на которые никто не ссылается
- страницы без ссылки на запись — нарушение правила перелинковки
- длины `title` и `description`
- карта редиректов и её конфликты
- файлы в `media/`, которых не ждёт ни одна страница, и контент, осевший в `static/`
- папки без пояснительной записки `heron-readme.md` — информация, не ошибка
- **поля, которые есть не у всех элементов списка**: у движка строгий режим неопределённых значений, и обращение к отсутствующему ключу роняет сборку. Шаблон пишут по первому элементу, а падает он на шестом. Это не ошибка контента — у половины документов действительно нет места выдачи; это предупреждение автору шаблона писать `d.get("place")`

Гоняется в CI на каждый push. Это замена схемы валидации, от которой мы отказались ради простоты входа: контроль остаётся, но не требует писать и поддерживать схемы.

## 13. Производительность

Сайт на 40 страниц в трёх языках — это 120 страниц. Всё, кроме картинок, — разбор, связи, рендеринг, генераторы, запись — укладывается в пару секунд. Дорогая часть одна: кодирование нарезок.

Замер: 95 мастеров, 2062 нарезки, четыре ядра.

| Сборка | Время |
|---|---|
| холодная, кэша нет | 157 с |
| повторная, кэш цел, `dist` стёрт | 4 с, из них картинки 0.3 с |

Отсюда два правила. Первое: кэш нарезок обязан переживать удаление `dist`, иначе его нет вовсе. Второе: холодную сборку спасают только ядра — у прода и CI кэша нет по определению.

Где слушает `heron serve`: без `--host` — `127.0.0.1` на машине человека и `0.0.0.0` в образе HERON (там выставлен `HERON_IN_CONTAINER=1`). Внутри контейнера `127.0.0.1` — сам контейнер, и проброшенный порт `docker run -p 127.0.0.1:8000:8000` до такого сервера не доходит. Префикс `127.0.0.1:` публикует порт только на машину человека: без него docker открывает его всем интерфейсам компьютера. `--host 0.0.0.0` вне контейнера открывает черновики всей сети — движок об этом предупреждает. Порт занят — `E031` с подсказкой взять другой.

Инкрементального рендера страниц нет: `heron serve` пересобирает всё при изменении файла, и без картинок это пара секунд. Изменение определяется снимком «путь → (время, размер)» по `content/`, `data/`, `media/`, `img/`, `static/`, `theme/` и файлам корня сайта за один обход: добавление, удаление, переименование и правка с тем же временем видны все.

## 14. Тесты

Обязательные, без них работа не принимается:

- парсер секций: якоря, вложенные заголовки, дубликаты, текст до первой секции
- структурированные секции: facts, faq, steps, timeline на валидных и битых данных
- построение URL из путей, включая `_index.md` и языковые префиксы
- резолв связей, включая ссылку в никуда
- **каждый URL из карты редиректов отдаёт 301 на адрес, который существует и отвечает 200.** Это единственное, что защищает индекс при переезде. Проверяется на настоящем nginx, в том числе на не-ASCII адресах в обеих формах, без слеша и на обрезанном слаге (`tests/test_redirects_unicode.py`, `tests/test_gone.py`)
- каждая собранная страница содержит ровно один `<h1>`
- все внутренние ссылки в собранном HTML ведут на существующие файлы
- `hreflang` симметричен: если A ссылается на B, то B ссылается на A
- sitemap не содержит страниц с `noindex` и содержит все остальные
- две сборки подряд дают побайтово одинаковый результат

Отдельно, за пределами unit-тестов: прогон собранного сайта через Lighthouse в CI сайта. Пороги задаёт сайт (`22-deploy.md` §4); ориентир — LCP менее 2 секунд, CLS менее 0.05.

## 15. Точки расширения

Модули из `heron/modules/` и внешние плагины пишутся против одного набора хуков. Разница только в поставке: модуль лежит в ядре, плагин ставится пакетом и объявляется в `site.yaml`.

Плагин — функция `register(hooks)`, вызывается при загрузке, при каждой сборке и проверке заново (состояние модуля между сборками не сохраняется).

| Хук | Когда вызывается | Аргументы → результат | `check` |
|---|---|---|---|
| `on_config` | после загрузки `site.yaml` и `theme.yaml` | `(config, theme)` — правка или проверка конфига | да |
| `block:<имя>` | при разборе секции с классом `{#id .<имя>}` | `(section)` → данные секции; `section.kind = <имя>`. Встроенные типы так не подменяются | да |
| `on_page_parsed` | после разбора каждой страницы, до связей | `(page)` — правка модели страницы | да |
| `on_tree_built` | после обхода `content/`, `data/` и дат, до связей | `(site)` — свои связи и группировки | да |
| `hooks.filter(имя, f)` / `hooks.add_global(имя, v)` | при сборке окружения Jinja2 | свои фильтры и переменные темы; встроенные имена не перекрываются | — |
| `on_page_rendered` | после рендера каждой страницы | `(page, html)` → новый HTML или `None`. Обработчики идут цепочкой: каждый получает результат предыдущего | — |
| `on_generate` | после генераторов, до проверки владельцев | `(site, config)` → `{путь: текст}` — свои файлы сборки; совпадение с чужим путём — `E026` | — |
| `on_build_finished` | **после** записи результата, только удачной сборки | `(site, config, dist)` — экспорт, уведомления. Исключение не делает сборку неудачной: сайт записан (`result.failed` ложно), ошибка — в `result.finish_errors`, `heron build` пишет «сайт записан и цел, но упало завершающее действие» и выходит с **кодом 3**. Остальные обработчики `on_build_finished` при этом всё равно вызываются | — |

`on_build_finished` раньше вызывался до записи и мог вернуть файлы. **Совместимость:** файлы оттуда больше не записываются — сборка проходит и печатает пояснение «файлы сборки объявляются в `on_generate`»; плагину нужно перенести генерацию в `on_generate` и принять третий аргумент `dist`. Неудачная сборка (ошибка или предупреждение в строгом режиме) до `on_page_rendered`, `on_generate` и `on_build_finished` может не дойти — они не обязаны вызываться.

Больше на старте не заводим: API, придуманный под будущее, всегда придуман неправильно.

**Хуки действуют только на этапе сборки.** Плагина, который «принимает форму», не существует — в момент POST движок уже отработал и вышел. Всё, что живёт в рантайме, — это `heron-relay`, отдельный сервис (см. `23-distribution.md`).

Источники плагинов и порядок разрешения — `core/resolver.py`: локальная папка `plugins/` сайта → установленный пакет (entry point группы `heron.plugins`) → git-ссылка. Локальный сильнее.
