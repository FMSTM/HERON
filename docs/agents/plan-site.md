# Сценарий Б: спроектировать сайт по отчёту о старом сайте

**На входе:** отчёт о том, как был устроен и как работал старый сайт (страницы, разделы, адреса, что приносило обращения, что болело), и/или сам старый сайт: выгрузка, sitemap, Search Console.
**На выходе — четыре вещи:**

1. документ «структура сайта» по форме [`templates/structure.md`](templates/structure.md);
2. черновик `site.yaml` (по [`templates/site.yaml`](templates/site.yaml)) и раздел `types`/`links` для `theme.yaml` (по [`templates/theme.yaml`](templates/theme.yaml));
3. таблица переноса: старый адрес → ключ → адрес на каждом языке → тип → 301 или 410;
4. вопросы заказчику — всё, что нельзя решить без него.

Этого достаточно, чтобы по сценарию А ([`build-site.md`](build-site.md)) собрать сайт без новых вопросов.

## Главное правило

**Сначала — что движок уже умеет** ([`capabilities.md`](capabilities.md)). Структуру сайта строят из возможностей движка, а не из того, как было устроено на старом. Задача на движок появляется, только если потребности нет ни в одной таблице, и оформляется отдельно (последний раздел). Предлагать «доработку движка» для того, что делается полем, секцией или связью, — ошибка.

## Шаги

### 1. Инвентаризация старого сайта

Собери в таблицу всё, что отвечало кодом 200: страницы, записи, разделы, категории, теги, архивы, пагинацию, служебные адреса. Источник — sitemap старого сайта, выгрузка CMS, Search Console. На каждый адрес — что это, сколько показов и кликов, есть ли текст.

### 2. Решение по каждому адресу

| Что это было | Что делаем | Как в HERON |
|---|---|---|
| Страница с содержимым, которое остаётся | переносим | файл в `content/`, старый адрес — в `redirect_from` этого файла |
| Две-три страницы об одном | склеиваем | одна страница, все старые адреса — в её `redirect_from` |
| Категория или архив, у которого есть смысл раздела | раздел | папка с `_index.md`; адрес категории — в его `redirect_from` |
| Архив по датам, автор, тег, пагинация, `?p=`, служебные пути CMS | убираем | `gone` в `site.yaml`: точные адреса или префиксы `/wp-*`, `/?p=*` |
| Дорвеи и мусор после взлома | убираем | `gone` префиксами |
| Страница без содержимого и без трафика | не переносим | `gone`, если адрес в индексе; иначе ничего |

301 — «переехало, вот куда», 410 — «больше нет». 404 оставляют только тому, о чём поисковик и так не знает. Адреса с кириллицей переносить как есть — движок сам совместит кириллицу и `%D0%…` (`20` §2, «Старые адреса»).

### 3. Языки

- какие языки будут и какой основной (`default_lang` отдаётся из корня);
- если старый сайт был на одном языке, а новый на двух — старые адреса пишутся в `redirect_from` файлов **того языка, на котором был старый контент**;
- имена файлов одинаковые во всех языках (ключ), разные адреса языков — полем `slug`. Обычно имена файлов — транслитерация основного языка, `slug` — у второго;
- если перевод появится позже — дев-сборка допускает пустой язык, прод — нет, если пуст основной (`20` §3).

### 4. Типы страниц

Тип оправдан **своей раскладкой**. Если две группы страниц рисуются одинаково — это один тип. Типичный набор сайта услуг: `home`, `category` (каталоги), `service`, `article`, `page` (всё прочее прозой), `404`. Свой тип для одиночной страницы (`about`, `contacts`) — только если у неё своя раскладка.

На каждый тип — список секций (якорь, форма из `20` §4.4, что туда идёт, откуда берётся текст). Секции, для которых в источнике нет материала, отмечаются как необязательные, а не придумываются.

### 5. Разделы и связи

- раздел — папка; адрес ребёнка зависит от папки навсегда. Если страница относится к нескольким направлениям — **не вкладывать**, а положить плоско и связать полями связей (`links` в `theme.yaml`, многие-ко-многим);
- «связанные услуги», «статьи по теме», «где упоминается» — поля связей с `back:`;
- раздел на сотни страниц — одна страница каталога без пагинации; если это неудобно — подразделы папками.

### 6. Что живёт не в страницах

- контакты, реквизиты, часы, соцсети — блоки `contact`, `organization` в `site.yaml` (тема и разметка берут их оттуда);
- отзывы, цифры доверия, команда — `data/*.yaml`;
- название сайта и суффикс `title` по языкам — `site.name_<lang>`, `seo.title_suffix_<lang>`;
- счётчики — `analytics`; сведения для нейросетей — `seo.llms_note`;
- разметка schema.org — `schema.entity` в `site.yaml`, типы по типам страниц — `theme.yaml`. Цены в разметке — только если сайт их публикует (`seo.allow_prices`).

### 7. Вопросы заказчику

В список вопросов уходит всё, что нельзя взять из источника. Ничего из этого не заполняется «правдоподобно»:

- факты: телефоны, адрес, часы, год основания, цифры, имена, лицензии и свидетельства;
- цены и «от», бесплатность чего-либо;
- какие услуги актуальны, каких не хватает;
- языки к запуску; кто вычитывает тексты, если в них есть утверждения, за которые отвечает заказчик;
- счётчики и доступы: Search Console, аналитика, DNS;
- судьба разделов без очевидного решения (форум, блог, архив).

Каждый вопрос — с вариантами и рекомендацией, чтобы заказчик отвечал выбором.

### 8. Сверка с документацией

Перед сдачей пройди по своей структуре и для каждого решения назови раздел документации, который его обеспечивает. Если раздела нет — либо ты придумал возможность, которой нет (переделай решение), либо это задача на движок (ниже).

## Задача на движок

Только если потребности нет в [`capabilities.md`](capabilities.md) и её нельзя закрыть средствами сайта и темы.

```markdown
### <короткое название>

**Сайту нужно:** что должно получиться для посетителя или поисковика.
**Сейчас в HERON:** что есть и почему не подходит — со ссылкой на раздел документации.
**Без этого:** что будет на сайте, если не делать (обходной путь, если есть).
**Не предлагаю реализацию** — её выбирает тот, кто ведёт движок.
**Как проверить:** что должно получиться на собранном сайте.
```

Задача не должна содержать имён сайта, доменов и слагов: движок общий для всех сайтов.
