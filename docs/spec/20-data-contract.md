## 0. Что это за система

Генератор статического сайта из markdown-файлов. На вход — папка с контентом, картинками, темой и одним конфигом. На выходе — готовый HTML в `dist/`, который отдаёт nginx.

Ключевое правило, из которого выводится всё остальное:

> **markdown-файл — это именованный склад контента. Тема — это раскладка.**
> Файл не знает, где что покажется. Тема не знает, что написано.
> Связь между ними — по идентификаторам секций.

Практическое следствие: порядок секций в файле не влияет на порядок блоков на странице. Редактор пишет в удобном ему порядке, тема раскладывает в правильном.

**Формы — свойство сайта, а не движка.** Сам сайт остаётся статикой при любом раскладе: если форма есть, её POST принимает отдельный сервис `heron-relay`, а не сборщик. На одном сайте форм нет вовсе — единственная конверсия телефонный звонок; на другом есть. Контракт формы описывается в `site.yaml` (раздел 5), реализация — в `23-distribution.md`.

### Как поставляется движок

Решение от 2026-09-14, отменяет прежнее «движок, контент и тема в одном репозитории».

**Движок в папке сайта отсутствует.** Он поставляется одним артефактом — образом `heron:<версия>`, он же публикуется pip-пакетом для локальной разработки. Папка сайта содержит только контент, данные, картинки, тему и конфиг; строк питона в ней нет.

Сайт объявляет требуемую версию движка первой строкой `site.yaml` (`heron: ">=0.4,<0.5"`). Движок отказывается собирать сайт, версию которого не поддерживает, — это единственное, что не даст трём сайтам разъехаться по несовместимым движкам.

Всё, что описано ниже, — контракт между движком и папкой сайта. Он одинаков для всех сайтов на движке, какой бы теме они ни принадлежали.

## 1. Структура проекта

```
<сайт>/
├── site.yaml                 конфиг сайта, первой строкой — версия движка
├── .env                      секреты. Не в git, не в образе. Нужен только сервисам
├── .env.example              то же с пустыми значениями, в git есть
│
├── content/
│   ├── uk/
│   ├── ru/
│   └── en/
│
├── data/                     yaml-справочники: перечни, таблицы, реквизиты
├── img/                      картинки контента, мастера 1:1
├── static/                   favicon, webmanifest, .well-known — копируются как есть
│
├── theme/                    тема этого сайта
│   ├── theme.yaml
│   ├── base.html
│   ├── templates/            шаблоны типов страниц
│   ├── modules/              шаблоны модулей
│   ├── partials/             шапка, подвал, мобильная панель, баннер куков
│   ├── i18n/                 строки интерфейса темы по языкам
│   └── assets/               css, js, логотип, иконки
│
├── plugins/                  локальные плагины этого сайта. Обычно пусто
│
├── Dockerfile                кладёт `heron new`/`heron init`
├── compose.yml               кладёт `heron new`/`heron init`
├── build.sh                  кладёт `heron new`/`heron init`
└── dist/                     результат сборки. В git не хранится
```

Кода движка здесь нет. `heron/` в папке сайта — ошибка, а не структура.

**`data/`** — справочники, которым не место в теле markdown: перечни услуг с атрибутами, таблицы сравнения, реквизиты, списки документов. Доступны шаблонам как `data.<имя файла>`.

**`theme/`** — тема этого сайта, одна. Внутри неё лежат Jinja-шаблоны (`templates/`) — слово «шаблон» закреплено за ними, «тема» за пакетом целиком. Если темы в папке нет, движок резолвит её по имени из `site.yaml` (установленный пакет `heron-theme-<имя>` или git-ссылка); локальная `theme/` всегда сильнее.

Человек, ведущий сайт, работает только с `site.yaml`, `content/`, `data/`, `img/`. Всё остальное трогает разработчик.

## 2. Дерево контента и URL

**Путь файла определяет URL.** Никаких отдельных карт маршрутов.

```
content/uk/index.md                 →  /
content/uk/about.md                 →  /about/
content/uk/contacts.md              →  /contacts/
content/uk/guides/_index.md         →  /guides/
content/uk/guides/getting-started.md →  /guides/getting-started/
content/uk/services/_index.md       →  /services/
content/uk/services/consulting.md   →  /services/consulting/
content/ru/services/consulting.md   →  /ru/services/consulting/
content/en/index.md                 →  /en/
```

Правила:

- имя папки — сегмент URL, имя файла без расширения — слаг
- `_index.md` — страница самой папки
- язык по умолчанию (`uk`) отдаётся из корня, остальные с префиксом
- все URL заканчиваются слешем, канонический вид — со слешем
- слаг только латиница, цифры и дефис. Файл с иным именем валит сборку
- слаг можно переопределить полем `slug` во фронтматтере, но обычно не нужно

### Ссылки внутри контента относительны языку

Внутренняя ссылка пишется **без языкового префикса** — движок подставляет его сам, зная язык страницы:

```markdown
[услуга](/services/consulting/)
```

На странице языка по умолчанию адрес остаётся как есть, на странице другого языка становится `/<lang>/services/consulting/`.

Один и тот же markdown даёт правильные адреса в любом языковом дереве. Перевод — это копия файла с переписанным текстом, а не с переписанными ссылками: иначе одна забытая ссылка после перевода становится битой ссылкой в проде.

Не трогаются внешние адреса, `mailto:`, `tel:`, якоря и пути к `/img/`, `/static/`, `/assets/`.

Отдельно: **`redirect_from` языку не относительно.** Там лежат реальные старые адреса, с которыми сайт жил раньше, — они историчны, а не относительны.

Ссылка на страницу, которой на этом языке нет, ведёт на версию языка по умолчанию, а в отчёт попадает предупреждение. Читатель оказывается на существующей странице другого языка, а не в 404.

**Добавление страницы — это создание одного md-файла.** Она сама появляется в меню, в каталоге своей папки, в sitemap, в hreflang, в перелинковке и в `llms.txt`. Удаление файла убирает её отовсюду. Никаких списков, которые надо править параллельно.

## 3. Языки

Три полноценных дерева одинаковой формы: `content/uk/`, `content/ru/`, `content/en/`. Все три языка живут с запуска.

- `uk` — язык по умолчанию, отдаётся из корня без префикса
- соответствие страниц между языками — **по совпадению относительного пути**. `services/consulting.md` в трёх деревьях — одна и та же страница на трёх языках
- если перевода нет — страница просто отсутствует, а в переключателе языков её пункт неактивен. Молча вести на главную или показывать 404 запрещено
- `hreflang` проставляется на все существующие языковые версии плюс `x-default` на украинскую
- одна страница — один язык. Смешение языков внутри файла недопустимо

Слаги в разных языках могут отличаться (`konsultatsiya` / `consulting` / `beratung`), связь идёт по пути папки и имени файла. Если слаг переопределён полем `slug`, связь сохраняется по имени файла.

## 4. Формат markdown-файла

### 4.1 Общий вид

**Каждый файл начинается с SEO-блока, и только потом идёт контент.** Порядок обязателен и одинаков во всех файлах всех типов.

SEO-блок — это фронтматтер между `---`, разделённый на восемь пронумерованных групп рамками из комментариев и **прокомментированный построчно**. Человек, открывший файл впервые, должен понять, за что отвечает каждая строка, не сверяясь с этим документом.

Группы и их порядок:

| № | Группа | Что внутри |
|---|---|---|
| 1 | Основное | `title` `description` `h1` `canonical` `robots` |
| 2 | Ключевые запросы | только комментарий: основной ключ, дополнительные, сколько всего |
| 3 | Open Graph | `og_type` `og_title` `og_description` `og_image` `og_image_alt` |
| 4 | Twitter / X | `twitter_card` `twitter_title` `twitter_description` `twitter_image` |
| 5 | Schema.org | блок `schema` — уточнения разметки для этой страницы |
| 6 | Карточка и каталог | `image` `image_alt` `order` `children_type` `type` |
| 7 | Служебное | `updated` `published` `priority` |
| 8 | Связи | поля связей, объявленные темой, плюс `redirect_from` и `gone` |

Образец полностью заполненного блока кладёт `heron page` — он же служит шаблоном для новых страниц: скопировать, заменить значения, комментарии оставить как есть.

**Что живёт в `site.yaml`, а не в файле страницы:** имя сайта, локаль, `twitter:site`, `og_default_image`, реквизиты организации для разметки, ссылки на соцсети для `sameAs`, суффикс `title`. В странице — только то, что у неё своё.

**Что движок генерирует сам и в файле не пишется:** `hreflang` на все существующие языковые версии плюс `x-default`, `canonical` по собственному URL, `BreadcrumbList`, `FAQPage` при наличии секции `faq`, `dateModified` из `updated`, запись в `sitemap.xml` и в `llms.txt`.

Правила блока:

- **порядок групп фиксирован.** Человек находит нужное на одном и том же месте в любом файле
- **комментарии обязательны** и переносятся из файла в файл без изменений. Это не украшение: сайт ведёт не разработчик, подсказка должна быть под рукой, а не в спецификации
- **группа 2 обязательна** на каждой контентной странице. Движок её не читает, но она удерживает правило «один интент — одна страница»: чтобы дописать чужой кластер, надо сначала вписать его туда и увидеть, что ему нужна своя страница
- **мета-тег `keywords` не выводится.** Google игнорирует его с 2009 года, а конкурентам он показывает всю семантику проекта
- **пустые необязательные поля остаются с комментарием, а не удаляются** — иначе через полгода никто не вспомнит, что их можно заполнить
- `twitter_*` заполняются только когда должны отличаться от `og_*`; пустые движок подставляет из Open Graph
- в комментариях нет ничего про деньги: ни сумм, ни слов «ціна», «вартість», «оплата», см. документ сайта

Дальше — контент. Текст до первого заголовка становится секцией `intro`, затем секции вида `## Заголовок {#anchor}`, при необходимости с классом модуля: `{#red-flags .alert}`, `{#timeline .timeline}`.

```markdown
## Что это такое {#what}

Короткое объяснение простыми словами…

## Кому подходит {#who}

- Первый признак
- Второй признак
```

### 4.2 Фронтматтер

YAML между `---`. Обязательны три поля на любой странице:

| Поле | Назначение |
|---|---|
| `title` | содержимое `<title>`. До 60 знаков, иначе предупреждение при сборке |
| `h1` | заголовок на странице. Отличается от `title`: `title` пишется под выдачу, `h1` под человека, который уже открыл страницу |
| `description` | `meta description`. До 155 знаков, иначе предупреждение |

Тип страницы **не указывается в файле** — он наследуется от папки (раздел 5).

Необязательные поля, общие для всех типов:

| Поле | По умолчанию | Назначение |
|---|---|---|
| `slug` | имя файла | переопределение сегмента URL |
| `image` | — | превью для карточки в каталоге |
| `image_alt` | — | обязательно, если задан `image` |
| `og_image` | `seo.og_default_image` | картинка для соцсетей, 1200×630 |
| `og_title` | значение `title` | заголовок в ленте соцсети |
| `og_description` | значение `description` | описание в ленте |
| `order` | 999 | порядок в каталогах и меню, по возрастанию |
| `updated` | дата файла | попадает в sitemap и в `dateModified` |
| `published` | `true` | `false` — страница не собирается и нигде не появляется |
| `noindex` | `false` | `true` — `robots: noindex` и исключение из sitemap |
| `redirect_from` | — | список старых URL, с которых нужен 301 на эту страницу |

`redirect_from` — рабочий инструмент переезда с WordPress: старый адрес пишется рядом с новым контентом, а не в отдельной таблице, которая разъедется.

### 4.3 Секции

Секция — блок контента с идентификатором. Синтаксис — обычный markdown-заголовок с якорем:

```markdown
## Что это такое {#what}
```

Секция — всё от этого заголовка до следующего заголовка **того же уровня** с якорем или до конца файла. Вложенные заголовки (`###`) принадлежат секции.

Правила:

- идентификатор: латиница, цифры, дефис
- порядок секций в файле безразличен
- один идентификатор дважды в файле — ошибка сборки
- текст до первой секции считается вводным абзацем, доступен теме как `intro`
- секция, которую тема не использует, не ошибка — попадает в отчёт `heron check`

Заголовок секции — это контент, который увидит посетитель. Якорь — это адрес для темы. Их разделение принципиально: заголовок правят, адрес — нет.

### 4.4 Структурированные секции

Некоторые модули ждут не прозу, а данные. Формат внутри секции определяется модулем, который её рендерит. Никаких особых синтаксисов — всё это валидный markdown, читаемый глазами и в любом редакторе.

**Факты — таблица из двух колонок:**

```markdown
## Коротко {#quick-facts}

Формат      | очно и онлайн
Длительность| 4 недели
Начало      | каждый понедельник
```

**FAQ — заголовки третьего уровня как вопросы:**

```markdown
## Частые вопросы {#faq}

### Сколько это занимает?
Обычно около четырёх недель…

### Можно ли перенести?
Да, за сутки до начала…
```

**Шаги — нумерованный список, жирный текст как заголовок шага:**

```markdown
## Как это устроено {#how}

1. **Заявка.** Оставляете обращение любым удобным способом…
2. **Подтверждение.** Перезваниваем и согласуем время…
```

**Список — обычный маркированный:**

```markdown
## Что понадобится {#needs}

- Документ, удостоверяющий личность
- Заполненная анкета
```

**Две колонки — два списка под заголовками третьего уровня:**

```markdown
## Когда подходит, а когда нет {#pros-cons}

### Подходит
- Нужен результат в сжатые сроки
- Задача понятна и ограничена

### Не подходит
- Требования меняются каждую неделю
- Решение нужно «ещё вчера»
```

**Чек-лист — группы заголовками третьего уровня, внутри списки:**

```markdown
## Что взять с собой {#checklist}

### Документы
- Паспорт
- Договор

### Дополнительно
- Список вопросов
```

**Таблица и сравнение — обычная markdown-таблица:**

```markdown
## Что выбрать {#compare}

|            | Базовый           | Расширенный        |
|------------|-------------------|--------------------|
| Срок       | 2 недели          | 4 недели           |
| Поддержка  | по почте          | по почте и в чате  |
```

**Врезка-подсказка — цитата:**

```markdown
## Совет {#tip}

> Если сроки горят, скажите об этом сразу — это меняет порядок работ.
```

## 5. `site.yaml`

Всё, что повторяется на каждой странице, живёт здесь в одном экземпляре. На старом сайте адрес был вписан руками в двух местах и разошёлся — это ровно та проблема, которую решает этот файл.

```yaml
heron: ">=0.4,<0.5"          # версия движка, которую требует сайт. Обязательна

site:
  domain: example.com
  theme: main                # имя темы. Локальная theme/ перекрывает
  default_lang: uk
  languages: [uk, ru, en]
  name: Название сайта

# Блоки ниже движок не разбирает — они целиком уходят в шаблоны.
# Их имена и состав придумывает тема, см. «Что ядро проверяет, а что пропускает».
contact:
  phone: "+00 000 000 0000"
  address: "улица и дом"
  city: Город
  hours_display: "Пн–Пт 09:00–18:00"

organization:
  name: Название организации
  same_as:
    - https://example.com/social

seo:
  title_suffix: " — Название сайта"
  og_default_image: img/og/default.jpg
  twitter_card: summary_large_image
  llms_txt: true
  robots_extra: []
  feed: article              # тип страниц для ленты. Нет ключа — нет ленты

nav:
  main: [about, services, contacts]

build:
  fail_on_warning: false
  allow_raw_html: false      # сырой HTML в markdown. По умолчанию запрещён

plugins: []                  # имена установленных плагинов

# Формы принимает heron-relay, а не сборщик. Движку описание нужно, чтобы
# отдать теме состав полей и упасть, если тема рисует форму, которой здесь нет
forms:
  consult:
    fields: [name, phone, message]
    sinks: [mail, crm]

sinks:
  mail: {to: info@example.com, smtp_env: SMTP_URL}
  crm:  {webhook: https://crm.example.com/hook, secret_env: CRM_SECRET}
```

`forms` и `sinks` читает не движок, а `heron-relay`. Движок использует их только чтобы отдать теме описание формы для разметки и чтобы упасть, если тема рисует форму, которой нет в конфиге.

Значения из `contact` и `organization` идут одновременно в разметку страницы, в JSON-LD и в блоки темы. Меняются в одном месте — это то, что не даёт адресу разойтись между шапкой и подвалом.

### Что ядро проверяет, а что пропускает насквозь

Уточнение от 2026-09-14, по итогам реализации контрактов.

Ядро строго валидирует только свои ключи: `heron`, `site`, `seo`, `nav`, `build`, `plugins`, `forms`, `sinks`. Опечатка внутри них — остановка с `E011`.

Блоки, которых движок не знает — `contact`, `organization`, `analytics`, любые свои — **проходят насквозь** и достаются шаблонам как есть. Ядро в их смысл не вникает: иначе оно начнёт знать предметную область каждого сайта по отдельности, и граница, ради которой всё затевалось, исчезнет.

Проверку наличия при этом мы не теряем. Тема объявляет, что ей нужно, в `theme.yaml`:

```yaml
requires:
  - contact.phone
  - organization.name
forms:
  - consult
```

Движок проверяет, что эти пути в `site.yaml` заполнены, и останавливается с понятным перечнем, если нет. Тема просит — сайт даёт — движок сверяет, не понимая предметной области.

Туда же переехали типы JSON-LD: `types.<тип>.jsonld` задаётся в `theme.yaml`. Соответствие «такой-то тип страницы → такой-то тип разметки schema.org» принадлежит теме: у сайта услуг, магазина и справочника оно разное, и модуль движка знать его не обязан.

## 6. `theme.yaml`

Паспорт темы. Служит документацией и основой отчёта `heron check`, а не жёстким валидатором.

```yaml
name: main
version: "1.0"
title: Тема сайта

# что тема ждёт от site.yaml. Движок проверит наличие, не вникая в смысл
requires:
  - contact.phone
  - organization.name

# формы, которые тема рисует. Их описание должно быть в site.yaml
forms: [consult]

modules:
  - breadcrumbs
  - prose
  - facts
  - list
  - alert-list
  - steps
  - timeline
  - faq
  - cards
  - quote
  - table
  - gallery
  - author

types:
  home:
    uses: [intro, about, services, faq]
    jsonld: [WebSite]
  category:
    uses: [intro, outro]
    jsonld: [CollectionPage]
  service:
    uses: [intro, quick-facts, what, who, how, faq]
    jsonld: [Service]
  article:
    uses: [intro]
    jsonld: [Article]
  page:
    uses: [intro]

# связи между страницами. Ядро найдёт, проверит и построит обратную ссылку,
# не зная, что означает само отношение
links:
  - field: related
    type: service
    back: mentioned_in

# пропорции и ширины, которые движок нарежет из мастеров 1:1
images:
  widths: [400, 800, 1200, 1600]
  ratios: ["1:1", "16:9", "4:3"]
  formats: [avif, webp]
```

Тип страницы реализуется файлом `templates/<тип>.html` — обычным шаблоном Jinja2, где порядок блоков виден сверху вниз:

```jinja
{% extends "base.html" %}
{% block content %}
  {{ mod.breadcrumbs() }}
  {{ mod.hero() }}
  {{ mod.facts('quick-facts') }}
  {{ mod.prose('what') }}
  {{ mod.prose('who') }}
  {{ mod.list('contra') }}
  {{ mod.steps('how') }}
  {{ mod.timeline('recovery') }}
  {{ mod.prose('price') }}
  {{ mod.faq('faq') }}
  {{ mod.cards('treats') }}
  {{ mod.call() }}
  {{ mod.author() }}
{% endblock %}
```

`mod.prose('what')` берёт секцию `what`; если её нет — не выводит ничего, ни заголовка, ни пустой рамки. Обвязка условиями вокруг каждого модуля не нужна.

## 7. Картинки

`img/` — одна общая папка, по языкам не делится. Ссылка и `alt` живут в md, поэтому для разных языков можно указать разные файлы — например скан документа на каждом из языков.

- ссылки в md относительные от корня: `img/services/consulting.png`
- `alt` обязателен. Картинка без `alt` — предупреждение сборки
- движок сам делает варианты под брейкпоинты, конвертирует в WebP и AVIF, проставляет `width`, `height`, `srcset`, `loading="lazy"` кроме LCP-картинки. Оригиналы не трогаются
- `og_image` не режется и не конвертируется — соцсети ждут JPEG или PNG 1200×630

### 7.1 Один мастер, слоты кропятся при сборке

**В репозитории лежит ровно один файл на сущность — квадратный мастер 1:1 с объектом по центру и пустым запасом не меньше 15% по каждому краю.** Все пропорции, которые нужны теме, движок режет из него центральным кропом:

```
1:1    исходник, лежит в img/
16:9   карточка в каталоге и на главной
4:3    иллюстрация на странице процедуры, состояния, статьи
```

Запас по краям нужен, чтобы при кропе в 16:9 не срезало объект. Если объект в мастере упирается в край — сборка выдаёт предупреждение, а не молча режет.

Второй пакет изображений под другое соотношение не генерируется. Это правило появилось после того, как выяснилось, что на главной слот 16:9, а на странице процедуры другой — и это чуть не превратилось в два комплекта из 27 файлов.

### 7.2 Прозрачность и темы

Иллюстрации хранятся **с альфа-каналом** (PNG или WebP) и кладутся на подложку, которую даёт тема. Следствия:

- **JPEG для иллюстраций запрещён** — нет альфы, белая плашка останется намертво и в тёмной теме будет светиться прямоугольником. JPEG остаётся только для фотографий
- **Заливать фон в цвет темы нельзя** — это тот же прямоугольник, просто в цвет
- Белый фон допустим только как промежуточный этап генерации: модели проще нарисовать чистый контур на плоском фоне, чем сразу выдать корректную альфу. В репозиторий уходит вырезанное
- Второй файл под тёмную тему не делается. Одно изображение работает в обеих, если тело объекта светлое, а контур средней светлоты: тёмный контур на тёмном фоне даёт около 2:1 по контрасту, и силуэт расплывается. Конкретные тона задаёт документ темы, а не этот
- Подложка под иллюстрацией всегда нейтральная. Карточка в цвет объекта съедает силуэт
- Фотографии в тёмной теме не инвертируются и не затемняются фильтром

`static/` копируется в `dist/` как есть, без обработки: favicon, `site.webmanifest`, `.well-known/security.txt`.

## 8. `.env`

**Сборке секреты не нужны ни одного.** Она идёт без сети и читает только файлы сайта. `.env` принадлежит сервисам — `heron-relay`, позже админке — и в контейнер сборки не монтируется никогда.

Файл закладывается сразу, чтобы потом не переделывать.

```
SMTP_HOST=
SMTP_PORT=
SMTP_USER=
SMTP_PASSWORD=
TELEGRAM_BOT_TOKEN=
ADMIN_USER=
ADMIN_PASSWORD_HASH=
SESSION_SECRET=
DB_PATH=
```

Правила обращения:

- `.env` в `.gitignore` и в `.dockerignore`. В репозитории лежит `.env.example` с пустыми значениями
- монтируется **файлом**, не через `environment:` и не через `--env-file`: переменные окружения видны в `docker inspect` любому с доступом к сокету, смонтированный файл — нет
- читается в момент использования, не при старте
- монтируется только в тот контейнер, которому нужен. nginx про почту не знает
- пароль администратора хранится хешем, не открытым текстом
- секреты никогда не попадают в логи. Самая частая утечка — не взлом, а трейсбек при ошибке подключения

Отдельно: для отправки почты брать API-ключ почтового сервиса, а не SMTP-пароль от ящика. Утечка ключа — спам с домена. Утечка пароля от ящика — доступ ко всей переписке владельца.

## 9. Что генерируется, а что лежит руками

Генерируется движком в `dist/`, в репозитории отсутствует:

`sitemap.xml` и по одному на язык · `robots.txt` · `llms.txt` · `404.html` · `redirects.map` для nginx · JSON-LD внутрь страниц · `hreflang` и канониклы · `feed.xml` когда появятся статьи.

Лежит руками в `static/`: favicon и его варианты · `site.webmanifest` · `.well-known/security.txt`.

`robots.txt`, положенный руками, через полгода начинает врать — на текущем сайте это уже произошло с sitemap, который генерировался заброшенным плагином и отдавал битые адреса.

## 10. Ограничения, которые нельзя нарушать

- **Никакого JavaScript для отображения контента.** Скрипты обслуживают только тему, куки-баннер, мобильное меню и аккордеон FAQ. Числа и текст обязаны быть в HTML: на текущем сайте счётчики 9000+ и 2200+ живут только в JS, и для робота на их месте стоят нули
- **Одна страница — один H1**, иерархия заголовков без пропусков уровней
- **Пустой блок не выводится.** Заголовок без содержимого хуже отсутствующего
- **Факты не выдумываются.** Данные, которых заказчик не подтвердил, остаются отсутствующими и попадают в сводку долгов, а не заполняются правдоподобным текстом. Пустой блок лучше вымысла
- **Целевое действие доступно с любой страницы** — это требование темы, и тема отвечает за то, чтобы оно выполнялось на каждом шаблоне
