# HERON — поставка движка

### Версия движка и окружение сайта — разные вещи

Окружение сайта (`SITE_ENV`) отвечает на вопрос, каким будет САЙТ: дев
закрыт от индексации и собирается без счётчиков, прод открыт. Версия
движка отвечает на вопрос, каким КОДОМ его собрали.

Эти оси независимы, и связывать их нельзя. Человек, которому нужен
закрытый от индексации сайт, чтобы спокойно поработать над контентом,
не должен из-за этого получить сырую ветку разработки движка и чужие
ошибки. Дев-сайт собирается стабильным движком — это нормальное,
ожидаемое сочетание.

Сырой движок берут только тогда, когда занимаются самим движком, и
делают это явно: `ENGINE=local`, `ENGINE=dev`, `ENGINE=beta`.

## 1. Почему отдельно

Прежнее решение — движок, контент и тема в одном репозитории, разделение после запуска — было верным для монолита и неверно для pip-пакета. Сайт не содержит движок, он его устанавливает. Стоимость разделения на старте — три строки в конфигурации; стоимость разделения потом — переписать Dockerfile, CI, документацию и разобрать историю коммитов.

Практическая причина сильнее теоретической: сайтов несколько. Копия ядра в каждом репозитории означает столько же расходящихся движков. Правка парсера, сделанная на одном сайте, не доедет до остальных; публичный репозиторий будет отставать от того, на чём сайты реально работают; ссылка на него с этих сайтов будет работать против проекта.

## 2. Артефакты

Артефакт ровно один, в двух упаковках одного и того же кода.

| Упаковка | Адрес | Для чего |
|---|---|---|
| Образ | `ghcr.io/OWNER/heron:<версия>` | сборка на любой машине без установки питона; прод и CI |
| Пакет | `pip install heron` | локальная разработка: правка контента без докера на каждый абзац |

Внутри образа — Python, пакет `heron`, `ENTRYPOINT ["heron"]` и непривилегированный пользователь. Больше ничего.

Темы и плагины — отдельные переносимые единицы, поставляются пакетами или git-ссылками. В образ движка они не вшиты.

### Версии и совместимость

`site.yaml` первой строкой объявляет требуемую версию:

```yaml
heron: ">=0.1,<0.2"
```

Движок сверяет себя с этим требованием до всего остального и при расхождении останавливается с `E012`, называя свою версию и требуемую. Это единственное, что не даст трём сайтам разъехаться по несовместимым движкам.

Версионирование семантическое. Ломающее изменение контракта папки, формата `site.yaml`, `theme.yaml` или набора хуков — это минорная версия до 1.0 и мажорная после. Изменение контракта без смены версии — ошибка релиза, а не мелочь.

## 3. Команды

Команды движка — `new`, `init`, `check`, `serve`, `build`, `page` — описаны в `21-engine.md` §10, это вся его поверхность. Упаковки в образ среди них нет: её делает хост (раздел 5).

### Два входа, один выход

```bash
# папки не было
heron new мой-сайт
# правите мой-сайт/site.yaml: домен, языки, тема, меню
heron init мой-сайт          # достроить папки под написанное
heron build мой-сайт         # → мой-сайт/dist/

# папка с контентом уже есть
heron init ~/SOURCE/готовый-контент
heron check ~/SOURCE/готовый-контент
heron build ~/SOURCE/готовый-контент --env prod --out /tmp/site
```

То же самое образом — `docker run … ghcr.io/fmstm/heron:prod <команда>` (README, «Быстрый старт»), а для нескольких сайтов — `scripts/site.sh` (раздел 5).

`init` — та же раскладка, но для существующей папки: смотрит, что есть, дописывает недостающее, ничего не перезаписывает без `--force` и печатает отчёт о найденном и добавленном.

**Клонирование репозитория движка в папку сайта не является способом установки** и не поддерживается. Способов ровно два: образ и pip-пакет. Клон репозитория движка рядом с сайтами нужен только ради `scripts/site.sh`.

## 4. `new` неинтерактивен

Вопросов команда не задаёт и флагов языков и темы не принимает: одинаковый вызов даёт одинаковую папку. Языки, тема и меню объявляются в `site.yaml` — единственном источнике правды, — а `heron init` догоняет структуру папок под написанное. Интерактив ломает автоматизацию: появляются флаги `--yes` для скриптов и CI, и поддерживать приходится два пути вместо одного.

### Что кладут `new` и `init`

```
<сайт>/
├── site.yaml              версия движка, домен, языки (один), тема, пустое меню
├── .gitignore             dist/, .heron-cache/
├── heron-readme.md        пояснительная записка — и в каждой папке ниже
├── content/<lang>/        по папке на язык из site.yaml; пусто — страницы пишет человек
├── data/  media/  static/  plugins/          пусто
└── theme/                 скелет: theme.yaml, base.html, templates/ (home, page, 404),
                           modules/, partials/ (header, footer, analytics), i18n/, assets/
```

Сборочной обвязки — Dockerfile, compose, `build.sh`, `.env` — в папке сайта нет и быть не должно (`20` §1): она живёт в репозитории движка.

## 5. Два выхода: папка и образ

Выход выбирается командой сборки, а не при создании сайта.

**Папка.** `heron build` кладёт готовый сайт в `dist/` (или в `--out`). Её можно отдать любым nginx, залить на шаред-хостинг, положить в статический хостинг — движок при этом больше не нужен. Рядом с HTML лежит `.heron-nginx.conf` — конфиг сервера под этот сайт (ниже).

**Образ.** Образ nginx с сайтом внутри собирает хост из репозитория движка:

```bash
./scripts/site.sh <сайт> build <окружение>   # → out/<сайт>-<окружение>
./scripts/site.sh <сайт> image <окружение>   # Dockerfile.site: nginx-unprivileged + статика + конфиг
./scripts/site.sh <сайт> smoke <окружение>   # поднять образ и проверить коды ответа
./scripts/site.sh <сайт> push <окружение>    # в реестр из REGISTRY
```

Контекст сборки образа — уже собранная папка `out/<сайт>-<окружение>`, а не папка контента: в образ физически не может попасть ни `.git`, ни исходники картинок, и движка в работающем контейнере нет. Настройки — `env/.env.<сайт>.<окружение>` (пример с пояснениями — `env/.env.example`): путь к контенту, `SITE_ENV`, движок (`ENGINE`), имя образа, реестр.

**Своей команды упаковки движок не имеет и иметь не должен**: docker-сокет внутрь контейнера сборки не пробрасывается никогда (доступ к сокету равносилен руту на хосте), поэтому `docker build` выполняет хост.

### Страница 404 и отдача

Статика сама по себе не умеет отвечать 404: сервер по умолчанию отдаёт свою страницу, и нарисованную темой не видит никто. Поэтому конфиг nginx **собирается вместе с сайтом** — движок кладёт его в `dist/.heron-nginx.conf`, а образ переносит в `conf.d` и убирает из корня. Список языковых локаций берётся из `site.yaml`: основной язык живёт в корне, остальные в своих папках, и написанный руками список разошёлся бы с содержимым папки в первый же раз, когда основной язык сменят. Правила такие:

* локации строятся по `site.languages`: корень — язык по умолчанию, плюс `location ^~ /<lang>/` на каждый неосновной язык. Одноязычный сайт получает одну корневую локацию; языков, которых нет в списке, в конфиге нет;
* перед локациями стоят карты 301 (`redirect_from`) и 410 (`gone`): ответ по ним уходит до обращения к файлам;
* на несуществующий адрес отдаётся `404.html` из корня сайта;
* адрес с языковым префиксом получает 404 своего языка: `/ru/…` → `/ru/404/index.html`; адрес с префиксом основного языка папки не имеет и попадает на корневую 404;
* код ответа остаётся **404**. Заглушка с кодом 200 попадает в индекс и плодит дубли — это дороже любого удобства;
* сама страница 404 помечена `internal`: открыть её по прямой ссылке как обычную страницу нельзя;
* скрытые файлы не отдаются вовсе — рядом со статикой лежит служебное, а папку могут разложить и руками на чужой сервер; `/.well-known/` остаётся доступным, иначе не выпустить сертификат.

`heron serve` отдаёт ту же 404 и тем же правилом выбора языка: локальный просмотр не должен отличаться от того, что увидит посетитель. Собирает он при этом **не в папку сайта**, а во временную папку машины: папка контента монтируется только на чтение и принадлежит тому, кто правит текст, — просмотр не имеет права оставлять в ней ни `dist`, ни кэш. Карты 301 и 410 `heron serve` не изображает: он отдаёт файлы. Ответы сервера по `redirect_from` и `gone` проверяются на образе — `scripts/site.sh <сайт> smoke <окружение>` — или на любом nginx с собранным `.heron-nginx.conf`.

### Метка сборки

Вопрос «почему правка не видна» почти всегда означает «отдаётся вчерашняя статика», а не «сборка сломалась». Поэтому окружение сборки несёт версию движка, время сборки и, если рядом есть git, короткий коммит контента: `env.version`, `env.built_at`, `env.revision` и готовая строка `env.stamp`.

Показывать её или нет — дело темы, но показывать в проде нельзя: это служебная информация, а не часть сайта. Тема выводит метку под условием `not env.is_prod`.

### Проверки и дымовой прогон

Набор проверок один и живёт в одном месте — `scripts/check.sh`: граница ядра по всему дереву, формат, линтер, тесты. CI зовёт тот же скрипт. Два набора — локальный и «как в CI» — расходятся в первый же день: локально гоняли линтер, а падало на форматировании.

`./scripts/site.sh <сайт> smoke <окружение>` поднимает **собранный образ**, дожидается ответа и сверяет коды: корень и `robots.txt` — 200, несуществующий адрес — 404, языковой раздел — 200 и 404 на своём несуществующем, служебный конфиг рядом со статикой — 404, **каждый адрес из `redirects.map` — 301 туда, куда объявлено**, каждый точный адрес из `gone.map` — 410. Кириллица в адресах кодируется перед запросом. Контейнер гасится, логи показываются при падении.

Проверка заводится не от любви к автоматике: «контейнер умирает на старте» ловили браузером заказчика. Права на файлы, неподхваченный конфиг и упавший nginx снаружи выглядят одинаково — пустой страницей.

### Теги образа

Публикуются: имя ветки, **точная версия** по тегу `vX.Y.Z`, `latest` для тега и короткий sha. Подвижного `X.Y` нет намеренно: сайт объявляет требование к движку в `site.yaml` и должен иметь возможность закрепиться на том, что не поедет под ним завтра.

## 6. Резолвер тем и плагинов

Один механизм на обе сущности — второго не заводим, иначе придётся помнить, какой где.

Порядок разрешения, первый найденный выигрывает:

1. **локально в папке сайта** — `theme/` для темы, `plugins/<имя>/` для плагина;
2. **установленный пакет** — `heron-theme-<имя>`; для плагина — entry point группы `heron.plugins`;
3. **git-ссылка**, если указана явно в `site.yaml`.

Локальное всегда сильнее. Тема разрабатывается прямо в сайте, без публикации на каждую правку CSS; вынести её в пакет можно позже, не меняя ни строчки в контенте.

Плагины — обычные pip-пакеты, устанавливаются в образ сайта одной строкой Dockerfile. **Своего формата пакетов и своего загрузчика движок не изобретает.** Локальная папка `plugins/` — для одноразовых плагинов конкретного сайта, которые публиковать незачем.

Тема не найдена — `E013`. Плагин из `plugins:` не установлен или упал при загрузке — `E014`.

## 7. Что можно расширять, а что нельзя

Набор хуков и их семантика — `21-engine.md`, раздел 15.

Главное разграничение, которое нельзя размывать:

- **Build-time** — хуки сборки. Свои типы секций, свои связи, свои фильтры Jinja, свои генераторы. Работают внутри восьми этапов конвейера.
- **Runtime** — всё, что происходит, когда посетитель уже на сайте. Хуков движка здесь нет и быть не может: в этот момент движок отработал и вышел.

«Плагин форм для статического генератора» — противоречие в терминах. Приём POST живёт в `heron-relay`.

## 8. Формы и `heron-relay`

Отдельный образ, один процесс, **без базы**. Появляется на сайтах, где есть формы; сайт без форм не разворачивает его вовсе.

Схема: статическая страница шлёт POST → relay валидирует по описанию формы из `site.yaml` → антиспам → рассылает по приёмникам.

```yaml
forms:
  callback:
    fields: [name, phone, message]
    sinks: [mail, crm, telegram]

sinks:
  mail:     {to: info@example.com, smtp_env: SMTP_URL}
  crm:      {webhook: https://crm.example.com/hook, secret_env: CRM_SECRET}
  telegram: {chat_id_env: TG_CHAT}
```

Антиспам: honeypot-поле, минимальное время заполнения, ограничение частоты по адресу. Капча (Turnstile) — опционально, включается в конфиге, по умолчанию выключена.

Приёмники независимы: недоступность CRM не отменяет письма. Ошибка любого приёмника не возвращается посетителю как ошибка отправки — он свою часть сделал.

**Про базу.** Relay остаётся stateless. SQLite подключается **только как спул повторной отправки**, когда приёмник лежит: заявка не теряется и досылается. Это не хранилище заявок — хранилище это CRM.

Черта, которую нельзя переходить: **как только в базу поедет контент или настройки сайта, HERON превращается в WordPress.** Файлы — единственный источник истины.

## 9. Модель безопасности

Сборщик статики — процесс, которому не нужно ничего. Поэтому забираем всё.

```bash
docker run --rm \
  --network=none \
  --read-only --tmpfs /tmp \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --user "$(id -u):$(id -g)" \
  -v "$PWD:/site" \
  ghcr.io/OWNER/heron:0.1.0 build --strict
```

| Мера | Что даёт |
|---|---|
| `--network=none` | сборка читает и пишет только локальные файлы. Сети ей не нужно ни на одном этапе. Скомпрометированная зависимость не сольёт и не притащит ничего. Побочно дисциплинирует дизайн: подтянуть шрифт или картинку «на этапе сборки» физически нельзя |
| `--user $(id -u):$(id -g)` | `dist/` создаётся владельцем папки, а не рутом. В образе `USER heron`, но флаг важнее: без него на Linux-VPS результат сборки принадлежит чужому uid. Образ не должен зависеть от конкретного `$HOME` — иначе сломается с произвольным uid |
| `--read-only` + tmpfs | записываемы только `/site/dist` и `/site/.heron-cache` — сборка и кэш нарезок. Кэш переживает `rm -rf dist` намеренно: в нём всё, что дорого посчитать, и удалить его безопасно в любой момент |
| `--cap-drop=ALL` | генератору HTML не нужна ни одна capability |
| `no-new-privileges` | никакого повышения через suid |
| нет `.env` в сборке | секретов у сборки нет; `.env` монтируется только в relay |
| нет docker-сокета | никогда, ни при каких условиях |

**Рантайм:** `nginxinc/nginx-unprivileged`, слушает 8080 не от рута. Официальный `nginx` стартует мастер-процессом от рута ради 80-го порта — здесь это не нужно, впереди прокси.

**Сырой HTML в markdown выключен по умолчанию** (`build.allow_raw_html: false`, ошибка `E015`). При переносе контента из WordPress туда приедет `<script>` от какого-нибудь виджета, и лучше, чтобы сборка на этом упала, чем молча вклеила.

**Цепочка поставки:** зависимости залочены (`uv.lock`), базовый образ прибит по digest, а не по тегу, образ собирается в CI из публичного репозитория. Тогда `heron:0.1.0` воспроизводим, и можно доказать, что в нём то же, что в гите.

**Граница ядра проверяется машиной.** В репозитории движка стоит pre-commit, запрещающий коммит с упоминанием любого из сайтов на движке, имён клиентов и телефонов. Список хранится хешами (`scripts/boundary-hashes.txt`) — сами имена в публичный репозиторий не попадают; добавление нового сайта — правка этого файла, а не хука. Дисциплина не масштабируется, хук масштабируется.

## 10. Репозитории

| Репозиторий | Содержимое | Видимость |
|---|---|---|
| `HERON` | `heron/` (contracts, core, modules, cli, scaffold), `tests/`, `docs/`, `scripts/site.sh`, `Dockerfile`, `Dockerfile.site` | публичный |
| репозиторий сайта | контент, данные, картинки, тема — без сборочной обвязки | на усмотрение владельца сайта |

Для правки движка рядом с сайтом движок ставится editable-инсталлом (`uv pip install -e ../HERON`) или собирается из исходников через `ENGINE=source` в `scripts/site.sh`: правки видны сразу, без публикации образа.

## 11. Что за рамками

- **Мультисайт в одной папке.** Одна папка — один сайт, жёстко. Мультисайт удваивает сложность резолва путей ради экономии, которой на трёх разных сайтах нет.
- **Админка.** Отложена до появления реальной нужды. Правило на момент, когда она появится: правит файлы и коммитит, в базу не пишет.
- **Инкрементальная сборка.** На объёме в сотню страниц не нужна. `serve` пересобирает всё.
