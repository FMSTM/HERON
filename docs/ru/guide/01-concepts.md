# 01 · Понятия

Здесь восемь понятий, на которых стоит всё остальное в HERON. Каждое объяснено на примере. Прочитав их, можно открывать любой раздел документации и понимать, о чём он.

Если движок ещё не установлен - начните с [00 · Установка](00-install.md). А если хочется сразу попробовать руками, переходите к [02 · Первый сайт](02-first-site.md) и возвращайтесь сюда, когда что-то покажется непонятным.

## Движок и сайт - отдельно

В HERON две части, и они никогда не смешиваются.

**Движок** - это программа `heron`. Вы получаете её одним из двух способов: Docker-образом `ghcr.io/fmstm/heron:<тег>` или пакетом Python, поставленным через pipx. Движок не копируют внутрь сайта и не правят под конкретный сайт: он один и тот же для всех.

**Сайт** - это обычная папка с вашими файлами. В ней нет ни строчки кода движка:

```
мой-сайт/
├── site.yaml       конфиг: домен, языки, тема, меню, SEO-настройки
├── content/        страницы в markdown, по папке на язык
├── media/          картинки, видео, документы
├── data/           yaml-справочники: отзывы, команда, реквизиты
├── static/         файлы по точному адресу: favicon, .well-known
├── theme/          тема: шаблоны Jinja2, стили, строки интерфейса
└── plugins/        свои плагины, обычно пусто
```

Движок читает эту папку и собирает из неё готовый сайт. Ваши файлы при сборке он не меняет.

Какой движок нужен сайту, записано в первом ключе `site.yaml`, например `heron: ">=0.3,<0.4"` - «подойдёт любая версия 0.3». Поэтому один движок обслуживает сколько угодно сайтов, а у каждого сайта может быть своя версия: старый сайт спокойно живёт на прежней версии, пока новый пробует свежую.

→ Подробно: [`20` §0-1](../spec/20-data-contract.md#what-the-system-is)

## Контракт

Контракт - это договор между движком и папкой сайта. В нём записано всё, на что можно опираться: какие файлы где лежат, какие поля бывают у страницы, какие ключи бывают в `site.yaml`, что движок сделает сам и на что ответит ошибкой. Контракт один для всех сайтов; полностью он описан в [`spec/20-data-contract.md`](../spec/20-data-contract.md).

Зачем это нужно на практике: если в папке что-то не так, вы получите не молча сломанную страницу, а понятную ошибку с кодом и файлом - например, `E002` или `E006` - и номером строки там, где он известен. Путь к файлу страницы в таких сообщениях пишется от папки `content/`: `en/about.md`, а не `мой-сайт/content/en/about.md`.

## Страница, ключ и адрес

**Страница - это markdown-файл, а путь файла задаёт адрес.** Положили файл `content/en/about.md` - получили страницу `/about/`. Вот пример для сайта, где основной язык английский, а второй - русский (`default_lang: en`, `languages: [en, ru]`):

```
content/en/index.md                →  /
content/en/about.md                →  /about/
content/en/services/_index.md      →  /services/              страница самого раздела
content/en/services/design.md      →  /services/design/
content/ru/about.md                →  /ru/o-nas/              slug: o-nas
content/ru/services/_index.md      →  /ru/uslugi/             slug: uslugi
content/ru/services/design.md      →  /ru/uslugi/dizajn/      slug: dizajn
```

Файл `_index.md` внутри папки - это страница самого раздела: `services/_index.md` открывается по адресу `/services/`, а страницы раздела - по адресам ниже, например `/services/design/`.

У каждой страницы есть две вещи, которые по умолчанию совпадают, но означают разное:

- **ключ** - путь файла без `.md`, например `services/design`. Ключ одинаков во всех языках. По нему движок понимает, что английская и русская страницы - переводы друг друга, и по нему страницу называют в меню и в ссылках;
- **адрес** - то, что посетитель видит в браузере. Его меняет поле `slug`, а ключ при этом остаётся прежним. Поэтому у русской версии адрес `/ru/uslugi/dizajn/`, а ключ тот же - `services/design`.

Зачем их разделять: адрес можно сделать понятным на каждом языке, а ссылки и меню, написанные ключами, от этого не ломаются.

Главная страница - файл `index.md`, её ключ `/`. Страница «не найдено» - файл `404.md`.

→ Подробно: [`20` §2](../spec/20-data-contract.md#content-tree-and-urls)

## Языки

Каждый язык сайта - это папка в `content/`: английские страницы лежат в `content/en/`, русские - в `content/ru/`. Какие языки есть и какой из них основной, задаёт `site.yaml`:

```yaml
site:
  default_lang: en       # отдаётся из корня: /about/
  languages: [en, ru]    # остальные - с префиксом: /ru/o-nas/
```

Страницы основного языка открываются по коротким адресам, остальных - с приставкой языка.

Перевод страницы - это файл с тем же именем в папке другого языка. Адрес у перевода может быть свой, через `slug`. Переведённые страницы сами получают теги hreflang друг на друга - так поисковик понимает, какую версию показать человеку, - а `x-default` указывает на версию основного языка.

Осторожно с `default_lang`: поменять его - значит поменять адреса всех страниц сайта сразу.

→ Подробно: [`20` §3](../spec/20-data-contract.md#languages)

## SEO-блок и фронтматтер

Каждый файл страницы начинается с **SEO-блока** - настроек страницы в формате YAML между двумя строками `---` (в мире markdown такой блок называют фронтматтером). Блок разбит на восемь групп, у каждой есть комментарий: основное, ключевые запросы, Open Graph, Twitter, schema.org, карточка, служебное, связи.

Обязательны только три поля:

- `title` - заголовок страницы в выдаче поисковика и во вкладке браузера;
- `h1` - главный заголовок на самой странице;
- `description` - короткое описание, которое поисковик показывает под заголовком.

Остальное заполняется по мере надобности. Пустые поля остаются закомментированными - они подсказывают, что ещё можно задать.

Стартовые страницы приходят с полным блоком, и команда `page` кладёт его в каждую новую страницу. Можно и проще: новая страница - это копия любого файла с поправленными значениями.

→ Подробно: [`20` §4.1-4.2](../spec/20-data-contract.md#page-overview)

## Секции и их формы

После SEO-блока идёт текст страницы. Всё, что стоит до первого заголовка, - вступление. Дальше идут **секции**, каждая начинается с заголовка `##`:

```markdown
## Как мы работаем {#how}

1. **Заявка.** Пишете или звоните.
2. **Встреча.** Обсуждаем задачу.
```

`{#how}` после заголовка - якорь, имя секции для темы. По якорю тема решает, где на странице показать секцию, поэтому порядок секций в файле не важен: тема сама поставит каждую на своё место.

Кроме места, у секции есть **форма**, и её движок понимает сам, по обычной разметке markdown. Нумерованный список - это шаги, заголовки `### Вопрос?` - вопросы и ответы (FAQ), строки `ключ | значение` - факты, таблица - таблица. Всего форм тринадцать. Объявлять ничего не нужно: пишете нумерованный список - тема получает шаги.

→ Подробно: [`20` §4.3-4.4](../spec/20-data-contract.md#sections)

## Тип страницы и тема

**Тема** - это папка `theme/`: шаблоны Jinja2, модули, стили, строки интерфейса. Тема решает, как сайт выглядит, а контент - что на нём написано. Поменяли тему - тексты остались прежними, изменился только вид.

**Тип страницы** выбирает, каким шаблоном её рисовать: страница типа `service` рисуется шаблоном `theme/templates/service.html`. Тип задают так:

- полем `type` в самом файле страницы;
- полем `children_type` в `_index.md` раздела - тогда этот тип получают страницы раздела;
- по умолчанию: у главной тип `home`, у остальных - `page`.

Какие типы бывают, решает тема: в файле `theme/theme.yaml` она описывает свои типы, их секции, связи между страницами и пропорции картинок.

→ Подробно: [`20` §6](../spec/20-data-contract.md#theme-yaml), [гайд по теме](04-theme.md)

## Сборка

Команда `build` читает папку сайта, проверяет её по контракту и собирает готовый сайт в папку `dist/`. Туда попадает всё, что нужно для публикации: HTML страниц, `sitemap.xml`, `robots.txt`, `llms.txt`, разметка JSON-LD для поисковиков, картинки, нарезанные под разные экраны, карты перенаправлений 301 и 410 и конфиг nginx.

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build мой-сайт
```

Сборка бывает двух видов:

- **черновая сборка** (dev) - по умолчанию. Сайт закрыт от поисковиков, счётчики не подключаются: можно спокойно смотреть и показывать;
- **боевая сборка** (prod) - с флагом `--env prod`. Это версия для публикации.

Результат выкладывают одним из двух способов: кладут папку `dist/` на любой хостинг или упаковывают её в образ nginx с сайтом внутри.

→ Подробно: [`21` §4](../spec/21-engine.md#build-pipeline), [гайд по выкладке](06-deploy.md)
