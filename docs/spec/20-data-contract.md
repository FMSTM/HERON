## 0. Что это за система

Генератор статического сайта из markdown-файлов. На вход — папка с контентом, картинками, темой и одним конфигом. На выходе — готовый HTML в `dist/`, который отдаёт nginx.

Ключевое правило, из которого выводится всё остальное:

> **markdown-файл — это именованный склад контента. Тема — это раскладка.**
> Файл не знает, где что покажется. Тема не знает, что написано.
> Связь между ними — по идентификаторам секций.

Практическое следствие: порядок секций в файле не влияет на порядок блоков на странице. Редактор пишет в удобном ему порядке, тема раскладывает в правильном.

**Формы — свойство сайта, а не движка.** Сам сайт остаётся статикой при любом раскладе: если форма есть, её POST принимает отдельный сервис `heron-relay`, а не сборщик. На одном сайте форм нет вовсе — единственная конверсия телефонный звонок; на другом есть. Контракт формы описывается в `site.yaml` (раздел 5), реализация — в `23-distribution.md`.

### Как поставляется движок

Решение от 2026-09-14, отменяет прежнее «движок, контент и тема в одном репозитории».

**Движок в папке сайта отсутствует.** Он поставляется одним артефактом — образом `heron:<версия>`, он же публикуется pip-пакетом для локальной разработки. Папка сайта содержит только контент, данные, картинки, тему и конфиг; строк питона в ней нет.

Сайт объявляет требуемую версию движка первой строкой `site.yaml` (`heron: ">=0.1,<0.2"`). Движок отказывается собирать сайт, версию которого не поддерживает, — это единственное, что не даст трём сайтам разъехаться по несовместимым движкам.

Всё, что описано ниже, — контракт между движком и папкой сайта. Он одинаков для всех сайтов на движке, какой бы теме они ни принадлежали.

## 1. Структура проекта

```
<сайт>/
├── site.yaml                 конфиг сайта, первой строкой — версия движка
├── .gitignore                dist/, .heron-cache/ — кладёт heron new
│
├── content/
│   ├── en/                   по папке на каждый язык из site.languages;
│   │   ├── index.md          главная — кладёт heron new/init
│   │   └── 404.md            страница «не найдено» — кладёт heron new/init
│   └── ru/
│
├── data/                     yaml-справочники: перечни, таблицы, реквизиты
├── media/                    картинки, видео и файлы контента, мастера любого соотношения
├── static/                   только то, что обязано лежать по точному адресу: webmanifest, .well-known
│
├── theme/                    тема этого сайта
│   ├── theme.yaml
│   ├── base.html
│   ├── templates/            шаблоны типов страниц
│   ├── modules/              шаблоны модулей
│   ├── partials/             шапка, подвал, счётчики
│   ├── i18n/                 строки интерфейса темы по языкам
│   └── assets/               css, js, логотип, иконки
│
└── plugins/                  локальные плагины этого сайта. Обычно пусто
```

Результат сборки — `dist/`: `heron build` без `--out` кладёт его внутрь папки сайта (он в `.gitignore`), `scripts/site.sh` — в `out/<сайт>-<окружение>` в репозитории движка, не трогая папку сайта вовсе. Кэш нарезок — `.heron-cache/` рядом с результатом.

**Dockerfile, compose, `build.sh` и `.env` в папке сайта запрещены.** Вся сборочная обвязка живёт в репозитории движка (`scripts/site.sh`, `Dockerfile.site`, `env/.env.<сайт>.<окружение>`), секреты сервисов — у сервисов (раздел 8).

Кода движка здесь нет. `heron/` в папке сайта — ошибка, а не структура.

**`data/`** — справочники, которым не место в теле markdown: перечни услуг с атрибутами, таблицы сравнения, реквизиты, списки документов. Доступны шаблонам как `data.<имя файла>`.

**`theme/`** — тема этого сайта, одна. Внутри неё лежат Jinja-шаблоны (`templates/`) — слово «шаблон» закреплено за ними, «тема» за пакетом целиком. Если темы в папке нет, движок резолвит её по имени из `site.yaml` (установленный пакет `heron-theme-<имя>` или git-ссылка); локальная `theme/` всегда сильнее.

Человек, ведущий сайт, работает только с `site.yaml`, `content/`, `data/`, `media/`. Всё остальное трогает разработчик.

### Пояснительная записка в каждой папке: heron-readme.md

`heron new` кладёт `heron-readme.md` в корень и в каждый созданный каталог. Три части: что это за папка, что сюда класть, **чего сюда не класть и куда вместо этого**. Третья часть обязательна: файл кладут не туда не потому, что не знают назначения папки, а потому, что не знают, чем соседняя лучше.

Документация в отдельном файле спецификации эту задачу не решает: её читают один раз при знакомстве, а решение «куда положить» принимается через месяц и в другом окне.

**Имя зарезервировано, и движок такие файлы не замечает нигде** — на любом уровне вложенности, в любом каталоге, независимо от регистра:

- в `content/` — не страница: не разбирается, не заводит адрес, не считается в статистике;
- в `static/` — не копируется в собранный сайт;
- в `media/` — не ресурс: не проверяется, не копируется, не значится неиспользуемым;
- в `theme/`, `data/`, `plugins/` — просто не замечается.

Правило одно на весь движок, без исключений по каталогам. Обычный `README.md` эту роль исполнить не мог: в `content/` он не становился страницей по случайности, а не по правилу, а из `static/` уезжал в сеть — эта папка копируется байт в байт, и на сайте появлялся `/README.md`.

Язык записок — тот, что выбрали при создании сайта; нет перевода — кладётся английский, без ошибки. Сайтам, заведённым раньше, записки не нужны: их отсутствие — строка в отчёте, а не ошибка.

**Мусор операционной системы** — `.DS_Store`, `Thumbs.db`, `desktop.ini` — в собранный сайт не попадает ниоткуда. Он заводится в `static/` сам, без участия человека, и уезжал в сеть по той же причине.

## 2. Дерево контента и URL

**Путь файла определяет URL.** Никаких отдельных карт маршрутов.

```
default_lang: en, languages: [en, ru]

content/en/index.md                  →  /
content/en/about.md                  →  /about/
content/en/contacts.md               →  /contacts/
content/en/guides/_index.md          →  /guides/
content/en/guides/getting-started.md →  /guides/getting-started/
content/en/services/_index.md        →  /services/
content/en/services/design.md        →  /services/design/
content/ru/index.md                  →  /ru/
content/ru/about.md                  →  /ru/o-nas/              slug: o-nas
content/ru/services/_index.md        →  /ru/uslugi/             slug: uslugi
content/ru/services/design.md        →  /ru/uslugi/dizajn/      slug: dizajn
```

Правила:

- имя папки — сегмент URL, имя файла без расширения — слаг
- `_index.md` — страница самой папки
- язык по умолчанию (`default_lang` из `site.yaml`) отдаётся из корня, остальные с префиксом
- все URL заканчиваются слешем, канонический вид — со слешем
- слаг только латиница, цифры и дефис. Файл с иным именем валит сборку
- слаг можно переопределить полем `slug` во фронтматтере, но обычно не нужно

### Имя файла — это ключ, `slug` — это адрес

Две разные вещи, которые по умолчанию совпадают:

- **имя файла и путь папок** — идентификатор страницы. По нему сводятся
  переводы, по нему страница называется в `nav` из `site.yaml`, по нему
  тема находит её через `page_of('<ключ>')`. Ключ главной — `/`
- **`slug`** — сегмент адреса, который видит посетитель

```yaml
# content/ru/services/_index.md
slug: uslugi
```

```
content/en/services/_index.md        →  /services/
content/en/services/design.md        →  /services/design/
content/ru/services/_index.md        →  /ru/uslugi/
content/ru/services/design.md        →  /ru/uslugi/design/       slug у страницы нет
content/ru/services/design.md        →  /ru/uslugi/dizajn/       со slug: dizajn
```

Слаг раздела уводит за собой всех детей: адрес собирается из цепочки
сегментов, а не из строки пути. Слаг обычной страницы меняет только её
последний сегмент.

Чего переименование адреса **не** делает: не рвёт связь между языками,
не требует править `nav` в `site.yaml`, не меняет ключ страницы. Английский
раздел живёт по `/services/`, русский — по `/ru/uslugi/`, и это
по-прежнему одна страница на двух языках, потому что файл у них называется
одинаково: ключ у обоих — `services`.

Слаг подчиняется тем же правилам, что имя файла: латиница, цифры и дефис,
один сегмент, без слешей. Негодное значение — ошибка сборки, а не тихий
откат к имени файла: подставить молча значит отдать странице адрес,
которого автор не ждёт, и узнает он об этом из выдачи.

Два файла, дающие один адрес, — ошибка `E004`, независимо от того, чем
именно они его дали: одинаковым слагом, или слагом, совпавшим с именем
соседнего файла.

Старый адрес после переименования закрывается `redirect_from` — он
языку не относителен и пишется полностью.

### Ссылки внутри контента относительны языку

Внутренняя ссылка пишется **от корня и без языкового префикса** — движок сам приводит её к адресу на языке страницы, со всеми слагами и префиксом.

Написанный путь `/a/b/` движок разбирает так:

1. **Как ключ страницы.** Ключ — путь папок плюс имя файла без расширения (`guides/x`), ключ главной — `/`. Нашёлся ключ — подставляется адрес этой страницы на языке текущей страницы.
2. **Как адрес в языке текущей страницы** — тот же путь с её префиксом (`/ru/a/b/` на русской странице).
3. **Как адрес в языке по умолчанию** или как полный адрес с префиксом. Нашлась страница чужого языка — подставляется её версия на языке текущей страницы.

Ключ сильнее адреса: он не меняется, когда переименовывают слаг. Поэтому надёжнее всего писать ссылки ключами — путём файлов, а не тем, что видно в адресной строке.

Пример на разных слагах:

```
content/en/guides/_index.md        (slug нет)             →  /guides/
content/ru/guides/_index.md        slug: rukovodstva      →  /ru/rukovodstva/
content/en/guides/x.md                                    →  /guides/x/
content/ru/guides/x.md                                    →  /ru/rukovodstva/x/
```

| Написано | На en-странице | На ru-странице |
|---|---|---|
| `[x](/guides/x/)` — ключ | `/guides/x/` | `/ru/rukovodstva/x/` |
| `[x](/guides/x/?a=1#faq)` | `/guides/x/?a=1#faq` | `/ru/rukovodstva/x/?a=1#faq` |
| `[x](/rukovodstva/x/)` — адрес ru без префикса | — | `/ru/rukovodstva/x/` |
| `[главная](/)` — ключ главной | `/` | `/ru/` |

Один и тот же markdown даёт правильные адреса в любом языковом дереве. Перевод — это копия файла с переписанным текстом, а не с переписанными ссылками: иначе одна забытая ссылка после перевода становится битой ссылкой в проде.

- **ключ есть, а перевода на язык страницы нет** — ссылка ведёт на версию языка по умолчанию (нет и её — на первую версию по порядку `languages`), в отчёт, в группу «ссылки», идёт предупреждение. Читатель оказывается на существующей странице другого языка, а не в 404;
- **не нашлось ничего** — ссылка остаётся как написана, в отчёт идёт предупреждение с файлом, номером строки и самой ссылкой. Это не ошибка сборки;
- **якорь и параметры** (`#faq`, `?a=1`) сохраняются;
- **не трогаются** внешние адреса, `mailto:`, `tel:`, адреса без схемы (`//cdn…`), чистые якоря, пути к `/media/`, `/static/`, `/assets/` и пути к файлам с расширением (`/llms.txt`, `/feed.xml`): слаг страницы точки не содержит.

Отдельно: **`redirect_from` языку не относительно.** Там лежат реальные старые адреса, с которыми сайт жил раньше, — они историчны, а не относительны.

### Старые адреса: кириллица и percent-encoding

Старый адрес с кириллицей существует в двух видах: `/новости/` и `/%D0%BD%D0%BE%D0%B2%D0%BE%D1%81%D1%82%D0%B8/`. В `redirect_from` и в `gone` (раздел 5) его можно писать **в любом из них** — движок приводит запись к той форме, в какой адрес сравнивает nginx (декодированный `$uri`), и 301 или 410 срабатывает на обе:

```yaml
redirect_from:
  - /новости-компании/                                 # как в адресной строке
  - /%d0%ba%d1%80%d0%b5%d0%b4%d0%b8%d1%82%d1%8b/       # как в выгрузке sitemap
```

Правила нормализации:

- percent-encoding раскрывается, регистр шестнадцатеричных цифр не важен (`%D0` = `%d0`);
- текст приводится к Unicode NFC: так кодируют адреса браузеры, а редактор мог сохранить «й» двумя символами;
- **регистр букв сохраняется**: `/About/` и `/about/` — разные адреса;
- **завершающий слеш:** запись без слеша получает его (`/новости` = `/новости/`), кроме адресов, похожих на файл (`/index.php`, `/page.html`). Сервер отвечает 301 или 410 и на вариант без слеша, и со слешем. Префикс `gone` (`/wp-*`) слеш не получает;
- слаг, обрезанный старой системой посреди буквы (`/%d0%ba%d1%80%d0/` — последний байт без пары), после декодирования не является текстом. Такая запись остаётся в percent-форме, и сервер сверяет её с сырым адресом запроса без учёта регистра `%xx`. Писать её нужно именно в percent-форме — как она пришла из старого sitemap;
- дубли, совпадение с адресом страницы (`E009`) и пересечения с `gone` (`E022`) проверяются по нормализованной форме: `/кредит/` и его percent-запись — один и тот же адрес.

В `dist/redirects.map` и `dist/gone.map` адреса лежат уже в нормализованной форме. В конфиге nginx ключи карт стоят в кавычках, пробелы и спецсимволы экранированы.

**Добавление страницы — это создание одного md-файла.** Она сама появляется в меню, в каталоге своей папки, в sitemap, в hreflang, в перелинковке и в `llms.txt`. Удаление файла убирает её отовсюду. Никаких списков, которые надо править параллельно.

### Страница 404

Текст страницы «не найдено» — контент, как любой другой: файл `404.md` в корне каждого языка.

```
content/en/404.md   →  dist/404.html          (и /404/index.html)
content/ru/404.md   →  dist/ru/404/index.html
```

- **тип** — `404` по имени файла, объявлять его не нужно (как главной `index.md` — `home`). Рисуется шаблоном темы `templates/404.html`;
- **поля** — как у любой страницы: `title`, `h1`, `description` обязательны (`E002`). `description` в выдачу не попадёт, но правило одно на все файлы;
- **в карту сайта, `llms*.txt`, hreflang и ленту** страница 404 не попадает никогда, `noindex` ставить не нужно;
- **отдача** — сервер отвечает кодом **404** и телом страницы языка из адреса: `/ru/…` → `/ru/404/index.html`, всё остальное → `/404.html`. Сама страница помечена `internal`: по прямой ссылке её не открыть (`23-distribution.md`, «Страница 404 и отдача»);
- **файла нет** — движок собирает 404 этого языка из шаблона темы без текста контента (заголовок и пояснение тема берёт из своих строк `t`) и пишет предупреждение в группу «контент». Нет и шаблона `templates/404.html` — предупреждение, и сервер отдаёт свою встроенную заглушку. Язык без единой страницы 404 не получает.

## 3. Языки

Набор языков сайт объявляет сам, в `site.yaml`:

```yaml
site:
  default_lang: en
  languages: [en, ru]       # от одного до любого числа кодов
```

- `languages` — от одного до N кодов вида `en`, `ru`, `en-gb`. Повтор кода или пустой список — `E011`
- `default_lang` обязан входить в `languages`, иначе `E011`. Язык по умолчанию отдаётся из корня (`/about/`), остальные — с префиксом (`/ru/about/`, или `/ru/o-nas/` со `slug: o-nas`)
- дерево контента на каждый язык — `content/<lang>/`. Папки языков, которых нет в `languages`, движок не читает
- соответствие страниц между языками — **по ключу**: относительный путь папок плюс имя файла. `services/design.md` в двух деревьях — одна страница на двух языках, какие бы `slug` у них ни стояли
- одна страница — один язык. Смешение языков внутри файла недопустимо

Слаги в разных языках могут отличаться (`design` / `dizajn`), связь идёт по ключу — и когда слаг взят из имени файла, и когда он объявлен полем `slug`.

### Что зависит от числа языков

| | Один язык | Два и больше |
|---|---|---|
| адреса | всё из корня | основной из корня, остальные `/<lang>/…` |
| `sitemap.xml` | сам список адресов (`<urlset>`) | индекс, плюс `sitemap-<lang>.xml` на каждый язык из `languages`, где есть индексируемые страницы |
| `hreflang` в `<head>` | не выводится | на каждой индексируемой странице: все её языковые версии, включая её саму, плюс `x-default` |
| `xhtml:link` в карте сайта | нет | у страниц, которые существуют хотя бы на двух языках |
| `page.translations` | всегда пуст | версии страницы на других языках, по ключу |
| файлы для нейросетей | `/llms.txt` — полный перечень страниц, `/llms-full.txt` — полные тексты. Языковых файлов нет | `/llms.txt` — оглавление, `/llms-<lang>.txt` и `/llms-full-<lang>.txt` на каждый язык |
| переключатель языка | в теме не выводится (`languages` длиной 1) | пункт на каждый язык; если перевода нет — пункт неактивен |
| nginx | одна корневая локация | плюс локация `/<lang>/` на каждый неосновной язык со своей 404 |

**`x-default`** ведёт на версию языка по умолчанию. Если у страницы такой версии нет — `x-default` не выводится вовсе: указывать на чужую страницу поисковику хуже, чем промолчать.

**Перевода нет** — страница просто отсутствует на этом языке, а в переключателе её пункт неактивен. Молча вести на главную или показывать 404 запрещено. Тема получает список кодов как `languages`, текущий язык как `lang`, версии страницы как `page.translations[<код>]`.

### Страница только не на основном языке

Такая страница собирается как обычная:

- попадает в карту сайта своего языка;
- `hreflang` указывает на неё саму, без `x-default`;
- в отчёт, в группу «переводы», идёт предупреждение «страница есть на `ru`, но нет на языке по умолчанию». Пока основной язык пуст целиком, это предупреждение не повторяется на каждой странице — достаточно строки о пустом языке.

### Пустой язык

Язык объявлен в `languages`, но `content/<lang>/` нет или в нём нет ни одной страницы:

| Ситуация | Дев | Прод (`--env prod`) |
|---|---|---|
| пуст неосновной язык | предупреждение в группе «языки» | то же предупреждение, сборка идёт |
| пуст язык по умолчанию, другие заполнены | предупреждение, сборка идёт | `E021` с кодом языка: корень сайта ответил бы 404 |
| пусты все языки | предупреждение, сборка идёт | `E017` |

Так второй язык можно наполнять раньше основного: дев-сборка показывает готовое, а в прод сайт без главной не уедет.

## 4. Формат markdown-файла

### 4.1 Общий вид

**Каждый файл начинается с SEO-блока, и только потом идёт контент.** Порядок обязателен и одинаков во всех файлах всех типов.

SEO-блок — это фронтматтер между `---`, разделённый на восемь пронумерованных групп рамками из комментариев и **прокомментированный построчно**. Человек, открывший файл впервые, должен понять, за что отвечает каждая строка, не сверяясь с этим документом.

Группы и их порядок:

| № | Группа | Что внутри |
|---|---|---|
| 1 | Основное | `title` `description` `h1` `canonical` `robots` |
| 2 | Ключевые запросы | только комментарий: основной ключ, дополнительные, сколько всего |
| 3 | Open Graph | `og_type` `og_title` `og_description` `og_image` `og_image_alt` |
| 4 | Twitter / X | `twitter_card` `twitter_title` `twitter_description` `twitter_image` |
| 5 | Schema.org | блок `schema` — уточнения разметки для этой страницы |
| 6 | Карточка и каталог | `image` `image_alt` `order` `children_type` `type` |
| 7 | Служебное | `updated` `published` `priority` |
| 8 | Связи | поля связей, объявленные темой, плюс `redirect_from` |

Блок со всеми восемью группами и комментариями кладут `heron new` и `heron init` в стартовые страницы (`index.md`, `404.md`) и `heron page` в каждую новую. Новая страница — копия файла с правкой значений; комментарии остаются как есть, их язык задаёт `build.notes` (`ru` или `en`).

**Что живёт в `site.yaml`, а не в файле страницы:** имя сайта (по языкам — раздел 5), локаль, `twitter:site`, `og_default_image`, реквизиты организации для разметки, ссылки на соцсети для `sameAs`, суффикс `title`. В странице — только то, что у неё своё.

**Что движок генерирует сам и в файле не пишется:** `hreflang` на все существующие языковые версии плюс `x-default` (правила — раздел 3), `canonical` по собственному URL, `BreadcrumbList`, `FAQPage` при наличии секции `faq`, `datePublished` из `date`, `dateModified` из `updated`, запись в `sitemap.xml` и в `llms.txt`.

Правила блока:

- **порядок групп фиксирован.** Человек находит нужное на одном и том же месте в любом файле
- **комментарии обязательны** и переносятся из файла в файл без изменений. Это не украшение: сайт ведёт не разработчик, подсказка должна быть под рукой, а не в спецификации
- **группа 2 обязательна** на каждой контентной странице. Движок её не читает, но она удерживает правило «один интент — одна страница»: чтобы дописать чужой кластер, надо сначала вписать его туда и увидеть, что ему нужна своя страница
- **мета-тег `keywords` не выводится.** Google игнорирует его с 2009 года, а конкурентам он показывает всю семантику проекта
- **пустые необязательные поля остаются с комментарием, а не удаляются** — иначе через полгода никто не вспомнит, что их можно заполнить
- `twitter_*` заполняются только когда должны отличаться от `og_*`; пустые движок подставляет из Open Graph

Дальше — контент. Текст до первого заголовка становится секцией `intro`, затем секции вида `## Заголовок {#anchor}`, при необходимости с классом модуля: `{#red-flags .alert}`, `{#timeline .timeline}`.

```markdown
## Что это такое {#what}

Короткое объяснение простыми словами…

## Кому подходит {#who}

- Первый признак
- Второй признак
```

### 4.2 Фронтматтер

YAML между `---`. Это **единственный авторитетный список полей**: модель страницы (`21` §6) и образец `heron page` следуют за ним.

Колонка «ядро» говорит, что движок делает с полем: **да** — читает и проверяет сам (`E002` — нет обязательного поля или значение не того типа; `E001` — фронтматтер не разбирается как YAML); **тема** — ядро поле не трактует, оно проходит насквозь и доступно шаблону как `page.meta.<поле>`. Колонка «группа» — номер группы SEO-блока из 4.1.

| Поле | Тип | По умолчанию | Ядро | Группа | Что делает |
|---|---|---|---|---|---|
| `title` | строка | — **обязательно** | да; длиннее 60 — предупреждение | 1 | `<title>` |
| `h1` | строка | — **обязательно** | да | 1 | заголовок на странице, `name` в разметке |
| `description` | строка | — **обязательно** | да; длиннее 155 — предупреждение | 1 | `meta description`, описание в `llms.txt` и в разметке |
| `slug` | строка | имя файла | да: латиница, цифры, дефис | 1 | последний сегмент адреса; ключ не меняет (раздел 2) |
| `canonical` | строка | собственный адрес | тема | 1 | тема выводит, если задано |
| `robots` | строка | — | тема | 1 | тема выводит; индексацию ядро решает по `noindex` |
| `og_title` | строка | `title` | да | 3 | заголовок в соцсетях |
| `og_description` | строка | `description` | да | 3 | описание в соцсетях |
| `og_image` | путь в `media/` | `seo.og_default_image` | да: файл обязан существовать (`E007`) | 3 | картинка 1200×630, не режется |
| `og_type`, `og_image_alt` | строка | — | тема | 3 | |
| `twitter_card`, `twitter_title`, `twitter_description`, `twitter_image` | строка | из `og_*` | тема | 4 | заполняются, только если должны отличаться от `og_*` |
| `schema` | карта | — | да: сливается в JSON-LD поверх `site.yaml` | 5 | уточнения разметки страницы (раздел 5) |
| `image` | путь в `media/` | — | да: `E007`, если файла нет | 6 | превью в каталоге и в карточках связей |
| `image_alt` | строка | — | да: предупреждение, если есть `image` без `alt` | 6 | |
| `nav_title` | строка | имя файла | да | 6 | короткое имя в меню и крошках (см. ниже) |
| `order` | целое | `999` | да | 6 | порядок в каталогах и меню, по возрастанию |
| `type` | строка | из папки, см. ниже | да: у типа должен быть шаблон (`E008`) | 6 | тип страницы — какой шаблон её рисует |
| `children_type` | строка | — | да; читается только в `_index.md` | 6 | тип детей раздела |
| `video` | путь в `media/` или полный URL | — | да: файл обязан существовать | 6 | ролик страницы, `page.video` (раздел 7.5) |
| `video_poster` | путь в `media/` | — | да: обязателен при локальном `video` (`E019`) | 6 | |
| `video_title` | строка | — | да | 6 | |
| `date` | дата `ГГГГ-ММ-ДД` | — | да | 7 | дата публикации: `datePublished` в разметке, порядок и `<published>` в ленте; в шаблоне `page.date` |
| `updated` | дата `ГГГГ-ММ-ДД` | см. `build.updated_from` | да | 7 | подпись, `lastmod`, `dateModified` |
| `published` | `true`/`false` | `true` | да | 7 | `false` — страница не собирается и нигде не появляется (`--drafts` включает) |
| `noindex` | `true`/`false` | `false` | да | 7 | `robots: noindex`, исключение из sitemap и `llms.txt` |
| `priority` | число | — | тема | 7 | в sitemap ядро его не выводит |
| `redirect_from` | список путей | `[]` | да: путь от корня, нормализация — раздел 2 | 8 | старые адреса, с которых 301 на эту страницу |
| поля связей | список имён или карт `{slug, note}` | — | да, если объявлены темой в `links`: имя обязано найтись (`E006`) | 8 | связи между страницами (раздел 6) |
| `gone` | список путей | — | устарело: читается с предупреждением | 8 | перенесите в `gone` в `site.yaml` (раздел 5) |
| любые свои | любое | — | тема | — | `page.meta.<поле>`; объявить, что тема их ждёт, — `fields` в `theme.yaml` |

Поля «тема» в группах 1, 3, 4 и 7 — часть SEO-блока, который кладёт заготовка: их заполняют там, где тема умеет их вывести. Ядро не придумывает за тему, как их рисовать, и не ругается на пустые.

#### Тип страницы

Тип выбирает шаблон: страница типа `service` рисуется `theme/templates/service.html` (или шаблоном, который тема назвала в `types.service.template`). Откуда берётся тип, по убыванию силы:

1. поле `type` в самом файле — для любой страницы, **включая одиночную вне раздела** (`about.md` с `type: about` рисуется `templates/about.html`);
2. для `_index.md` — `type` этого же файла; для обычной страницы — `children_type` из `_index.md` её папки;
3. для `_index.md` подраздела — `children_type` родительской папки;
4. главная (`index.md` в корне языка) — `home`;
5. иначе — `page`.

Шаблона для получившегося типа в теме нет — `E008`.

#### Ключ главной

Ключ страницы — путь папок плюс имя файла без расширения (раздел 2). У главной — `index.md` в корне языка — ключ **`/`**. Одно правило на всех:

- в меню: `nav: {main: ["/", about, services]}`;
- в ссылке из текста: `[на главную](/)` — главная на языке страницы;
- в шаблоне: `page_of('/')` — главная на языке текущей страницы, `page_of('services')` — любая другая страница по ключу; нет такой — `none`;
- в подстановках блока `schema`: `{{ pages.home.url }}`. Путь подстановки пишется через точки, и `/` в нём не написать, поэтому здесь главная называется `home`. Файл `home.md` в корне языка подстановкам недоступен — движок предупреждает о нём.

#### Короткое имя в меню: `nav_title`

Имя файла задаёт адрес и потому пишется латиницей. Если сайт не на латинице, в меню нужно слово на его языке, а `title` для этого не годится: он написан под поисковую выдачу и длинный. Поле объявляет сама страница, и живёт оно рядом с ней — у каждого языка свой файл, синхронизировать нечего. У раздела имя объявляет его `_index.md`.

Не объявлено — движок берёт имя файла. Одноязычному сайту, где файлы названы словами, заполнять нечего. `heron check` показывает страницы, которые попали в меню без короткого имени.

`redirect_from` — рабочий инструмент переезда с WordPress: старый адрес пишется рядом с новым контентом, а не в отдельной таблице, которая разъедется.

#### Дата публикации

`date` — когда страница вышла, `ГГГГ-ММ-ДД`, необязательное. Не путать с `published`: то — флаг «собирать ли страницу вообще», и с `updated`: то — дата последней правки.

```yaml
date: 2026-03-14        # вышла
updated: 2026-09-02     # последний раз правили
```

- разметка: `datePublished` из `date`, `dateModified` из `updated` (или из `build.updated_from`). Нет поля — нет ключа в разметке, выдумывать дату движок не будет;
- лента (`seo.feed`) сортируется по `date`, страница без неё — по дате обновления; у записи с `date` есть `<published>`;
- шаблону — `page.date` (объект даты, `{{ page.date.isoformat() }}` или свой формат).

#### Дата обновления

`updated` во фронтматтере — то, что поставил человек. Оно перебивает всё
и всегда: есть страницы, где дата — факт, а не метка сборки, и двигать её
перекомпиляцией нельзя.

Не поставил — источник выбирает сайт ключом `build.updated_from`:

| Значение | Откуда дата |
|---|---|
| `manual` (по умолчанию) | ниоткуда. Нет поля — нет даты, как было всегда |
| `git` | дата последнего коммита, затронувшего файл |
| `file` | время файла на диске |

Разрешённое значение одно и питает всех троих сразу: подпись под текстом
(`page.updated` в шаблоне), `lastmod` в карте сайта, `dateModified` в
разметке. Разъехаться они не могут по устройству.

Про `file` нужно знать главное: время файла — это время **записи на диск**,
а не время правки текста. Копирование без сохранения атрибутов (`cp` без
`-a`, распаковка архива, выкладка через панель хостинга, свежий клон)
ставит всем файлам одно время, и сайт объявит себя обновлённым целиком,
не изменившись ни на букву. Поисковик такую карту сайта перестаёт
принимать всерьёз, а подпись под текстом врёт уже людям. Поэтому движок
эту подпись распознаёт: если у всех страниц время совпадает с точностью
до минуты — это копия, и дата не проставляется вовсе. Отсутствие даты
честнее выдуманной.

`git` таких оговорок не требует: история хранит время изменения
содержимого, а не файла, и переживает копирование, клонирование и переезд.

### 4.3 Секции

Секция — блок контента с идентификатором. Синтаксис — обычный markdown-заголовок с якорем:

```markdown
## Что это такое {#what}
```

Секция — всё от этого заголовка до следующего заголовка **того же уровня** с якорем или до конца файла. Вложенные заголовки (`###`) принадлежат секции.

Правила:

- идентификатор: латиница, цифры, дефис
- порядок секций в файле безразличен
- один идентификатор дважды в файле — ошибка сборки
- текст до первой секции считается вводным блоком, доступен теме как `intro`
- секция, которую тема не использует, не ошибка — попадает в отчёт `heron check`
- секция, которую тема ждёт, а в файле её нет, тоже не ошибка: значение пустое,
  блок не рендерится, в отчёт идёт строка «тема ждёт секцию X, в файле её нет»

Заголовок секции — это контент, который увидит посетитель. Якорь — это адрес для темы. Их разделение принципиально: заголовок правят, адрес — нет.

#### Состав секции

Секция приезжает в тему не плоским куском разметки, а разобранной на части.
Макет режет страницу мельче, чем заголовок и текст под ним: подводку рисуют
одним кеглем, примечание другим, цитату — врезкой.

| Поле | Что это |
|---|---|
| `id` | якорь из `{#anchor}` |
| `title` | текст заголовка |
| `classes` | классы из якоря: `.alert`, `.timeline` |
| `lead` | абзацы до первого списка, таблицы или группы `###` |
| `body` | основной узел секции, разобранный по своему формату |
| `note` | абзацы после основного узла |
| `note_title` | жирный зачин первого абзаца примечания, если он есть |
| `callout` | содержимое цитаты `>`, где бы она ни стояла в секции |
| `links` | ссылки секции списком `{title, href}` |

Нет ни списка, ни таблицы, ни групп — вся секция это `body` типа «проза»,
`lead` и `note` пустые.

**Жирный зачин.** Абзац вида `**Текст до точки.** Дальше обычный текст`
разбирается надвое: зачин уезжает в `note_title` (или в `term` элемента
списка), из тела абзаца он удаляется. Признак — жирный фрагмент в самом
начале абзаца, заканчивающийся точкой, двоеточием или тире.

**Пункт списка** вида `**Термин.** Пояснение` разбирается в пару
`{term, text}`. Пункт без зачина в таком списке — пара с пустым `term`.
Список, где зачина нет ни у одного пункта, остаётся списком строк.

Разметка внутри значений сохраняется: `**жирный**` и `[текст](ссылка)`
доезжают до темы разметкой, а не экранированным текстом, включая ссылки
внутри жирного фрагмента. Ссылки собираются ещё и отдельным списком `links`
того элемента, где встретились, — тема вправе нарисовать их и в тексте,
и строкой чипов.

#### Вводный блок

Текст до первого заголовка разбирается на абзацы:

| Поле | Что это |
|---|---|
| `lead` | первый абзац |
| `promise` | второй абзац, необязательный |
| `intro` | весь вводный блок целиком, как раньше |

Три абзаца и больше — предупреждение `heron check` с именем файла: третий
и далее не попадут в шаблон. `intro` сохраняется, чтобы не ломать темы,
написанные до этого правила.

### 4.4 Формы секций (`kind`)

Некоторые модули ждут не прозу, а данные. Особого синтаксиса нет — всё это валидный markdown, читаемый глазами и в любом редакторе. Движок определяет **форму** секции по содержимому или по классу в якоре и отдаёт её теме полем `section.kind`, а разобранные данные — `section.data` (в шаблоне модуля — `items`).

#### Таблица форм

| `kind` | Разметка | Признак | Что получает тема (`items`) | Пример |
|---|---|---|---|---|
| `prose` | любой текст | ничего из ниже перечисленного не подошло; или класс `.prose` | строка html всей секции (то же, что `html`) | `Просто абзац.` |
| `list` | маркированный список | `- пункт` | список строк html. Если хоть у одного пункта жирный зачин `**Термин.**` — список пар: строка html с полями `.term`, `.text`, `.links` | `- раз`<br>`- **Термин.** Пояснение` |
| `alert-list` | маркированный список | только класс `.alert` | как у `list` | `## Тревожные признаки {#flags .alert}` |
| `checklist` | группы `###`, в каждой список | три и больше групп со списками; или класс `.checklist` | список групп `{title, html, items, has_list}`; `items` — как у `list` | `### Документы`<br>`- паспорт` × 3 группы |
| `two-lists` | группы `###`, в каждой список | ровно две группы со списками; или класс `.two-lists` | как у `checklist` | `### Подходит` / `### Не подходит` |
| `steps` | нумерованный список | `1. пункт` | список `{n, tag, title, text, html, links, top}` | `1. **[ЧАЩЕ] Заявка.** Текст` |
| `table` | markdown-таблица | есть строка-разделитель `\|---\|` | `{head: [ячейки], rows: [[ячейки]]}` | `\| Что \| Где \|`<br>`\|---\|---\|` |
| `facts` | строки `Ключ \| Значение` | строки с `\|` **без** строки-разделителя | список `{key, value}` | `Формат \| очно` |
| `faq` | группы `###` без списков | заголовки `###`, ни в одном нет списка | список `{q, a}`; `a` — html ответа | `### Сколько длится?`<br>`Около месяца.` |
| `timeline` | строки `Период \| Событие` или нумерованный список | только класс `.timeline` | как у `facts` (`{key, value}`) или как у `steps` | `## Восстановление {#recovery .timeline}` |
| `callout` | цитата `>` | в секции есть цитата и нет списка; или класс `.callout` | строка html цитаты | `> Если сроки горят — скажите сразу.` |
| `gallery` | маркированный список картинок | только класс `.gallery` | как у `list` | `- ![подпись](media/a.png)` |

Кроме `items`, у любой секции есть разобранные части — `lead`, `body`, `note`, `note_title`, `callout`, `links` (раздел 4.3), — и `html` целиком.

#### Порядок распознавания

Класс в якоре сильнее содержимого. Без класса форма определяется **по первому подошедшему правилу**, в таком порядке:

1. **`table`** — markdown-таблица со строкой-разделителем;
2. **`facts`** — строки `ключ | значение` без строки-разделителя;
3. **`steps`** — нумерованный список;
4. **группы `###` со списками**: ровно две — **`two-lists`**, три и больше — **`checklist`**. Одна группа со списком формой не считается и уходит дальше по порядку (обычно в `list`, заголовок группы при этом в `items` не попадает — нужен класс `.checklist`);
5. **`faq`** — группы `###`, ни в одной нет списка;
6. **`list`** — маркированный список;
7. **`callout`** — цитата `>`, если списка в секции нет. Секция «список и совет к нему» остаётся `list`, совет доступен теме как `section.callout`;
8. **`prose`** — всё остальное.

#### Чем похожие формы отличаются

- **`checklist` и `two-lists`** записываются одинаково — группы `###` со списками. Различает их число групп (две или три и больше) либо класс. Смысл разный: две колонки противопоставляют («подходит / не подходит»), чек-лист перечисляет («документы / дополнительно / на приём»), и тема рисует их по-разному;
- **`facts` и `timeline`** записываются одинаково — строки `ключ | значение`. По содержимому их не различить: без класса это всегда `facts`, шкала — только с классом `.timeline`;
- **`facts` и `table`**: `facts` — это не markdown-таблица, у неё нет шапки и строки-разделителя, ведущая `|` не нужна; markdown её рендерит абзацем, а движок разбирает в пары. Как только появляется строка `|---|---|`, это `table` с шапкой и любым числом колонок.

#### Классы в якоре, которые задают форму

| Класс | Форма |
|---|---|
| `.alert` | `alert-list` |
| `.callout` | `callout` |
| `.checklist` | `checklist` |
| `.facts` | `facts` |
| `.faq` | `faq` |
| `.gallery` | `gallery` |
| `.list` | `list` |
| `.prose` | `prose` |
| `.steps` | `steps` |
| `.table` | `table` |
| `.timeline` | `timeline` |
| `.two-lists` | `two-lists` |

Отдельно `{.top}` на пункте нумерованного списка — признак главного шага (без него `top` у первого шага). Неизвестный класс — предупреждение, форма определяется по содержимому.

#### Битый ввод

Разбор ошибается мягко: класс задан, а содержимое ему не подходит (`.steps` над маркированным списком, `.facts` без единой строки с `|`), — секция отдаётся как `prose`, в отчёт идёт предупреждение «класс не подходит к содержимому». В `facts` строки без `|` среди нормальных пропускаются с предупреждением. Валить сборку из-за пропущенной палочки в таблице нельзя.

#### Шаг подробнее

Шаг может нести метку и ссылки:

```markdown
1. **[ЧАЩЕ ВСЕГО] Без визита.** Заявка и [проверка документов](/services/).
```

превращается в `{n: 1, tag: "ЧАЩЕ ВСЕГО", title: "Без визита", text: "…", links: [{title, href}]}`. Метка — фрагмент в квадратных скобках в самом начале пункта, целиком в верхнем регистре; из текста он вырезается. Метки нет — поле пустое.

#### Тема называет ожидаемую форму

Одна и та же секция на разных страницах бывает разной формы: `{#recovery}` на одной странице — шкала, на другой — проза. Обе валидны, тема получает `section.kind` и решает сама.

Тема вправе назвать ожидаемую форму в `theme.yaml`: `uses: ["recovery:timeline"]`. Имя формы обязано быть из таблицы выше, иначе тема не загрузится. Расхождение формы на конкретной странице — не ошибка сборки, а строка в отчёте `heron check`.

#### Необязательные секции

Ядро не знает, какие секции у страниц бывают: это предметная область сайта. Все секции типа — и обязательные по смыслу, и необязательные — объявляет тема в `types.<тип>.uses` (раздел 6). Секция из `uses`, которой нет в файле, — строка в сводке долгов, а не ошибка; секция в файле, которой нет в `uses`, — строка в отчёте `heron check` («тема не использует»), это ловит опечатку в якоре.

## 5. `site.yaml`

Всё, что повторяется на каждой странице, живёт здесь в одном экземпляре. Адрес, вписанный руками в шапку и в подвал, рано или поздно расходится — это ровно та проблема, которую решает этот файл.

```yaml
heron: ">=0.1,<0.2"          # версия движка, которую требует сайт. Обязательна

site:
  domain: example.com
  theme: main                # имя темы. Локальная theme/ перекрывает
  default_lang: en
  languages: [en, ru]
  name: Название сайта

# Блоки ниже движок не разбирает — они целиком уходят в шаблоны.
# Их имена и состав придумывает тема, см. «Что ядро проверяет, а что пропускает».
contact:
  phone: "+00 000 000 0000"
  address: "улица и дом"
  city: Город
  hours_display: "Пн–Пт 09:00–18:00"

organization:
  name: Название организации
  same_as:
    - https://example.com/social

seo:
  title_suffix: " — Название сайта"
  og_default_image: media/og/default.jpg
  twitter_card: summary_large_image
  llms_txt: true
  llms_note:                 # сведения о сайте для файлов, которые читает нейросеть
    en: |
      ### How to reach us

      Phone: +00 000 000 00 00, 9 to 18.
      Appointments by phone only.
    ru: |
      ### Как с нами связаться

      Телефон: +00 000 000 00 00, с 9 до 18.
      Запись — только по телефону.
  robots_extra: []
  feed: article              # тип страниц для ленты. Нет ключа — нет ленты

nav:
  main: [about, services, contacts]

build:
  fail_on_warning: false
  allow_raw_html: false      # сырой HTML в markdown. По умолчанию запрещён
  updated_from: manual       # откуда дата обновления: manual | git | file
  workers: 0                 # процессов на нарезку картинок. 0 — по числу ядер

plugins: []                  # имена установленных плагинов

gone:                        # адреса, на которые сервер отвечает 410. См. ниже
  - /sample-page/
  - /wp/*
  - /?p=*

# Формы принимает heron-relay, а не сборщик. Движку описание нужно, чтобы
# отдать теме состав полей и упасть, если тема рисует форму, которой здесь нет
forms:
  callback:
    fields: [name, phone, message]
    sinks: [mail, crm]

sinks:
  mail: {to: info@example.com, smtp_env: SMTP_URL}
  crm:  {webhook: https://crm.example.com/hook, secret_env: CRM_SECRET}
```

`forms` и `sinks` читает не движок, а `heron-relay`. Движок использует их только чтобы отдать теме описание формы для разметки и чтобы упасть, если тема рисует форму, которой нет в конфиге.

Значения из `contact` и `organization` идут одновременно в разметку страницы, в JSON-LD и в блоки темы. Меняются в одном месте — это то, что не даёт адресу разойтись между шапкой и подвалом.

### Блок `analytics`

Публичные идентификаторы счётчиков. Это ключ ядра, он валидируется: неизвестный ключ — `E011`.

```yaml
analytics:
  ga4: G-XXXXXXX        # Google Analytics 4
  gtm: GTM-XXXXXX       # Google Tag Manager
  metrika: 12345678     # Яндекс.Метрика, число или строка
```

- это не секреты: идентификаторы видны в исходнике любой страницы. Поэтому они в `site.yaml`, а не в `.env`;
- выводит счётчики **тема** (`partials/analytics.html` в заготовке), ядро лишь решает, можно ли: шаблону доступен признак `env.analytics`. Он включён в прод-сборке (`--env prod`) и выключен в остальных; перебивается переменной окружения `SITE_ANALYTICS=0|1`. На деве счётчики не выводятся, чтобы тестовые заходы не попадали в статистику живого сайта;
- заготовка темы выводит `ga4` и `gtm`. Яндекс.Метрику заготовка не выводит: ключ `metrika` ядро принимает, но вывести его — дело темы сайта, которой он нужен.

### `seo.llms_note` — сведения о сайте для нейросетей

Файлы `llms*.txt` состоят из заголовков и описаний страниц. Того, что нужно
читателю в первую очередь — как связаться, когда работаете, чего сайт не
делает, — в них нет: на сайте эти сведения разбросаны по страницам, а в
перечень попадают только `h1` и `description`.

`seo.llms_note` — готовый markdown по коду языка, который движок вставляет в
файлы этого языка дословно. Подстановок и шаблонизации нет: это данные, а не
шаблон. Языка нет в словаре — в его файлах блока нет, молча: сайт вправе
описать не все языки.

Про объём: файл читает модель с ограниченным контекстом, и всё, что вы туда
положите, отъедает место у самого содержимого сайта. Несколько строк фактов —
то, что нужно; страница текста — нет.

Про уровень заголовка: начинать блок с `###` или ниже. `#` того же уровня, что
заголовок файла, формально допустим, но читается как начало нового документа.

**Блок предназначен для фактов о сайте, а не для указаний читающей модели.**
Текст, загруженный с чужого сайта, потребитель вправе считать данными, а не
инструкциями, — и правильно делает. Попытки управлять чужим агентом через этот
файл бесполезны, а выглядят как внедрение инструкций: такому сайту перестают
доверять целиком, вместе с честной его частью.

Куда попадает блок, дословно, без шаблонизации:

| Файл | Текст какого языка | Место |
|---|---|---|
| `/llms-<lang>.txt` | этого языка | после заголовка и описания, до перечня страниц |
| `/llms-full-<lang>.txt` | этого языка | после заголовка, до текстов страниц |
| `/llms.txt` на многоязычном сайте | языка по умолчанию | после описания, до списка языковых версий |
| `/llms.txt` и `/llms-full.txt` на одноязычном | единственного языка | как в языковых файлах |

### Значения по языкам

Название сайта на языках пишется по-разному, а суффикс `title` на чужом языке в выдаче — брак. Для трёх ключей ядра значение задаётся на каждый язык суффиксом `_<код языка>`:

```yaml
site:
  name: Daybreak
  name_ru: Рассвет
seo:
  title_suffix: " — Daybreak"
  title_suffix_ru: " — Рассвет"
  og_default_image: media/og/en.png
  og_default_image_ru: media/og/ru.png
```

| Ключ | По языкам |
|---|---|
| `site.name` | `site.name_<lang>` |
| `seo.title_suffix` | `seo.title_suffix_<lang>` |
| `seo.og_default_image` | `seo.og_default_image_<lang>` |

- `ключ_<lang>` сильнее ключа без суффикса; языку без своего значения достаётся значение без суффикса;
- суффикс языка, которого нет в `site.languages`, — `E011`;
- **шаблон получает готовые значения языка страницы**: `site.site.name`, `site.seo.title_suffix`, `site.seo.og_default_image` уже подставлены, фильтр не нужен. То же видят подстановки блока `schema` (`{{ site.name }}`), заголовки `llms*.txt` и ленты;
- обе картинки `og_default_image*` объявлены сайтом: движок проверяет их наличие и кладёт в сборку, как любые файлы из `media/`;
- остальные ключи ядра от языка не зависят. Блоки сайта (`contact`, `organization` и свои) переводятся тем же суффиксом (`address_ru`), но их разбирают подстановки schema (ниже) и тема, а не ядро.

Заготовка темы (`heron new`) уже выводит `<title>` с суффиксом, `og:*`, название в шапке и подвале из этих значений.

### Блок `build`

| Ключ | Значения | По умолчанию | Что делает |
|---|---|---|---|
| `notes` | `ru` \| `en` | `en` | язык комментариев и пояснений, которые кладут `heron init` и `heron page`. Перебивается флагом `--notes` и переменной `HERON_NOTES`. На сборку не влияет |
| `fail_on_warning` | `true`/`false` | `false` | предупреждения валят сборку, как `--strict` |
| `allow_raw_html` | `true`/`false` | `false` | сырой HTML в markdown; при `false` — `E015` |
| `updated_from` | `manual` \| `git` \| `file` | `manual` | откуда дата обновления страницы, если `updated` не поставлен руками |
| `workers` | 0–64 | `0` | процессов на нарезку картинок; `0` — по числу ядер |

**`updated_from`.** `updated` во фронтматтере перебивает автоматику всегда. Без него:

- `manual` — даты нет вовсе;
- `git` — дата автора последнего коммита, затронувшего файл, в UTC без времени. Файл с незакоммиченными правками или которого нет в истории — время файла и предупреждение с путём. **История недоступна** — не репозиторий, нет `git`, клон обрезан (`--depth 1`) — сборка не падает: движок берёт время файлов и пишет **одно** предупреждение на сборку. В CI для этого режима нужен полный клон (`fetch-depth: 0`, `22-deploy.md` §4);
- `file` — время файла на диске. Если у всех страниц оно совпадает с точностью до минуты, это копия, а не правки, и дата не ставится вовсе.

Подробности режимов — «Дата обновления» в разделе 4.2.

### Блок `schema`: разметка без дублирования данных

Что размечать, решает тема (`types.<тип>.jsonld`) и сама страница (блок `schema` во фронтматтере). Чем заполнять — `site.yaml`, блок `schema`. Ядро подставляет то, что знает само: `name`, `description`, `url`, `inLanguage`, `dateModified`, хлебные крошки и вопросы-ответы.

```yaml
schema:
  entity:                       # сквозной узел сайта
    "@id": "#owner"
    "@type": Person
    name: "{{ organization.name }}"
    description: "{{ organization.about }}"
    telephone: "{{ contact.phone }}"
    address:
      "@type": PostalAddress
      streetAddress: "{{ contact.street }}"
      addressLocality: "{{ contact.city }}"
      addressCountry: "{{ contact.country }}"
    geo:
      "@type": GeoCoordinates
      latitude: "{{ contact.geo.0 }}"
      longitude: "{{ contact.geo.1 }}"
```

**Подстановки, а не копии.** `{{ contact.city }}` читается из того же `site.yaml`, откуда значение берёт тема. Второй копии адреса не заводится: разошедшийся адрес в разметке никто не заметит глазами — его видит только поисковик.

**Язык подставляется сам.** На русской странице `{{ contact.address }}` — это `address_ru`, на английской — `address_en`; нет языкового ключа, берётся ключ без хвоста. Один блок работает для всех языков.

**Списки разворачиваются звёздочкой.** `{{ contact.social.*.href }}` — список адресов из списка карт `{href, name}`. Иначе соцсети переписывают в разметку руками и забывают обновить.

**Адреса страниц и базовый адрес** доступны подстановкам: `{{ site.base }}` — корень сайта, `{{ pages.<ключ>.url }}` — адрес страницы с таким ключом на языке текущей страницы, `{{ pages.<ключ>.image }}` — её картинка, `{{ pages.<ключ>.h1 }}`, `.title`, `.description`. Вписывать адрес страницы руками не нужно: он меняется вместе со слагом, а разметку после переименования никто не перечитывает. Главная в подстановках называется `home` (в остальных местах её ключ — `/`, см. 4.2).

**Связи страницы доступны подстановкам:** `{{ related.topics.*.url }}` — адреса связанных страниц, `.h1`, `.note`, `.description`. Перечень уже собран движком по правилам темы, и переписывать те же ссылки во фронтматтере значит завести второй список, который разойдётся с первым на третьей правке.

**Якорный `@id` становится абсолютным.** `"@id": "#owner"` внутри узла страницы движок превращает в `https://домен/#owner`: относительный идентификатор разрешается от адреса документа, и на каждой странице получилась бы своя сущность, а связь между узлами молча распалась бы.

**Чего нет — того нет.** Ключ, для которого значения не нашлось, не выводится вовсе. Пустое поле в разметке хуже отсутствующего: поисковик считает его заявленным.

**Сквозной узел** попадает на каждую индексируемую страницу целиком, а не ссылкой: страницы независимы, и краулер не обязан сначала зайти на главную. `@id` один на весь сайт и на все языки — это одна сущность, а не три. На странице с `noindex` узла нет: разметка там бессмысленна.

**Проверки на сборке** (`E020`):

- разметка каждой страницы разбирается как JSON;
- объявленный темой тип присутствует в графе;
- если `schema.entity` объявлен — он есть на каждой индексируемой странице; если он объявляет `address.addressLocality` или `geo`, их значения не пустые (подстановка не нашла данных — значит их забыли заполнить). Узел без адреса вовсе — сайт без офиса — это нормально, ядро предметную область не решает;
- **поля про деньги** — `offers`, `price`, `priceRange`, `priceCurrency`, `paymentAccepted`, `lowPrice`, `highPrice`, `priceSpecification` — запрещены, пока сайт не разрешил их явно:

```yaml
seo:
  allow_prices: false   # по умолчанию. true — цены в разметке разрешены
```

Запрет по умолчанию — не забывчивость в данных, а защита: если сайт не публикует стоимость на страницах, она не должна утечь через разметку. Сайт, который цены публикует, ставит `allow_prices: true`.

Отчёт после сборки считает страницы по типам узлов, чтобы было видно, что разметка доехала.

### Блок `gone`: 410 для того, чего больше нет

После переезда и после взлома остаются адреса, у которых нет и не будет страницы: архивы категорий, пагинация, служебные пути старой системы, дорвеи. На них сервер отвечает **410 Gone** — «этого больше нет, выкиньте из индекса». 404 говорит поисковику «может, появится», и он продолжает проверять адрес месяцами.

Страницы у таких адресов нет, поэтому живут они в `site.yaml`, ключом ядра `gone` (валидируется, ошибка — `E011`). Три формы записи:

| Запись | Что закрывает |
|---|---|
| `/sample-page/` | ровно этот адрес |
| `/wp/*` | всё, что начинается с `/wp/`: `/wp/`, `/wp/wp-login.php`, `/wp/a/b/c/` |
| `/?p=*` | адрес `/` с параметром `p` любого значения: `/?p=123`, `/?utm=1&p=5` |
| `/?p=12` | адрес `/` с параметром `p`, равным `12` |

- звёздочка допустима только в конце пути или вместо значения параметра целиком. Параметр в записи один. Якорь (`#…`) серверу не приходит и в записи запрещён;
- пересечение с адресом существующей страницы (точное или префиксом) — `E022`, сборка останавливается. Сайт не может одновременно иметь страницу и объявлять, что её нет;
- пересечение с `redirect_from` любой страницы — тоже `E022`: адрес либо переехал (301), либо исчез (410);
- запись-параметр с адресом страницы не пересекается: `/?p=*` не закрывает главную, только главную с этим параметром;
- одна и та же запись дважды — предупреждение;
- кириллица и percent-encoding — по тем же правилам, что `redirect_from` (раздел 2).

Сервер отвечает 410 **до обращения к файлам**: движок вписывает список картой в конфиг nginx, который собирает вместе с сайтом (`23-distribution.md`, «Страница 404 и отдача»). Человекочитаемая копия — `dist/gone.map`.

Поле `gone` на странице устарело: адрес, которого больше нет, некуда честно приписать. Оно ещё читается — адреса уходят в тот же список, — но каждая такая страница даёт предупреждение «перенесите в `site.yaml`».

### Что ядро проверяет, а что пропускает насквозь

Уточнение от 2026-09-14, по итогам реализации контрактов.

Ядро строго валидирует только свои ключи: `heron`, `site`, `seo`, `nav`, `build`, `analytics`, `plugins`, `forms`, `sinks`, `gone`. Опечатка внутри них — остановка с `E011`.

Блоки, которых движок не знает — `contact`, `organization`, `analytics`, любые свои — **проходят насквозь** и достаются шаблонам как есть. Ядро в их смысл не вникает: иначе оно начнёт знать предметную область каждого сайта по отдельности, и граница, ради которой всё затевалось, исчезнет.

Проверку наличия при этом мы не теряем. Тема объявляет, что ей нужно, в `theme.yaml`:

```yaml
requires:
  - contact.phone
  - organization.name
forms:
  - callback
```

Движок проверяет, что эти пути в `site.yaml` заполнены, и останавливается с понятным перечнем, если нет. Тема просит — сайт даёт — движок сверяет, не понимая предметной области.

Туда же переехали типы JSON-LD: `types.<тип>.jsonld` задаётся в `theme.yaml`. Соответствие «такой-то тип страницы → такой-то тип разметки schema.org» принадлежит теме: у сайта услуг, магазина и справочника оно разное, и модуль движка знать его не обязан.

## 6. `theme.yaml`

Паспорт темы. Служит документацией и основой отчёта `heron check`, а не жёстким валидатором.

```yaml
name: main
version: "1.0"
title: Тема сайта

# что тема ждёт от site.yaml. Движок проверит наличие, не вникая в смысл
requires:
  - contact.phone
  - organization.name

# формы, которые тема рисует. Их описание должно быть в site.yaml
forms: [callback]

modules:
  - breadcrumbs
  - prose
  - facts
  - list
  - alert-list
  - steps
  - timeline
  - faq
  - cards
  - quote
  - table
  - gallery
  - author

types:
  home:
    uses: [intro, about, services, faq]
    jsonld: [WebSite]
  category:
    uses: [intro, outro]
    jsonld: [CollectionPage]
  service:
    uses: [intro, quick-facts, what, who, how, faq]
    jsonld: [Service]
  article:
    uses: [intro]
    jsonld: [Article]
  page:
    uses: [intro]

# связи между страницами. Ядро найдёт, проверит и построит обратную ссылку,
# не зная, что означает само отношение
links:
  - field: related
    type: service
    back: mentioned_in
  - field: topic           # поле во фронтматтере страницы-источника
    type: topic            # на страницы какого типа ссылается (необязательно)
    on: service            # у страниц какого типа поле должно быть
    required: 1            # сколько ссылок минимум

# пропорции и ширины, в которые движок впишет мастера
images:
  widths: [400, 800, 1200, 1600]
  ratios: ["1:1", "16:9", "4:3"]
  formats: [avif, webp]
```

Тип страницы реализуется файлом `templates/<тип>.html` — обычным шаблоном Jinja2, где порядок блоков виден сверху вниз:

```jinja
{% extends "base.html" %}
{% block content %}
  {{ mod.breadcrumbs() }}
  {{ mod.hero() }}
  {{ mod.facts('quick-facts') }}
  {{ mod.prose('what') }}
  {{ mod.prose('who') }}
  {{ mod.list('contra') }}
  {{ mod.steps('how') }}
  {{ mod.timeline('recovery') }}
  {{ mod.prose('price') }}
  {{ mod.faq('faq') }}
  {% for p in page.related.get('related', []) %}
    <a href="{{ p.url }}">{{ p.h1 }}</a>
  {% endfor %}
  {{ mod.call() }}
  {{ mod.author() }}
{% endblock %}
```

`mod.prose('what')` берёт секцию `what`; если её нет — не выводит ничего, ни заголовка, ни пустой рамки. Обвязка условиями вокруг каждого модуля не нужна.

**Связи — не секции.** `mod.<модуль>('<id>')` ищет секцию с таким якорем в тексте страницы. Связанные страницы в тексте не лежат: движок собирает их из полей связей в `page.related.<поле>` (и обратные — в `page.related.<back>`). Тема перебирает этот список сама, как в примере выше, или вызывает свой модуль без аргумента, который читает `page.related`. Вызов `mod.cards('related')` ничего не выведет — секции `related` на странице нет.

#### Обратные связи

`back: <имя>` — ядро строит обратный список: если `a.md` ссылается на `b` полем `related`, у `b` появляется `page.related.<имя>` со страницей `a`. Тема рисует его так же, как прямой.

- **связь внутри одного типа разрешена**: услуга ссылается на услуги (`field: related, type: service, back: related_from`), обратный список строится как обычно;
- **ссылка страницы на саму себя** пропускается с предупреждением в группе «связи». Ни в прямой, ни в обратный список она не попадает;
- **одно имя обратной связи у нескольких объявлений** (например, `topic` из услуг и из статей с одним `back: mentioned_in`) даёт **один смешанный список**: страницы всех типов вместе, без дублей;
- **порядок** и прямого, и обратного списка — по `order`, затем по `h1` без учёта регистра. Порядок, в котором ссылки записаны во фронтматтере, не сохраняется: его задаёт `order` целевых страниц;
- **отфильтровать по типу** тема может сама — у элемента списка есть `type`, как у любой страницы: `{% for p in page.related.mentioned_in if p.type == 'article' %}`;
- `on` на построение связей не влияет: связь строится у любой страницы, где поле заполнено. `on` говорит только, у страниц какого типа пустое поле — повод для предупреждения (ниже).

#### Обязательные связи: `required`

`required: N` — тема ждёт у страницы минимум `N` ссылок в этом поле. Это **предупреждение**, не ошибка: недописанная перелинковка не повод не выкладывать сайт, но видеть её надо. Оно попадает в группу «связи» отчёта сборки и `heron check`:

- поле заполнено, но ссылок меньше `N` — предупреждение на любой странице, где поле есть: «related: ссылок 0, тема ждёт минимум 1»;
- поле пустое или его нет — предупреждение только у страниц типа `on`: «поле 'topic' не заполнено, а тема ждёт минимум 1». Без `on` движок не знает, каким страницам поле положено, и про пустое молчит;
- ссылка на страницу, которой нет, — по-прежнему ошибка `E006`, независимо от `required`.

Ключ `on` пишется без кавычек: YAML читает голое `on` как «истину», и движок возвращает ему имя сам.

#### Связи с подписями

Поле связи принимает две формы — список имён и список карт, в одном
списке можно смешивать:

```yaml
services:
  - slug: express-review
    note: Основной способ, когда сроки горят
  - full-review
```

**Страница называется в связях именем своего файла без расширения**, а не
адресом. Ключ карты исторически называется `slug`, но значение в нём — то же
имя файла.

Адрес для этого не годится: он задаётся полем `slug`, у языков разный, и
связь по адресу означала бы, что английская страница и её русский перевод
связаны с разными вещами — хотя связь описывает предмет, а не URL. Переименование
адреса на связи не влияет никак.

Имя ищется в пределах своего языка. Два файла с одинаковым именем в разных
папках одного языка — ошибка `E006` про неоднозначность: движок не угадывает,
какой из них имелся в виду.

Подпись не задана — движок подставляет `promise` целевой страницы, нет
и его — `description`. Имя, которому не нашлось страницы, — ошибка сборки,
как и раньше.

## 7. Картинки

`media/` — одна общая папка на картинки и видео, по языкам не делится. Ссылка и `alt` живут в md, поэтому для разных языков можно указать разные файлы — например скан документа на каждом из языков.

- ссылки в md относительные от корня: `media/services/design.png`
- `alt` обязателен. Картинка без `alt` — предупреждение сборки
- движок сам делает варианты под брейкпоинты, конвертирует в WebP и AVIF, проставляет `width`, `height`, `srcset`, `loading="lazy"` кроме LCP-картинки. Оригиналы не трогаются
- `og_image` не режется и не конвертируется — соцсети ждут JPEG или PNG 1200×630

### 7.1 Папка ресурсов называется media

Раньше она называлась `img`. Имя обещало только изображения, поэтому видео класть было некуда — оно оседало в `static/` и ехало в сборку мимо всякой обработки. Теперь в `media/` лежит и то, и другое.

Переезд — разовый проход по сайту, и пока он не сделан, сайт обязан собираться: ронять чужую работу ради своего переименования движок не вправе. Поэтому:

- есть `media/` — тихо, это норма;
- есть только `img` — собирается как раньше, одно предупреждение о переименовании;
- есть обе — `E018`, сборка останавливается. Это не переходное состояние, а развилка: в какой папке правда, движок не знает, а гадать дороже;
- есть `media/` и при этом `static/media` — тоже `E018`: статика копируется в корень, и обе папки метят в одни адреса. Совпадение имён там — тихая перезапись, которую замечают уже в сети.

Пути внутри сайта пишутся от корня сайта: `media/foto/portrait.jpg`. Форма `./media/…` тоже принимается.

### 7.2 Где движок ищет файлы

Картинка узнаётся **по значению, а не по имени поля**: имена движок не угадывает, тема вправе назвать своё поле как угодно. Значением считается путь, который начинается с папки медиа и заканчивается известным расширением; строка из прозы под это не попадает, потому что проверяется целиком, а не вхождением.

В `media/` лежит **любой файл контента**, а не только изображение: ролик, памятка в PDF, презентация. Изображения движок режет под пропорции и конвертирует, всё остальное копирует как есть — список обрабатываемых расширений остаётся явным, но файл не из него не ошибка. Иначе каждый новый тип файла требовал бы правки ядра, а до неё оседал бы в `static/` мимо всех проверок.

В сборку попадают **только объявленные** файлы. Лежащее в `media/`, но никем не упомянутое, никуда не едет и попадает в отчёт строкой «файлы в media, которых никто не ждёт»: это не ошибка — мастер часто кладут раньше, чем пишут страницу, — но и не повод копить в папке старые версии годами.

Файл тяжелее 10 МБ даёт предупреждение с именем страницы, независимо от типа. Это не ошибка: бывает и репортаж на двадцать минут. Но узнать об этом человек должен на сборке, а не от посетителя с мобильным интернетом.

Ищутся файлы везде, где тема может их объявить:

- поля `image` и `og_image`;
- **любое** дополнительное поле фронтматтера, на любой глубине: строка, карта, список, список карт, карта со списками внутри. Раскладывать пути и подписи в два параллельных списка, связанных только порядком, больше не нужно;
- тело страницы — обычные ссылки на картинки в markdown;
- справочники `data/`: сквозные блоки живут там, и картинка оттуда такая же настоящая. В сообщении об ошибке владельцем назовётся файл справочника.

Глубина обхода ограничена: YAML-якоря дают общие объекты, и предел дешевле, чем однажды ловить зациклившийся обход.

Значение с собственной схемой (`https://…`, `//…`) картинкой сайта не считается — это чужой файл, и искать его на своём диске движок не идёт.

Опечатка в пути даёт `E007` с именем страницы — и во вложенном поле тоже. Раньше такая картинка терялась молча: ни ошибки, ни предупреждения, просто пустое место на странице.

### 7.3 Что не надо резать

Тема вправе сказать, что файлы по такому-то пути трогать не нужно:

```yaml
images:
  ratios: ["1:1", "16:9", "4:3"]
  widths: [400, 800, 1200, 1600]
  formats: [avif, webp]
  as_is: [media/docs/]
```

Такой файл копируется в сборку как есть: ни вариантов, ни конвертации. Скан документа не иллюстрация — его открывают целиком и в одном виде, адаптивные размеры ему не нужны. Три соотношения на четыре ширины в двух форматах — это два десятка файлов на каждый скан, которые никто никогда не запросит, и минуты сборки на каждую дюжину.

Путь пишется началом, как и `crop`. Проверка существования, `E007` и предупреждение о весе работают как для любого другого объявленного файла.

### 7.4 Адрес файла для темы: media_url

Тема умела получить от движка только готовый `<picture>`. Адрес файла как такового не получить было ничем — а он нужен постоянно: ссылка «открыть скан», `href` модального окна, адрес для скачивания, картинка в разметке для соцсетей, ссылка на документ из текста. Без него файл дублировали в `static/`: два места, которые надо не забыть поправить вместе.

```jinja
{{ media_url('media/docs/0002.webp') }}
{{ media_url('media/foto/portrait.jpg', ratio='4:3', width=1200) }}
{{ 'media/docs/pamyatka.pdf'|media_url }}
```

- без параметров — адрес самого файла в сборке. Мастер копируется в сборку рядом с вариантами именно ради этого;
- с `ratio` — адрес нарезанного варианта; `width` берёт ближайший размер **не меньше** запрошенного, а если таких нет — самый крупный: отдать крупнее и дать браузеру сжать честнее, чем показать мыло;
- `format` выбирает формат варианта; без него — исходный формат мастера, потому что это адрес для ссылки и скачивания, а не для `<picture>`;
- запрошенного варианта нет — **предупреждение** с путём и адрес исходника. Молча отдавать пустую строку нельзя: именно так теряются картинки, и замечают это глазами через неделю после выката;
- файла нет на диске — та же ошибка `E007`, что и для любого объявленного файла;
- работает и для файлов, которые движок не обрабатывает: PDF, ролик, архив.

### 7.5 Видео

```yaml
video: media/video/obzor.mp4
video_poster: media/video/obzor-poster.jpg
video_title: "Обзор мастерской"
```

В шаблон это приходит готовым объектом `page.video` с полями `src`, `poster`, `title` и `external`. Тема не разбирает схемы адресов сама: сегодня это свой файл, завтра сторонний хостинг, и каждая тема училась бы этому заново.

- значением `video` может быть внешняя ссылка — различается по схеме адреса. Локальный путь отдаётся файлом, полный адрес — вставкой стороннего плеера. Список площадок не зашит;
- `video_poster` **обязателен** при локальном файле, иначе `E019`. Без постера браузер тянет первый кадр, то есть грузит видео до того, как посетитель нажал «играть»; на мобильном интернете это десятки мегабайт за просмотр страницы, которую пролистали дальше. У стороннего плеера свой постер — там ничего не требуется;
- видео не перекодируется и не режется, копируется как есть. Проверяется наличие файла и наличие постера;
- нет поля `video` — `page.video` пустой, и блок не рисуется;
- секция `{#video}` в контенте даёт подпись и описание, сам файл берётся из фронтматтера.

### 7.6 Иллюстрация вписывается, фотография кропается

**В репозитории лежит один файл на сущность — мастер любого соотношения
с прозрачным фоном.** Движок вписывает его в каждое соотношение, которое
просит тема, и добивает прозрачными полями до нужного размера:

```
4:3    мастер, лежит в media/ — соотношение любое
16:9   карточка в каталоге и на главной — вписывается, поля прозрачные
1:1    квадратный слот — вписывается, поля прозрачные
```

Кроп иллюстраций запрещён. Фотографии — портреты, интерьеры, работы —
режутся центральным кропом, как раньше: у них нет альфа-канала, и поля им
взять неоткуда. Признак один: есть альфа — вписываем, нет — кропаем. Тема
вправе назвать исключения явно.

Предупреждения «объект упирается в край мастера» больше нет: при вписывании
это перестало быть проблемой.

**Почему так.** Квадратный мастер с запасом по краям — требование, которое
иллюстраторы не выполняют: рисунок почти всегда доходит до границы кадра,
и любой центральный кроп его срезает. Перерисовывать файлы под каждую
пропорцию дороже, чем вписывать, а вписывание даёт тот же результат без
запаса по краям.

### 7.7 Прозрачность и темы

Иллюстрации хранятся **с альфа-каналом** (PNG или WebP) и кладутся на подложку, которую даёт тема. Следствия:

- **JPEG для иллюстраций запрещён** — нет альфы, белая плашка останется намертво и в тёмной теме будет светиться прямоугольником. JPEG остаётся только для фотографий
- **Заливать фон в цвет темы нельзя** — это тот же прямоугольник, просто в цвет
- Белый фон допустим только как промежуточный этап генерации: модели проще нарисовать чистый контур на плоском фоне, чем сразу выдать корректную альфу. В репозиторий уходит вырезанное
- Второй файл под тёмную тему не делается. Одно изображение работает в обеих, если тело объекта светлое, а контур средней светлоты: тёмный контур на тёмном фоне даёт около 2:1 по контрасту, и силуэт расплывается. Конкретные тона задаёт документ темы, а не этот
- Подложка под иллюстрацией всегда нейтральная. Карточка в цвет объекта съедает силуэт
- Фотографии в тёмной теме не инвертируются и не затемняются фильтром

### 7.8 static — запасной выход, а не вторая папка для картинок

`static/` копируется в `dist/` **байт в байт по тому же пути**: без обработки, без проверок и без упоминания в контенте. Это её единственное назначение и единственная причина существования.

Она нужна файлам, которые обязаны лежать по точному адресу и которые движок трогать не должен:

- подтверждение прав вебмастера,
- `.well-known/security.txt`,
- `ads.txt`, проверочные файлы платёжных систем,
- `site.webmanifest`, favicon.

**Картинкам, видео и документам там не место** — их дом `media/`, где они получают проверку на существование, варианты под брейкпоинты и внятную ошибку при опечатке. **Оформлению сайта** — логотипу, иконкам интерфейса, шрифтам — тоже не место: их дом `theme/assets/`, потому что это часть темы, а не контента.

Правило держится не на честном слове: `heron check` называет файл с расширением картинки или видео, найденный в `static/`, и предлагает перенести его в `media/`. Без этого через полгода там снова окажутся фотографии — положить файл в обход обработки всегда быстрее, чем объявить его в контенте.

**Пустая `static/` — нормальное состояние сайта.** У большинства сайтов там не лежит ничего.

### Чего тема ждёт от движка

Тема живёт в репозитории сайта и обновляется отдельно от движка. Поэтому
она объявляет свои требования к нему прямо в `theme.yaml`:

```yaml
heron: ">=0.1"          # версия движка, на которую рассчитана тема
fields: [nav_title]     # поля фронтматтера, к которым обращаются шаблоны
```

Движок проверяет это на первом этапе, до обхода контента. Несовпадение —
одна ошибка `E012` с именем темы и списком полей, а не по ошибке на каждую
страницу с бесполезной подсказкой «опечатка во фронтматтере».

Оба ключа необязательны. Тема, не объявившая ничего, собирается как
раньше — до первого расхождения, которое тогда вылезет при рендере.

## 8. `.env`

**Сборке секреты не нужны ни одного.** Она идёт без сети и читает только файлы сайта. `.env` принадлежит сервисам — `heron-relay`, позже админке — и в контейнер сборки не монтируется никогда.

Файл закладывается сразу, чтобы потом не переделывать.

```
SMTP_HOST=
SMTP_PORT=
SMTP_USER=
SMTP_PASSWORD=
TELEGRAM_BOT_TOKEN=
ADMIN_USER=
ADMIN_PASSWORD_HASH=
SESSION_SECRET=
DB_PATH=
```

Правила обращения:

- `.env` в `.gitignore` и в `.dockerignore`. В репозитории лежит `.env.example` с пустыми значениями
- монтируется **файлом**, не через `environment:` и не через `--env-file`: переменные окружения видны в `docker inspect` любому с доступом к сокету, смонтированный файл — нет
- читается в момент использования, не при старте
- монтируется только в тот контейнер, которому нужен. nginx про почту не знает
- пароль администратора хранится хешем, не открытым текстом
- секреты никогда не попадают в логи. Самая частая утечка — не взлом, а трейсбек при ошибке подключения

Отдельно: для отправки почты брать API-ключ почтового сервиса, а не SMTP-пароль от ящика. Утечка ключа — спам с домена. Утечка пароля от ящика — доступ ко всей переписке владельца.

## 9. Что генерируется, а что лежит руками

Генерируется движком в `dist/`, в репозитории отсутствует:

`sitemap.xml` (на многоязычном сайте — индекс и по файлу на язык) · `robots.txt` · `llms.txt` (на многоязычном — и по файлу на язык) · `404.html` · `redirects.map` для nginx · JSON-LD внутрь страниц · `hreflang` и канониклы · `feed.xml` когда появятся статьи.

Лежит руками в `static/`: favicon и его варианты · `site.webmanifest` · `.well-known/security.txt`.

`robots.txt`, положенный руками, через полгода начинает врать: адреса меняются, а файл — нет. С картой сайта, которую строит сторонний плагин, происходит то же самое.

## 10. Ограничения, которые нельзя нарушать

- **Никакого JavaScript для отображения контента.** Скрипты обслуживают только тему, куки-баннер, мобильное меню и аккордеон FAQ. Числа и текст обязаны быть в HTML: счётчик, который рисует скрипт, для робота стоит нулём
- **Одна страница — один H1**, иерархия заголовков без пропусков уровней
- **Пустой блок не выводится.** Заголовок без содержимого хуже отсутствующего
- **Факты не выдумываются.** Данные, которых заказчик не подтвердил, остаются отсутствующими и попадают в сводку долгов, а не заполняются правдоподобным текстом. Пустой блок лучше вымысла
- **Целевое действие доступно с любой страницы** — это требование темы, и тема отвечает за то, чтобы оно выполнялось на каждом шаблоне
