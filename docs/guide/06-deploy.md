# 06 · Сборка и выкладка

Как собрать сайт для прода, упаковать его в образ и вести несколько сайтов на разных версиях движка. Для того, кто выкладывает, — человека или агента-сборщика.

## Два выхода: папка или образ

| | Папка `dist/` | Образ nginx |
|---|---|---|
| Чем | `heron build` | `scripts/site.sh <сайт> image` |
| Что внутри | HTML, картинки, карты, `.heron-nginx.conf` | nginx-unprivileged, статика, конфиг под этот сайт |
| Куда | любой хостинг статики, свой nginx | любой хост с докером, k8s |
| 301, 410, своя 404 | подключить `.heron-nginx.conf` в свой nginx | уже включены |

Выход выбирается командой, а не при создании сайта: одна и та же папка собирается и так, и так. → [`23` §5](../spec/23-distribution.md#5-два-выхода-папка-и-образ)

## Окружение сайта

Дев и прод — это **флаг сборки**, а не другой образ движка:

| | `--env dev` (по умолчанию) | `--env prod` |
|---|---|---|
| индексация | закрыта: `noindex` и `Disallow: /` | открыта |
| счётчики из `analytics` | нет | есть |
| метка сборки (версия, время, коммит) | тема может показать | не показывается |

`--strict` превращает предупреждения в ошибки — для прода обязателен. Перебить по отдельности: `SITE_INDEXABLE=false`, `SITE_ANALYTICS=false` — прод-подобное превью, закрытое от поисковиков.

**Домен по окружению.** Дев-сборка на своём адресе должна ссылаться на себя, а не на боевой домен. Для этого в `site.yaml`:

```yaml
site:
  domain: example.com          # боевой
  domains:
    dev: dev.example.com       # canonical, sitemap, hreflang, robots — на этот адрес в дев-сборке
```

Имя окружения то же, что в `--env`: один рычаг управляет и индексацией, и доменом.

## Один сайт

```bash
H="docker run --rm -v $PWD:/site -w /site --user $(id -u):$(id -g) ghcr.io/fmstm/heron:prod"
$H build мой-сайт --env prod --strict
```

`мой-сайт/dist/` — готовый сайт. Пересборка в ту же папку убирает то, чего больше нет (удалённые и снятые страницы, старые адреса), и не трогает чужие файлы; неудачная или строгая сборка с предупреждениями не меняет в `dist/` ничего — там остаётся прошлая удачная версия. `static/` не может молча заменить сгенерированный файл (`E026`); если `robots.txt` нужен свой — `build.overrides: [robots.txt]`. Залейте папку на хостинг статики (тогда 301/410 настраиваются средствами хостинга по `dist/redirects.map` и `dist/gone.map`) или отдайте своим nginx — ниже.

### Свой nginx на сервере

`dist/.heron-nginx.conf` — готовый `server {}` вместе с картами 301/410. Он подключается **в контекст `http`**, как любой файл сайта. Пример для Debian/Ubuntu с nginx из apt:

```bash
sudo cp -r мой-сайт/dist /var/www/мой-сайт
sudo cp мой-сайт/dist/.heron-nginx.conf /etc/nginx/sites-enabled/мой-сайт.conf
# в файле поправьте root на /var/www/мой-сайт и listen/server_name под свой хост
sudo nginx -t && sudo systemctl reload nginx
```

**301 и 410 различают регистр.** Каждый старый адрес — отдельный `location = "/старый/" { return 301 "/новый/"; }`, префикс из `gone` — `location ^~`. Так `/About/` и `/about/` остаются разными адресами, как и везде в движке: строковые карты `map` сравнивают без учёта регистра и превращали `redirect_from: /Page/` в редирект `/page/` на саму себя. Хэш-таблиц у точных location нет, поэтому `map_hash_bucket_size` вписывать не нужно ни в файл сайта, ни в `nginx.conf` хоста; ключ `nginx.hash_sizes` в `site.yaml` устарел и ничего не делает. Регулярные карты остались только для адресов с параметром (`/?p=*`) и для битых percent-адресов.

**Скрытые файлы** (`/.git/…`, `/ru/.env`, `/media/.x`) отвечают 404 в корне, под каждым языком, в `media/` и `assets/`; доступна только `/.well-known/`.

Если nginx есть на машине, где идёт сборка, движок сам прогоняет `nginx -t` на собранном конфиге и пишет результат в отчёт; не прошёл — предупреждение, при `--strict` — ошибка.

Посмотреть локально — `heron serve мой-сайт` (в образе: `docker run --rm -p 8000:8000 -v "$PWD":/site -w /site ghcr.io/fmstm/heron:beta serve .` — в контейнере просмотр сам слушает все интерфейсы, `--host 0.0.0.0` можно не писать): та же 404, что увидит посетитель, сборка во временную папку, папка сайта не пачкается. 301 и 410 `serve` не изображает — их проверяет `smoke` на образе.

## Образ из репозитория сайта

Сайт обычно живёт в своём репозитории, и клона HERON рядом нет. Образ собирает переиспользуемый workflow HERON — свой Dockerfile писать не нужно:

```yaml
# .github/workflows/image.yml в репозитории сайта
name: image
on:
  push:
    branches: [main]

jobs:
  image:
    uses: FMSTM/HERON/.github/workflows/site-image.yml@prod
    permissions:
      contents: read
      packages: write
    with:
      env: dev          # dev или prod
      engine: prod      # тег движка: prod, beta или 0.1.0
```

Workflow соберёт сайт движком из образа, упакует `dist/` в nginx по рецепту той же версии HERON, поднимет образ, прогонит дымовую проверку и отправит его в `ghcr.io/<владелец>/<репозиторий>:<окружение>`. Параметры: `path` — папка сайта внутри репозитория, `image` и `tag` — своё имя образа, `strict` — `true`/`false` (по умолчанию строгая только prod), `push: false` — собрать и проверить без отправки. Пока бета не стала продом, звать `@beta` с `engine: beta`.

## Несколько сайтов: `scripts/site.sh`

Из клона репозитория движка:

```bash
git clone https://github.com/FMSTM/HERON.git && cd HERON
HERON_NOTES=ru ./scripts/site.sh мойсайт new ~/sites/мой-сайт
```

`new` создаёт папку сайта — в терминале с теми же вопросами, что и `heron new`, — и заводит `env/.env.мойсайт.dev` и `.prod`. Папка может уже существовать и быть под git. Дальше всё — одной командой:

```bash
./scripts/site.sh мойсайт check dev     # отчёт без сборки
./scripts/site.sh мойсайт build dev     # → out/мойсайт-dev
./scripts/site.sh мойсайт serve dev     # nginx на localhost:$PORT
./scripts/site.sh мойсайт stop          # погасить просмотр
./scripts/site.sh мойсайт build prod
./scripts/site.sh мойсайт image prod    # образ IMAGE_NAME:IMAGE_TAG
./scripts/site.sh мойсайт smoke prod    # поднять образ, проверить коды
./scripts/site.sh мойсайт push prod     # в REGISTRY
./scripts/site.sh мойсайт init          # достроить папку после правки site.yaml
```

Папка контента монтируется **только на чтение**: всё, что производит сборка, живёт в `out/`, контент ничем не пачкается. Прошлый результат в `out/` перед сборкой не стирается: неудачная сборка оставляет там прошлый рабочий сайт, а устаревшее удачная сборка убирает сама. Скрипт работает и в bash 3.2 (macOS по умолчанию), и без терминала.

Коды выхода `heron build`: 0 — собрано; 1 — ошибка, `dist/` не тронут; 3 — сайт записан, но упало завершающее действие плагина (`on_build_finished`).

Настройки сайта — `env/.env.<сайт>.<окружение>`, в гит не попадают. Образец с пояснениями — [`env/.env.example`](../../env/.env.example):

| Переменная | Что задаёт |
|---|---|
| `SITE_PATH` | путь к папке сайта |
| `SITE_ENV` | `dev` или `prod` — каким будет сайт |
| `STRICT` | строгая сборка |
| `ENGINE` | каким движком собирать (ниже) |
| `IMAGE_NAME`, `IMAGE_TAG` | имя образа сайта |
| `REGISTRY`, `REGISTRY_CONFIG` | реестр для `push` и докер-конфиг для него; пусто — `push` запрещён |
| `PORT` | порт просмотра |
| `HERON_NOTES` | язык комментариев и записок, которые кладёт `init`: `ru` или `en` |

Секреты форм (SMTP, вебхуки) сюда не кладутся: сборка статическая, всё, что она видит, может оказаться в HTML.

## Дымовой прогон

`site.sh <сайт> smoke <окружение>` поднимает собранный образ и сверяет ответы (саму проверку делает `scripts/smoke-site.sh` — тот же скрипт зовёт workflow образа сайта):

- корень и `robots.txt` — 200, несуществующий адрес — 404;
- каждый язык из конфига сборки — 200 и своя 404;
- скрытые файлы и служебные (`.heron-nginx.conf`, `.heron-manifest.json`) — 404 в корне, под языками, в `media/` и `assets/`;
- **каждый** адрес из `redirects.map` — 301 туда, куда объявлено, и цель отвечает 200 сама, без второго редиректа;
- **каждый** точный адрес из `gone.map` — 410.

Упал — контейнер гасится, логи nginx печатаются. → [`23` §5, «Проверки и дымовой прогон»](../spec/23-distribution.md#проверки-и-дымовой-прогон)

## Версии движка

**Сайт закрепляет движок сам** — первой строкой `site.yaml`:

```yaml
heron: ">=0.1,<0.2"
```

Движок не из диапазона откажется собирать (`E012`). Обновление движка для сайта — смена этой строки, осознанно и по одному сайту.

**Каким движком собирает `site.sh`** — `ENGINE` в env-файле:

| Значение | Когда |
|---|---|
| пусто | точная версия из `site.yaml`, если она там точная; иначе исходники рядом; иначе `:prod` |
| `ghcr.io/fmstm/heron:prod` | стабильный — обычный выбор |
| `ghcr.io/fmstm/heron:0.1.0` | закрепиться на версии |
| `source` | собрать из исходников рядом — только когда правите сам движок |

**Теги образа движка:**

| Тег | Что это |
|---|---|
| `:X.Y.Z` | точная версия, не меняется никогда |
| `:prod` | то, на чём стоят сайты |
| `:beta` | обкатка следующей версии на живых сайтах |
| `:dev` | разработка движка; для сайтов не предназначен |

Какой образ на руках, показывает `--version`: ветка, коммит и время сборки, например `heron, version 0.1.0 (beta, 55249f0, 2026-10-08 19:12 UTC)`. Номер версии один на всю ветку разработки, а по коммиту видно, свежая ли бета. Из исходников — `(source, <коммит>)`.

Подвижного `:X.Y` нет намеренно: сайт должен иметь возможность закрепиться на том, что не поедет под ним завтра.

## Чек-лист перед выкладкой

1. `site.yaml`: домен, языки, `heron:` с диапазоном, счётчики.
2. `build --env prod --strict` проходит без ошибок.
3. Сводка «Не заполнено» пуста или осознанно принята.
4. `smoke prod` зелёный: 200, 404, все 301 и 410.
5. После выкладки — карта сайта в Search Console.
