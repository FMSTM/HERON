# HERON: инструкция для агента

Эта папка — для того, кто получил задачу «собери сайт на HERON» или «спроектируй сайт на HERON» и ссылку на этот репозиторий. Код движка читать не нужно: всё, что сайту можно и нельзя, описано в документации. Если документация и поведение движка расходятся — это ошибка движка, её надо записать в отчёт, а не обходить.

## Два сценария

| Что у тебя на входе | Что нужно на выходе | Документ |
|---|---|---|
| Структура контента (дерево страниц, типы, секции) и, возможно, тексты | Рабочая папка сайта: `site.yaml`, контент, тема; сборка без ошибок | [`build-site.md`](build-site.md) |
| Отчёт о старом сайте (как был устроен, какие страницы, адреса, что работало) и/или сам старый сайт | Структура контента, черновик `site.yaml` и `theme.yaml`, таблица старых адресов, список вопросов заказчику | [`plan-site.md`](plan-site.md) |

Перед тем как предложить доработку движка, сверься с [`capabilities.md`](capabilities.md): там перечислено, чем закрывается каждая типичная потребность сайта. Почти всё, что нужно сайту услуг, блогу или справочнику, уже есть.

## Какой движок брать

| Ситуация | Движок |
|---|---|
| Сайт в работе, обычный случай | образ `ghcr.io/fmstm/heron:prod` |
| Сайт обкатывает бету движка | `ghcr.io/fmstm/heron:beta` |
| Нужна неподвижная версия | `ghcr.io/fmstm/heron:X.Y.Z` |
| Нет докера | `pip install git+https://github.com/FMSTM/HERON.git@prod` (или `@beta`), команда `heron` |
| Несколько сайтов на одной машине | клон этого репозитория и `scripts/site.sh` (README, «Если сайтов несколько») |

Сайт объявляет требуемую версию первой строкой `site.yaml`: `heron: ">=0.1,<0.2"`. Чужую версию движок собирать откажется (`E012`).

Проверить, что движок на месте: `docker run --rm ghcr.io/fmstm/heron:prod --version`.

## Правила, которые нельзя нарушать

1. **Факты не выдумываются.** Телефоны, адреса, цены, сроки, имена, номера лицензий, цифры «400+ дел» — только из источника, который дал заказчик. Нет факта — поле или секция остаётся пустой, а вопрос уходит в список вопросов. Пустой блок движок не рисует; выдуманный — рисует.
2. **`site.yaml` — единственная точка правды.** Языки, тема, домен, меню, счётчики, 410 — там. Флагов «язык» и «тема» у команд нет.
3. **Папка сайта = только контент.** Dockerfile, compose, `build.sh`, `.env` в неё не кладутся. Сборка и упаковка — командами движка и `scripts/site.sh`.
4. **Ключ страницы — путь файла, адрес — `slug`.** Файлы называются одинаково во всех языках; разные адреса языков задаются полем `slug`. Ссылки в тексте и в `nav` пишутся ключами.
5. **Структура важнее разметки.** Тема раскладывает секции по якорям; порядок секций в файле не важен. Форма секции (`kind`) определяется её разметкой — см. таблицу форм.
6. **Предупреждение — это работа, а не шум.** Сборка с предупреждениями проходит, но каждое предупреждение — либо долг контента (в список долгов), либо ошибка (исправить). `--strict` превращает их в ошибки — так собирается прод.
7. **Не правь движок из сайта.** Если чего-то не хватает — оформи задачу на движок (шаблон в `plan-site.md`), а на сайте оставь самый простой честный вариант.

## Шаблоны

- [`templates/site.yaml`](templates/site.yaml) — все ключи ядра с пояснениями;
- [`templates/theme.yaml`](templates/theme.yaml) — типы, секции, связи, картинки;
- [`templates/page.md`](templates/page.md) — фронтматтер страницы, восемь групп;
- [`templates/structure.md`](templates/structure.md) — форма документа «структура сайта», результат сценария планирования.

Все четыре проверяются тестами движка: `site.yaml` и `theme.yaml` проходят валидацию, `page.md` разбирается. Если шаблон устарел — тесты движка упадут раньше, чем ты его возьмёшь.
