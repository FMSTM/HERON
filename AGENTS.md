# HERON для агентов

Это единая инструкция для агента, который получил ссылку на этот репозиторий и задачу про сайт. Код движка читать не нужно: всё, что сайту можно и нельзя, описано в документации. Расходятся документация и поведение движка — это ошибка движка: записать в отчёт, не обходить.

**Нет клона репозитория — та же документация есть в образе, ровно той версии, что и движок:**

```bash
docker run --rm ghcr.io/fmstm/heron:prod docs                     # оглавление
docker run --rm ghcr.io/fmstm/heron:prod docs architect           # тема целиком
docker run --rm ghcr.io/fmstm/heron:prod docs --search "E023"     # поиск: файл, строка, контекст
docker run --rm -v "$PWD":/site -w /site --user $(id -u):$(id -g) \
  ghcr.io/fmstm/heron:prod docs --export .heron-docs              # папкой, ссылки работают
```

Ссылки ниже — пути в репозитории; в выгрузке `--export` они те же.

## Что такое HERON — за минуту

HERON — движок статических сайтов, образ `ghcr.io/fmstm/heron:<тег>` (или pip-пакет, команда `heron`). Он **создаёт** папку сайта (`new`, `init`, `page`) и **собирает** её по контракту (`build`, `check`, `serve`).

Сайт — папка без кода движка: `site.yaml` (единственный конфиг), `content/<язык>/` (страницы в markdown), `media/`, `data/`, `static/`, `theme/`. Страница = файл, путь файла = адрес. Каждый файл начинается с SEO-блока из восьми групп, дальше — вступление и секции `## Заголовок {#якорь}`. Тема ставит секции на места по якорям.

Если ты видишь HERON впервые, прочитай [`docs/guide/01-concepts.md`](docs/guide/01-concepts.md) — семь понятий, на которых стоит всё остальное.

```bash
H="docker run --rm -v $PWD:/site -w /site --user $(id -u):$(id -g) ghcr.io/fmstm/heron:prod"
$H new мой-сайт --notes ru --name "Сайт" --domain example.com --lang en,ru -y   # без вопросов
$H check мой-сайт              # отчёт без сборки
$H build мой-сайт --env prod --strict
```

## Роли

Работа над сайтом делится на четыре роли. Один агент может пройти их все подряд, а может получить только одну — тогда он работает в её границах и передаёт результат дальше.

```
 Архитектор ──▶ структура, site.yaml, типы ──┬──▶ Дизайнер ──▶ тема ──────┐
                                             └──▶ Контент и SEO ──▶ страницы ┴──▶ Сборщик ──▶ сайт, образ, отчёт
```

| Задача на входе | Роль | Подробно |
|---|---|---|
| «Вот старый сайт / отчёт о нём — спроектируй новый» | Архитектор | [`docs/agents/architect.md`](docs/agents/architect.md) |
| «Напиши страницы», «перенеси тексты», «поправь SEO», «добавь перевод» | Контент и SEO | [`docs/agents/content.md`](docs/agents/content.md) |
| «Сделай тему», «сверстай по макету», «добавь тип страницы» | Дизайнер | [`docs/agents/designer.md`](docs/agents/designer.md) |
| «Собери сайт по структуре», «выложи», «упакуй в образ» | Сборщик (и остальные роли по ходу) | [`docs/agents/builder.md`](docs/agents/builder.md) |

Прежде чем предлагать доработку движка — [`docs/agents/capabilities.md`](docs/agents/capabilities.md): почти всё, что нужно сайту, уже есть.

### Архитектор

**Цель.** Структура сайта, по которой остальные роли работают без новых вопросов.

**Вход.** Отчёт о старом сайте, выгрузка, sitemap, Search Console; или описание задачи заказчика.

**Выход.**
1. документ «структура сайта» по форме [`templates/structure.md`](docs/agents/templates/structure.md): дерево страниц, ключи, типы, секции по типам, языки;
2. черновик `site.yaml` ([образец](docs/agents/templates/site.yaml)) и разделы `types`/`links` для `theme.yaml` ([образец](docs/agents/templates/theme.yaml));
3. таблица переноса: старый адрес → ключ → новый адрес по языкам → 301 или 410;
4. вопросы заказчику — с вариантами и рекомендацией.

**Читать.** [`capabilities.md`](docs/agents/capabilities.md), гайды [01](docs/guide/01-concepts.md) и [05 «переезд»](docs/guide/05-seo.md), контракт [`20`](docs/spec/20-data-contract.md) §2–3, §5–6.

**Правила.** Структура строится из возможностей движка, а не из устройства старого сайта. Тип оправдан своей раскладкой. Страница в нескольких разделах — плоско и связями. Задача на движок — только если потребности нет в `capabilities.md`.

**Готово, когда:** у каждой страницы есть ключ, тип и язык; у каждого типа — список секций с формами; у каждого старого адреса — решение 301/410; каждое решение ссылается на раздел документации.

### Контент и SEO

**Цель.** Страницы, которые собираются без ошибок, и SEO-блок, заполненный по делу.

**Вход.** Структура от архитектора (или существующий сайт), тексты и факты от заказчика.

**Выход.** Файлы `content/<язык>/…md`, картинки в `media/`, данные в `data/`, `redirect_from` у страниц, список долгов контента и вопросов.

**Читать.** Гайды [03 · Страницы и контент](docs/guide/03-content.md) и [05 · SEO](docs/guide/05-seo.md); образец страницы [`templates/page.md`](docs/agents/templates/page.md); контракт [`20`](docs/spec/20-data-contract.md) §4.

**Правила.** Новая страница — `heron page <тип> <имя>` или копия готового файла; SEO-блок не сокращается, комментарии не удаляются. `title` ≠ `h1`. Ссылки на свои страницы — ключом от корня, без языкового префикса. Нет материала — секции нет. Контакты и реквизиты — в `site.yaml`, не в тексте.

**Готово, когда:** `check` без ошибок; у каждой страницы заполнены `title`, `h1`, `description`; у картинок есть `alt`; сводка «Не заполнено» перенесена в отчёт.

### Дизайнер

**Цель.** Тема, которая рисует все типы страниц из структуры и не ломается на неполном контенте.

**Вход.** Типы и секции от архитектора, макет или описание вида.

**Выход.** `theme/`: `theme.yaml`, шаблон на каждый тип, модуль на каждую форму, `i18n/<язык>.yaml`, стили.

**Читать.** Гайд [04 · Тема и дизайн](docs/guide/04-theme.md); контракт [`20`](docs/spec/20-data-contract.md) §4.4, §6–7; движок [`21`](docs/spec/21-engine.md) §6–7.

**Правила.** Шаблон не содержит текстов контента и данных сайта: тексты — в секциях, реквизиты — `site.*`, строки интерфейса — `t.*`. Секции выводятся через `mod.<модуль>('<якорь>')`, без условий вокруг. Картинки — только через `picture()`.

**Готово, когда:** у каждого типа из `types` есть шаблон; у каждой формы из `uses` — модуль; сборка на стартовом и на полном контенте проходит; в отчёте нет недостающих строк `i18n`.

### Сборщик

**Цель.** Сайт, который собирается `--env prod --strict` и отвечает правильными кодами.

**Вход.** Структура, `site.yaml`, тема и контент — или задача «собери по структуре», тогда сборщик ведёт остальные роли сам.

**Выход.** Рабочая папка сайта; `dist/` или образ; отчёт: что сделано, долги контента, вопросы, оставленные предупреждения.

**Читать.** Гайды [02 · Первый сайт](docs/guide/02-first-site.md) и [06 · Сборка и выкладка](docs/guide/06-deploy.md); коды ошибок — [`21`](docs/spec/21-engine.md) §11.

**Правила.** `site.yaml` — единственная точка правды: флагов «язык» и «тема» у команд нет. В папку сайта не кладутся Dockerfile, compose, `.env`. Предупреждение — либо долг контента, либо ошибка, не шум.

**Готово, когда:** `build --env prod --strict` проходит; `smoke prod` зелёный; отчёт сдан.

## Общие правила для всех ролей

1. **Факты не выдумываются.** Телефоны, адреса, цены, сроки, имена, номера, цифры — только из источника заказчика. Нет факта — поле пустое, вопрос в список. Пустой блок движок не рисует; выдуманный — рисует.
2. **`site.yaml` — единственная точка правды** о сайте: языки, тема, домен, меню, счётчики, 410.
3. **Папка сайта — только контент.** Сборка и упаковка — командами движка и `scripts/site.sh`.
4. **Ключ страницы — путь файла, адрес — `slug`.** Имена файлов одинаковы во всех языках; ссылки и меню пишутся ключами.
5. **Структура важнее разметки.** Порядок секций в файле не важен; форму секции задаёт её разметка.
6. **Предупреждение — работа.** `--strict` превращает их в ошибки — так собирается прод.
7. **Движок не правится из сайта.** Не хватает возможности — задача на движок (шаблон в [`architect.md`](docs/agents/architect.md)), на сайте — самый простой честный вариант.

## Если меняешь сам движок

Это репозиторий движка, а не сайта. `uv sync --group dev`, `./scripts/check.sh` перед каждым коммитом. Никаких имён сайтов, доменов, слагов и предметной лексики в коде, тестах и доках — проверяет `scripts/check-boundaries.sh`. Документация меняется в том же коммите, что и поведение.
