# 05 · SEO

Что HERON генерирует сам, что заполняете вы и как переехать со старого сайта, не потеряв выдачу. Для того, кто отвечает за поиск, — человека или агента контента и SEO.

## Что генерируется само

Ничего из этого не пишется руками и не лежит файлом — собирается на каждой сборке из страниц и `site.yaml`, поэтому не устаревает:

| Что | Откуда | Подробно |
|---|---|---|
| `<title>`, meta description, canonical | `title` + `seo.title_suffix`, `description`, адрес страницы | [`20` §4.2](../spec/20-data-contract.md#frontmatter) |
| Open Graph и Twitter | поля групп 3–4, иначе `title`/`description`/`seo.og_default_image` | [`20` §4.2](../spec/20-data-contract.md#frontmatter) |
| `sitemap.xml` | все опубликованные индексируемые страницы, `lastmod` из `updated` | [`21` §9](../spec/21-engine.md#sitemap) |
| hreflang в `<head>` и в карте | переводы по имени файла, `x-default` — язык по умолчанию | [`20` §3](../spec/20-data-contract.md#languages) |
| `robots.txt` | `seo.robots_extra` + строка `Sitemap:`; на дев-сборке - только `Disallow: /` | [`21` §9](../spec/21-engine.md#robots-txt) |
| JSON-LD | тип от темы, данные от страницы и блока `schema` в `site.yaml`, крошки, FAQ | [`21` §9](../spec/21-engine.md#json-ld) |
| `llms.txt`, `llms-full.txt` | дерево страниц, `description`, `seo.llms_note` | [`21` §9](../spec/21-engine.md#llms-txt) |
| 301 и 410 | `redirect_from` страниц и `gone` в `site.yaml`, сразу в конфиг nginx | [`21` §9](../spec/21-engine.md#redirects) |
| картинка в выдаче | обложка страницы: `og:image`, `twitter:image`, `primaryImageOfPage` в JSON-LD, первая картинка записи в `sitemap.xml` - одна картинка во все места | [`20` §6, «Обложка страницы»](../spec/20-data-contract.md#page-cover) |
| крупные превью | `<meta name="robots" content="max-image-preview:large, max-snippet:-1, max-video-preview:-1">` на каждой индексируемой странице прод-сборки | [`21` §7](../spec/21-engine.md#cover-robots) |
| карта картинок | `<image:image>` в записи страницы: обложка первой, затем картинки из текста, не больше 20 | [`21` §9](../spec/21-engine.md#sitemap) |
| имя сайта | `WebSite` с `name` и `alternateName` на главной, из `site.name` и `site.alternate_names` | [`21` §9](../spec/21-engine.md#json-ld) |
| закрытая дев-сборка | без `--env prod`: `noindex` на всём, `Disallow: /`, без счётчиков | [`23`, «Версия движка и окружение сайта»](../spec/23-distribution.md#engine-version-vs-site-environment) |

## Что заполняете вы <a id="you-fill"></a>

**На каждой странице** — группа 1 SEO-блока:

- `title` — до 60 знаков, для выдачи. Суффикс сайта добавится сам;
- `h1` — для того, кто страницу уже открыл. Не копия `title`;
- `description` — до 155 знаков: что человек получит на странице;
- группа 2 «ключевые запросы» — движок её не читает, это рабочая записка: один интент — одна страница. Два файла с одним основным запросом — сигнал, что их надо слить.

Остальные группы — по надобности: своя картинка для соцсетей (3), уточнение разметки (5), картинка в каталоге и `alt` к ней (6), дата публикации, `noindex` (7), старые адреса (8).

**Один раз на сайт** — в `site.yaml`:

```yaml
site:
  domain: example.com
  name: Workshop
  name_ru: Мастерская        # значение для русских страниц
seo:
  title_suffix: " — Workshop"
  title_suffix_ru: " — Мастерская"
  og_default_image: media/og/default.jpg
  llms_txt: true
  llms_note:                 # факты о сайте для нейросетей, по языкам
    en: |
      Phone for bookings: …
    ru: |
      Телефон для записи: …
contact: { phone: "…", city: "…" }
organization: { name: "…" }
schema:
  entity:                    # сквозной узел: кто стоит за сайтом
    "@type": Organization
    name: "{{ organization.name }}"
    telephone: "{{ contact.phone }}"
analytics:
  ga4: G-XXXXXXX
```

`{{ … }}` в `schema` — подстановки из того же `site.yaml`: адрес и телефон живут в одном месте и не расходятся между вёрсткой и разметкой. → [`20` §5, «Блок schema»](../spec/20-data-contract.md#schema-block)

**Обложка.** Какую фотографию сделать обложкой, решаете вы; всё остальное движок делает сам.

- Берётся первая найденная: `og_image` страницы, затем `image`, затем первая картинка во вводном блоке или в `hero`, затем `seo.og_default_image` сайта. Подпись к картинке - `og_image_alt`, иначе `image_alt`.
- Размер: не меньше 1200 px по ширине. Меньше - отдаётся как есть, `heron check` предупреждает «обложка меньше 1200 px».
- Композиция: лицо или главный предмет в центральной трети кадра. Соцсети и выдача режут превью по-разному, края пропадают первыми.
- Обложка должна быть непрозрачной. Подложку движок не добавляет, прозрачный PNG у краулера окажется на чёрном или белом фоне.
- Обложки нет вообще - на странице нет `og:image` и `primaryImageOfPage`, `heron check` предупреждает. Это не ошибка сборки, но превью в мессенджере будет пустым.
- Если вы сами задали `primaryImageOfPage` или `entity.image` в блоке `schema`, ваше значение главнее вычисленного.

**Как ищут сайт.** `site.alternate_names` - другие написания названия: старое имя, транслитерация, сокращение. Для отдельного языка - `alternate_names_ru` и так далее.

```yaml
site:
  name: Workshop
  alternate_names: [Workshop Studio, Мастерская]
  alternate_names_ru: [Воркшоп]
```

Пустой список - ключа в разметке нет. Писать сюда стоит только то, как людей реально ищут и называют сайт, а не ключевые запросы.

**Цены в разметке** запрещены по умолчанию (`E020`): если сайт не показывает стоимость на страницах, она не должна утечь в JSON-LD. Разрешить — `seo.allow_prices: true`.

**Дата обновления.** `lastmod` и `dateModified` берутся из `updated` во фронтматтере, а если его нет — из источника `build.updated_from`: `git` (дата последнего коммита файла), `file` (время файла) или `manual` (только руками). Ручное `updated` сильнее источника: если вписать его всем страницам при переносе, git-даты работать перестанут. Отчёт после сборки покажет, у скольких страниц так вышло. Поисковику даты уходят полным ISO 8601 с поясом: из git — время коммита (`2026-10-17T11:30:12+02:00`), ручной день — полночь UTC (`2026-10-14T00:00:00+00:00`); на странице подпись остаётся датой. Дата из будущего и обновление раньше публикации — предупреждения, при `--strict` ошибки.

## Картинка и дополнительные ссылки в Google <a id="google-images-sitelinks"></a>

Честно о границах: движок готовит всё, что зависит от сайта, но показ решает Google.

- **Картинка в выдаче.** Разметка и карта картинок дают поисковику право показать картинку, а не обязательство. После выкладки обычно проходит 2-3 недели, пока она появится, а у части страниц не появится вовсе.
- **Что проверить в Search Console:**
  1. Rich Results Test (проверка расширенных результатов): вставьте адрес страницы, убедитесь, что разметка читается без ошибок и `primaryImageOfPage` на месте.
  2. «Проверка URL» -> «Запросить индексирование»: для главной и нескольких ключевых страниц после выкладки.
  3. Отчёт «Картинки» (в разделе эффективности поиска, тип поиска «Картинки»): через несколько недель там должны появиться показы.
- **Дополнительные ссылки (sitelinks) разметкой не включаются.** Специальной разметки для них нет, и движок её не придумывает. Google строит их сам. На это влияют: понятная навигация в HTML (меню из обычных ссылок), крошки, уникальные `title` у страниц, отсутствие дублей страниц и брендовый спрос, то есть сколько людей ищет сайт по названию. Первое под вашим контролем, последнее приходит со временем.
- **Крупные превью** (`max-image-preview:large`) включены в `<head>` сами. Отключается только закрытием страницы: `noindex: true`.
- **Дев-сборка.** Без `--env prod` страницы закрыты `noindex, nofollow`, картинок в `sitemap.xml` нет, адреса указывают на дев-домен. Проверять показ в Google на ней бессмысленно.

## Проверка разметки schema.org <a id="schema-check"></a>

Движок сверяет каждый узел вашей разметки со словарём schema.org 29.3, который лежит внутри него. Он ловит то, что поисковик потом молча проигнорирует: типа нет в словаре, свойство не подходит типу, значение не из перечисления, тип значения не тот, использовано устаревшее, картинка из разметки не попала в сборку. Это коды `SCH001`-`SCH006`, полный список - [`21` §11](../spec/21-engine.md).

**Прод и дев.** С `--env prod` находка - ошибка, сборка останавливается. В остальных окружениях это предупреждение: сайт собирается, но в отчёте строка с находкой. `heron check --env prod` покажет, что остановит боевую сборку, не собирая сайт.

**Как читать находку.** В отчёте строка вида `КОД файл:путь - причина (страниц: K)`: код говорит, что не так, файл и путь - где поправить, число страниц - сколько страниц это затронет. Одинаковая находка с разных страниц и языков приходит одной строкой. Под ней - «ключ исключения»: готовая строка, которую можно скопировать.

**Сначала исправьте.** Исключение нужно только тогда, когда исправить сейчас нельзя. Чаще всего правка - это замена свойства или типа, как в примере ниже.

**Как оформить исключение.** Запись в `site.yaml`, причина обязательна, срок по желанию:

```yaml
schema_exceptions:
  - key: "SCH002:site.yaml:schema.entity.worksFor"   # ключ скопирован из отчёта
    reason: "переход на practicesAt после смены темы"
    until: 2026-12-31                                  # необязательно
```

- без `reason` сборка остановится с `E011`, тот же ключ дважды - тоже `E011`;
- после даты `until` исключение перестаёт действовать, находка возвращается, отчёт пишет «Исключение просрочено»;
- исключение, которое ничего не поймало, отчёт назовёт лишним: уберите его;
- один раз, без правки файла: `heron check --allow-schema "<ключ>"` или то же у `heron build`;
- записанное анкетой исключение бессрочное: если такой ключ уже был (в том числе просроченный), причина заменяется, а срок `until` снимается; при необходимости поставьте срок руками.

**Анкета помогает.** `heron setup` перед записью `site.yaml` проверяет сквозной узел и блоки `schema` и показывает три списка: действующие находки, исключённые и просроченные. Находку можно убрать из файла или записать исключением, тогда анкета потребует причину.

### Пример: врач, было и стало

Все данные вымышленные. Раньше врача описывали как `Physician` и привязывали к клинике через `worksFor`:

```yaml
schema:
  entity:
    "@id": "#owner"
    "@type": Physician
    name: "Иван Образцов"
    worksFor:
      "@type": MedicalClinic
      name: "Клиника Образец"
    medicalSpecialty: "терапия"
```

Начиная с релиза 24.0 конкретный врач - `IndividualPhysician`. Это организационный тип, поэтому `worksFor` у него недопустим (`SCH002`). Место работы задаётся свойством `practicesAt` с типом из списка словаря, а специальность - только значением `MedicalSpecialty`, адресом вида `https://schema.org/<имя>`:

```yaml
schema:
  entity:
    "@id": "#owner"
    "@type": IndividualPhysician
    name: "Иван Образцов"
    practicesAt:
      "@type": MedicalClinic
      name: "Клиника Образец"
    medicalSpecialty: https://schema.org/Gastroenterologic
```

Свойство `practicesAt` в словаре пока числится в разделе pending: оно допустимо, отчёт лишь упомянет его как сведение. Если специальность записана произвольной строкой, это `SCH003`: значение не из перечисления. → [`20` §5, «Блок schema»](../spec/20-data-contract.md#schema-block)

## Языки

- Перевод — файл с тем же именем в папке языка; hreflang и переключатель языков появятся сами.
- У перевода может быть свой адрес (`slug`) — связь держится на имени файла.
- Один язык — нет hreflang, нет языковых карт и `llms-<язык>.txt`: лишнее не генерируется.
- Нет перевода — в отчёте предупреждение, в переключателе язык погашен; ссылки на такую страницу с других языков ведут на версию языка по умолчанию.
- Основной язык пуст — боевая сборка остановится (`E021`).

## Переезд со старого сайта <a id="migrate-from-old-site"></a>

Цель — ни один проиндексированный адрес не должен отдать 404.

1. **Выгрузите старые адреса.** Откуда взять список:
   - Search Console -> «Страницы» -> экспорт (CSV, движок берёт первый столбец, похожий на адрес);
   - старая карта сайта (`sitemap.xml`), адреса выпишите по строке;
   - выгрузка WordPress или логи сервера.

   Сохраните в файл `old-urls.txt`: по строке на адрес, строки с `#` и пустые пропускаются. Затем:

   ```bash
   heron check мой-сайт --old-urls old-urls.txt
   ```

   Каждый адрес должен вести на страницу, в `redirect_from` или в `gone`. Остальные попадут в предупреждения с предполагаемой целью:

   ```
   старый адрес /uslugi-dlya-primera/ никуда не ведёт; вероятно, поставить 301 на /ru/uslugi/: redirect_from: [/uslugi-dlya-primera/] во фронтматтере content/ru/uslugi.md
   старых адресов: 120, без пути: 7
   ```

   Закрыть предупреждение - добавить адрес в `redirect_from` указанной страницы (или другой, если цель угадана неверно) либо в `gone`, и запустить проверку снова: сводка должна дойти до «без пути: 0».

   **Адрес без языкового префикса.** Старые адреса обычно без `/ru/`, а в новом сайте у неосновного языка префикс есть. `/x/` и `/ru/x/` для сервера разные адреса, поэтому редирект с `/ru/x/` старый `/x/` не обслуживает. Пример: старая страница `/uslugi-dlya-primera/` (вымышленный слаг), новая живёт на `/ru/uslugi/`. Записывайте старый адрес ровно так, как он был, без префикса:

   ```yaml
   redirect_from:
     - /uslugi-dlya-primera/
   ```

   **Регистр.** `/About/` и `/about/` для сервера разные адреса: записывайте как в выгрузке. Адрес сравнивается так же, как его видит nginx: схема и хост отбрасываются, `%XX` и кириллица равны, со слешем и без - один адрес; параметры запроса учитываются только записями `gone` с параметром; повторы в файле считаются один раз.

Цель подбирается по последнему сегменту адреса, похожему на слаг или заголовок страницы. Не нашлось - предлагается главная языка, и тогда решаете вы: либо подходящая страница, либо `gone`.
2. **Адрес переехал** — впишите его в SEO-блок новой страницы:

   ```yaml
   redirect_from:
     - /старая-страница/
     - /%D1%81%D1%82%D0%B0%D1%80%D0%B0%D1%8F/
   ```

   Кириллица и percent-encoding нормализуются: обе формы выше — один адрес, 301 сработает на любую, со слешем и без.
3. **Адреса больше нет** — в `gone` в `site.yaml`. Сервер ответит 410, и поисковик выкинет адрес быстрее, чем после 404:

   ```yaml
   gone:
     - /sample-page/        # ровно этот адрес
     - /wp/*                # всё под /wp/
     - /?p=*                # главная с параметром p
   ```

4. **Соберите.** Движок проверит, что старый адрес не совпадает с живой страницей, не ведёт в два места и не образует цепочку (`E009`), а 410 не пересекается со страницами и редиректами (`E022`).
5. **Проверьте на образе:** `scripts/site.sh <сайт> smoke prod` поднимает nginx и проверяет ответы 200, 404, каждый 301 и каждый 410 — [06 · Сборка и выкладка](06-deploy.md).

Подробно: [`20` §2, «Старые адреса»](../spec/20-data-contract.md#old-addresses-cyrillic), [`22` §6](../spec/22-deploy.md#migrate-existing-site).

## Перед выкладкой

```bash
heron build мой-сайт --env prod --strict
```

`--strict` превращает предупреждения в ошибки: битая ссылка, картинка без `alt`, незаполненная обязательная связь не уедут в прод. Отчёт сборки считает страницы по типам разметки — видно, что JSON-LD доехал до всех.
