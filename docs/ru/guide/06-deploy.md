# 06 · Сборка и выкладка

В этом разделе - как собрать сайт для публикации, выложить его на хостинг или свой сервер, упаковать в Docker-образ и вести несколько сайтов на разных версиях движка. Он для того, кто выкладывает сайт, - человека или AI-агента в роли сборщика.

> **Поставили движок без Docker?** Тогда в каждой команде всё, что стоит до имени образа (`ghcr.io/fmstm/heron:…`) включительно, замените словом `heron`. Подробнее - [в разделе об установке](00-install.md#without-docker).

Как и в [02 · Первый сайт](02-first-site.md), команды запускаются из папки, в которой лежит папка сайта `мой-сайт`.

## Два варианта результата: папка или образ

Собранный сайт можно получить в двух видах:

| | Папка `dist/` | Образ nginx |
|---|---|---|
| Чем собрать | `heron build` | `scripts/site.sh <сайт> image` |
| Что внутри | HTML, картинки, карты сайта, `.heron-nginx.conf` | nginx-unprivileged, статика, конфиг под этот сайт |
| Куда выложить | любой хостинг статики, свой nginx | любой сервер с Docker, k8s |
| 301, 410, своя 404 | подключить `.heron-nginx.conf` в свой nginx | уже включены |

Вариант выбирается командой сборки, а не при создании сайта: одна и та же папка сайта собирается и так, и так. Подробнее - [`23` §5](../spec/23-distribution.md#two-outputs).

## Черновая и боевая сборка

Черновая (dev) и боевая (prod) сборка - это **флаг команды сборки**, а не другой образ движка:

| | `--env dev` (по умолчанию) | `--env prod` |
|---|---|---|
| поисковики | сайт закрыт: `noindex` и `Disallow: /` | сайт открыт |
| счётчики из `analytics` | не подключаются | подключаются |
| метка сборки (версия, время, коммит) | тема может её показать | не показывается |

Флаг `--strict` превращает предупреждения в ошибки - для боевой сборки он обязателен. Каждое свойство можно перебить отдельно переменными окружения `SITE_INDEXABLE` и `SITE_ANALYTICS`. Передайте их внутрь контейнера флагом `-e`: переменная, заданная только в вашем терминале, до движка не дойдёт. Так получается превью, похожее на боевую сборку, но закрытое от поисковиков:

```bash
docker run --rm -e SITE_INDEXABLE=false -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build мой-сайт --env prod
```

**Свой домен для черновой сборки.** Черновая сборка, выложенная на отдельный адрес, должна ссылаться на этот адрес, а не на боевой домен. Для этого в `site.yaml`:

```yaml
site:
  domain: example.com          # боевой
  domains:
    dev: dev.example.com       # canonical, sitemap, hreflang, robots - на этот адрес в черновой сборке
```

Имя окружения в `domains` то же, что во флаге `--env`: один переключатель управляет и индексацией, и доменом.

## Один сайт

Боевая сборка одного сайта:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build мой-сайт --env prod --strict
```

Готовый сайт появится в `мой-сайт/dist/`. Что стоит знать об этой папке:

- **Пересборка в ту же папку** убирает то, чего на сайте больше нет (удалённые и снятые с публикации страницы, старые адреса), и не трогает чужие файлы.
- **Неудачная сборка** или строгая сборка с предупреждениями не меняет в `dist/` ничего - там остаётся прошлая удачная версия.
- **`static/` не может молча заменить сгенерированный файл** - это ошибка `E026`. Если нужен свой `robots.txt`, разрешите замену явно: `build.overrides: [robots.txt]`.

Коды выхода `heron build`:

- 0 - собрано;
- 1 - ошибка, `dist/` не тронут;
- 2 - неверные флаги или аргументы;
- 3 - сайт записан, но упало завершающее действие плагина (`on_build_finished`).

Дальше папку можно залить на любой хостинг статики. Тогда перенаправления 301 и ответы 410 настраиваются средствами хостинга по файлам `dist/redirects.map` и `dist/gone.map` (второй появляется, только если в `site.yaml` задан `gone`). Или отдайте папку своим nginx - об этом ниже.

### Свой nginx на сервере

В `dist/.heron-nginx.conf` лежит готовый блок `server {}` вместе с правилами 301 и 410. Он подключается **в контекст `http`** nginx, как конфиг любого сайта. Пример для Debian/Ubuntu с nginx, установленным через apt:

```bash
sudo mkdir -p /var/www/мой-сайт && sudo cp -r мой-сайт/dist/. /var/www/мой-сайт/
sudo cp мой-сайт/dist/.heron-nginx.conf /etc/nginx/sites-enabled/мой-сайт.conf
# в файле поправьте root на /var/www/мой-сайт и listen/server_name под свой хост
sudo nginx -t && sudo systemctl reload nginx
```

Первые две строки копируют сайт и его конфиг, третья - напоминание поправить пути и имя хоста в скопированном конфиге, последняя проверяет конфиг и перезагружает nginx.

**301 и 410 различают регистр букв.** Каждый старый адрес - отдельное правило `location = "/старый/" { return 301 "/новый/"; }`, префикс из `gone` - правило `location ^~`. Поэтому `/About/` и `/about/` остаются разными адресами, как и везде в движке.

Следствие: 301 и 410 срабатывают только при точном совпадении регистра. Запрос `/about/` при записи `/About/` получит 404 - и для латиницы, и для кириллицы. Если нужен и такой вариант адреса, добавьте его в `redirect_from` (или `gone`) отдельной строкой.

Настраивать `map_hash_bucket_size` и ключ `nginx.hash_sizes` в `site.yaml` больше не нужно: ключ устарел и ничего не делает.

**Скрытые файлы** (`/.git/…`, `/ru/.env`, `/media/.x`) отвечают 404 в корне, под каждым языком, в `media/` и `assets/`. Доступна только папка `/.well-known/`.

Конфиг включает HSTS на год вместе с поддоменами (заголовок `Strict-Transport-Security`) и служебный адрес `/healthz` для проверки, что сервер жив. Если домен ещё не работает по https или под ним есть поддомены без https, уберите все строки `add_header Strict-Transport-Security` - их в конфиге несколько, по одной на блок `location`. Подробности - в [`22`](../spec/22-deploy.md).

Если на машине, где идёт сборка, установлен nginx, движок сам прогоняет `nginx -t` на собранном конфиге и пишет результат в отчёт. Не прошёл - предупреждение, а со `--strict` - ошибка.

### Посмотреть локально

```bash
docker run --rm -it -p 127.0.0.1:8000:8000 -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod serve мой-сайт
```

Это тот же просмотр, что в шаге 2 первого сайта. В контейнере он сам слушает все интерфейсы, так что флаг `--host 0.0.0.0` писать не нужно. Просмотр показывает ту же страницу 404, что увидит посетитель, собирает сайт во временную папку и не пачкает папку сайта.

Чего просмотр не изображает: 301, 410 и закрытие скрытых файлов. Их проверяет дымовой прогон `smoke` - автоматическая проверка готового образа (о ней ниже), а `site.sh serve` поднимает настоящий nginx, где всё это работает.

## Образ из репозитория сайта

Обычно сайт живёт в своём репозитории на GitHub, и клона движка рядом нет. Docker-образ сайта собирает готовый переиспользуемый workflow HERON - свой Dockerfile писать не нужно. Добавьте в репозиторий сайта файл:

```yaml
# .github/workflows/image.yml в репозитории сайта
name: image
on:
  push:
    branches: [main]

jobs:
  image:
    uses: FMSTM/HERON/.github/workflows/site-image.yml@prod
    permissions:
      contents: read
      packages: write
    with:
      env: dev          # dev или prod
      engine: prod      # тег движка: prod, beta или X.Y.Z
```

На каждый push в `main` workflow соберёт сайт движком из образа, упакует `dist/` в nginx по рецепту той же версии HERON, поднимет образ, прогонит дымовую проверку и отправит образ в `ghcr.io/<владелец>/<репозиторий>:<окружение>`.

Что можно задать в `with:`:

| Вход | По умолчанию | Что делает |
|---|---|---|
| `env` | `dev` | окружение сборки |
| `engine` | `prod` | тег движка: `prod`, `beta`, `dev`, `X.Y.Z`, можно `@sha256:<digest>` |
| `path` | `.` | папка сайта внутри репозитория, без `..` |
| `image` | `ghcr.io/<владелец>/<репозиторий>` | имя образа сайта |
| `tag` | имя окружения | тег образа |
| `strict` | `auto` | `auto` - строго для `prod`; `true`/`false` |
| `nginx_image` | официальный образ nginx, закреплённый по digest | на нём `nginx -t` до сборки образа |
| `export_docs` | `false` | сырые файлы документации в `static/` |
| `push` | `true` | `false` - собрать и проверить без отправки |

Если в `engine` указана точная версия, рецепт образа и дымовая проверка берутся из тега `vX.Y.Z`. Тег `v0.1.0` выпущен до появления `scripts/smoke-site.sh`, поэтому с ним workflow не работает: используйте `prod` или `beta` либо версию новее.

Workflow отдаёт выход `image` - полное имя собранного образа с тегом.

Вход `export_docs` нужен только сайту самого движка. Перед сборкой тот же образ движка выкладывает в `static/` сайта сырые файлы документации этой версии - `agents/{ru,en}/**`, `schema/<major.minor>/*.json` и `AGENTS.md`; на запись при этом смонтирована только папка `static/`. Обычному сайту его включать не нужно ([`22` §4](../spec/22-deploy.md)).

Пока бета не вышла в prod, для беты вызывайте workflow как `@beta` вместе с `engine: beta`.

## Несколько сайтов: `scripts/site.sh`

Если вы ведёте несколько сайтов, удобнее работать из клона репозитория движка: там есть скрипт `scripts/site.sh`, который делает всё одной командой.

```bash
git clone https://github.com/FMSTM/HERON.git && cd HERON
mkdir -p ~/sites
HERON_NOTES=ru ./scripts/site.sh mysite new ~/sites/мой-сайт
```

Первая строка скачивает движок и переходит в его папку, вторая создаёт папку для сайтов, если её ещё нет. Третья создаёт сайт с именем `mysite` в папке `~/sites/мой-сайт`:

- в терминале `new` задаёт те же вопросы, что и `heron new`, и заводит файлы настроек `env/.env.mysite.dev` и `env/.env.mysite.prod`;
- папка сайта может уже существовать и быть под git;
- имя сайта в `site.sh` - латиница, цифры и дефис: из него собирается имя образа `heron-site-<сайт>`, а кириллицу Docker не принимает. Сама папка сайта может называться как угодно;
- в клоне `new` собирает образ движка из исходников, и `ENGINE` на это не влияет, поэтому первый запуск занимает время.

Дальше каждое действие - одна команда:

```bash
./scripts/site.sh mysite check dev     # отчёт без сборки
./scripts/site.sh mysite build dev     # → out/mysite-dev
./scripts/site.sh mysite serve dev     # образ nginx из out/ и просмотр на localhost:$PORT; сначала build
./scripts/site.sh mysite stop dev      # погасить просмотр
./scripts/site.sh mysite build prod
./scripts/site.sh mysite image prod    # образ IMAGE_NAME:IMAGE_TAG
./scripts/site.sh mysite smoke prod    # поднять образ, проверить коды
./scripts/site.sh mysite push prod     # в REGISTRY
./scripts/site.sh mysite init          # достроить папку после правки site.yaml
```

Папка сайта монтируется **только на чтение**: всё, что производит сборка, живёт в `out/`, и контент ничем не пачкается. Прошлый результат в `out/` перед сборкой не стирается: неудачная сборка оставляет там прошлый рабочий сайт, а устаревшие файлы удачная сборка убирает сама. Скрипт работает и в bash 3.2 (стоит в macOS по умолчанию), и без терминала.

Настройки каждого сайта лежат в `env/.env.<сайт>.<окружение>` и в git не попадают. Образец с пояснениями - [`env/.env.example`](https://github.com/FMSTM/HERON/blob/prod/env/.env.example):

| Переменная | Что задаёт |
|---|---|
| `SITE_PATH` | путь к папке сайта |
| `SITE_ENV` | `dev` или `prod` - каким будет сайт |
| `STRICT` | строгая сборка |
| `ENGINE` | каким движком собирать (ниже) |
| `IMAGE_NAME`, `IMAGE_TAG` | имя образа сайта |
| `REGISTRY`, `REGISTRY_CONFIG` | реестр для `push` и докер-конфиг для него; пусто - `push` запрещён |
| `PORT` | порт просмотра |
| `HERON_NOTES` | язык справки, сообщений и комментариев в файлах: `ru` или `en` |

Секреты форм (SMTP, вебхуки) сюда не кладутся: сборка статическая, и всё, что она видит, может оказаться в HTML.

## Дымовой прогон

Команда `site.sh <сайт> smoke <окружение>` поднимает собранный образ и проверяет, что сайт отвечает как надо. Саму проверку делает `scripts/smoke-site.sh` - тот же скрипт вызывает и workflow образа сайта. Что проверяется:

- корень и `robots.txt` отвечают 200, несуществующий адрес - 404;
- каждый язык из конфига сборки отвечает 200 и отдаёт свою 404;
- скрытые и служебные файлы (`.heron-nginx.conf`, `.heron-manifest.json`) отвечают 404 в корне, под языками, в `media/` и `assets/`;
- **каждый** адрес из `redirects.map` отвечает 301 туда, куда объявлено, а цель сама отвечает 200, без второго редиректа;
- **каждый** точный адрес из `gone.map` отвечает 410.

Если проверка упала, контейнер останавливается и печатаются логи nginx. Подробнее - [`23` §5, «Проверки и дымовой прогон»](../spec/23-distribution.md#checks-and-smoke).

## Версии движка

**Сайт сам закрепляет, какой движок ему подходит**, - первым ключом `site.yaml`, `heron:`:

```yaml
heron: ">=0.3,<0.4"
```

Движок не из этого диапазона откажется собирать сайт (ошибка `E012`). Обновить движок для сайта - значит поменять этот ключ: осознанно и по одному сайту.

**Каким движком собирает `site.sh`**, задаёт переменная `ENGINE` в env-файле сайта:

| Значение | Когда |
|---|---|
| пусто | точная версия из `site.yaml`, если она там точная; иначе исходники рядом; иначе `:prod` |
| `ghcr.io/fmstm/heron:prod` | стабильный - обычный выбор |
| `ghcr.io/fmstm/heron:0.1.0` | закрепиться на версии |
| `source` | собрать из исходников рядом - только когда правите сам движок |

**Теги образа движка:**

| Тег | Что это |
|---|---|
| `:X.Y.Z` | точная версия, не меняется никогда |
| `:prod` | то, на чём работают сайты |
| `:beta` | обкатка следующей версии на живых сайтах |
| `:dev` | разработка движка; для сайтов не предназначен |
| `:latest` | последний релиз без суффикса (`vX.Y.Z`, но не `-rc`); для сайтов лучше точная версия |
| `:sha-<коммит>` | сборка конкретного коммита, например `sha-55249f0` |

Какой образ у вас на руках, показывает `--version`: ветка, коммит и время сборки, например `heron, version 0.1.0 (beta, 55249f0, 2026-10-08 19:12 UTC)`. Номер версии один на всю ветку разработки, а по коммиту видно, свежая ли бета. Движок, собранный из исходников, пишет `(source, <коммит>)`.

Подвижного тега `:X.Y` нет намеренно: сайт должен иметь возможность закрепиться на том, что завтра не поменяется у него под ногами.

### Переход сайта с 0.2 на 0.3 <a id="upgrade-0-3"></a>

Движок 0.3 строже к боевой сборке: страница, в которой остался текст заготовки `heron page` 0.2 (`TODO: что человек получит на странице` в `description`, «Вводный абзац - то, что попадёт в сниппет» в тексте), с `--env prod` не собирается - ошибка `E040` с файлом и полем. Так же не собирается сайт, в котором есть SVG с исполняемым содержимым или ссылкой на другой файл, - ошибка `E043` со списком файлов. Движок 0.2 такие сайты публиковал, поэтому проверьте сайт до того, как переключите его на 0.3.

1. **Разрешите сайту оба движка.** Первый ключ `site.yaml`: `heron: ">=0.2,<0.4"`. Так сайт собирается и движком 0.2, на котором он сейчас работает, и 0.3.
2. **Соберите сайт движком 0.3 в боевом режиме у себя.** Вторая команда ниже (образ `:beta` - движок 0.3, пока он не стал `:prod`). Сборка ложится во временную папку контейнера и никуда не выкладывается: нужен только список ошибок.
3. **Допишите страницы из списка `E040`.** Откройте каждую командой `page add` с её ключом (третья команда) и замените текст заготовки своим - или уберите секцию, которая не нужна.
4. **Поправьте SVG из списка `E043`.** Проверка - четвёртая команда (`check`): она называет каждый SVG в `media/`, `static/` и в теме, где есть скрипт, обработчик `on*`, инструкция `<?…?>`, DOCTYPE или то, что тянет другой файл (`url(…)` и `<use>` не на `#id` своего файла, `@import`, картинка по адресу). Сайт отдаёт такие файлы как есть, открытый по прямой ссылке файл выполнился бы в браузере - поэтому 0.3 не пускает их в прод. Откройте файл в редакторе и сохраните заново как простой SVG (Inkscape: «Сохранить как» → «Простой SVG»; Illustrator: «Экспорт» → SVG, без «Сохранить возможности редактирования Illustrator»), уберите скрипты и ссылки на чужие файлы - или замените картинку на PNG. Градиенты `url(#id)`, картинку внутри файла (PNG, JPEG, GIF, WebP) и обычные ссылки в `<a>` оставлять можно.
5. **Повторите шаг 2**, пока ошибок не останется, и только потом переключайте сайт на 0.3 (`ENGINE` в env-файле сайта или образ `:prod` после выпуска).

Папки без своей `_index.md`, которые делал 0.2 (`services/` для `--folder services`), в 0.3 работают как раньше. `check` советует сделать такую папку категорией - `heron category add services`. Спешить не нужно, но учтите: раздел, не переведённый на язык, не публикует на нём и страниц внутри. Поэтому `category add` спрашивает поля раздела на каждом языке, где в папке уже есть страницы, и предупреждает, какие переведённые страницы выпадут из prod, если перевод пропустить; без терминала (`-y`, `--answers` без ответа для этого языка) такой раздел не записывается - `E039`, пока вы не ответите за язык или явно не согласитесь (`<язык>: pending` в ответах). То же - когда новая страница или перенос делают такую папку разделом попутно. Если файлы языков одной страницы расходятся в общих полях (тип, порядок, обложка, публикация), `check` скажет об этом предупреждением: в 0.3 такие поля правятся на основном языке и пишутся во все файлы.

```bash
docker pull ghcr.io/fmstm/heron:beta
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:beta build . --env prod --out /tmp/heron-03
docker run --rm -it -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:beta page add services/roofing .
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:beta check .
```

Тему 0.2 тоже стоит перевести на контракт 0.3 - отдельный список в [07 · «Перенос темы с 0.2 на 0.3»](07-theme-author.md#migrate-0-3).

## Чек-лист перед выкладкой

1. В `site.yaml` заданы домен, языки, `heron:` с диапазоном версий и счётчики.
2. `build --env prod --strict` проходит без ошибок.
3. Сводка «Не заполнено» в отчёте пуста или вы осознанно её приняли.
4. `smoke prod` зелёный: 200, 404, все 301 и 410.
5. После выкладки карта сайта отправлена в Search Console.

## Если сайт собирает агент

Граница простая: **собирает агент, публикует человек.**

Агент запускает `check`, `build --env prod --strict`, при необходимости `serve`, читает отчёт и чинит то, что относится к его роли. Результат он сдаёт отчётом `agents/work/report.md` и списком вопросов `agents/work/questions.md`.

Публикация - не его дело: `.heron/scripts/publish.sh`, `docker push`, `site.sh push`, `git push` и merge выполняете вы, после того как прочитали отчёт и посмотрели diff. Так же не его - `Dockerfile`, compose, `.env`, токены и код в `plugins/`. Полный список границ - в [`roles/builder.md`](../roles/builder.md) и [`README.md`](../README.md) комплекта.
