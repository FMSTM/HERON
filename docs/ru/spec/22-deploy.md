# HERON - развёртывание сайта

**Статус:** действует для движка 0.1; раздел 2 описывает запуск без образа сайта, раздел 8 - не реализованное. История правок - в CHANGELOG и git.
**Документ 3 из 4.** Предыдущие: `20-data-contract.md`, `21-engine.md`. Следующий: `23-distribution.md`.

Работающие пути выкладки: образ сайта через `scripts/site.sh <сайт> image|smoke|push <окружение>` в репозитории движка (`23-distribution.md` §5) и переиспользуемый workflow `site-image.yml` в репозитории сайта (раздел 4). Дальше образ запускается как любой контейнер nginx. Готовая папка `dist/` тоже годится: её отдаёт любой nginx с конфигом `dist/.heron-nginx.conf`.

---

## 1. Что разворачиваем

Один сайт - одна папка и один репозиторий. В нём контент, данные, картинки, тема и конфиг. **Кода движка в нём нет**: движок приходит образом `ghcr.io/<owner>/heron:<версия>`.

Отсюда два следствия, определяющих весь деплой:

- обновление движка - это смена образа при сборке, а не мерж чужого кода в репозиторий сайта;
- откат движка - возврат прежнего образа.

`site.yaml` объявляет требование к движку, движок сверяет себя с ним и останавливается с `E012`. Какой образ собирает сайт, выбирает запускающий: вход `engine` у `site-image.yml`, `ENGINE` у `scripts/site.sh`. Без `ENGINE` скрипт берёт точную версию из `site.yaml`, если она записана как X.Y.Z, иначе исходники рядом со скриптом, иначе `ghcr.io/fmstm/heron:prod`. Диапазон версией не считается. Обновление и откат - смена этого значения.

## 2. Контейнеры

Два, оба лёгкие. Третий (`relay`) появляется только на сайтах с формами.

**Сборщик** - образ движка. Запускается разово, собирает сайт в `dist/` и завершается. Между сборками не работает и ресурсов не ест. Собирать его на целевой машине не нужно: он тянется из реестра.

**Веб** - nginx, отдаёт `dist/`. Единственный постоянно работающий процесс. Образ `nginxinc/nginx-unprivileged` - мастер-процесс не от рута, слушает 8080; наружу смотрит прокси.

Базы данных нет. Приложения нет. Отдавать статику - единственное, что делает сайт в проде.

Вариант без образа сайта. Этот файл лежит на сервере отдельно от репозитория сайта: Dockerfile, compose и `.env` в папке сайта запрещены (`20` §1). Путь к сайту задаётся в `volumes`.

```yaml
services:
  build:
    image: ghcr.io/OWNER/heron:0.1.0
    profiles: ["build"]              # не поднимается вместе с web
    user: "${UID}:${GID}"
    network_mode: "none"             # сборке сеть не нужна
    read_only: true
    tmpfs: ["/tmp"]
    cap_drop: ["ALL"]
    security_opt: ["no-new-privileges:true"]
    volumes:
      - /srv/site:/site             # путь к сайту на сервере
    command: ["build", "--strict"]

  web:
    # тот же digest, что в Dockerfile.site
    image: nginxinc/nginx-unprivileged:1.30.6-alpine@sha256:782bb89768cc87b7f95c18b95baa1af250e5d451f26794f59363540161147c01
    restart: unless-stopped
    volumes:
      - /srv/site/dist:/usr/share/nginx/html:ro
      # конфиг собирает движок: языки, 404, карты 301 и 410 уже внутри
      - /srv/site/dist/.heron-nginx.conf:/etc/nginx/conf.d/default.conf:ro
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/healthz"]
      interval: 30s
      timeout: 3s
      retries: 3
```

Запуск сборки: `UID=$(id -u) GID=$(id -g) docker compose --profile build run --rm build`.

`dist/` монтируется в nginx только на чтение. Сборщик пишет туда, веб только читает.

Сборщику не монтируется `.env`: секретов у сборки нет, она идёт без сети. Разбор модели безопасности - `23-distribution.md`, раздел 9.

## 3. Что на сервере

Сервер получает либо образ сайта (`23-distribution.md` §5), либо готовую папку `dist/`. Скриптов установки и выкладки, `deploy.conf` и `.env` в поставке нет: секретов у статического сайта нет, а то, что появится с relay, описано в разделе 8. Атомарная подмена каталога сборки - идея на будущее, см. раздел 8.

## 4. CI

Переиспользуемый workflow `site-image.yml` выполняет: сборку (`--strict` для `prod`), `nginx -t` на стоковом nginx, сборку образа, дымовую проверку кодов ответа, включая `redirects.map` и `gone.map` (каждый старый URL отдаёт 301 или 410), отправку в реестр. `heron check --strict`, Lighthouse и выкладку на сервер сайт добавляет отдельными job сам: готовых шагов для них движок не поставляет.

Дымовая проверка карты редиректов - не формальность. Это единственное, что защищает индекс при переезде со старой системы.

Тесты самого движка гоняются в CI **репозитория движка**, а не сайта: сайт потребляет готовый образ и не обязан знать, как тот собран.

**Что не попадает в образ сайта.** Контекст образа - собранный `dist/`, поэтому исходники сайта в нём отсутствуют физически: ни `.git`, ни мастера картинок, ни комплект для агентов (`agents/`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` - `20` §1). Проверять это отдельно в CI сайта не нужно - это свойство сборки, закреплённое тестами движка.

**Шаг перед сборкой.** Переиспользуемый workflow `site-image.yml` принимает необязательный вход `export_docs` (`true`/`false`, по умолчанию `false`) - белый список, а не произвольная команда: при `true` он **тем же образом движка** в рабочей копии репозитория до сборки, пока папка ещё не смонтирована только на чтение, выполняет `heron docs --export static/agents --all-langs`, `heron schema --export static/schema/<major.minor> --lang en` и `heron schema --export static/schema/<major.minor>/ru --lang ru` (версия - из `heron --version` того же образа) и `heron docs agents > static/AGENTS.md`. Так сайт движка выкладывает сырые файлы документации (`23` §12). Политика запуска та же: без сети, без capabilities, не от рута, корень контейнера только на чтение. На запись смонтирована только папка `static/` сайта (в контейнере она `/out`), а не папка сайта и не вся рабочая копия: при `path: "."` это был бы корень checkout вместе с `.git` и `.heron/` (рецепт и дымовая проверка, по которым дальше идёт сборка образа). Символическая ссылка вместо `static/` или `static/AGENTS.md` - ошибка шага: монтирование и перенаправление вывода пошли бы по ней за пределы папки сайта. Если образ движка не умеет `schema --lang`, шаг выкладывает одну схему без `ru/` и пишет предупреждение. В образ ничего не добавляется, кроме того, что потом попадёт в `dist/` обычной сборкой.

В `site-image.yml` вся история репозитория уже подтягивается (`fetch-depth: 0`), совет про историю ниже нужен только для собственного workflow сайта.

Входы workflow `site-image.yml` (выход один - `image`, полное имя образа с тегом):

| Вход | По умолчанию | Что делает |
|---|---|---|
| `env` | `dev` | окружение сборки |
| `engine` | `prod` | тег движка `prod`, `beta`, `dev`, `X.Y.Z`; можно `@sha256:<digest>` |
| `path` | `.` | папка сайта внутри репозитория, без `..` |
| `image` | `ghcr.io/<владелец>/<репозиторий>` | имя образа сайта |
| `tag` | имя окружения | тег образа |
| `strict` | `auto` | `auto` - строго для `prod`; `true` / `false` |
| `nginx_image` | стоковый `nginx:1.30.6-alpine` по digest | на нём `nginx -t` до сборки образа |
| `export_docs` | `false` | сырые файлы документации в `static/` |
| `push` | `true` | отправлять ли образ в реестр |

**Кэш нарезок в CI.** Без него каждая сборка холодная: на сайте в сотню картинок это минуты процессорного времени на любую правку текста. Рецепт только для собственного workflow сайта. В `site-image.yml` кэш нарезок не сохраняется: каждая его сборка холодная. При сборке с `--out` кэш лежит рядом с папкой результата, в `.heron-cache/`, и кладётся в кэш раннера как обычная папка:

```yaml
- uses: actions/cache@v4
  with:
    path: .heron-cache
    key: heron-media-${{ hashFiles('media/**', 'theme/theme.yaml') }}
    restore-keys: heron-media-
```

Ключ включает тему не для красоты: `widths`, `ratios` и `formats` входят в хеш каждой записи, и правка `theme.yaml` обесценивает кэш целиком.

Кэш влияет только на скорость. Потерялся, протух, не восстановился - сборка просто будет холодной, результат тот же побайтово. Поэтому промахи кэша чинить не нужно, а `build.workers` в CI стоит прибить руками: ядра там делят с другими задачами.

**Если сайт включил `build.updated_from: git`, истории нужно доехать до сборки.** GitHub Actions клонирует репозиторий обрезанным - только последний коммит, - и тогда история формально есть, а дат в ней нет: движок откатится на время файлов, а файлы после клона все датированы временем клона. Весь сайт объявит себя обновлённым сегодня, и так при каждой сборке. Лечится одной строкой:

```yaml
- uses: actions/checkout@v7
  with:
    fetch-depth: 0
```

То же самое касается сборки из архива или из копии папки без `.git`: даты перейдут на время файлов. Если даты важны - история должна быть рядом с контентом в момент сборки.

### CI движка: кеши, jobs и сброс кеша

Workflow `ci.yml` репозитория движка состоит из четырёх jobs. `quality` (линт и тесты), `browser` (Chromium-проверки) и `image-build` (сборка и проверка образа, только на push) идут **параллельно**. `publish` (публикация образа, только на push) ждёт их все: `needs: [quality, browser, image-build]`. `publish` не пересобирает образ: он получает проверенный в `image-build` образ артефактом `heron-candidate` (`docker save`/`docker load`, срок хранения 1 день), поэтому публикуется ровно тот образ, что прошёл дымовую проверку. Раннер закреплён явно, `ubuntu-26.04`.

**Concurrency.** Группа `${{ github.workflow }}-${{ github.ref }}`: один активный запуск на ветку или pull request. Устаревший запуск отменяется новым только для pull request и ветки `dev`. На `beta`, `prod` и тегах отмена выключена: там идёт публикация образа.

| Что кешируется | Где | Ключ |
|---|---|---|
| Зависимости Python (uv) | `quality`, `browser`: `astral-sh/setup-uv`, `enable-cache` | хеш `uv.lock` (`cache-dependency-glob`) |
| `.deb` nginx | `quality`: `~/.apt-archives` | `apt-nginx-<ОС>-<архитектура>-ubuntu-26.04` |
| Chromium Playwright | `browser`: `~/.cache/ms-playwright` | `playwright-<ОС>-<версия Playwright>` |
| Слои Docker (buildx, бэкенд gha) | `image-build` (пишет и читает) | `scope=heron-engine` |
| Слои Docker образа сайта | `site-image.yml` | `scope=heron-site` |

Попадание в кеш Chromium пропускает скачивание браузера, но системные библиотеки всё равно ставятся (`playwright install-deps`). Промах кеша слоёв Docker влияет на время сборки `image-build`, а публикуется в любом случае образ, прошедший проверку. Результат холодной сборки может отличаться: она заново ставит незакреплённый пакет git (шаг установки git в `Dockerfile`).

**Как сбросить кеш.**

- Сменить версию в ключе. Для Chromium это шаг `версия Playwright для ключа кеша` (версия `1.63.0` в `ci.yml`, её же нужно менять в командах `playwright`); для `.deb` nginx - метка `ubuntu-26.04` в ключе; для uv достаточно изменить `uv.lock`. Старый кеш перестанет находиться и со временем вытеснится сам.
- Удалить точечно: `gh cache list`, затем `gh cache delete <id или ключ>`; все сразу - `gh cache delete --all`.
- Вручную в интерфейсе: репозиторий, вкладка Actions, раздел Caches слева, кнопка удаления у нужной записи.

Слои Docker лежат в том же хранилище кешей GitHub Actions (записи индекса `scope=heron-engine` и `scope=heron-site`; сами блоки лежат под ключами по хешу, поэтому фильтр `gh cache list` по scope найдёт не всё): они видны в `gh cache list` и удаляются теми же способами. Кеш `heron-site` принадлежит репозиторию сайта, а не движка. Лимит хранилища на репозиторий - 10 ГБ, при превышении GitHub вытесняет самые старые записи.

## 5. nginx

Минимум, который обязан быть в конфиге:

- отдача статики: HTML с `Cache-Control: no-cache`, `assets/` и `media/` с `public, max-age=86400`
- сжатие gzip для текста, стилей, скриптов, svg, карт и разметки; brotli конфиг не включает
- 301 из `redirect_from` и 410 из `gone` отдаются без обращения к файлам. Карты уже вписаны в конфиг, который движок собирает вместе с сайтом (`dist/.heron-nginx.conf`); `redirects.map` и, если задан `gone`, `gone.map` в `dist/` - человекочитаемые копии
- `try_files` с завершающим слешем, единый канонический вид URL
- `/healthz` для healthcheck
- заголовки: `X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy`, HSTS
- **запрет исполнения чего-либо**: сайт статический, PHP и любой обработчик отсутствуют как класс
- закрыты dot-файлы

CSP строгий: `script-src 'self'`; исключение одно - домены счётчиков, включённых в `analytics` файла `site.yaml`. Для `heron-relay` исключения в конфиге пока нет: сервис не реализован.

## 6. Переезд с существующего сайта <a id="migrate-existing-site"></a>

Порядок, при котором сайт не проседает. Конкретные правила редиректов - дело сайта, здесь только последовательность.

**Подготовка.** Новый сайт собирается и поднимается на служебном поддомене. Проверяется всё: страницы, языки, разметка, скорость.

**Карта редиректов.** Полный список старых адресов снимается с живого sitemap. Для каждого прописывается `redirect_from` в соответствующем md-файле; то, чего больше не существует, - архивы, служебные пути, дорвеи - пишется в `gone` в `site.yaml`, точными адресами или префиксами (`20` §5). Дымовая проверка образа проходит на служебном домене.

Разница между 301 и 410 принципиальна: 301 говорит поисковику «адрес переехал, вот новый», 410 - «этого больше нет, выкинь из индекса». Служебные сущности старой системы - это второе, и притворяться, что они временно недоступны, смысла нет.

**Переключение.** Прокси переводится на новый контейнер. Старый стек остаётся поднятым, но недоступным снаружи - на случай отката.

**После.** Sitemap переотправляется в Search Console. Неделю смотрим отчёт по ошибкам сканирования. Если тихо - старый стек гасится, каталоги архивируются.

## 7. Бэкап

Резервировать нужно только то, что нельзя восстановить сборкой.

**Нужно:** репозиторий сайта с контентом и картинками - он же и есть источник истины; секреты сервисов, когда они появятся.

**Не нужно:** `dist/` вместе с конфигом nginx - пересобирается за секунды. `.heron-cache/` - тем более. Образ движка - он в реестре и прибит версией.

Сайт целиком восстанавливается из git: клон и сборка. Это главное практическое преимущество перед системами, где восстановление означает разворачивание базы.

## 8. Что появится позже

Заложено в структуре, не реализуется сейчас:

**`heron-relay`** - третий контейнер на сайтах с формами: приём POST, валидация по схеме из `site.yaml`, антиспам, рассылка в почту, вебхук CRM и Telegram. Без базы; SQLite только как спул повторной отправки. Секреты из смонтированного `.env`, только в этот контейнер - nginx про них не знает.

**Собственная аналитика** - приём событий вместо внешнего счётчика. Отдельный эндпоинт relay, отдельное решение по хранению.

**Атомарная выкладка** - сборка в соседний каталог и подмена `dist` одним переименованием, с возвратом прежнего при ошибке. Скриптов для этого в поставке нет.

**Админка** - веб-редактор md-файлов с запуском пересборки. Правило, без которого её нельзя делать: **админка правит файлы и коммитит их в git, а не пишет в базу.** Иначе HERON превращается в ту самую систему, от которой сайты уходят.

Ни одно из них не требует переписывания того, что делается сейчас, - при условии, что границы из `21-engine.md` и `23-distribution.md` соблюдены.
