# HERON - движок

**Документ 2 из 4.** Предыдущий: `20-data-contract.md`. Следующие: `22-deploy.md` (развёртывание сайта), `23-distribution.md` (поставка движка).

---

## 1. Что делает движок

Читает папку сайта - `site.yaml`, `content/`, `data/`, `media/`, `static/` и тему - и отдаёт готовый статический сайт в `dist/`.

Одна команда, один проход, никакого состояния между запусками. Собрать дважды подряд - получить побайтово одинаковый результат.

Движок живёт в образе `ghcr.io/fmstm/heron:<канал или версия>` и в pip-пакете, а не в папке сайта. Первым делом он сверяет свою версию с требованием `heron:` из `site.yaml` и отказывается собирать несовместимый сайт (`E012`).

Сборка идёт **без сети**. Ни один этап не ходит наружу: всё, что нужно сайту, лежит в папке сайта.

## 2. Стек

Python 3.12. Зависимости минимальны - каждая должна быть оправдана, потому что сопровождать это будет начинающий разработчик.

| Пакет | Зачем |
|---|---|
| `markdown-it-py` | парсинг markdown; `{#id}` разбирает собственное правило движка (`heron/core/parser/markdown.py`) |
| `PyYAML` | фронтматтер и конфиги |
| `Jinja2` | шаблоны |
| `Pillow` | ресайз и конвертация картинок |
| `pydantic` | валидация фронтматтера и `site.yaml` со внятными сообщениями |
| `click` | CLI |

Пакетный менеджер - `uv`. Линтер и форматтер - `ruff`. Тесты - `pytest`.

Всё специфичное живёт в папке сайта: `content/`, `data/`, `site.yaml` и тема.

## 4. Конвейер сборки <a id="build-pipeline"></a>

Восемь этапов, строго по порядку. Каждый может остановить сборку.

**1. Загрузка конфигов.** Сверка версии движка с ключом `heron:` из `site.yaml`, затем сам `site.yaml` и `theme.yaml` найденной темы. Валидация pydantic. Версия не подходит, тема не найдена или тип страницы не имеет шаблона - остановка.

**2. Обход дерева.** Рекурсивный проход `content/<lang>/`. Для каждого файла определяется URL, тип (из `_index.md` папки или по умолчанию), язык. Формируется плоский список страниц.

Адрес и ключ строятся порознь:

- **ключ** - путь папок плюс имя файла без расширения. Он не смотрит на
  слаг никогда: склеить их значит запретить языкам разные адреса, а
  переименование адреса сделать разрывом связи между переводами
- **адрес** - та же цепочка сегментов, но каждый заменён слагом своего
  раздела, если раздел его объявил, и своим `slug`, если объявила сама
  страница

Слаги разделов собираются отдельным проходом по `_index.md` до обхода
файлов: дочернюю страницу движок встречает раньше, чем индекс её раздела,
а адрес ребёнка зависит от того, как назвал себя родитель.

#### Границы файлов

Сборка читает только исходники сайта, пишет только в папку сборки и кэш,
удаляет только то, чем владеет. Путь сначала нормализуется, затем
разрешается файловой системой со всеми символическими ссылками, и только
результат сравнивается с корнем (`heron/core/paths.py`). Строковая
проверка на `../` не применяется: символическая ссылка точек не содержит.

| Операция | Где разрешено | Нарушение |
|---|---|---|
| чтение страниц и данных | внутри `content/`, `data/` | файл-ссылка наружу - `E024` |
| чтение ресурсов | внутри `media/` (`img/`) | `media/../x`, ссылка наружу - `E024` со страницей, где объявлен путь |
| копирование `static/`, `assets/` темы | внутри своей папки; ссылка внутрь той же папки допустима | ссылка или папка-ссылка наружу - `E024` |
| шаблоны темы (`include`, `extends`) | внутри темы | шаблон-ссылка наружу - `E024` |
| запись результата | внутри папки сборки | имя с `..`, папка-ссылка наружу - `E024` |
| удаление | файлы манифеста прошлой сборки - только по настоящему пути внутри `dist/`; записи кэша - только внутри кэша | папка в `dist/` или каталог кэша, подменённые ссылкой наружу, пропускаются; запись кэша - ссылка наружу при чтении или записи - `E024` |
| корень кэша | `.heron-cache/` и `.heron-cache/renditions/` - настоящие папки рядом со сборкой; ссылка выше них (вся папка сайта - ссылкой) допустима | корень или `renditions/` - ссылка, в том числе битая, - `E024` до любой записи и уборки |
| готовая нарезка | берётся из кэша, только если это обычный файл (тип по самому пути, без перехода по ссылкам) | ссылка или другой не-файл на месте нарезки убирается - сама запись, не цель - и нарезка кодируется заново; папка на её месте - `E024`, dist не меняется |
| сами папки | `content/`, `data/`, `media/`, `static/`, `plugins/` - внутри сайта; `assets/`, `i18n/`, `templates/`, `modules/` и файлы строк `i18n/<язык>.yaml` - внутри темы | папка или файл строк - ссылка наружу - `E024` |
| плагины из `plugins:` | имя - `^[a-z0-9][a-z0-9_-]*\Z`, без повторов; папка `plugins/<имя>/` и её `__init__.py` - настоящие, не ссылки | имя вне правила - `E011` (схема) или `E014` (резолвер, вызванный напрямую); сама `plugins/`, папка плагина или `__init__.py` - ссылка наружу - `E024`; проверка до исполнения кода плагина, и при `build`, и при `check`. Проверяется только точка входа плагина (папка `plugins/`, `plugins/<имя>`, `__init__.py`): плагин - произвольный код сайта и может импортировать всё, что лежит рядом; вложенные ссылки внутри пакета плагина не проверяются |
| запись в папку сайта (`new`, `init`, `setup`, `theme get`) | `site.yaml`, `content/`, тема, `.heron/`, `.gitignore`, комплект `agents/` и корневые `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, резервные копии в `.heron-cache/setup/` - итоговый путь внутри папки сайта; ссылка на другое место того же сайта допустима | файл или любая папка по пути к нему - ссылка наружу, в том числе битая, - `E024`; конфигуратор проверяет все свои цели до первой записи, внешние файлы не меняются |
| зарезервированные имена корня: `agents/`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` (`20` §1) | сборка и `check` их не читают, `serve` не наблюдает; `check` читает только `agents/heron-kit.yaml` - мягко, для сведения; `init --agents` пишет внутрь по правилу строки выше | ссылка на их месте сборке безразлична (она туда не ходит); битый или чужой манифест - одна строка сведения, не ошибка. Те же имена **не в корне** (`content/<язык>/agents.md`, `static/AGENTS.md`) - обычные файлы своих папок |
| обход папок | папка-ссылка внутрь той же папки даёт свои пути рядом с исходными (`latest/` → `v2/`); петля по цепочке предков отсекается | папка или файл исходников не читается (права, диск) - `E030`, а не тихо неполная сборка |

Папки не пересекаются: папка сборки (`--out`) не может быть корнем сайта,
содержать его, совпадать с `content/`, `data/`, `media/`, `static/` или
темой и лежать внутри них; кэш не пересекается ни с ними, ни со сборкой.
Нарушение - `E024` до начала работы. `dist/` внутри папки сайта - норма.

Здесь же выясняется дата обновления, источник задаёт `build.updated_from`
(`manual` по умолчанию, `git`, `file`). Приоритет один и тот же при любом
источнике: `updated` из фронтматтера перебивает автоматику всегда.

Режим `git` спрашивает историю **двумя** вызовами на всю сборку, а не двумя
на файл: один обход истории отдаёт даты по всем путям сразу, второй -
список незакоммиченных файлов. На сайте в несколько сотен страниц разница
между этим и `git log -1` на каждый файл - секунды против минут. Берётся
время коммитера (`%cI`) с его поясом: момент, когда правка попала в
историю, а значит и на сайт не раньше. Время автора бывает старше на
недели (ребейз, черри-пик). После разрешения дат `dates.check` ищет даты
позже момента сборки и обновления раньше публикации - предупреждения
вида «даты», при `--strict` ошибки (`20` §4.2). Переименования не отслеживаются:
для сайта переименование файла - это смена адреса, страница действительно
изменилась.

История недоступна - не репозиторий, гита нет в образе, история обрезана
(`clone --depth 1`) - сборка не падает: движок откатывается на время файлов
и говорит об этом **одним** предупреждением на сборку. Предупреждение с
путём файла остаётся там, где оно про конкретный файл: его нет в истории
или в нём незакоммиченные правки. Иначе сборка из копии без `.git` дала бы
двести одинаковых строк и забила бы сводку.

Дата приводится к календарной дате в UTC, без времени: результат не должен
зависеть от часового пояса машины, на которой запущена сборка.

**3. Парсинг.** Для каждой страницы: фронтматтер → модель, тело → секции, структурированные секции → данные. Ошибки собираются, не прерывая проход - чтобы разработчик увидел все сразу, а не по одной за прогон.

**4. Резолв связей.** Дочерние страницы каталогов, поля связей, объявленные темой в `links`, языковые соответствия, меню, хлебные крошки, обратные ссылки. Ссылка на несуществующую страницу - остановка.

Внутренние ссылки текста приводятся к языку страницы не приклеиванием префикса, а через страницу: написанный путь разбирается сначала как ключ, потом как адрес в языке страницы, потом как адрес языка по умолчанию (полное правило и пример - `20` §2). У найденной страницы берётся версия языка текущей страницы, и подставляется её адрес. Обрабатываются страницы всех языков, включая основной: ссылка-ключ на раздел со слагом и там отличается от адреса. Перевода нет - предупреждение, и ссылка ведёт на версию языка по умолчанию: читатель попадает на существующую страницу, а не в 404.

Отдельно проверяются ссылки, написанные руками в тексте: каждая вида
`/…/` обязана разрешаться в существующую страницу по тому же правилу.
Не разрешается - предупреждение с путём файла, номером строки и самой
ссылкой. Это предупреждение, а не ошибка: битая ссылка внутри текста не
повод не выкладывать остальной сайт. Но и молчать нельзя - адрес раздела
задаётся слагом, и переименование раздела оставляет написанные адресом
ссылки указывать в никуда до первого нажатия. Пропускаются внешние
адреса, якоря, пути к `/media/`, `/static/`, `/assets/` и к файлам с
расширением.

**Большие разделы.** Пагинации у движка нет, и это решение, а не пробел. Раздел со ста и более детьми - это **одна** страница каталога: `page.children` отдаёт теме всех детей сразу, отсортированных по `order`, затем по `h1`. Адресов вида `/faq/page/2/` движок не создаёт, поэтому вопросов с их каноникалом, `prev`/`next` и попаданием в карту сайта не возникает: в sitemap попадают раздел и каждый ребёнок, по одной записи.

Как показать длинный список удобно - забота темы: сгруппировать детей по полю (`groupby` в Jinja), вывести оглавление с якорями, свернуть группы в `<details>`. Все ссылки при этом обязаны быть в HTML (`20` §10): подгрузка списка скриптом прячет страницы от поисковика. Сто ссылок на странице каталога - нормальный размер; если раздел вырастет до тысяч, его делят на подразделы папками - у каждого свой `_index.md`, свой адрес и своя запись в карте.

Проверено на разделе из 120 страниц (`tests/test_large_section.py`).

**5. План картинок.** Для каждого мастера - имена и размеры всех нарезок, которые тема может попросить (пропорции × ширины × форматы, запасной формат - одна ширина `fallback_width`). Ничего не кодируется: шаблонам нужны только имена и `width`/`height`, а их даёт геометрия мастера. Оригиналы не трогаются.

**После рендера и генераторов - нарезка.** Движок ищет ссылки на `media/` во всём собранном тексте: страницах, картах, разметке, файлах плагинов, стилях темы и статике. Кодируется и кладётся в сборку только пересечение этих ссылок с планом. Мастер целиком кладётся, только если на него есть ссылка (`media_url(src)`, og:image) или он объявлен «сырым»: картинка из текста страницы, `og_image`, `twitter_image`, `video_poster`, `seo.og_default_image`. Файлы, которые движок не режет (видео, PDF, svg, `as_is`), копируются как раньше.

Нарезки живут **в кэше**, адресованном содержимым мастера, а в сборку попадают жёсткой ссылкой (подробно - «Кэш нарезок» ниже). Ссылки на `media/` в markdown - от корня сайта: `media/x.svg`, `./media/x.svg` и `/media/x.svg` в картинке и в ссылке выводятся как `/media/x.svg` на любой глубине страницы.

Кодирование раскидывается по ядрам, задача - мастер, а не отдельная нарезка: дробить мельче значит декодировать исходник семьсот раз вместо девяноста пяти. Число процессов - `build.workers`, ноль означает по числу ядер. Прогресс тикает в порядке исходного списка, а не готовности: иначе лог перестаёт читаться, а смотрят в него как раз на долгой сборке.

Замер на сайте с 95 мастерами и 2062 нарезками, четыре ядра: холодная сборка 157 с, повторная - 4 с, из них картинки 0.3 с.

**6. Рендеринг.** Каждая страница через `templates/<тип>.html` темы (или шаблон, названный в `types.<тип>.template`). Страница 404 основного языка дополнительно кладётся в корень как `404.html` (`20` §2, «Страница 404»).

**7. Генерация служебного.** sitemap, robots, llms.txt, redirects, feed. JSON-LD встраивается на шаге 6.

**8. Запись результата.** Этапы 6-7, `static/`, `theme/assets/`, нарезки и файлы плагинов только *заявляют* выходные файлы; пишет один шаг - и только после того, как сборка признана удачной (ошибок нет, а в строгом режиме нет и предупреждений; отчёт, разметка и `nginx -t` проверены до записи).

#### Запись результата

- **Владельцы.** У каждого пути сборки один владелец: страница, генератор (sitemap, robots, llms, карты, конфиг nginx, лента), `static/`, ресурс темы, медиа, плагин. Два владельца у одного пути - `E026` с обоими именами; файл и папка с одним именем (`about` и `about/index.html`) - тоже `E026`. Единственная разрешённая подмена - генерированный файл файлом из `static/`, перечисленный в `build.overrides` (`20` §5).
- **Неудача не трогает прошлую версию.** Ошибка или предупреждение в строгом режиме - в `dist/` не записано ничего.
- **Применение.** Новое готовится во временной `dist/.heron-staging/` (та же файловая система) и ставится на место переименованием. Удаляются только устаревшие файлы, которыми владела прошлая сборка, - их список в `dist/.heron-manifest.json` (наружу его не отдаёт nginx: скрытые файлы - 404). Чужие файлы в `dist/` не трогаются; чужой файл на месте нужного пути - `E026`. Перед первым переименованием манифест атомарно переписывается списком «прошлое ∪ новое» (журнал): если применение оборвётся посреди (кончился диск), в `dist/` может остаться смесь версий, но все появившиеся файлы уже числятся своими - следующая удачная сборка уберёт лишнее своё и не тронет чужое. По окончании манифест - точный список новой сборки.
- **Чужой файл.** Обычный файл на нужном пути, которого нет в манифесте, - `E026` до любого изменения `dist/` (те же байты - не спор). Папка, собранная прошлой версией движка без манифеста (в ней лежит `.heron-nginx.conf`), считается своей - один раз, до первого манифеста.
- **Проверяется итог.** `nginx -t` гоняется на том содержимом `.heron-nginx.conf`, которое ляжет в сборку, - в том числе подменённом статикой через `build.overrides`.
- **Служебные имена.** `.heron-manifest.json` и `.heron-staging/` в корне сборки пишет только движок: файл с таким путём из `static/` или плагина - `E026`.
- **Одна сборка за раз.** Применение идёт под блокировкой файла `.<папка сборки>.heron-lock` рядом с папкой сборки: две сборки в одну папку одновременно применяются по очереди, а не вперемешку.
- **Неизменившееся не переписывается.** Файл с теми же байтами остаётся с прежним временем (ETag и кэш браузеров живут), нарезка - с той же жёсткой ссылкой на кэш. Общий с кэшем или с прошлой версией inode не правится на месте никогда: заменяется запись каталога, не данные.
- **Что инкрементально, а что нет.** Дорогое - кодирование картинок - берётся из кэша и не повторяется (§8, «Кэш нарезок»). HTML рендерится весь при каждой сборке: зависимости страниц (меню, каталоги, связи, переводы, карты) не отслеживаются, и это не инкрементальный рендер. Зато результат повторной сборки совпадает с холодной побайтово при одинаковых входах и `SOURCE_DATE_EPOCH`, а в `dist/` записываются только изменившиеся файлы.
- **Время сборки.** Метка сборки (`env.stamp`) берёт время из `SOURCE_DATE_EPOCH`, если он задан, - так сборки воспроизводимы.

После - сводка: сколько страниц по языкам и типам, сколько предупреждений, список долгов по контенту.

Предупреждения группируются по виду: `картинки`, `связи`, `ссылки`, `меню`,
`переводы`, `языки`, `прочее`, а также `нет перевода`, `даты`, `контент`, `seo` и `редиректы` (всего 12 видов; порядок групп задаёт `ORDER` в `heron/core/report.py`, виды вне него печатаются после «нет перевода» по алфавиту). Сверху то, что ломает страницу для посетителя,
снизу то, что заметит только редактор. В каждой группе шесть примеров, полный
список пишется в `<рядом с dist>/.heron-cache/warnings.txt`. Без группировки
сотня однотипных замечаний про переводы прятала десяток важных про картинки,
которых нет на диске.

Ход сборки виден в терминале: этап, время с его начала, счётчик и полоска
внутри длинных этапов - нарезки картинок, рендера, записи файлов. В не-терминал
(CI, докер без `-t`, перенаправление в файл) перерисовывать нечего, поэтому
этап объявляется сразу, как начался, длинные этапы отмечаются раз в две
секунды, в конце пишется итог. Каждая строка выталкивается из буфера сразу:
иначе весь лог доезжает до человека одной пачкой в конце и сборка неотличима
от зависшей.

## 5. Парсер секций

Сердце системы, поэтому подробно.

Тело файла разбирается `markdown-it-py` со своим правилом атрибутов заголовка. Секция - заголовок с якорем `{#id}` и всё содержимое до следующего заголовка с якорем **того же или более высокого уровня** либо до конца файла. Уровень задаёт первый заголовок с якорем в файле; якорь глубже этого уровня остаётся внутри текущей секции.

Правила:

- заголовки без якоря секцию не начинают и принадлежат текущей
- текст до первой секции доступен как `intro`
- идентификатор: `[a-z0-9-]+`. Иное - ошибка
- дубликат идентификатора в файле - ошибка
- у секции сохраняются: `id`, `title` (текст заголовка), `level`, `html` (отрендеренное содержимое без заголовка), `raw` (исходный markdown)
- и разобранные части: `lead` (абзацы до основного узла), `body` (сам узел), `note` с `note_title` (абзацы после), `callout` (цитата) и `links`
- вводный блок отдаётся тремя полями: `lead` - первый абзац, `promise` - второй, `intro` - весь текст целиком. Третий абзац и далее - предупреждение: в шаблоне для них места нет

Тема сама решает, показывать ли заголовок секции: `mod.prose('what')` выводит и заголовок и текст, а `mod.facts('quick-facts')` заголовок игнорирует, потому что рисует рамку с фактами.

### Формы секций

Каждая секция после разбора получает поле `kind` - одну из тринадцати форм: `prose`, `list`, `alert-list`, `checklist`, `two-lists`, `steps`, `table`, `facts`, `faq`, `timeline`, `callout`, `gallery`, `tabs` - и `data` с разобранными данными этой формы. Таблица форм, признаки, порядок распознавания и форма данных - `20` §4.4, это единственное место, где они описаны. Список форм в коде - `heron.contracts.theme.KINDS`, порядок автоопределения - `heron.core.parser.blocks.AUTO_ORDER`.

Разбор ошибается мягко: класс задан, а содержимое не подходит, - секция отдаётся прозой и пишется предупреждение. Валить сборку из-за пропущенной палочки в таблице нельзя.

Модель секции:

```python
class Section:
    id: str                # якорь из {#anchor}
    title: str             # текст заголовка
    level: int
    line: int | None       # строка заголовка
    classes: list[str]     # классы из якоря: alert, timeline, …
    raw: str               # исходный markdown без заголовка
    html: str              # отрендеренное содержимое без заголовка
    kind: str              # форма: prose, list, … - см. 20 §4.4
    data: Any              # разобранные данные формы; в шаблоне модуля - items
    lead: str              # абзацы до основного узла
    promise: str           # второй абзац вводного блока
    note: str              # абзацы после
    note_title: str        # жирный зачин примечания
    callout: str           # цитата, где бы она ни стояла
    links: list[dict]      # ссылки секции {title, href}
    body: Any              # свойство: data, а для прозы - html
```

## 6. Модель страницы <a id="page-model"></a>

Поля фронтматтера живут в `page.meta` - по одному атрибуту на каждую строку таблицы `20` §4.2, плюс поля темы, которые ядро не трактует (`page.meta.<поле>`, а все разом - `page.meta.extra`). Сама страница добавляет то, что движок выяснил при обходе и резолве:

```python
class Page:
    lang: str                      # код языка
    source: str                    # путь файла от content/: ru/services/x.md
    key: str                       # ключ: services/x; у главной - пустая строка, в шаблонах и nav - "/"
    meta: PageMeta                 # фронтматтер, см. 20 §4.2
    url: str                       # адрес с префиксом языка и слагами: /ru/rukovodstva/x/
    type: str                      # тип страницы, правило выбора - 20 §4.2
    sections: dict[str, Section]   # секции по якорю
    intro: Section | None          # текст до первой секции
    auto_updated: date | datetime | None  # дата из git или файла, если updated не задан руками
    links: list[tuple[int, str]]   # ссылки текста как написаны: строка и адрес

    # заполняется на этапе резолва
    parent: Page | None
    children: list[Page]
    translations: dict[str, Page]  # версии на других языках, по ключу
    breadcrumbs: list[Page]
    related: dict[str, list[Page]] # связи, объявленные темой, и обратные

    # вычисляемые
    title: str                     # meta.title
    h1: str                        # meta.h1
    updated: date | None           # meta.updated, иначе auto_updated
    generated: bool                # страница создана движком
    date                           # дата публикации
    date_at                        # она же с временем
    updated_at                     # дата обновления с временем и поясом
    nav_title: str                 # meta.nav_title, иначе имя файла
    video: Video | None            # разобранные meta.video*
    cover: dict | None             # обложка: src, url, width, height, alt; нет - None (20 §4.2)
    slug: str                      # последний сегмент url
    name: str                      # имя файла без расширения
    is_index: bool                 # _index.md или главная

    def section(self, id): ...     # секция по якорю
    def has(self, id): ...         # есть ли такая секция
```

**Обложка.** `page.cover` вычисляется по порядку `og_image`, `image`, первая картинка `intro` или `hero`, `seo.og_default_image` языка (`20` §4.2). Источник определяется по исходному тексту, до рендера, поэтому обложка соседней страницы (`page_of('services').cover`) не зависит от порядка рендеринга. Внешний URL берётся как есть; путь, которого нет в плане сборки, даёт `None`.

`Site.page(key, lang)` находит страницу по ключу на языке; в шаблоне то же самое - `page_of(key)`.

## 7. Рендеринг <a id="rendering"></a>

Jinja2, `autoescape` включён, `StrictUndefined` - обращение к несуществующей переменной валит сборку, а не выводит пустоту. Это ловит опечатки в теме на этапе сборки.

Тема - недоверенный код: её ставят из каталога, по ссылке или архивом. Поэтому шаблоны собираются в неизменяемой песочнице Jinja (`ImmutableSandboxedEnvironment`): служебные атрибуты Python (`__globals__`, `__class__` и подобные) закрыты, списки и словари из шаблона не меняются (`.append`, `.update`). Сверх песочницы закрыты методы самого pydantic `BaseModel` у `site` и `theme` (`parse_file`, `model_construct` и т. п. - поля и собственные методы схем доступны), любые атрибуты путей и методы `env`, которые строят окружение заново. Обращение к закрытому - `E033` с именем шаблона. Изменение данных `heron check` находит ещё до сборки, разбором шаблонов (§12); как накапливать данные без `.append` и `.update` - рецепты в [`guide/04`, «Накопление данных в шаблоне без `append`»](../guide/04-theme.md#accumulate-data-without-append). Фильтры и функции плагинов сайта (`plugins/`) - код самого сайта, на них песочница не распространяется.

Шаблону доступны: `page`, `site` (весь `site.yaml`), `data` (содержимое `data/`), `nav`, `t` (строки интерфейса темы), `mod` (макросы модулей), `lang` и `languages`, `hreflang`, `page_of(key, lang=None)` (страница по ключу, по умолчанию на текущем языке, главная - `'/'`), `picture`, `media_url`, `absolute` (последние два доступны и фильтрами), `jsonld()`, `pages` (объект сайта со всеми страницами), `theme` (`theme.yaml` как модель), `env` (окружение сборки: `name`, `indexable`, `analytics`, `version`, `revision`, `built_at`, `stamp`).

### Макросы модулей

`mod.<модуль>(<id секции>)`. Логика одинаковая для всех:

1. секции с таким id нет → вернуть пустую строку, ничего не рендерить
2. секция есть → отрендерить `theme/modules/<модуль>.html`, передав ей данные секции

Модули без аргумента (`mod.call()`, `mod.author()`, `mod.breadcrumbs()`) берут данные из `site` и `page`, а не из секций.

Пустая строка вместо блока - принципиально: заголовок без содержимого хуже отсутствующего блока.

### Строки интерфейса

Тексты, принадлежащие теме, а не контенту («Book now» / «Записаться», «Read more» / «Читать далее»), живут в `theme/i18n/<lang>.yaml` и доступны как `t.book_now`. Иначе они окажутся зашиты в шаблоны и тема перестанет быть переносимой между языками.

### Контракт темы: поля блоков и подсказки <a id="theme-contract"></a>

Тема описывает в `theme.yaml` не только какие страницы она рисует, но и из чего они состоят: секции каждого типа, поля каждого блока, виды категорий и подсказки к ним. Это описание одно на всех: его читают `heron check`, `heron describe` (§10), опросник, студия, справочная страница темы и агент. Отдельного «API для редактора» нет.

Пример - кусок стартовой темы:

```yaml
languages: [ru, en]                # языки подсказок темы

types:
  page:
    uses: [intro, "*"]             # секции по порядку; "*" - любые блоки
    hint_ru: Обычная страница - текст и блоки любой формы
    hint_en: An ordinary page - text and blocks of any form
    children_type: page            # тип страниц внутри категории этого типа
    views:                         # как категория показывает свои страницы
      key: view                    # ключ фронтматтера _index.md, который выбирает вид
      default: cards
      options:
        cards: {hint_ru: Карточки сеткой, hint_en: Cards in a grid}
        list: {hint_ru: Список строками, hint_en: A list of rows}
    sections:
      intro:
        required: true
        hint_ru: Вводный абзац - о чём страница
        hint_en: The intro paragraph - what the page is about

modules:
  faq:
    kinds: [faq]                   # формы секций, которые рисует модуль
    schemaorg: FAQPage
    hint_ru: Вопросы и ответы - вопрос заголовком, ответ под ним
    hint_en: Questions and answers - the question as a heading, the answer under it
    fields:
      - name: items
        type: list
        required: true
        md: groups                 # где значение лежит в markdown
        hint_ru: Пары вопрос - ответ
        hint_en: Question - answer pairs
        fields:
          - {name: q, type: text, required: true, md: heading, max_length: 120, schemaorg: Question.name, hint_ru: Вопрос, hint_en: The question}
          - {name: a, type: markdown, required: true, md: content, schemaorg: Answer.text, hint_ru: Ответ, hint_en: The answer}
```

**Ключи.**

- `languages` - языки подсказок темы. Не задано - языки суффиксов, которые встречаются в подсказках.
- `modules` - список имён, как раньше, или описание каждого модуля: `scope` (`section` - рисует секцию, `page` - берёт данные из страницы и сайта, как `mod.breadcrumbs()`), `kinds` (формы секций из `20` §4.4; не задано - форма с именем модуля), `schemaorg` (тип разметки блока), `fields` (поля блока), подсказки.
- `types.<тип>.sections.<якорь>` - секция из `uses`: `required` (обязательна ли), `fields` (свои поля секции, у которой нет формы, - так описан `intro`), подсказки. Якорь `"*"` - подсказка к «любым блокам». Порядок секций - порядок `uses`; секция, которой нет в `uses`, - `E041`.
- `types.<тип>.children_type` - тип страниц внутри категории этого типа, из `types` той же темы.
- `types.<тип>.fields` - свои поля фронтматтера страниц этого типа: то, что шаблоны читают через `page.meta.get(…)` (`eyebrow`, `status`, `metrics`). Описание - как у поля блока (таблица ниже), но без `md`: значение лежит в SEO-блоке под именем поля. Имя не совпадает с полем движка (`title`, `slug`, `order`, `image`, `translation`, `view`, …) - иначе `E041`. Опросник и студия показывают их группой «Поля темы»; `heron check` - обязательное пустое, значение не из `values` или не того типа - `E042`, длина и число пунктов вне пределов - предупреждение. На других языках поля с текстом (`text`, `markdown`, `list`, `link`) переводятся, как SEO-блок; остальные (`enum`, `number`, `flag`, `date`, `ref`, `image`) - одни на все языки: правка на основном языке пишет то же значение во все файлы, пометки перевода не ставит. Поле без текста с `translatable: true` - своё у каждого языка, как обложка: нет своего значения - при сборке значение основного языка (`20` §4.2, «Обложка страницы»); новая копия языка его не копирует, правка на основном в другие файлы не пишет, `check` о расхождении не предупреждает. Флаг годится всем типам без текста; у поля с текстом и у поля блока он ничего не меняет - `heron check` предупреждает (`build_theme_translatable`), не ошибка. Ключ `fields` верхнего уровня `theme.yaml` - другое: список имён полей движка, которых ждёт тема (`E023`).
- `types.<тип>.views` - виды категории: `key` (ключ фронтматтера страницы категории, по умолчанию `view`), `default` (вид без ключа), `options` (виды темы с подсказками). Перечень видов придумывает тема - движок проверяет только, что `default` есть в `options`.

**Поле блока.**

| Ключ | Что это |
|---|---|
| `name` | имя поля: строчная латиница, цифры, `_`, с буквы |
| `type` | `text`, `markdown`, `list`, `image`, `link`, `number`, `date`, `enum`, `ref`, `flag` (да или нет) |
| `required` | обязательно ли |
| `md` | где значение лежит в markdown: место из словаря ниже |
| `min_length`, `max_length` | длина текста |
| `min_items`, `max_items` | число пунктов списка |
| `ratio`, `min_width` | пропорция (`16:9`) и ширина картинки, только у `image` |
| `values` | допустимые значения, только у `enum` (и у него обязательно) |
| `ref` | у `ref` - на страницы какого типа ссылается поле |
| `schemaorg` | свойство разметки, в которое уходит значение: `Question.name` |
| `item` или `fields` | у списка - тип каждого пункта или поля каждого пункта, одно из двух |
| `translatable` | только у своего поля типа без текста: своё значение у каждого языка, нет своего - основного языка |

**Места в markdown (`md`).** Словарь общий для всех тем: каждое место - форма, которую уже понимает разбор секций (§5, `20` §4.4). По нему опросник находит значение в файле и пишет его на то же место.

| Место | Что в файле |
|---|---|
| `body` | всё содержимое секции |
| `first-paragraph`, `second-paragraph` | первый и второй абзацы вводного блока |
| `lead` | абзацы до основного узла: списка, таблицы, групп `###`, строк «ключ \| значение» |
| `quote` | цитата `> …` |
| `items`, `numbered` | пункты списка `- …` и нумерованного `1. …` |
| `bold`, `tag`, `text`, `more` | жирный зачин `**Термин.**`, метка `[МЕТКА]`, текст после зачина, продолжение пункта с отступом |
| `groups`, `heading`, `heading-id`, `content` | группы `### Заголовок`, текст заголовка, его якорь `{#id}`, всё под ним |
| `pairs`, `key`, `value` | строки `ключ \| значение` и их части |
| `table-head`, `table-rows`, `cells` | шапка таблицы, строки, ячейки строки |
| `image`, `alt` | путь картинки `![подпись](путь)` и подпись |

**Подсказки.** `hint` - одна строка для наведения, `help` - что это, на что влияет на сайте и в поиске, хороший пример, частые ошибки; у модуля ещё `example` - образец markdown. По языкам - суффиксом, как в `site.yaml`: `hint_ru`, `help_en`, `example_uk`; ключ без суффикса - для языков, у которых своего текста нет. Подсказки бывают у типа, секции, модуля, поля, вида и блока `views`.

**Служебные поля** описывает движок (`heron/contracts/fields.py`, тексты - словарь сообщений, ru и en), тема их не повторяет. Это SEO-блок (`title`, `h1`, `description`), адрес (`slug`, категория - папка страницы, `type`, `children_type`), меню (`nav.main` в `site.yaml`, `nav_title`, `order`), обложка (`image`, `image_alt`), соцсети (`og_image`, `og_title`, `og_description`; `image` и `og_image` - свои у каждого языка, нет своих - основного, в `describe` у них `inherits: true`), публикация (`noindex`, `published`, `date`, `updated`, `redirect_from`, `translation` - пометка «перевод не готов», `20` §4.2) и у каждого блока - заголовок `## …` и якорь `{#…}`. Порядок и группы - одни для `describe`, опросника и студии.

**Проверка.** Тема без `fields` собирается как раньше - секции остаются свободным markdown. `heron check` один раз предупреждает: «нет описания полей: опросник и студия покажут только SEO-блок». Тема, у которой `fields` есть, обязана дать `hint` каждому типу, секции из `sections`, модулю из описания, полю и виду - на каждом своём языке; чего-то нет - `heron check` даёт `E041` со списком путей (`modules.faq.fields.items.fields.q (en)`). Сборку отсутствие подсказки не останавливает. Негодное описание - неизвестное место `md` или тип, список без `item` и `fields`, `enum` без `values`, `default` вне `options`, `children_type` или `ref` на тип, которого нет, повтор имени поля, своё поле типа с `md` или с именем поля движка - `E041` при чтении `theme.yaml`, как любая ошибка паспорта. `E008` - только про шаблоны: у типа нет шаблона, файл строк темы негоден.

Стартовая тема описана полностью на ru и en (`heron/scaffold/text/theme-contract.yaml` - общий для обоих языков пояснений кусок её `theme.yaml`); тест сверяет образцы markdown каждого её модуля с разбором секций.

### Демо темы и справка <a id="theme-demo"></a>

**Демо обязательно.** Демо темы - контент сайта, из которого её упаковывают: образец подачи под нишу, который автор темы продумывает один раз. Оно обязано показать всё, что объявил контракт: у каждого типа из `types` - хотя бы одна страница из файла (достроенная движком 404 не считается); каждый модуль из `modules` хоть раз нарисовал непустой HTML (`mod.<имя>()` секции или модуль страницы); каждый вид из `views` - на странице с дочерними страницами, у которой ключ вида (`views.key`) равен виду, а у вида по умолчанию - ключа нет или он равен виду. Вид считается по паре «ключ - имя»: у типов с одним набором видов достаточно показать вид на странице любого из них. «Показан» решает настоящий рендер: страницы собираются шаблонами темы, `Modules` записывает каждый вызов, вернувший не пустоту (`core/demo.py`). Проверяют `heron theme pack` (до записи архива) и `heron check --theme`; обычный `heron check` демо не требует. Пропуски - `E037` со списком («тип 404: нет ни одной демо-страницы», «блок gallery (gallery): не показан…», «вид раздела list…»); ошибки шаблонов на демо-страницах идут своими кодами. У темы без `fields` неполное демо - предупреждение (вид «прочее») с тем же списком, `pack` его печатает и архив пишет. `pack` без `site.yaml` в папке - `E037`: без него не прочитать языки и страницы демо.

**Справка темы** собирается из контракта (тот же объект, что `heron describe --json`) и демо, руками её не пишут (`core/render/themeref.py`). В ней: типы страниц (подсказки, шаблон, секции по порядку `uses`, поля секций, `children_type`, `jsonld`, демо-страницы типа); каждый модуль - подсказка, справка, поля с местом в markdown и по примеру на каждую форму, которую он рисует: живой пример (модуль темы рисует секцию демо в окружении её страницы) и рядом исходный markdown секции (заголовок с якорем и классами и содержимое), с файлом и адресом страницы; модуль без примера - пометка и образец `example` из `theme.yaml`; виды разделов с ключом и строкой, которая их включает, и живым видом страницы раздела; разметка schema.org (`types.*.jsonld`, `schemaorg` модулей и полей); стили - CSS-файлы `assets/` и переменные `:root`; строки интерфейса `i18n/<язык>.yaml`. Примеры берутся с языка справки, нет страниц на нём - с языка по умолчанию.

Где видно: `heron docs theme-ref [путь] [--lang ru|en]` - текстом (примеры - исходный markdown и файл); служебная страница черновой сборки - `/_heron/theme/` на языке по умолчанию и `/_heron/theme/<язык>/` на остальных языках сайта, с живыми примерами в стилях темы (её CSS подключён). Страница пишется любой сборкой, кроме `--env prod`, и `heron serve`; в карту сайта, `llms.txt` и меню не попадает, у неё `<meta name="robots" content="noindex, nofollow">`. Рамка страницы - на языке справки, если движок его знает (ru, en), иначе на языке сообщений. Шаблон, упавший на примере, не роняет сборку: на месте примера - текст ошибки.

### Модель правки страницы <a id="edit-model"></a>

Опросник в консоли, студия в браузере и агент с `--answers` правят страницы одним ядром - `heron/edit/`. Своей базы у него нет: источник правды - файл страницы. Модель держит его текст целиком и знает, в каких символах лежит каждое значение.

- **Чтение.** `load(файл или текст, контракт)`; контракт - объект `heron describe` (`core/describe.py`, `contract`). SEO-блок читается дважды: `yaml.safe_load` даёт значения, `yaml.compose` - их места в тексте. Тело режется на секции тем же правилом, что у сборки (§5), форма секции определяется тем же разбором, а поля блока находят свои значения по `md` из словаря мест («Контракт темы» выше).
- **Список полей.** `fields(page)` - служебные поля движка по группам (`contracts/fields.py`), у категории и главной - вид отображения из `views` типа, затем разметка schema.org типа (`schema.<Тип>`), затем секции в порядке `uses`: заголовок, якорь и поля блока. У поля - значение, значение по умолчанию (что придёт из `site.yaml` и темы, если ничего не вводить), `hint`, `help`, ограничения и группа. Один и тот же список видят консоль, студия и агент.
- **Правка.** `set(page, путь, значение)` заменяет только символы этого поля и возвращает новую страницу. Пути: `title`, `schema.Service.serviceType`, `sections.faq.heading`, `sections.faq.items.0.q`; номер за концом списка добавляет пункт, пустое значение убирает поле. Нового ключа в SEO-блоке нет - раскомментируется заготовка `# og_title:   # подсказка` вместе с подсказкой, иначе ключ дописывается перед `---`; сброс возвращает строку в заготовку. Новые строки пишутся переводом строки самого файла. Секции целиком - `add_section` (по порядку `uses`, с классом якоря для форм, которые узнаются только по классу) и `remove_section`.
- **Без потерь.** Без правок `dump(load(файл))` даёт те же байты: комментарии, ручная разметка, порядок ключей и секций, `\r\n`, BOM и отсутствие перевода строки в конце остаются. При замене списка целиком совпавшие пункты остаются как были написаны. `tests/test_edit_lossless.py` проверяет это на всех демо и образцах страниц движка и на страницах-фикстурах тестов, а для каждого поля - что правка меняет только его место.
- **Только чтение.** То, что не записать без потерь, показывается, но не правится, и у поля есть причина: заголовок, подчёркнутый строкой ниже; место `md`, которого нет в словаре; блок в другой форме, чем ждёт тема; SEO-блок, который не читается как YAML; тело с ошибкой разбора (`E016`, `E003`). Категория (папка файла) и пункт меню (`nav.main` в `site.yaml`) живут вне файла: категорию переносят команды страниц и категорий, правку меню страница копит в `site_changes()`.
- **Проверка.** `validate(page, корень_сайта)` - те же правила, что у `heron check`: модель `PageMeta` и её замечания (длина `title` и `description`, `title` = `h1`, `image` без `image_alt`), плюс контракт темы: обязательные поля и секции, длина, число пунктов, допустимые значения, картинка (есть ли файл, ширина от `min_width` или `images.cover_width`, пропорции `ratio`) и разметка страницы (тип есть в словаре schema.org, свойство есть у типа).
- **Языки.** Ключ страницы - путь от папки языка без `.md`, как у сборки. `files(корень, site, ключ)` - файлы страницы на всех языках `site.yaml`, основной первым, и есть ли каждый; `folder_type` - тип страницы по её папке (`children_type` категории).

### Обложка и `robots_meta` в шаблоне <a id="cover-robots"></a>

Кроме перечисленного, шаблон получает:

- `page.cover` - обложка страницы (раздел 6);
- `cover_url(page, min_width=1200)` - абсолютный адрес обложки в JPEG/PNG не уже `min_width` (по умолчанию 1200 независимо от `images.cover_width`; крупнее - передайте `min_width` явно); нет такого варианта - адрес мастера; обложки нет - пустая строка. Он же доступен фильтром: `{{ page|cover_url }}`;
- `robots_meta` - строка для `<meta name="robots">`: `max-image-preview:large, max-snippet:-1, max-video-preview:-1` для индексируемой страницы прод-сборки, иначе `noindex, nofollow`. Страница с `noindex: true` и любая не-прод сборка получают закрытый вариант.

```jinja
{% set cover = cover_url(page) %}
{% if cover %}<meta property="og:image" content="{{ cover }}">
<meta name="twitter:image" content="{{ cover }}">{% endif %}
<meta name="robots" content="{{ robots_meta }}">
```

Имена `cover_url` и `robots_meta` зарезервированы: эти имена движок считает своими при проверке шаблонов темы.

## 8. Картинки

Для каждой картинки, на которую ссылается контент:

- варианты по ширине: 400, 800, 1200, 1600 - но не больше исходной
- форматы: AVIF и WebP на всех ширинах; исходный - запасной для `<img src>` (у мастера WebP запасной файл тоже WebP; расширение берётся от мастера), одной шириной `images.fallback_width` (800), не больше ширины кадра. Другие ширины исходного формата режутся, только если их попросили через `media_url(src, ratio, width)`
- режется только то, на что есть ссылка в собранном сайте: пропорция, которую ни один шаблон не попросил, в сборку не попадает
- `srcset` и `sizes` проставляются модулем
- `width` и `height` обязательны в разметке - иначе прыгает вёрстка и растёт CLS
- `loading="lazy"` на всё, кроме картинки первого экрана
- нарезки хранятся в кэше, а в сборку попадают жёсткой ссылкой

Обложка страницы (`20` §4.2) режется особо: мастер всегда попадает в сборку целиком, а к запасным файлам добавляется JPEG/PNG шириной `max(images.fallback_width, images.cover_width)`, но не шире кадра (`images.cover_width` по умолчанию 1200). Мастер уже `cover_width` отдаётся целиком, `heron check` предупреждает.

Картинка, на которую есть ссылка, но которой нет на диске: в строгом режиме (`--strict` или `build.fail_on_warning`) - ошибка `E007` и остановка сборки; при обычной сборке - предупреждение «нет файла <путь>» (вид «картинки»), сборка идёт. `heron check` строже обычной сборки: отсутствующую картинку он считает ошибкой `E007` и без `--strict`. Битая картинка в проде дороже, чем упавшая сборка, поэтому для CI включайте `--strict`.

Режутся только `.jpg`, `.jpeg`, `.png`, `.webp` (`KEEP` в `heron/core/media.py`). `.avif`, `.gif`, `.svg` и любой другой файл копируются как есть, без вариантов.

### Кэш нарезок

Кодирование - самая дорогая часть сборки: 95 мастеров при трёх пропорциях, четырёх ширинах и трёх форматах дают больше двух тысяч файлов и минуты работы процессора. Правка одной строки в CSS не должна их стоить.

**Где лежит.** Рядом с папкой сборки, не внутри неё (`<родитель --out>/.heron-cache/`):

```
.heron-cache/
├── renditions/v5-<настройки кодировщика>/
│   └── <sha256 мастера>/
│       ├── shape.json             ширина, высота, есть ли прозрачность
│       ├── crop-16x9-800.webp     нарезка: способ, пропорция, ширина, формат
│       └── .used                  когда запись последний раз нужна была сборке
└── warnings.txt                   полный список предупреждений последней сборки
```

**Поворот по EXIF.** Мастер читается так, как его показывает браузер: тег Orientation (2-8) применяется до определения размеров, кадрирования и кодирования, в нарезку тег не идёт. Версия формата кэша - `v5`: записи `v4` повёрнутых фотографий были нарезаны без поворота, сборка их не берёт, уборка снимает.

**Идентичность - содержимое и параметры.** Папка записи - sha256 байтов мастера, имя файла - параметры преобразования; настройки кодировщика (качество, скорость) - в имени папки версии. Имя файла в сборке (`media/photo-16x9-800.webp`) берётся от сайта, байты - из записи по хешу. Поэтому «файл с таким именем уже есть» ничего не значит: изменённый мастер - другая запись, два сайта с одинаковым `media/photo.jpg` и разным содержимым не смешиваются, а с одинаковым - делят запись честно.

**Общий кэш и конкурентные сборки.** Несколько сайтов, собираемых в одну папку (`--out out/a`, `--out out/b`), делят `out/.heron-cache`. Файлы пишутся во временный файл рядом и ставятся `os.replace`: две сборки, режущие одно и то же, пишут одинаковые байты и никогда не видят недописанного файла.

**Как попадает в сборку.** Жёсткой ссылкой (§4, «Запись результата»); не вышло - копией. Общий inode не правится на месте никогда: и сборка, и кэш меняют только записи каталога.

**Что считается изменением.** Мастер - по содержимому. Состав нарезок - по спеку темы (`widths`, `ratios`, `formats`, `crop`, `fallback_width`): новая ширина кодируется, уже закодированные ширины и пропорции переиспользуются. Мастер, который уже видели, не декодируется ради плана: размеры и прозрачность - в `shape.json`.

**Уборка.** Кэш общий, поэтому «не нужно этой сборке» - не повод удалять. Сборка держит разделяемую блокировку кэша от плана картинок до записи результата; уборке нужна исключительная, и пока кто-то собирает, она откладывается до следующей сборки. Сборка отмечает нужные ей записи (`.used`); раз в сутки под исключительной блокировкой удаляются записи, которыми не пользовалась ни одна сборка 30 дней, и записи прошлых форматов. Нарезка, уже стоящая в сборке, удалением записи не задевается. Кэш прежнего формата (`media.json`, `media/` по путям сайта - он и смешивал сайты) удаляется при первой сборке.

**Кэш можно удалять в любой момент.** Он влияет только на скорость: первая сборка после удаления будет холодной. Именно поэтому он в `.gitignore` и именно поэтому прод и CI не обязаны его иметь.

**Одинаковые имена нарезок.** `media/photo.jpg` и `media/photo.png` дают одни и те же имена (`photo-16x9-800.webp`) - `E027`: переименуйте один из мастеров. Адреса нарезок существующих сайтов от этого правила не меняются.

### Сколько процессов

Кодирование независимо и упирается в процессор, поэтому раскидывается по ядрам. Задача - мастер, а не отдельная нарезка: дробить мельче значит декодировать исходник семьсот раз вместо девяноста пяти.

`build.workers` в `site.yaml`, ноль - по числу ядер машины. Ставят руками там, где ядра делят с другими задачами: в CI сборка сайта не одна на машине, и забрать все ядра значит замедлить соседей.

Прогресс тикает в порядке исходного списка, а не готовности. Иначе лог перестаёт читаться, а смотрят в него как раз на долгой сборке.

Число процессов выбирают по порядку: флаг `--workers N` у `heron build` и `heron serve` (0-64), переменная `HERON_WORKERS`, `build.workers`. Значение переменной вне 0-64 - `E011` с подсказкой; флаг вне диапазона отвергает сам `click`.

**Сбой пула не валит сборку.** В окружениях с ограниченным обменом между процессами (песочница macOS, контейнер без семафоров, часть CI) пул не создаётся или умирает. Тогда движок один раз предупреждает (`pool_fallback`) и кодирует остаток последовательно; нарезки, уже лежащие в кэше (`_reusable`), не кодируются повторно, результат побайтно тот же, что при `workers=1`. Сбоем пула считаются `BrokenProcessPool` и отказ при создании пула или `submit`: любой `OSError` (любой `errno`: `EACCES`, `ENOSPC`, `EROFS`, `ENOENT`, `EIO`... - типичные сбои `/dev/shm` в контейнере) и `NotImplementedError` об отсутствии семафоров. Это безопасно: если причина - настоящая ошибка диска, последовательная нарезка встретит её снова и поднимет как есть. Из `result()` ловится только `BrokenProcessPool`. В предупреждении `pool_fallback` - текст ошибки с `errno`. Ошибки воркера - `HeronError`, `PIL.*`, `ValueError`, а также `OSError` диска - пробрасываются как есть, фолбэк в них не включается.

### Скорость кодировщиков

У webp и avif выставлены явные регуляторы скорости - не умолчания библиотеки. Умолчание может смениться с обновлением зависимости и сделать сборку впятеро медленнее без единой строчки в нашем коде.

Замер avif на наборе из 95 мастеров, 800px, quality 82:

| speed | время на вариант | размер | к выбранному |
|---|---|---|---|
| 0 | 5.33 с | 43.0K | −5.7% |
| 4 | 0.69 с | 44.4K | −2.6% |
| **6** | **0.13 с** | **45.6K** | - |
| 8 | 0.05 с | 47.3K | +3.6% |
| 10 | 0.02 с | 57.1K | +25.0% |

Итоговые параметры кодировщика (не настраиваются из `site.yaml` и `theme.yaml`): `quality` 82 для webp, avif и jpeg; webp `method=4`; avif `speed=6`; PNG - без `quality`.

Выбрана шестёрка: четвёрка стоит впятеро дороже по времени ради двух с половиной процентов размера, десятка экономит время ценой четверти веса. У webp тем же способом выбран `method=4`: самый медленный режим давал 7 секунд на вариант вместо 0.1 при выигрыше около двух процентов.

## 9. Генераторы

### sitemap <a id="sitemap"></a>

Состав зависит от числа языков в `site.languages`:

- **один язык** - `sitemap.xml` и есть список адресов (`<urlset>`). Индекс над единственным файлом ничего не добавляет, кроме лишнего запроса;
- **два и больше** - `sitemap.xml` становится индексом, рядом лежит `sitemap-<lang>.xml` на каждый язык из `languages`, у которого есть индексируемые страницы. Языка, которого нет в списке, нет и в карте.

Включаются страницы с `published: true` и `noindex: false`, кроме страницы 404. `lastmod` из `updated`, полной датой с поясом (`20` §4.2). У записи, у которой есть версии хотя бы на двух языках, - `xhtml:link` на все версии плюс `x-default`, если есть версия языка по умолчанию. Тот же набор выводится в `<head>` (переменная шаблона `hreflang`), но с отличиями: в карте `xhtml:link` пишется только при наборе больше двух ссылок, а `hreflang` в шаблоне на многоязычном сайте есть у каждой страницы, даже без переводов (самоссылка); на одноязычном - пустой список. Полные правила - `20` §3.

**Картинки.** Запись страницы несёт `<image:image><image:loc>` (пространство `xmlns:image` объявляется, только если картинки есть): обложка первой, затем картинки из текста страницы (intro и секции, без блоков кода; берутся только ссылки на `.jpg`, `.jpeg`, `.png`, `.webp`, адресом мастера; картинки фронтматтера и `data/` кроме обложки не идут), всего не больше 20 (константа `SITEMAP_IMAGES`, не настройка), без повторов, только абсолютные адреса домена окружения (адрес обложки тот же, что отдаёт `cover_url`). Картинок в карте нет у сборок, которые не индексируются: на dev страницы закрыты `noindex, nofollow`, а адреса указывают на dev-домен.

Служебных типов записей в sitemap нет по определению: в системе нет сущностей без URL. Служебные записи, какие оставляют в картах сайта плагины CMS, здесь невозможны архитектурно.

### robots.txt <a id="robots-txt"></a>

В индексируемой сборке: `User-agent: *` и `Allow: /`, затем `seo.robots_extra`, пустая строка и обязательная строка `Sitemap:` с абсолютным адресом. В закрытой сборке (`env.indexable=false`) всегда `User-agent: *` и `Disallow: /`, без `Sitemap` и без `robots_extra`. Собирается, а не лежит файлом: положенный руками, он через полгода начинает врать.

### llms.txt <a id="llms-txt"></a>

По формату llmstxt.org: заголовок сайта, краткое описание, разделы со списком страниц и однострочными описаниями из `description`. Строится из того же дерева, что и меню, и по той же политике, что карта сайта: страница с `noindex` (или вне карты) не попадает ни в общий список, ни в список детей своего каталога.

При `seo.llms_txt: true` дополнительно `llms-full.txt` - весь текст сайта одним файлом.

**Одноязычный сайт** языковых файлов не получает: `/llms.txt` сразу содержит полный перечень страниц (с блоком `seo.llms_note` этого языка), `/llms-full.txt` - полные тексты, и они ссылаются друг на друга. Оглавление из одной ссылки заставило бы модель сделать лишний шаг ради того же содержимого.

**На многоязычном сайте файл собирается на каждый язык**, а не только на основной:

- `/llms.txt` - корневой: название сайта, описание и список языковых версий. Перечня страниц в нём нет, это оглавление;
- `/llms-<язык>.txt` - полный перечень страниц своего языка. В шапке ссылки на остальные версии и на корневой файл, чтобы модель, попавшая сразу на русский, знала о существовании других;
- `/llms-full-<язык>.txt` - то же с полным текстом, при `seo.llms_txt: true`.

**Навигация замкнута: тупиков в наборе нет.** Из любого файла можно дойти до любого другого:

| Файл | Куда ведёт из шапки |
|---|---|
| `/llms.txt` | на краткую и на полную версию каждого языка |
| `/llms-<язык>.txt` | на корневой, на краткие версии других языков, на свою полную |
| `/llms-full-<язык>.txt` | на корневой, на полные версии других языков, на свою краткую |

Ссылка между краткой и полной версией одного языка - не про языки, поэтому она есть и на одноязычном сайте, где блока «другие языки» нет вовсе. Полные файлы отключены (`seo.llms_txt: false`) - ссылок на них нет нигде.

Подписи строк - на языке самого файла, для корневого - на языке сайта по умолчанию; исключение - две подписи, зашитые по-русски для любого языка: `## Языковые версии` в корневом `/llms.txt` и `Все языковые версии:` в шапке `/llms-<язык>.txt` и `/llms-full-<язык>.txt` (переводятся только `TO_FULL`, `TO_SHORT`, `PAGES`, `FULL_TITLE`). Языку, которого нет в наборе подписей, достаётся английская: она понятна и модели, и человеку, а выдуманный перевод - никому. Готовые подписи есть для `uk`, `ru`, `en`, `de`, `pl`; в перечне языковых версий язык вне набора подписан своим кодом (`fr`).

Языки не смешиваются в одном файле намеренно: модель отвечает на языке того текста, который прочла, а близкие языки - украинский с русским - она путает чаще всего. Раздельные файлы дают ей выбрать нужный, перекрёстные ссылки - найти остальные.

Формат llmstxt.org языковых версий не описывает, поэтому конвенция своя: файл читает модель, ей достаточно внятной строки человеческим текстом.

Язык, у которого нет ничего, кроме заглушки, в список не попадает: ссылка на пустой файл хуже её отсутствия - модель уйдёт по ней и вернётся ни с чем.

**Сведения о сайте.** `seo.llms_note` даёт на каждый язык кусок markdown, который вставляется дословно:

- в `/llms-<язык>.txt` - после краткого описания, до перечня страниц;
- в `/llms-full-<язык>.txt` - после заголовка, до текстов страниц;
- в `/llms.txt` - текст языка сайта по умолчанию.

Порядок именно такой: сначала «что это за сайт», потом «как с ним иметь дело», потом содержимое. Читателю нужен ответ раньше оглавления - за ответом он и пришёл.

Блок не ищется в готовом тексте и никуда не «вставляется» постфактум: файл собирается списком строк, и место блока задано в момент сборки. Поиск по готовому файлу спотыкался бы о тексты страниц, где встречаются и заголовки, и цитаты, похожие на шапку.

Содержимое блока - факты о сайте, а не указания читающей модели. Текст с чужого сайта потребитель вправе считать данными, а не инструкциями; попытка управлять через него чужим агентом бесполезна и выглядит как внедрение инструкций.

### JSON-LD <a id="json-ld"></a>

Встраивается в `<head>` каждой страницы, тип зависит от типа страницы:

Типы разметки объявляет **тема**, ключом `types.<тип>.jsonld` в `theme.yaml`: у сайта услуг, магазина и справочника соответствие разное, и ядро его знать не обязано. Тип может объявить и сама страница: каждый ключ блока `schema` фронтматтера (кроме `entity`) со значением-картой, которого нет в `types.<тип>.jsonld`, добавляется в граф как новый узел.

Ядро строит то, что действительно знает само:

| Что | Откуда берётся |
|---|---|
| `@type`, объявленный темой | `theme.yaml` |
| `name`, `description`, `url`, `inLanguage` | страница: для узла `WebSite` `name` - `site.name` на языке страницы, при пустом - `site.domain`; для остальных типов - `h1` страницы (не `title`). `inLanguage`, `datePublished`, `dateModified` выводятся, только если словарь schema.org 29.3 разрешает их типу; тип вне словаря не фильтруется |
| `datePublished` | поле `date`, полночь UTC: `2026-03-14T00:00:00+00:00` |
| `dateModified` | `updated` или `build.updated_from`; из git - время коммита с поясом |
| поля организации и прочие реквизиты | блок `schema` в `site.yaml` |
| уточнения по конкретной странице | блок `schema` во фронтматтере |
| `BreadcrumbList` | построенные крошки, всегда, кроме главной |
| `primaryImageOfPage` | обложка страницы: `ImageObject` с `url`, `width`, `height` и `caption` из `alt` обложки (пустые `width`/`height` выбрасываются); добавляется к типам из фиксированного списка `WEBPAGE_TYPES` (`WebPage`, `AboutPage`, `CheckoutPage`, `CollectionPage`, `MediaGallery`, `ImageGallery`, `VideoGallery`, `ContactPage`, `FAQPage`, `ItemPage`, `MedicalWebPage`, `ProfilePage`, `QAPage`, `RealEstateListing`, `SearchResultsPage`), если сайт не задал свой. Появляется только у узлов из `types.<тип>.jsonld` темы и блока `schema`; стартовая тема `WebPage` не объявляет, узел `FAQPage`, собранный из секции, картинку не получает |
| `alternateName` | `site.alternate_names` языка страницы, в любом узле `WebSite` на любой странице, где его объявила тема или страница |
| `FAQPage` | секция, разобранная как `faq` |

Слияние многоуровневое: поля ядра, затем `schema.<тип>` из `site.yaml`, затем `schema.<тип>` фронтматтера страницы (вложенные карты сливаются, прочее заменяется), затем подстановки `{{ }}`. Данные организации живут в `site.yaml` и не дублируются в контенте.

Функция `jsonld()` отдаёт готовый JSON: один узел - объект с `@context`, несколько - `@graph`, графа нет - пустая строка. Символы `<`, `>`, `&`, U+2028 и U+2029 экранируются (`\u003c`), поэтому значение поля не может закрыть `<script>`.

**Проверка по словарю.** После сборки графа каждая страница отдаёт узлы пакету `heron/schemaorg`: типы, свойства, перечисления и типы значений сверяются со словарём schema.org 29.3 (`schemaorg-29.3.json`, коды `SCH001`-`SCH005`), картинки разметки - со сборкой (`SCH006`). Путь находки переводится в файл-источник и ключ: сквозной узел - `site.yaml`, `schema.entity.<путь>`; тип из темы - `theme.yaml`, `types.<тип>.jsonld.<i>`; блок страницы - файл контента; хлебные крошки и вопросы-ответы - `engine`. Ключ находки `<КОД>:<файл>:<путь>`, одинаковые ключи со страниц и языков сливаются в одну находку со счётчиком страниц. На `prod` находка - ошибка, иначе предупреждение; строка `schema_exceptions` в `site.yaml` или `--allow-schema` переводит её в раздел «Исключения разметки» отчёта. Страница с `noindex` проверяется так же. Существующие проверки `E020` остаются как были.

**Атрибуция.** Словарь - Schema.org vocabulary, release 29.3, https://schema.org, лицензия Creative Commons Attribution-ShareAlike 3.0 (CC BY-SA 3.0). Индекс собран движком из выпуска без описаний терминов; источник, коммит и сумма sha256 записаны в `heron/schemaorg/NOTICE.md`, файл едет в пакет и образ.

### redirects <a id="redirects"></a>

Собирает все `redirect_from` со всех страниц в `dist/redirects.map` формата nginx:

```
/old/address/  /new/address/;
```

Старые адреса сначала нормализуются: percent-encoding раскрывается, текст приводится к NFC, регистр сохраняется, завершающий слеш добавляется всем, кроме файлов (`20` §2, «Старые адреса»). Пример с кириллицей: `/%D0%BA%D1%80%D0%B5%D0%B4%D0%B8%D1%82` и `/кредит/` дают одну строку карты `/кредит/  /credits/;`, и 301 срабатывает на обе формы, со слешем и без. Адрес, который после декодирования не текст (слаг обрезан посреди буквы), остаётся в percent-форме и сверяется с `$request_uri`.

Проверки на этапе сборки - по нормализованной форме: старый URL не совпадает ни с одним существующим, один старый URL не ведёт в два места, цепочек нет (`E009`).

Рядом - список 410 из ключа `gone` в `site.yaml` (`20` §5): точные адреса, префиксы `/wp/*` и адреса с параметром `/?p=*`. Пересечение со страницей или с `redirect_from` - `E022`. Копия списка - `dist/gone.map`.

Обе карты движок вписывает в конфиг nginx, который собирает вместе с сайтом (`dist/.heron-nginx.conf`): точный адрес - `location = "/старый/"` (и вариант без слеша), префикс - `location ^~ "/wp/"`, запись с параметром - регулярная карта `map "$uri?$args"`, битый percent-адрес - регулярная карта по `$request_uri` (регистр `%xx` не важен, регистр букв важен). Строковые карты не используются: nginx сравнивает их без учёта регистра, а адреса движка регистр различают. **301 и 410 срабатывают только при точном совпадении регистра** с записью в `redirect_from` или `gone`: адрес в другом регистре (`/about/` при записи `/About/`, латиница и кириллица одинаково, точный адрес и префикс) получает 404. Это задуманное поведение, его закрепляет `tests/test_nginx_redirect_case.py`; нужен второй вариант регистра - он пишется отдельной записью. Ответ уходит без обращения к файлам. Адреса 301 и 410 сверяются между собой, со страницами и со служебными адресами в форме без завершающего слеша - сервер отвечает на обе (`/a.html` и `/a.html/` - один адрес; совпадение - `E009` или `E022`). Управляющие символы в старом адресе (`%0A`, `%00`) - тоже `E009`/`E022`. Префикс `gone`, совпадающий со служебным (`/media/`, `/assets/`, `/.well-known/`, языковой `/<lang>/`), и 301/410 на служебных страницах 404 - `E022`.

### feed

`dist/feed.xml` в формате Atom - только если в `site.yaml` задан `seo.feed`: тип страниц, которые идут в ленту. Берутся опубликованные и индексируемые страницы этого типа на языке по умолчанию, не больше `seo.feed_limit` (20). Порядок - по дате публикации (`date`), у страниц без неё - по дате обновления, новые сверху. У записи есть `<published>`, если задана `date`, и `<updated>` - полной датой с поясом, как в разметке. Заголовок ленты - `h1` главной языка по умолчанию, иначе `site.name`, иначе домен; запись: `title` = `h1`, `link` и `id` - абсолютный адрес, `summary` = `description`, `updated` = `updated` или `date` (иначе `1970-01-01`); `updated` ленты - самая поздняя из записей; при равных датах порядок по адресу (по убыванию).

### Конфиг nginx <a id="nginx-conf"></a>

Генератор `heron/modules/nginx.py` пишет `dist/.heron-nginx.conf`: `listen 8080`, `root /usr/share/nginx/html`, `/healthz`; заголовки безопасности (`nosniff`, `Referrer-Policy`, CSP, HSTS); `Cache-Control: no-cache` для страниц и `public, max-age=86400` для `/media/` и `/assets/`; gzip; запрет скрытых файлов, кроме `/.well-known/`; `location ^~ /<lang>/` со своей 404 для неосновных языков; комментарии на языке `build.notes`.

**Переменные окружения.** `SITE_ENV` - окружение для `check --env` и `build --env` (флаг, затем `SITE_ENV`, затем дев); `HERON_NOTES` - язык пояснений для всех команд, включая `init`, `setup`, `docs`, `schema`: справка, сообщения, рамка ошибок, отчёт `check` и `build`, комментарии и записки в файлах сайта, язык `docs` и `schema`, если у них нет своего `--lang`; `HERON_IN_CONTAINER=1` - режим образа (включается и по наличию файла `/.dockerenv`); `HERON_DEBUG=1` - как `--debug`; `HERON_WORKERS` - процессы нарезки; `SOURCE_DATE_EPOCH` - время сборки для `env.stamp` (§4); `HERON_THEMES_URL` - каталог тем; `HERON_CHANNEL`, `HERON_REVISION`, `HERON_BUILT` - из них собирается строка `heron --version`.

- `requires` в `theme.yaml` - список путей к нужным блокам и полям `site.yaml` (`20` §2); если пути нет, `heron check` сообщает об этом до сборки;
- `-v`, `--verbose` (у `new` и `init`) печатает весь план файлов, а не краткую сводку; `-y`, `--yes` принимает значения по умолчанию без вопросов и подтверждения;
- `--drafts` включает `published: false` (у `serve` включено по умолчанию, `--no-drafts` выключает, у `check` и `build` парного флага нет); `--strict` превращает предупреждения в ошибки - режим для CI;
- `--allow-schema КЛЮЧ` (у `build` и `check`) - разовое исключение для находки `SCH001`-`SCH006`, ключ вида `<КОД>:<файл>:<путь>`; флаг повторяемый и действует только в этом запуске, `site.yaml` не меняется. Ключ проверяется тем же правилом, что `schema_exceptions[].key`; неверный - ошибка. `check --env ИМЯ` задаёт окружение для строгости `SCH`, как у `build`: флаг, затем `SITE_ENV`, затем дев. Без `--env` у `build` тоже действует `SITE_ENV`.
- `--env prod` - боевая сборка: индексация и счётчики. Без него - дев: `robots.txt` с `Disallow: /`, `noindex`, без счётчиков. Пустой сайт и пустой основной язык допустимы только в деве (`E017`, `E021`);
- `heron new` создаёт сайт в новой папке или в текущей (`.`). Папка может быть под git: `.git`, `.gitignore`, `.gitattributes`, `.gitmodules`, `.github`, `.gitlab`, `.DS_Store`, `.editorconfig`, `README`, `LICENSE` не мешают и не перезаписываются. Любой другой файл - отказ с перечнем того, что мешает, и советом `heron init`;
- **в терминале `new` задаёт вопросы**: язык пояснений, название, домен, языки сайта, основной язык (последний - только если языков больше одного). У каждого вопроса есть значение по умолчанию в скобках; введённое заменяет его целиком (`ru, de` на вопросе с `[en]` - два языка, а не три). Неверный ответ переспрашивается, в конце - сводка и подтверждение; отказ ничего не создаёт. Основной язык, которого нет в языках сайта, - не тупик: «en нет в языках сайта. Добавить? [Y/n]» - да дописывает его в конец списка, делает основным и печатает получившийся список, нет - снова вопрос об основном языке. `<` - назад к предыдущему вопросу (ниже, «Опрос в терминале: шаг назад»). **Без терминала** (агент, CI, `docker run` без `-it`) вопросов нет: значения из флагов `--name`, `--domain`, `--lang` (через запятую, первый - основной) или по умолчанию, и об этом печатается строка. Отдельного флага основного языка нет - основной всегда в списке; ответы `heron setup --answers` с `default_lang` не из `languages` - отказ с подсказкой («допишите его в site.languages или выберите site.default_lang из них»), язык сам не дописывается. `-y` отключает вопросы и в терминале. Ответы ложатся в `site.yaml`, под каждый язык сразу создаются `content/<язык>/index.md` и `404.md` с полным SEO-блоком: стартовый сайт собирается `--env prod --strict` без единого предупреждения. Дальше `site.yaml` - единственный источник правды, `heron init` достраивает папки под написанное;
- `--notes ru|en` - язык пояснений: комментарии во всех файлах скелета (`site.yaml`, `theme.yaml`, SEO-блок страниц), записки `heron-readme.md` и сообщения на экране: шаги и итог `new`, `init`, `page`, `check`, `build`, ошибки. Тому же языку следуют отчёт `check` и `build` (его разделы: «Страниц - N» / «Pages - N», типы, переводы, ссылки, сироты и прочие) и рамка сводки ошибок и предупреждений («Предупреждений - N» / «Warnings - N», виды предупреждений, «… и ещё N» / «… and N more», «что сделать» / «what to do»), а также ошибка раскладки `E024` у `init` и `new` (заголовок и подписи рамки). Подробности и подсказки ошибок и предупреждений следуют языку сообщений; текст самой библиотеки (ошибки Pydantic, PyYAML, Jinja2 и подобные) остаётся как есть; `E033` от `check` (§12) имеет текст и рецепт на обоих языках. Порядок: флаг → переменная окружения `HERON_NOTES` → `build.notes` из `site.yaml` → `en`. `new` записывает выбор в `build.notes`, поэтому `init` и `page` без флага держат язык, на котором сайт заведён. Языки самого сайта от него не зависят. `--notes` принимают все команды (и сам `heron` перед командой); на этом же языке справка `--help` и служебные строки разбора флагов (`Usage`/«Использование», `Error`/«Ошибка»), а комментарии рецепта `heron recipe` - на языке пояснений текущей папки. Язык справки выбирается до разбора аргументов: `--notes`, `HERON_NOTES`, `build.notes` из `site.yaml` текущей папки, иначе `en`; строка `heron --version` одна на оба языка - её разбирают скрипты. Если `site.yaml` не разбирается, после флага и `HERON_NOTES` язык ищется в его тексте строкой `notes: ru|en` (закомментированная не считается), иначе `en`: рамка ошибки `E011` и «что сделать» - на языке сайта;
- `heron init` смотрит, что в папке есть, дописывает недостающее, ничего не перезаписывает без `--force` и печатает, что нашёл и что добавил. **Нет `site.yaml` - сайт только заводится**: в терминале те же вопросы, что у `new`, с теми же флагами; языками по умолчанию предлагаются папки, которые уже лежат в `content/`. Есть `site.yaml` - вопросов нет, источник правды он;
- `new` в папке, где уже есть `site.yaml`, не перечисляет «мешающие файлы», а говорит, что сайт здесь уже есть, - на языке этого сайта (`build.notes`) - и предлагает `init`, `check`, `build` или как начать заново;
- **название по умолчанию** - имя репозитория из `origin` в `.git/config`, иначе имя папки. В контейнере папка всегда `/site`, поэтому без репозитория там предлагается `my-site`;
- `new` и `init` печатают сводку по смыслу (конфиг, контент по языкам, тема, папки, записки, что не тронуто) и блок «Что дальше» с готовыми командами под эту папку; полный список файлов - `-v`. В контейнере (`HERON_IN_CONTAINER=1` или `/.dockerenv`) каждая подсказка `heron …` в сообщениях - и здесь, и в ошибках, `check`, `build`, `page`, `setup` - печатается отдельной строкой полной командой `docker run … ghcr.io/fmstm/heron:<тег> …` под образ своего канала (`HERON_CHANNEL`: `prod`, `beta`, `dev`; релиз `vX.Y.Z` - тег `X.Y.Z`; без канала - `prod`): `-it` у `new`, `init`, `setup`, `serve`, ещё `-p 127.0.0.1:8000:8000` у `serve`, а у `setup`, `studio` и `--web` - `-p 127.0.0.1:8000:8000 -p 127.0.0.1:8001:8001` (второй порт - просмотр и справка темы; если в команде есть `--port` или `--preview-port`, в `-p` - их номера). Справка `--help` остаётся короткой;
- **пути - относительно текущей папки.** В образе (`HERON_IN_CONTAINER=1` или файл `/.dockerenv`) видна только смонтированная папка `/site`; путь с компьютера человека, которого внутри нет, даёт объяснение про монтирование и совет передать `.` или имя вложенной папки;
- **трейсбек наружу не выходит.** Ошибка движка печатается по форме: код и название, где, подробно, что сделать. Нет прав на запись - совет про `--user $(id -u):$(id -g)`. Непредвиденная ошибка - её вид, текст и совет повторить с `--debug` (или `HERON_DEBUG=1`), который отдаёт трейсбек целиком;
- `heron page add` и `heron category add` создают файл на каждом языке сайта с полным SEO-блоком и всеми секциями типа из `theme.yaml`, а существующий открывают на правку (ниже);
- `heron new` кладёт белую тему (светлая и тёмная, переключатель языков и вида) и её демонстрационные страницы в каждый язык: главная, `blocks.md` (все тринадцать форм), `themes.md`, `docs.md`, раздел `structure/` (`_index.md` с `view: list` и две страницы внутри), 404, меню `["/", blocks, themes, docs, structure]`, картинки `media/demo/`. Демо показывает каждый тип, блок и вид раздела белой темы (§7, «Демо темы и справка»). Тексты - на украинском, русском и английском, другие языки получают английские. Флага «без демо» нет: демонстрационные страницы - часть темы. `heron init` дописывает их новому языку, только если в основном языке ещё лежит `blocks.md`;
- **комплект для агентов** (`20` §1): `new` и `init` кладут `agents/` и корневые `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` на языке пояснений, если `build.agents` не `false`. `init` без флагов (и конфигуратор `setup`, который зовёт тот же `init`) файлы `agents/` только дописывает: недостающие кладёт, существующие не перезаписывает, `--force` на комплект без флага не действует; корневые указатели (`AGENTS.md`: имя, языки, домен, о проекте) обновляются по хешу из манифеста - нетронутый заменяется, правленный человеком остаётся. Язык при этом - `lang` манифеста, а не `build.notes`: недостающее и указатели ложатся на языке снимка, шапка манифеста не меняется. Если `build.notes` другой, сводка печатает строку-сведение «комплект оставлен на <язык>, build.notes - <язык>: сменить язык комплекта - heron init --agents» - при каждом `init`, пока языки расходятся. Манифеста нет, он битый или `lang` в нём не ru/en - берётся `build.notes`. `init --agents` - обновление комплекта по манифесту на языке `build.notes`: файлы, чьи sha256 совпадают с `agents/heron-kit.yaml`, заменяются новой версией, правленные пропускаются и перечисляются («правлен вами: `agents/roles/content.md`»), новые кладутся, лишние не удаляются; с `--force` заменяются и правленные. Если язык комплекта при этом меняется, `lang` манифеста становится новым, а сводка печатает «язык комплекта сменился: <старый> → <новый> (build.notes)»; повторный `init --agents` молчит. `--no-agents` у обеих команд ничего из комплекта не кладёт, манифест и `AGENTS.md` не трогает и записывает `build.agents: false`; `init --agents` на таком сайте включает комплект обратно (`build.agents: true`). Источник файлов - документация пакета (`heron/_docs/docs/<язык>/`), схемы генерируются той же функцией, что `heron schema --export`. Сводка `new`/`init` называет комплект одной строкой («инструкции для агентов: agents/, AGENTS.md - ru»), `-v` перечисляет файлы. Все записи - через проверку пути (`E024`), запись детерминирована (одинаковый вызов - одинаковые байты, кроме `created` без `SOURCE_DATE_EPOCH`);
- `heron docs` - документация ровно этой версии движка, из пакета: без аргументов - оглавление, с темой - файл целиком в markdown, `template <файл>` - образец, `--search` - строки с контекстом, `--export <папка>` - всё папкой с теми же путями, что в репозитории (`--all-langs` - оба языка в `ru/` и `en/`). **Язык:** `--lang ru|en`, иначе `--notes`/`HERON_NOTES`/`build.notes` из `site.yaml` текущей папки (в образе - смонтированной `/site`), иначе `en`. Темы читаются из `docs/<язык>/`; нет файла на этом языке - печатается файл другого языка, и первой строкой вывода идёт пометка на языке запрошенной темы: для `--lang en` - `[ru: no English translation yet]`, для `--lang ru` - `[en: перевода на ru пока нет]`; устаревший перевод (`docs/translation.yaml`, `23` §10) помечается так же: `[en: the translation lags behind ru]`. Оглавление (`heron docs` без аргументов) помечает в строке темы, что она откроется на другом языке: `(opens in ru)` для `en`, `(откроется на en)` для `ru`. Темы: `agents` - указатель репозитория (`AGENTS.md`, двуязычный), `kit` - README комплекта, `readme` - README репозитория по языку запроса (`README.md` для `en`, `README.ru.md` для `ru`; нет файла нужного языка - отдаётся другой с пометкой, как у остальных тем), роли `architect`, `content`, `designer`, `builder`, `capabilities`, гайды `install`, `concepts`, `first-site`, `pages`, `theme`, `seo`, `deploy`, `theme-author`, справочник `contract`, `engine`, `deploy-spec`, `distribution`, `architecture`, `skills` - навыки из `skills/`, `schemas` - какие схемы есть и как их получить; `template <файл>` - образец; `theme-ref [путь]` - справка темы сайта по пути (по умолчанию «.») из её контракта и демо (§7, «Демо темы и справка»). `--export` выкладывает `docs/<язык>/**`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` шаблона сайта и `schemas/` - ровно то, что получает новый сайт в `agents/`, - и советует начать с `README.md`. В пакет и образ едет только текст (оба языка и навыки - около 1 МБ, сжатым - около 300 КБ), картинки бренда - нет; тест следит, чтобы каждый файл документации был доступен как тема на своём языке;
- `heron schema` - JSON Schema (draft 2020-12) контрактов этой версии: `--site` (по умолчанию) - `site.yaml`, `--theme` - `theme.yaml`, `--frontmatter` - фронтматтер страницы (поля из `20` §4.2; поля связей, объявленные темой, и свои поля `page.meta` допускаются как дополнительные; правила, которых схема не выражает - завершающий перевод строки, зависимости полей, - записаны в `description` словами из контракта), `--setup` - ответы конфигуратора, `--describe` - вывод `heron describe --json`, `--errors` - реестр кодов ошибок: `{"$id": …, "$schema": …, "x-heron-version": …, "errors": {"E002": {"title": …, "hint": …}}}`, включая `SCH001`-`SCH006` (тот же словарь, что печатает движок; совпадает с §11). `--export <папка>` пишет все шесть файлов (флаг вида при этом не учитывается; два флага вида сразу - ошибка вызова): `site.schema.json`, `theme.schema.json`, `frontmatter.schema.json`, `setup.schema.json`, `errors.json`, `describe.schema.json`. Вывод детерминирован: ключи отсортированы, отступ 2, не-ASCII без экранирования, перевод строки в конце; два запуска побайтно равны. `$id` - `https://sitebuilder.heron.software/schema/<major.minor>/<имя>.schema.json`, у реестра - `.../errors.json`; поле `x-heron-version` - точная версия движка. Подсказки в редакторе: выгрузите схемы `heron schema --export schemas/` и укажите нужный файл в настройках YAML вашего редактора;
- `heron check --json` - тот же отчёт для агента и CI, одним JSON-объектом в stdout, человеческого вывода нет. Код выхода `0` - ошибок нет (при `--strict` - и предупреждений), `1` - есть. Поля: `ok` (bool), `version` (строка `heron --version` без префикса `heron, version`), `strict`, `pages` (число страниц, целое; `null`, если до разбора не дошло), `schema` (раздел разметки отчёта, `section.as_json()`, или `null`), `errors` - список `{code, path, line, message, hint}`, `warnings` - список `{kind, path, line, message}` (`kind` - служебное имя вида, по-русски, не переводится; `message` и `hint` - на языке сообщений, как в обычном выводе), `pending` - страницы с пометкой «перевод не готов», `{lang, path, published}` (`published` - попадает ли версия в эту сборку: в `--env prod` - нет, `20` §4.2), `kit` - `{present, engine, lang, current}` о комплекте `agents/` (`current` - совпадает ли `engine` манифеста с движком; манифест не читается - `present: true`, остальное `null`). С `--old-urls` потерянные старые адреса попадают в `warnings` (вид «редиректы», путь `old-urls`), а в объект добавляется раздел `old_urls` - `{summary, lost}`: `summary` - строка сводки, `lost` - список `{path, line, message}`, тексты на языке сообщений; без `--old-urls` раздела нет. Новые поля добавляются, существующие не переименовываются и не исчезают в пределах минорной версии.

Упаковки в образ среди команд движка нет: образ nginx с сайтом собирает **хост** - `scripts/site.sh <сайт> image <окружение>` из репозитория движка (`23-distribution.md` §5).

### Опрос в терминале: шаг назад <a id="steps-back"></a>

Оба опроса терминала - сайта (`new`, `init` без `site.yaml`) и страницы (`page add`, `category add`) - понимают `<`: ответ из одного этого знака возвращает к предыдущему вопросу. Подсказка об этом - один раз, во вступлении опроса.

- **Вопрос - каждый запрос ввода**: поле, «Изменить?» свёрнутой группы, категория, тип, вопрос «Добавить?» основного языка, «Записать?»/«Создать сайт?». Назад - через группы и секции. В списках по пункту на строке каждая строка пункта и каждое поле пункта с `+` - свой вопрос: `<` на строке пункта возвращает к предыдущему пункту (полю), на первом - к вопросу списка. Повторный вопрос после справки `?` или отказа проверки - тот же вопрос: `<` на нём уводит к вопросу перед ним.
- **Прежний ответ - в скобках**: вопрос, к которому вернулись, показывает данный на него ответ вместо значения по умолчанию, Enter его оставляет. Ответы на вопросы дальше не теряются: когда опрос до них дойдёт снова, они тоже стоят в скобках (если вопрос ещё задаётся - от нового ответа набор вопросов может измениться).
- **Первый вопрос**: `<` печатает «раньше вопросов нет: это первый» и спрашивает снова.
- **Сам знак**: значение `<` вводится как `\<`, а `\<` - как `\\<` (снимается одна обратная косая черта). `<b>`, `a < b` - обычный текст.
- **Ничего не пишется до конца**: опрос держит всё в памяти до последнего «Записать?»/«Создать сайт?»; Ctrl+C - выход без изменений. Шаг назад проходит опрос заново с данными ответами (`heron/steps.py`), без вопросов и молча, до нужного вопроса; страница при этом возвращается к состоянию до опроса.
- `--answers`, `--dump`, `-y` и запуск без терминала шага назад не знают: вопросов там нет.

### heron page add, heron page list, heron category add <a id="page-add"></a>

Страницы и категории создаёт и правит одна команда на объект, правило одно: **есть - открыть на правку, нет - создать**. Ядро - `heron/edit/entity.py` (найти, создать, править, перенести на всех языках) и `heron/edit/console.py` (консольный опросник); студия в браузере (`heron studio`, ниже) вызывает те же функции.

- `heron page add <ключ> [--type T] [--category путь] [--lang L] [--answers файл|-] [--dump] [--web] [-y] [путь]`. Ключ - путь от папки языка без `.md`: `about`, `services/roofing`; каждая часть - латиница в нижнем регистре, цифры и дефис, иначе `E005` до записи. `--category services` кладёт страницу в категорию: ключ `services/<имя>`. Без категории и без слеша ищется существующая страница с таким именем в любой категории: одна нашлась - открывается она.
- **Создание - сразу на всех языках `site.yaml`.** Тип по умолчанию (без `--type`) - `children_type` категории, иначе `page` (или первый тип темы); неизвестный тип - `E041`. Заготовка - полный SEO-блок с комментариями (`20` §4.1) и все секции типа из `uses`. Недостающие категории на пути создаются попутно, тоже на всех языках, - при создании и переносе; правка существующей страницы их не заводит. Под ключом уже лежит другое (страница вместо категории или наоборот) - `E004` с готовой командой для того, что там есть.
- **Опросник** (терминал на вводе и выводе, без `-y`): у новой страницы - категория из дерева (номер; номер и `+` - новая категория внутри; `+` - новая в корне), тип, если в теме их больше одного, затем поля `heron.edit.fields` по группам `groups` - те же, что покажет студия. У поля - значение, которое останется, если ничего не вводить (`Enter`; введённое заменяет его), одна строка `hint`; `?` - `help` целиком, `-` - очистить, `<` - назад к предыдущему вопросу (выше, «Опрос в терминале: шаг назад»). Проверка на лету - `edit.validate`, правила `heron check`: ошибка - поле спрашивается снова, предупреждение печатается. Группы «Меню», «Обложка», «Соцсети», «Публикация», «Разметка» открываются вопросом «Изменить?». Основной язык спрашивается целиком; на остальных - только поля с текстом (`title`, `h1`, `description`, `nav_title`, `slug`, подписи, заголовки и текст секций): перевод или `Enter` - пропустить. Пропущенное поле оставляет текст основного языка и ставит языку `translation: pending` (`20` §4.2); у существующего непереведённого языка опросник спрашивает, готов ли перевод. В конце - итог по файлам и «Записать?».
- **Без терминала** (агент, CI) или с `-y`: новая страница создаётся с заготовкой и флагами, остальные языки - с пометкой; существующая не меняется, команда печатает её файлы по языкам и как править. `--answers файл` (`-` - stdin) - ответы YAML: `key` (новый ключ - перенос), `type` (тип новой страницы), `<язык>:` - поля по путям `heron describe` и `--dump` (`title`, `menu`, `category`, `sections.intro.text`); у неосновного языка вместо полей можно `pending`. Новый язык без перевода всех полей с текстом получает пометку; `translation: null` снимает её. Неизвестный ключ, язык или поле, значение, которое не записать, и ошибки проверки - `E039` до записи, файлы не тронуты. Неосновной язык правит только поля со своим значением: поля с текстом, пометку `translation`, свои `redirect_from` и `updated`, разметку `schema`, свою обложку и картинку для соцсетей (`image`, `og_image`) и свои поля темы с `translatable: true` - пустое значение убирает поле из файла, и язык снова берёт значение основного; остальные (тип, порядок, флаги, дата, вид раздела, свои поля темы без текста, меню, категория, якорь блока) общие - их правит основной язык, и правка пишет общее поле во все файлы страницы; на другом языке - `E039`. Правка обложки на основном языке в другие файлы не пишет: язык без своей обложки берёт её при сборке, язык с копией той же обложки остаётся с ней, файл не трогается. Новая копия языка обложку с подписью, картинку для соцсетей и поля с `translatable: true` не копирует; подпись `image_alt` перевод спрашивает, если у языка есть обложка - своя или основного. Однострочное поле (`title`, `h1`, подписи, заголовок блока, пункт-строка) без перевода строки; текст блока не начинает нового блока - заголовок с якорем `{#…}` внутри значения и новый блок на неосновном языке, которого нет на основном, - `E039`. Раздел на месте папки 0.2, где на неосновном языке уже есть переведённые страницы, без перевода на этом языке спрятал бы их из прод (непереведённый раздел держит страницы внутри): без согласия - `E039` до записи со списком страниц; согласие - `<язык>: pending` в ответах `category add`. Если такой раздел создаётся попутно (новая страница или перенос внутрь папки), - `E039` с советом сначала `heron category add <папка>` с переводом. `--dump` печатает текущие значения в том же виде (у новой страницы - заготовку; у неосновного языка - поля перевода, свои `redirect_from` и `updated`, обложку и поля с `translatable: true`, только если они в файле есть, пометку `translation`), ничего не создаёт: `--dump`, затем `--answers` с тем же файлом - байт в байт без изменений, в том числе на сайте 0.2 и на частично переведённой странице.
- **Правка пишет только то, что изменилось.** У существующей страницы или категории (`--answers`, опросник, студия) запись меняет только файлы, текст которых стал другим. Языка без файла она не создаёт, пока его не перевели (поле этого языка) или не попросили копию (`pending`, «Пропустить язык»); категорий выше - тоже (их заводят создание и перенос). Папка без `_index.md` (так делал 0.2) работает как раньше - разделом без своей страницы: `heron check` предупреждает (путь - основного языка, если в папке есть его страницы) и советует `heron category add <путь>`, `page list` показывает её строкой категории с пометкой. `category add` на такой папке спрашивает поля раздела на каждом языке, где в ней есть страницы; язык, оставшийся без перевода, не публикует и их - опросник и студия перед записью называют эти страницы («N переведённых страниц на en выпадут из prod, пока раздел не переведён») и спрашивают подтверждение. Новая копия языка не наследует `redirect_from` и `updated` основного: у языков свои адреса и свои даты правки.
- `--lang L` - правка одного языка: у основного - всех полей, у другого - полей со своим значением (общие правит основной); язык не из `site.languages` - `E005`. Создание всегда идёт на всех языках.
- **Перенос и переименование** при правке: `--category` другой категории, поле «Категория» в опроснике или `key` в ответах. Файлы двигаются на всех языках (у категории - папка целиком), страница и все страницы внутри перенесённой категории получают `redirect_from` со своих прежних адресов (301, `20` §2), ключи в `nav` файла `site.yaml` следуют за ключом. Занятый ключ - `E004`, категория внутрь самой себя или перенос главной - `E005`; всё проверяется до первой записи.
- `site.yaml` (меню, ключи после переноса) пишется с сохранением комментариев автора, тем же способом, что у `heron setup`; все пути записи - внутри папки сайта, иначе `E024` до записи.
- `heron category add <путь> [--type T] [--children-type T] [--view V] …` - то же для категории: папка и её `_index.md` на всех языках с SEO-блоком, типом страниц внутри (`--children-type`, ключ `children_type`, по умолчанию - `children_type` типа категории в теме) и видом списка страниц (`--view`) - ключ и варианты из `views` типа (`heron describe`); вид, которого тема не знает, - `E041` со списком. Разметку раздела (schema.org `CollectionPage`, `ItemList`) ставит тема по своему контракту (`types.<тип>.jsonld`).
- `heron page list [путь] [--json]` - дерево категорий и страниц: на каких языках есть файл (`ru`), где перевод не готов (`de!`), где файла нет (`--`); `--json` - `{languages, default_lang, items: [{key, category, type, title, langs, implicit}]}`, состояние языка - `ok`, `pending` или `missing`; `implicit: true` - папка без `_index.md` ни на одном языке (вместо языков строка советует `heron category add <путь>`).
- `--web` - студия в браузере сразу на этом объекте (`heron studio`, ниже): у новой - заготовкой, которая станет файлами только после «Сохранить»; `--type`, `--children-type`, `--view` - её начальные значения, `--category` у существующей - перенос, который ждёт записи. `--port`, `--preview-port` и `--host` - как у `heron setup`. Сама команда ничего не пишет.
- Старая форма `heron page <тип> <ключ>` убрана в 0.3.0: такой вызов - `E038` с той же страницей новой командой (`page page about` - `heron page add about`, `--folder` - `--category`), в контейнере - полной командой Docker.

### heron describe <a id="heron-describe"></a>

`heron describe [имя] [путь] [--json] [--lang L]` показывает контракт темы сайта (§7, «Контракт темы») вместе со служебными полями движка и значениями по умолчанию из `site.yaml`. Тема находится так же, как при сборке.

- Без имени - всё коротко: служебные поля по группам, типы и их секции по порядку, блоки и их поля с подсказками `hint`. С именем типа или модуля - только он (у типа - и модули, которые нужны его странице), с подробной справкой `help` и образцом markdown. Неизвестное имя - `E041` со списком типов и модулей.
- `--lang` - язык подсказок: `ru`, `en` или другой язык темы (код вида `pt-br`, иначе ошибка вызова, код 2). Без него - язык пояснений. Нет текста на этом языке - текст без суффикса, затем английский. Служебные поля - на ru и en.
- `--json` - одним объектом для агента и программ, форма - `heron schema --describe` (`describe.schema.json`). Каждый ключ есть всегда; чего нет - `null` или пустой список.

Ключи верхнего уровня `--json`:

| Ключ | Что в нём |
|---|---|
| `$schema`, `heron`, `lang` | адрес схемы, версия движка, язык подсказок |
| `selected` | `{kind: type\|module, name}` или `null` без имени |
| `site` | значения из `site.yaml` на языке `lang`: `name`, `languages`, `default_lang`, `title_suffix`, `og_default_image`, `menu` (`nav.main`), `updated_from` |
| `theme` | `name`, `title`, `version`, `heron`, `languages` (языки подсказок), `described` (описала ли тема поля) |
| `groups` | группы служебных полей по порядку: `name`, `title` |
| `service` | служебные поля: `page` и `section` - `name`, `type`, `group`, `where` (`frontmatter`, `path`, `site.yaml`, `heading`), `key`, `default`, `default_from`, `hint`, `help` и ограничения |
| `md_places` | словарь мест в markdown: `name`, `hint` |
| `types` | типы: `name`, `template`, `jsonld`, `children_type`, `views`, `sections` (по порядку `uses`: `id`, `any`, `kind`, `module`, `required`, `fields`), подсказки |
| `modules` | модули: `name`, `scope`, `kinds` (`kind`, `class` - класс в якоре, `auto` - узнаётся без класса), `schemaorg`, `fields`, `example`, подсказки |

Поле в `fields` - все ключи поля блока (§7) и подсказки; у вложенных пунктов - свои `fields`. Тот же объект используют опросник и студия: список полей страницы - `service.page`, затем секции её типа.

### heron setup <a id="heron-setup"></a>

Конфигуратор вместо ручного `site.yaml`. Без флагов поднимает локальную страницу (адрес и порт - как у `heron serve`: в образе слушает `0.0.0.0`, порты публикуются только на петлю машины `-p 127.0.0.1:8000:8000 -p 127.0.0.1:8001:8001`). Второй порт (`--preview-port`, по умолчанию `--port` + 1) - отдельный источник (origin) браузера для черновой сборки, справки темы и картинок из `media/`: там работают скрипты темы, и они не видят ни ключа, ни `/api/*`; страница открывает их в `<iframe sandbox>` по своему ключу просмотра, который разрешает только смотреть. Ключ страница читает из адреса и сразу убирает (`history.replaceState`). Адрес второго порта страница строит из своего: схема и имя - из адресной строки, порт - `location.port` минус порт студии плюс порт просмотра (оба внутренних номера сервер передаёт странице; нет порта в адресе - от 80 или 443). Поэтому проброс со сдвигом (`-p 9000:8000 -p 9001:8001`) работает без флагов. `frame-src` и `img-src` студии и `frame-ancestors` просмотра считаются так же - от порта в заголовке `Host` запроса, а не от внутренних номеров. Человеку движок печатает одну ссылку - на студию с ключом; второй порт ему знать не нужно. `--preview-port` - только если этот порт занят; совпал с `--port` или вне 1-65535 - `E031` до запуска, занят - `E031` с подсказкой про `--preview-port`. Граница доступа - ключ, который движок печатает в терминале в адресе страницы после `#` (`http://localhost:8000/#ключ`): в саму страницу он не вшит, и без него `/api/*` (чтение ответов, загрузка темы, запись) отвечает 403. Клиент, который дотянулся до порта, но не видел терминала, получает только пустую страницу. Заголовок `Host` дополнительно обязан быть локальным - это защита от подмены DNS, а не граница доступа. `--answers файл` применяет те же ответы без браузера - для агента и CI, `-` читает stdin; `--dump` печатает записанные ответы в YAML: поправить и подать обратно. Схема ответов - `heron schema --setup`.

Конфигуратор открывается только в папке сайта: нет `site.yaml` - отказ с советом перейти в папку сайта или создать его (`heron new`). Изменённое поле помечено «было: X» с кнопкой «вернуть» - сравнение с тем, что сейчас записано в `site.yaml`.

Группы конфигуратора:

1. **сайт и домены** - `site.name`, рабочий домен, служебный домен → `site.domains.dev`. Рабочий домен - тот, с которым собирается прод: `site.domains.prod`, если он задан, иначе `site.domain`; поменяли его - меняются оба, остальные окружения `site.domains` не трогаются;
2. **языки** - справочник языков, выбранные - вкладками, основной - из выбранных. Если в `site.yaml` основной язык не среди `languages`, блок «Сайт» читается как записан (не сбрасывается), а под основным языком - предложение «en нет в языках сайта» с кнопкой «Добавить en в языки»: язык дописывается в конец списка и остаётся основным; можно и выбрать основной из списка. Запись с таким расхождением - отказ с той же подсказкой, что у `--answers`;
3. **о ком сайт** - «кто вы»: человек или организация и вид организации (`heron/setup/vocab.yaml`), затем сфера деятельности и специализация по классификатору `heron/setup/classifier.yaml` (у специализации бывает точный тип schema.org: стоматология → `Dentist`; компания с ним - `["Corporation", "Dentist"]`; человеку - `hasOccupation`; вид «Врач, принимает в клинике или больнице» даёт тип `IndividualPhysician` с полями: специальность (`medicalSpecialty`), место приёма `practicesAt` (тип из списка, название, адрес: улица, город, регион, индекс, страна), `hospitalAffiliation`, `isAcceptingNewPatients`; специальность из классификатора ложится в `medicalSpecialty` списком адресов `https://schema.org/<имя>`, только у организации и только если словарь schema.org разрешает свойство её типу); поля на каждом языке сайта (имя, название, должность, «чем занимаетесь»), адрес блоком (страна справочником с телефонным кодом, город, регион, индекс, улица, дом), конструктор контактов `тип · назначение · значение`. Сфера и специализация ложатся подписями в `organization.field_of_work` и `organization.specialization` (с хвостами языков), в разметку - `knowsAbout`;
4. **поиск** - хвост заголовка разделителем и текстом (`seo.title_suffix`: конфигуратор и `--answers` всегда ставят пробелы вокруг разделителя, текст без разделителя получает « - »), `seo.og_default_image`, `seo.allow_prices`;
5. **ИИ-ассистенты** - `seo.llms_note` вкладками по языкам сайта;
6. **аналитика** - `analytics.ga4` (формат `G-...`), `gtm` (формат `GTM-...`), `metrika` (только цифры) (в сборку только при `--env prod`);
7. **публикация** - `publish:`: «пока не знаю», GitHub (репозиторий, ветка, версия, окружение, `auto` - автоматическая сборка и публикация образа), Docker Hub, статика (на сервер или GitHub Pages - с веткой); при сборке образа - таблица dev/prod: домен, индексация, адрес образа; помощники `publish.helpers` - скрипт сборки, скрипт публикации, `.gitignore`, каждый включается отдельно. При «пока не знаю» в `publish:` остаются только выключенные помощники и движок, если он не `prod`, - повторное открытие конфигуратора их не возвращает;
8. **ключи и модули** - в разработке, полей нет;
9. **тема** - текущая, из каталога (белая - `starter`), по ссылке, своим архивом.

**Ключи `publish` в ответах** (`heron schema --setup`):

- `way` - `github`, `dockerhub`, `static` или `none` (по умолчанию `none`);
- `auto` - `true`;
- `env` - `dev` или `prod` (по умолчанию `dev`);
- `engine` - `prod`;
- `branch` - `main`;
- `repo`, `dockerhub_user`, `image`, `server`, `path` - пустая строка;
- `static_target` - `server` или `pages` (по умолчанию `server`);
- `helpers` - `build`, `publish`, `gitignore`, все по умолчанию `true`.

Как ответы ложатся в `site.yaml`:

- каждый факт - в одно место: название и описание - `organization`, адрес - `contact`, каналы связи - `contact.channels` (`{type, purpose, value}`), первый телефон и первая почта - ещё и `contact.phone`/`contact.email` (их зовут подвал темы и подстановки разметки); языковые значения - хвостом `_<язык>` (`city_de`). Узел разметки `schema.entity` пишется подстановками (`"{{ contact.phone }}"`), а не копиями: телефон меняется в одном месте;
- пропущенный вопрос убирает ключ - пустого значения в разметке не бывает; уровень цен попадает в разметку только при `seo.allow_prices: true`;
- ключи, которыми конфигуратор не ведает (`gone`, `forms`, `nginx`, свои блоки), остаются как были. Узел `schema.entity` сливается в три стороны: база - что конфигуратор записал бы для прежнего конфига; ответ не менялся - ключ остаётся как в файле (поля руками - `geo`, `openingHours`, `medicalSpecialty`, `founder`…, точный `@type`, свой `@id`), менялся - берётся новый, ответ убран - ключ убирается; прежний `site.yaml` - в `.heron-cache/setup/site.yaml.<время>`; две копии в одну секунду получают `-2`, `-3`: файл создаётся исключительно, существующая копия не перезаписывается. Комментарии в `site.yaml` (над ключом, в конце строки, хвост файла и свой блок) конфигуратор сохраняет;
- итог проверяется той же схемой, что и сборка; не прошёл - ничего не записано;
- после записи структура следует за конфигом: новый язык получает папку, главную и 404 (`heron init`).

Файлы рядом с `site.yaml` (каждый с отметкой `heron setup`; файл без отметки не перезаписывается, свой файл, ставший ненужным при смене способа, убирается):

| Способ | Файлы |
|---|---|
| помощник | `.heron/scripts/build.sh` - итоговая сборка образом HERON по той же политике, что `scripts/site.sh` и `site-image.yml`: без сети, корень образа только на чтение, без capabilities, не от рута; папка сайта - только на чтение, на запись - только `dist/`, `.heron-cache/` и `.dist.heron-lock` |
| помощник | `.heron/scripts/publish.sh` - публикация выбранным способом (`git push`, образ в Docker Hub, `rsync`); `.gitignore` |
| GitHub | с `auto` - `.github/workflows/image.yml` (зовёт `site-image.yml` той же ветки HERON; путь задаёт GitHub) |
| Docker Hub | скрипт публикации: сборка, `heron recipe` → образ nginx, `docker push` (вход - `docker login` на компьютере) |
| статика | скрипт публикации (`rsync` на сервер) или `.github/workflows/pages.yml` (GitHub Pages; сборка - та же политика запуска) |

Сборочной логики в папке сайта по-прежнему нет: скрипты и workflow - короткие вызовы образа HERON; Dockerfile и `.env` в папку сайта не кладутся. Скрипты лежат в скрытой папке `.heron/` (внутри - `scripts/`, место и для другого служебного): движок её не читает, в `dist/` она не попадает. Прежние `scripts/*.sh` с отметкой конфигуратора убираются при следующем сохранении.

**Ключи и модули** пока в разработке: в конфигураторе полей нет, в `site.yaml` и git ключи не пишутся никогда. Docker Hub берёт вход из `docker login`, workflow GitHub - короткоживущий токен сборки.

В разметку контакты идут так: `telephone`/`email` - подстановкой основных, `contactPoint` - по каналу с назначением (`contactType`: main → customer service, support → technical support, sales, marketing, booking → reservations, press), `sameAs` - публичные профили (`t.me/…`, `wa.me/…`, соцсети). Состав `contactPoint` и `sameAs` конфигуратор переписывает при каждом сохранении.

Движок для сборки сайта - `publish.engine`: канал (`prod`, `beta`, `dev`), точная версия `X.Y.Z` или любое из них с digest - `prod@sha256:<digest>`. С digest `site-image.yml` берёт рецепт с ветки канала, а образ движка - ровно этот.

Значения публикации уходят в команды оболочки и в YAML, поэтому проверяются при чтении ответов: ветка `publish.branch` - буквы, цифры и `. _ - + /` по правилам git (без `..`, `//`, начального `-`, хвоста `.lock`); сервер - `user@host` без начального `-`; папка на сервере - абсолютный путь из букв, цифр и `. _ - + ~ @` без `..` (её разбирает ещё и оболочка на сервере). В скриптах значения дополнительно взяты в кавычки, в workflow ветка записана строкой. `site-image.yml` получает свои входные значения переменными окружения и проверяет их до первого шага сборки.

**Разметка в конфигураторе.** Перед записью `site.yaml` конфигуратор проверяет узлы сайта (`site_findings`: сквозной узел и блоки `schema.<Тип>` по каждому языку, без страниц и темы). Страница показывает три списка: действующие находки, исключённые (причина и срок) и просроченные исключения. В состоянии страницы это `schema.findings` с ключами `active`, `excepted`, `expired`; исключённые и просроченные - `{key, code, path, field, reason, until}`, действующие и отказ режима `check` (ответ 409) - `{key, code, title, detail, hint, field, path, value, drop_label}`; `field` - поле конфигуратора, к которому привязана находка, или `null`. Неизвестный `schema.mode` - отказ «режим X: check, drop или except»; `except` без `reason` - отказ до проверки; если находок нет, режим ни на что не влияет. Режим `schema.mode` в ответах: `check` (по умолчанию) - находки не записываются, ответ отклоняется списком; `drop` - убрать указанные ключи `schema.drop` (все, если список не задан) из `site.yaml`, перечень убранного попадает в итог; `except` - дописать в `schema_exceptions` запись `key` + `reason` на каждую находку, `reason` обязательна; если исключение с этим ключом уже есть (в том числе просроченное), его причина заменяется, а срок `until` снимается - исключение становится бессрочным. После `drop` проверка повторяется, остаток - отказ.

### heron studio <a id="heron-studio"></a>

Студия - страница конфигуратора с тремя вкладками: «Сайт» (конфигуратор `site.yaml`, как у `heron setup`), «Страницы» и «Справка темы». Сервер, ключ и правила доступа те же, что у `heron setup` (ниже): адрес с ключом после `#` печатается в терминале, в образе - подсказка про `-p 127.0.0.1:8000:8000 -p 127.0.0.1:8001:8001` (второй порт - просмотр и справка темы, номера - из `--port` и `--preview-port`); рядом - строка о том, что просмотр студия откроет сама. Команды: `heron setup` открывает вкладку «Сайт», `heron studio` - «Страницы», `heron page add … --web` и `heron category add … --web` - «Страницы» сразу на объекте.

Своей логики сохранения и проверки у студии нет (`heron/studio/`): каждый запрос открывает объект заново с диска (`edit.entity.open_entity`), применяет действия над секциями и ответы в том же виде, что `--answers` (§10, `page add`), и зовёт те же функции, что CLI: `problems` и `issues` для проверки, `save` для записи, `tree` для дерева, сборку для просмотра. Нетронутые файлы остаются байт в байт, `site.yaml` пишется с комментариями автора.

Вкладка «Страницы»:

- **дерево** категорий любой вложенности и страниц всех языков, у каждой - языки: есть файл, перевод не готов (`de!`), файла нет. Перетаскивание страницы или категории на категорию (или «В корень») - перенос: файлы на всех языках, `redirect_from` со старых адресов (301), пункты меню следуют за ключом;
- **форма** - поля `edit.fields` по группам `groups`, те же, что у опросника: служебные поля, разметка schema.org, секции и блоки в своих формах (пункты списков - карточками с полями блока). У каждого поля - `hint` подсказкой при наведении и `?` со справкой `help` и примером, значение по умолчанию и откуда оно; поле только для чтения показывает причину;
- **языки** - вкладками: основной язык - все поля; остальные - поля с текстом и свои `redirect_from` и `updated`. Новый файл языка: пустое поле - не переведено, язык получит `translation: pending`; «Пропустить язык» - пометка сразу. У существующего языка - флажок «Перевод не готов»;
- **проверка на лету** - `edit.validate` после каждой правки: ошибки (запись не пройдёт, `E039`) и замечания у полей и списком;
- **создание** - «+ Страница» и «+ Категория»: имя, категория, тип, у категории - тип страниц внутри и вид списка. Правило то же, что у команд: есть - открывается на правку, нет - заготовка, которая станет файлами на всех языках после «Сохранить»; недостающие категории выше создаются при записи;
- **блоки** - «+ Блок» добавляет секцию `## Заголовок {#якорь}` выбранной формы на всех языках; форму, которую движок узнаёт по содержимому, задаёт первый пункт (без него - `E039`). Языки с готовым переводом получают блок с текстом основного языка и пометку `translation: pending`. «Убрать блок» убирает секцию на всех языках;
- **картинки** - «Загрузить» кладёт файл в `media/` сайта: только `.jpg`, `.png`, `.webp`, `.gif`, `.svg`, тип проверяется и по содержимому, SVG разбирается XML-парсером (сущности и `&#x73;` уже раскрыты) и не принимается, если в нём есть `script`, `foreignObject`, `iframe`, `embed`, `object`, любой атрибут `on*`, ссылка со схемой (`javascript:`, `vbscript:`, `data:`, `blob:`, `http:`…) или на другой хост (`//`), `<use>` не на `#id` своего файла, анимация, подменяющая ссылку или обработчик, `@import` и `url(…)` не на `#id` в стилях и атрибутах оформления (CSS читается как в браузере: экранирование `u\72l(` раскрыто, комментарии убраны), DOCTYPE или сущности, инструкция обработки `<?…?>`, кроме объявления XML (`<?xml-stylesheet type="text/xsl"?>` запускает XSLT), пространство имён XSLT или атрибут `xsl:` (их видит второй проход, expat), а также если файл не читается как XML (`<svg/onload=…>`), до 25 МБ; проходит то, что пишет обычный редактор: `url(#id)`, `href="#id"`, картинка `data:image/png|jpeg|gif|webp` в `<image>`, `http(s):` и `mailto:` в `<a>`; те же правила `heron check` и сборка применяют к каждому SVG в `media/`, `static/` и в теме (`E043`: в `check` и боевой сборке - ошибка, в черновой и `heron serve` - предупреждение); имя - латиница (`Team Photo 1.PNG` → `media/team-photo-1.png`), занятое имя - `-2`, тот же файл - тот же путь. Ширину и пропорции из контракта (обложка - от 1200 px) проверяет `edit.validate`;
- **меню** - поле «в меню» правит `nav.main` в `site.yaml`; переименование - кнопкой, ключ и адрес меняются с 301;
- «**Проверить**» - `heron check` с черновиками; «**Посмотреть**» - черновая сборка во временную папку (как у `heron serve`) и ссылка на эту страницу.

Вкладка «Справка темы» - служебная страница `/_heron/theme/` (§7, «Справка темы») из той же черновой сборки, внутри студии.

Запросы - `POST /api/studio/<имя>` с ключом в `X-Heron-Token`: `start` (с чего открыться), `tree`, `open` и `check` (форма после правок, ничего не пишет), `save`, `upload?name=…` (тело - файл), `site-check`, `preview`. Ответ с ошибкой - `400` с `code`, `error`, `hint` на языке страницы. Просмотр сборки, справка темы и картинки из `media/` отдаёт второй порт (`--preview-port`) по своему ключу просмотра: страница студии получает его в ответе `start` и открывает адреса с `?k=<ключ>`; по ключу порт ставит cookie `heron-preview` (`HttpOnly; SameSite=Lax`), дальше страницы, стили и картинки идут с ней; без ключа и без cookie - `403`. Ключ просмотра разрешает только смотреть. Страницу просмотра порт отдаёт со скриптом `/_studio/preview.js` первым в `<head>`: он убирает `?k=` из адресной строки (`history.replaceState`), как страница студии убирает свой ключ после `#`. Скрипты страницы - отдельные файлы `/_studio/*.js`, политика `script-src 'self'`, встроенных скриптов и обработчиков в разметке нет.

### heron theme <a id="heron-theme"></a>

Архив темы: `heron-theme.yaml` (имя, совместимые версии HERON), `theme/`, `demo/` - демонстрационные страницы темы: `content/<язык>/`, `media/`, `data/`. Источники: `starter` - встроенная стартовая (без сети), имя - каталог `HERON_THEMES_URL` (по умолчанию `catalog.json` репозитория `FMSTM/heron-themes`: имя → https-адрес и sha256), https-ссылка (`#sha256=<хеш>` в конце сверяется), файл `.zip` или `.tar.gz`.

Распаковка недоверчивая: абсолютные пути, `..`, ссылки и устройства, части пути `plugins`, `.git`, `__pycache__` и расширения `.py`, `.pyc`, `.sh`, `.exe`, `.bat`, `.cmd`, `.ps1`, `.so`, `.dll` - отказ `E032`. Таймауты: загрузка архива 20 с, каталог тем 3 с. Запрет файлов кода сам по себе тему не обезвреживает: шаблоны поставленной темы собираются в песочнице (§7); предел 200 МБ на архив, 50 МБ на файл, 5000 файлов. Битый или усечённый архив (zip или tar.gz), в том числе повреждённые сжатые данные, - тоже `E032` («the archive is damaged or truncated»), а не `BadZipFile`/`EOFError`; конфигуратор отвечает на такой архив `400 {"ok": false, "error": …}`. Тема проверяется схемой `theme.yaml` до установки; прежняя уезжает в `.heron-cache/setup/theme.<время>` (в ту же секунду - `theme.<время>-2`). Путь к архиву у `theme get` - от текущей папки, а нет там файла - от папки сайта. Это доверенный путь из терминала: абсолютный тоже разрешён. В конфигураторе (`--answers`, сервер) источник `file` без загрузки (`upload`) принимает только путь внутри сайта, от его корня (`themes/t.tar.gz`); абсолютный путь, `..` или ссылка наружу - `E024`, тема и резервные копии не тронуты, содержимое файла не читается. Архив для `--answers` кладут в папку сайта или ставят темой `heron theme get`. Демонстрационные страницы темы кладутся в каждый язык сайта и только туда, где файла нет: страница сайта не перезаписывается никогда. Нет страниц на языке сайта - берутся страницы основного языка, иначе первые. `theme get` перечисляет каждый разложенный файл темы и демо и число файлов, оставленных как есть, потому что у сайта они уже были. `heron theme pack` собирает архив из темы сайта и его контента - только если контент показывает всё, что объявил контракт темы (§7, «Демо темы и справка»; иначе `E037`, архив не пишется).

Сообщение об ошибке обязано содержать путь к файлу, номер строки, что не так и что сделать. `Ошибка в шаблоне` без адреса - не сообщение.

**Предупреждения:**

Формат строки ошибки: `<КОД> <путь>[:<строка>]: <сообщение>`, при подсказке следом строка `  что сделать: <подсказка>`; без пути - `<неизвестный файл>`. Так печатаются ошибки контента и сборки. Ошибка, прервавшая команду целиком (конфиг, тема, `heron page add`, `heron theme get`), печатается рамкой: код и название, `где`, `подробно`, `что сделать`.

**Вывод в терминал.** Текст темы, демо и сайта движок печатает видимым: управляющие символы C0 и C1 (кроме перевода строки и табуляции) выходят как `\x1b`, `\x07` и не выполняются - `ESC ] 52` не пишет в буфер обмена, `ESC [ 2 J` не стирает экран. Фильтр стоит на всём выводе команды (`heron.term`), а не у отдельных строк; цвет и жирный самого движка в терминале остаются, в файл и в канал они не попадают. Вывод `--json` (`check`, `page list`, `describe`) остаётся JSON: DEL, C1, U+2028/2029 и символы частной области в нём записаны кодом `\u009b`, и фильтру менять нечего. Такие символы в тексте темы `check --theme` называет ошибкой `E044`.

Предупреждения кода: `title` длиннее 60 знаков · `description` длиннее 155 · «картинка задана, а `image_alt` нет» (только если задан `image`; вид «прочее») · «`title` и `h1` совпадают» · «навигация `nav.main` пуста» (вид «seo», путь `site.yaml`) · «одинаковый `title` у N страниц (<язык>)» (среди индексируемых страниц одного языка) · «ссылок навигации нет в HTML главной (<язык>): меню строится скриптом».

Остальные предупреждения по ключам сообщений (тексты - `heron/texts/`):

| Область | Ключ | Когда |
|---|---|---|
| картинки | `media_heavy` | мастер весит слишком много |

| прочее | `build_svg_unsafe` | SVG в `media/`, `static/` или в теме с исполняемым содержимым (черновая сборка и `heron serve`; в `check` и боевой сборке - `E043`) |
| прочее | `build_implicit_folder` | папка со страницами без `_index.md` ни на одном языке (сайт 0.2): раздел собирается, совет - `heron category add <путь>` с переводом на каждом языке, где в папке есть страницы (иначе они уйдут из прод); путь - основного языка (только `heron check`) |
| переводы | `build_shared_differ` | файлы языков одной страницы расходятся в общих полях: тип, порядок, флаги, дата, вид раздела, свои поля темы без текста и без `translatable` (только `heron check`); обложка и картинка для соцсетей - свои у языка, в сверку не входят |
| прочее | `build_theme_translatable` | `translatable: true` у поля с текстом или у поля блока: флаг ничего не меняет, у них и так свой текст на каждом языке (`heron check`) |

«Секция в файле, которую тема не использует» и «отсутствие опциональной секции» - не предупреждения, а разделы отчёта `Report` (`unused_sections`, `missing_sections`); в счётчик «Предупреждений - N» и в `warnings.txt` они не попадают. Полный список пишется в `<рядом с dist>/.heron-cache/warnings.txt` строками `<вид>\t<путь>[:<строка>]\t<сообщение>` (вид по-русски, текст сообщения на языке сообщений; ошибка записи файла молча пропускается).

Отсутствие опциональной секции собирается в сводку долгов:

```
Тема ждёт секцию, а в файле её нет:
  contra       - 6 страниц: content/ru/design.md, content/ru/audit-basic.md, …
```

Строка перечисляет пути исходников `page.source`, до 5 штук, затем « …»; без списка строка не печатается.

**Обложка и старые адреса** (предупреждения `heron check`, не ошибки):

- `обложка меньше <images.cover_width> px: <путь>` (вид «картинки», число подставляется фактическое, по умолчанию 1200) - мастер обложки уже `images.cover_width`; что сделать: положить мастер не уже `images.cover_width`, иначе краулер получит маленькую картинку;
- `старый адрес <url> никуда не ведёт; вероятно, поставить 301 на <цель>: redirect_from: [<url>] во фронтматтере <файл>` (вид «редиректы», путь `old-urls`) - только с `--old-urls`; что сделать: добавить адрес в `redirect_from` указанной страницы или в `gone`.

Это тот самый список к заказчику, который иначе теряется. Он печатается после каждой сборки, а не вспоминается раз в квартал.

## 12. Отчёт `heron check` <a id="check-report"></a>

Без сборки, читает контент и тему и печатает:

- страницы по языкам и типам, что переведено, а что нет; «Перевод не готов» - страницы с `translation: pending` и опубликованы ли они в этой сборке (`20` §4.2)
- заполненность секций по каждому типу
- секции в файлах, которые тема не использует - ловит опечатку в якоре
- модули темы, которые не использует ни один тип
- внутренние ссылки: битые, и страницы, на которые никто не ссылается
- сироты: страницы, на которые не ведёт ни одна ссылка
- длины `title` и `description`
- разделы, которых нет в списке выше и которые печатает `Report.render`: «Формат секции не тот, которого ждёт тема (это не ошибка)» со строкой `<файл>: <секция> - ждали <формат>, пришло <формат>`; «В меню, но без короткого имени - покажется имя файла»; «`nginx -t` на собранном конфиге: прошёл»; «Ручная дата `updated` у M из N страниц перекрывает `updated_from`: <режим>».
- с `--old-urls <файл>`: каждый старый адрес должен вести на страницу, в `redirect_from` или в `gone`; по каждому без пути - предупреждение с предполагаемой целью и строкой сводки «старых адресов: N, без пути: M». Пустые строки и строки с `#` пропускаются, в CSV берётся первый столбец, похожий на URL. Адрес сравнивается так же, как его видит nginx: схема и хост отбрасываются, `%XX` и кириллица равны, со слешем и без - один адрес; регистр и языковой префикс различаются; параметры запроса учитываются только записями `gone` с параметром; повторы считаются один раз; в предупреждении печатается только путь; тексты предупреждений и сводки - на языке сообщений (§10, `--notes`)
- **разметка schema.org**: при сборке и в `check` - строки отчёта: «Разметка schema.org (словарь 29.3): узлов N, находок M (E ошибок, W предупреждений)», по каждой находке строка `КОД файл:путь - причина (страниц: K)` и «ключ исключения: ...»; затем «Исключения разметки: N» с причиной и сроком (или «разово (--allow-schema)»); «Лишнее исключение: <ключ> - ничего не ловит, уберите из schema_exceptions»; «Исключение просрочено: <ключ> - срок <дата> истёк, находка снова в силе»; сведение «Свойства из раздела pending: ...». В `--json` те же данные. На языке сообщений (§10, `--notes`).
- файлы в `media/`, которых не ждёт ни одна страница, и контент, осевший в `static/`
- папки без пояснительной записки `heron-readme.md` - информация, не ошибка
- комплект для агентов (`20` §1) - одна строка-сведение, не предупреждение: «`agents/`: инструкции для агентов, движок 0.1.0, ru; в сборку не входит», при расхождении версии - «комплект от 0.1.0, движок 0.2.0 - обновить: `heron init --agents`», при `build.agents: false` - «комплект отключён», без папки и без ключа - «комплекта нет - `heron init`»
- **поля, которые есть не у всех элементов списка**: у движка строгий режим неопределённых значений, и обращение к отсутствующему ключу роняет сборку. Шаблон пишут по первому элементу, а падает он на шестом. Это не ошибка контента - у половины документов действительно нет места выдачи; это предупреждение автору шаблона писать `d.get("place")`
- **изменение данных в шаблонах темы** - ошибка `E033` до сборки. Модуль `heron/core/check.py` шаблоны не исполняет, а разбирает самим Jinja (`Environment.parse` того же окружения, что у сборки) и ищет вызовы методов, которые закрывает песочница (§7): `.append`, `.extend`, `.insert`, `.update`, `.pop`, `.remove`, `.add`, `.setdefault`, `.clear`, `.sort`, `.reverse` и остальные из того же списка, в том числе обходные `x|attr('append')(…)` и `x['append'](…)`. Сообщение называет шаблон путём от корня сайта, номер строки, сам вызов и рецепт по смыслу метода (сложение списков, `namespace()`, `dict(d, key=value)`, фильтры `rejectattr`, `unique`, `sort`), в конце - `heron docs theme`; язык текста - язык сообщений (§10, `--notes`), в `--json` это поля `code`, `path`, `line`, `message`, `hint`. Разбираются `*.html`, `*.htm`, `*.j2`, `*.jinja`, `*.jinja2` темы, кроме `assets/` и `i18n/`, и файлы, которые шаблоны подключают по имени (`extends`, `include`, `import`, `from`). Не код для Jinja и не проверяются: текст вне тегов (JS в `<script>`, файлы `.js`), `{% raw %}`, комментарии; `{% set ns.x = … %}` - присваивание, а не вызов. Шаблон с битым синтаксисом пропускается - его называет сборка. **`check` здесь строже сборки:** он отмечает и шаблон, который тема не рендерит (сборка такой шаблон не трогает и проходит), и вызов меняющего метода у значения, чей тип статически не известен; глобальные значения плагинов проверяются по их настоящему типу. Не контейнерами `check` считает и потому не отмечает: `self` (блоки шаблона, `self.<блок>()`), псевдонимы `{% import … as h %}` (модуль шаблона) и объекты контекста движка `mod`, `t`, `env`, `page_of`, `picture`, `media_url`, `jsonld`, `cover_url`, `robots_meta` - например, `mod.update()` рендерит модуль `modules/update.html`. Имя, переопределённое в самом шаблоне (`set`, `for`, параметр макроса), уже не объект движка. Имена из `{% from … import x %}` к известным объектам не относятся: это может быть словарь, поэтому `{{ cfg.update({}) }}` даёт `E033` и в `check`, и в сборке. Как переписать такие места - [`guide/04`, «Накопление данных в шаблоне без `append`»](../guide/04-theme.md#accumulate-data-without-append)

В CI сайта команду добавляют сами: общий `site-image.yml` её не запускает, он собирает образ через `heron build`; локально - `scripts/site.sh <сайт> check`.

**Чего `check` не находит.** Он не рендерит шаблоны и ничего не пишет, поэтому не видит `E010`, `E026`, `E027`; проверки готовности прода `E017`, `E021`, `E028` выполняет только `build`. Зелёный `check` не гарантирует удачную сборку.

## 13. Производительность

Сайт на 40 страниц в трёх языках - это 120 страниц. Всё, кроме картинок, - разбор, связи, рендеринг, генераторы, запись - укладывается в пару секунд. Дорогая часть одна: кодирование нарезок.

Замер: 95 мастеров, 2062 нарезки, четыре ядра.

| Сборка | Время |
|---|---|
| холодная, кэша нет | 157 с |
| повторная, кэш цел, `dist` стёрт | 4 с, из них картинки 0.3 с |

Отсюда два правила. Первое: кэш нарезок обязан переживать удаление `dist`, иначе его нет вовсе. Второе: холодную сборку спасают только ядра - у прода и CI кэша нет по определению.

Где слушает `heron serve`: без `--host` - `127.0.0.1` на машине человека и `0.0.0.0` в образе HERON (там выставлен `HERON_IN_CONTAINER=1`). Внутри контейнера `127.0.0.1` - сам контейнер, и проброшенный порт `docker run -p 127.0.0.1:8000:8000` до такого сервера не доходит. Префикс `127.0.0.1:` публикует порт только на машину человека: без него docker открывает его всем интерфейсам компьютера. `--host 0.0.0.0` вне контейнера открывает черновики всей сети - движок об этом предупреждает. Порт занят - `E031` с подсказкой взять другой.

Инкрементального рендера страниц нет: `heron serve` пересобирает всё при изменении файла, и без картинок это пара секунд. Изменение определяется снимком «путь → (время, размер)» по `content/`, `data/`, `media/`, `img/`, `static/`, `theme/`, `plugins/` и файлам корня сайта за один обход: добавление, удаление, переименование и правка с тем же временем видны все. Комплект для агентов в снимок не входит: `agents/` не обходится, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` в корне пропускаются - правка инструкций сайт не меняет.

## 14. Тесты

Обязательные, без них работа не принимается:

- парсер секций: якоря, вложенные заголовки, дубликаты, текст до первой секции
- структурированные секции: facts, faq, steps, timeline на валидных и битых данных
- построение URL из путей, включая `_index.md` и языковые префиксы
- резолв связей, включая ссылку в никуда
- **каждый URL из карты редиректов отдаёт 301 на адрес, который существует и отвечает 200.** Это единственное, что защищает индекс при переезде. Проверяется на настоящем nginx, в том числе на не-ASCII адресах в обеих формах, без слеша и на обрезанном слаге (`tests/test_redirects_unicode.py`, `tests/test_gone.py`)
- каждая собранная страница содержит ровно один `<h1>`
- все внутренние ссылки в собранном HTML ведут на существующие файлы
- `hreflang` симметричен: если A ссылается на B, то B ссылается на A
- sitemap не содержит страниц с `noindex` и содержит все остальные
- две сборки подряд дают побайтово одинаковый результат
- **комплект для агентов не влияет на сборку:** `dist/` сайта с `agents/` и корневыми указателями побайтово равен `dist/` того же сайта без них; ни одного файла комплекта в `dist/`; `serve` не реагирует на правки в `agents/`
- `new --notes ru|en` кладёт комплект своего языка, `AGENTS.md` сайта - 60-100 строк, `CLAUDE.md` и `GEMINI.md` - ровно `@AGENTS.md`; все относительные ссылки в `agents/**` и `AGENTS.md` ведут на существующие файлы; `init --agents` не трогает правленный файл и заменяет нетронутый; `build.agents: false` держится
- `heron schema --export` дважды даёт одинаковые байты; образцы `templates/{site.yaml,theme.yaml,page.md}` проходят свои схемы; `errors.json` содержит каждый код из §11
- **паритет документации** (`23` §10): у каждого `docs/ru/**` есть `docs/en/**` с тем же путём и наоборот (кроме `docs/en/GLOSSARY.md`); одинаковое число строк, заголовков каждого уровня, пунктов списков, таблиц и строк в них, блоков кода и строк в каждом; та же последовательность явных якорей заголовков (`<a id="…"></a>`, `23` §10); то же множество относительных ссылок и их целей; в образцах `.yaml` и во фронтматтере `page.md` - те же ключи и значения не-строковых полей. Побайтно сравниваются только литеральные токены - команды, флаги, ключи, коды ошибок, пути, имена файлов; текст, комментарии и подписи внутри блоков кода переводятся; на `beta` и `prod` - перевод не отстаёт от исходника по `docs/translation.yaml`
- в документации и комплекте нет имени конкретного агента или компании-разработчика нейросетей вне перечня «какой агент какой файл читает» (белый список в тесте); сайт движка - только `sitebuilder.heron.software`

Отдельно, за пределами unit-тестов: Lighthouse в поставку движка не входит, прогон и пороги настраивает сам сайт (`22-deploy.md` §4); ориентир - LCP менее 2 секунд, CLS менее 0.05.

## 15. Точки расширения

Модули из `heron/modules/` и внешние плагины пишутся против одного набора хуков. Разница только в поставке: модуль лежит в ядре, плагин ставится пакетом и объявляется в `site.yaml`.

Плагин - функция `register(hooks)`, вызывается при загрузке, при каждой сборке и проверке заново (состояние модуля между сборками не сохраняется). Подписка на хук - `hooks.on(<имя хука>, функция)`, свой тип секции - `hooks.on("block:<имя>", функция)`. Пример: в `plugins/<имя>/__init__.py` - `def register(hooks): hooks.on("on_generate", f)`, в `site.yaml` - `plugins: [<имя>]`.

| Хук | Когда вызывается | Аргументы → результат | `check` |
|---|---|---|---|
| `on_config` | после загрузки `site.yaml` и `theme.yaml` | `(config, theme)` - правка или проверка конфига | да |
| `block:<имя>` | при разборе секции с классом `{#id .<имя>}` | `(section)` → данные секции; `section.kind = <имя>`. Встроенные типы так не подменяются | да |
| `on_page_parsed` | после разбора каждой страницы, до связей | `(page)` - правка модели страницы | да |
| `on_tree_built` | после обхода `content/`, `data/` и дат, до связей | `(site)` - свои связи и группировки | да |
| `hooks.filter(имя, f)` / `hooks.add_global(имя, v)` | при сборке окружения Jinja2 | свои фильтры и переменные темы; встроенные имена не перекрываются | - |
| `on_page_rendered` | после рендера каждой страницы | `(page, html)` → новый HTML или `None`. Обработчики идут цепочкой: каждый получает результат предыдущего | - |
| `on_generate` | после генераторов, до проверки владельцев | `(site, config)` → `{путь: текст}` - свои файлы сборки; совпадение с чужим путём - `E026` | - |
| `on_build_finished` | **после** записи результата, только удачной сборки | `(site, config, dist)` - экспорт, уведомления. Исключение не делает сборку неудачной: сайт записан (`result.failed` ложно), ошибка - в `result.finish_errors`, `heron build` пишет «сайт записан и цел, но упало завершающее действие» и выходит с **кодом 3**. Остальные обработчики `on_build_finished` при этом всё равно вызываются | - |

`on_build_finished` раньше вызывался до записи и мог вернуть файлы. **Совместимость:** файлы оттуда больше не записываются - сборка проходит и печатает пояснение «файлы сборки объявляются в `on_generate`»; плагину нужно перенести генерацию в `on_generate` и принять третий аргумент `dist`. Неудачная сборка (ошибка или предупреждение в строгом режиме) до `on_page_rendered`, `on_generate` и `on_build_finished` может не дойти - они не обязаны вызываться.

Больше на старте не заводим: API, придуманный под будущее, всегда придуман неправильно.

**Хуки действуют только на этапе сборки.** Плагина, который «принимает форму», не существует - в момент POST движок уже отработал и вышел. Всё, что живёт в рантайме, будет принимать отдельный сервис `heron-relay`; он пока не реализован (см. `23-distribution.md`).

Источники плагинов и порядок разрешения - `core/resolver.py`: локальная папка `plugins/` сайта → установленный пакет (entry point группы `heron.plugins`). Локальный сильнее.
