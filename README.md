### С HERON создавать сайты — просто.

Файловый движок сайтов. Контент в markdown, тема на Jinja2 — на выходе статический сайт или готовый образ nginx.

> ### ⚠️ Проект в разработке
>
> Движок собирает сайты, но ещё ни один сайт на нём не работает вживую. Релиза нет, версия не зафиксирована, контракты `site.yaml` и `theme.yaml` могут поменяться без обратной совместимости.
>
> **Не рекомендуется к использованию, если вы не понимаете, что делаете.** Ставить его на боевой сайт сейчас — значит подписаться на правку конфигов при каждом обновлении.

## Что это

Сайт — это папка: контент, картинки, тема, один конфиг. HERON читает её и отдаёт готовый HTML. Ни базы, ни админки, ни PHP — в проде работает только nginx, отдающий файлы.

- **Markdown — склад контента, тема — раскладка.** Порядок секций в файле не влияет на порядок блоков на странице. Связь между ними по идентификаторам.
- **Путь файла определяет URL.** Новая страница — это один новый файл. Она сама появляется в меню, каталоге, sitemap, hreflang и `llms.txt`.
- **SEO из коробки, а не отдельной задачей.** sitemap, канониклы, hreflang, JSON-LD, `llms.txt` и карта редиректов генерируются из того же фронтматтера, которым написана страница.
- **Движок не живёт в репозитории сайта.** Он приходит образом и прибивается версией в `site.yaml` — один движок на любое число сайтов, без копий и расхождений.

## Быстрый старт

Ничего клонировать не нужно. Движок — это один образ, и он умеет две команды:
создать папку сайта и собрать её.

```bash
docker pull ghcr.io/fmstm/heron:prod
```

Создать сайт:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" \
  ghcr.io/fmstm/heron:prod new мой-сайт
```

В папке появятся `site.yaml`, `content/`, `img/`, `static/`, `theme/`. Откройте
`site.yaml` и впишите домен, языки и меню — это единственное место, где сайт
описан. Затем догоните структуру под написанное:

```bash
docker run --rm -v "$PWD/мой-сайт:/site" --user "$(id -u):$(id -g)" \
  ghcr.io/fmstm/heron:prod init
```

Под каждый язык из `site.yaml` появится своя папка в `content/`. Дальше пишете
страницы в markdown и собираете:

```bash
docker run --rm -v "$PWD/мой-сайт:/site" --user "$(id -u):$(id -g)" \
  ghcr.io/fmstm/heron:prod build
```

Готовый сайт — в `мой-сайт/dist/`. Это обычная папка со статикой, её кладут на
любой хостинг. Посмотреть локально:

```bash
docker run --rm -p 8080:8080 -v "$PWD/мой-сайт/dist:/usr/share/nginx/html:ro" \
  nginxinc/nginx-unprivileged:1.27-alpine
```

`--user` не косметика: без него `dist/` окажется во владении root, и править его
вы потом не сможете.

## Дев-сборка и боевая

У сайта два режима, и переключаются они одним флагом:

```bash
… ghcr.io/fmstm/heron:prod build              # дев: закрыт от индексации
… ghcr.io/fmstm/heron:prod build --env prod   # боевой: индексация и счётчики
```

Дев-сборка отдаёт `robots.txt` с `Disallow: /`, ставит на страницы `noindex` и не
вставляет счётчики. Это режим по умолчанию: забыть закрыть сайт от поисковиков
нельзя, открыть его нужно осознанно.

**Версия движка к этому отношения не имеет.** Дев-сайт собирают тем же стабильным
образом `:prod`. Образы `:dev` и `:stage` — это ветки разработки самого движка,
они нужны только тем, кто движок и пишет.

## Сайт внутри образа nginx

Если сайт удобнее возить образом, а не папкой, рядом с `dist/` кладут три строки:

```dockerfile
FROM nginxinc/nginx-unprivileged:1.27-alpine
COPY dist /usr/share/nginx/html
EXPOSE 8080
```

```bash
docker build -t мой-сайт:1.0 мой-сайт
```

Движка в готовом образе нет — только nginx и статика.

## Если сайтов несколько

Когда сайтов больше одного, набирать `docker run` руками надоедает. В репозитории
движка есть `scripts/site.sh`: он держит настройки каждого сайта в отдельном файле
и делает то же самое одной командой.

```bash
git clone https://github.com/FMSTM/HERON.git && cd HERON
cp env/.env.example env/.env.мойсайт.dev   # впишите путь к папке сайта

./scripts/site.sh мойсайт build dev        # собрать
./scripts/site.sh мойсайт serve dev        # посмотреть на localhost:8080
./scripts/site.sh мойсайт image prod       # упаковать в образ nginx
```

Что и каким движком собирается, задаётся в том же файле: `SITE_ENV` — каким будет
сайт, `ENGINE` — каким движком его собрать. Пример рядом, с пояснениями.

## Пакетом, без докера

```bash
pip install git+https://github.com/FMSTM/HERON.git@prod
heron new мой-сайт && cd мой-сайт
heron check     # что не так с контентом и конфигом
heron serve     # локальный просмотр с пересборкой
heron build     # → dist/
```

## Безопасный запуск

Сборщику статики не нужно ничего — ни сети, ни прав, ни секретов. Так его и запускаем в CI и на сервере:

```bash
docker run --rm \
  --network=none \
  --read-only --tmpfs /tmp \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --user "$(id -u):$(id -g)" \
  -v "$PWD:/site" \
  ghcr.io/fmstm/heron:prod build --strict
```

Сборка идёт без сети: всё, что нужно сайту, лежит в папке сайта. Docker-сокет внутрь контейнера не пробрасывается никогда: упаковка сайта в образ — отдельный шаг на хосте, а не из контейнера.

Ровно этот запуск проверяется в CI на каждый пуш: образ создаёт сайт, собирает его и сверяет, что две сборки подряд дали одинаковые байты.

## Образы

Публикуются в [GitHub Container Registry](https://github.com/FMSTM/HERON/pkgs/container/heron).

**Собирайте сайты тегом `:prod`.** Остальные теги — это ветки разработки самого
движка, а не режимы вашего сайта: закрытая от индексации дев-сборка делается
флагом `--env`, а не сырым образом.

| Тег | Что это | Кому |
|---|---|---|
| `ghcr.io/fmstm/heron:prod` | то, на чём стоят сайты | всем, кто делает сайты |
| `ghcr.io/fmstm/heron:stage` | обкатка перед выпуском | тем, кто пишет движок |
| `ghcr.io/fmstm/heron:dev` | текущая разработка, может не работать | тем, кто пишет движок |
| `ghcr.io/fmstm/heron:sha-<хеш>` | конкретный коммит | для отладки |
| `ghcr.io/fmstm/heron:X.Y.Z` и `:latest` | релиз | появится с первым тегом |

Релизов пока нет, поэтому `:latest` не существует — это осознанно: тег, который никто не проверял на живом сайте, обещает то, чего никто не может сдержать.

Сайт указывает требуемую версию первой строкой `site.yaml`:

```yaml
heron: ">=0.3,<0.4"
```

Движок сверяет себя с этим требованием до всего остального и отказывается собирать сайт, версию которого не поддерживает.

## Разработка

```bash
git clone git@github.com:FMSTM/HERON.git && cd HERON
uv sync --group dev
uv run pytest
uv run heron --version
```

Ветки: `dev` — основная разработка, каждая фича своей веткой. `stage` — обкатка. `prod` — то, что работает; релиз режется тегом `vX.Y.Z`. Бейдж сборки вверху показывает `dev`, потому что там идёт работа.

**Граница ядра:** движок не знает ни про один конкретный сайт — ни имён, ни доменов, ни слагов разделов. Проверяется хуком `scripts/check-boundaries.sh` на каждый коммит и в CI по всем файлам репозитория, включая документацию и тесты.

```bash
pre-commit install
```
