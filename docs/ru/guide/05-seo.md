# 05 · SEO

Этот раздел - для того, кто отвечает за то, как сайт находят в поиске: человека или AI-агента в роли «Контент и SEO». Разберём, что движок делает для поисковиков сам, что нужно заполнить вам и как переехать со старого сайта, не потеряв позиции в выдаче.

> **Без Docker?** В командах ниже всё, что стоит до имени образа (`ghcr.io/fmstm/heron:…`) включительно, замените словом `heron` - подробнее [в разделе об установке](00-install.md#without-docker). Команды запускаются из папки, в которой лежит папка сайта `мой-сайт`.

## Что движок делает сам

Всё в этой таблице вы не пишете руками, и отдельным файлом это не хранится. Движок собирает это заново при каждой сборке - из страниц и `site.yaml`. Поэтому оно никогда не устаревает: поменяли заголовок страницы - на следующей сборке поменяются и `<title>`, и карта сайта, и разметка.

| Что | Откуда берётся | Подробно |
|---|---|---|
| `<title>`, meta description, canonical | `title` + `seo.title_suffix`, `description`, адрес страницы | [`20` §4.2](../spec/20-data-contract.md#frontmatter) |
| Open Graph и Twitter - карточка ссылки в соцсетях и мессенджерах | поля групп 3-4 SEO-блока, иначе `title`/`description`/`seo.og_default_image` | [`20` §4.2](../spec/20-data-contract.md#frontmatter) |
| `sitemap.xml` - карта сайта для поисковиков | все опубликованные индексируемые страницы, `lastmod` из `updated` | [`21` §9](../spec/21-engine.md#sitemap) |
| hreflang в `<head>` и в карте - связь переводов одной страницы | переводы находятся по имени файла, `x-default` - язык по умолчанию | [`20` §3](../spec/20-data-contract.md#languages) |
| `robots.txt` | `seo.robots_extra` + строка `Sitemap:`; на черновой сборке (dev) - только `Disallow: /` | [`21` §9](../spec/21-engine.md#robots-txt) |
| JSON-LD - разметка schema.org | тип от темы, данные от страницы и блока `schema` в `site.yaml`, крошки, FAQ | [`21` §9](../spec/21-engine.md#json-ld) |
| `llms.txt`, `llms-full.txt` - описание сайта для нейросетей | дерево страниц, `description`, `seo.llms_note` | [`21` §9](../spec/21-engine.md#llms-txt) |
| 301 и 410 - перенаправления и «адреса больше нет» | `redirect_from` страниц и `gone` в `site.yaml`, сразу в конфиг nginx | [`21` §9](../spec/21-engine.md#redirects) |
| картинка в выдаче | обложка страницы - одна картинка во все места: `og:image`, `twitter:image`, `primaryImageOfPage` в JSON-LD и первая картинка записи в `sitemap.xml`. `primaryImageOfPage` появляется, только если тема объявила для типа страницы `WebPage` или производный тип (`types.<тип>.jsonld`); стартовая тема этого не делает | [`20` §6, «Обложка страницы»](../spec/20-data-contract.md#page-cover) |
| крупные превью | `<meta name="robots" content="max-image-preview:large, max-snippet:-1, max-video-preview:-1">` на каждой индексируемой странице боевой сборки | [`21` §7](../spec/21-engine.md#cover-robots) |
| карта картинок | `<image:image>` в записи страницы: сначала обложка, затем картинки из текста, не больше 20 | [`21` §9](../spec/21-engine.md#sitemap) |
| имя сайта | `WebSite` с `name` и `alternateName` на главной, из `site.name` и `site.alternate_names`. Только если тип страницы объявляет `WebSite` в `jsonld` в `theme.yaml` (обычно тип `home`). Стартовая тема `jsonld` не объявляет: этих узлов на ней нет, а `og:image` и карта картинок работают | [`21` §9](../spec/21-engine.md#json-ld) |
| закрытая черновая сборка | без `--env prod`: `noindex` на всём, `Disallow: /`, без счётчиков | [`23`, «Версия движка и окружение сайта»](../spec/23-distribution.md#engine-version-vs-site-environment) |

## Что заполняете вы <a id="you-fill"></a>

### На каждой странице

Вверху каждого файла страницы - SEO-блок. Обязательна его группа 1:

- `title` - заголовок для выдачи, до 60 знаков. Окончание с названием сайта движок добавит сам;
- `h1` - заголовок на самой странице, для того, кто её уже открыл. Не копия `title`: если они совпадают, движок предупредит;
- `description` - описание под заголовком в выдаче, до 155 знаков: что человек получит на этой странице;
- группа 2 «ключевые запросы» - движок её не читает, это ваша рабочая записка. Правило: один интент (то, что человек хочет найти) - одна страница. Если у двух файлов один и тот же основной запрос, их стоит слить в одну страницу.

Остальные группы заполняйте по надобности: своя картинка для соцсетей (группа 3), уточнение разметки (5), картинка в каталоге и `alt` к ней (6), дата публикации и `noindex` (7), старые адреса (8).

### Один раз на весь сайт

Это настройки в `site.yaml`. Большую часть удобнее заполнить в конфигураторе (`setup`, см. [02 · Первый сайт](02-first-site.md)), но вот как они выглядят в файле:

```yaml
site:
  domain: example.com
  name: Workshop
  name_ru: Мастерская        # значение для русских страниц
seo:
  title_suffix: " - Workshop"
  title_suffix_ru: " - Мастерская"
  og_default_image: media/og/default.jpg
  llms_txt: true
  llms_note:                 # факты о сайте для нейросетей, по языкам
    en: |
      Phone for bookings: …
    ru: |
      Телефон для записи: …
contact: { phone: "…", city: "…" }
organization: { name: "…" }
schema:
  entity:                    # сквозной узел: кто стоит за сайтом
    "@type": Organization
    name: "{{ organization.name }}"
    telephone: "{{ contact.phone }}"
analytics:
  ga4: G-XXXXXXX
```

`{{ … }}` в блоке `schema` - подстановки из того же `site.yaml`. Телефон и адрес записаны в одном месте, поэтому на страницах и в разметке они всегда одинаковые. → [`20` §5, «Блок schema»](../spec/20-data-contract.md#schema-block)

### Обложка страницы

Обложка - картинка, которую видят в карточке ссылки в мессенджере и, если повезёт, в выдаче Google. Какую фотографию сделать обложкой, решаете вы; остальное движок делает сам.

- **Откуда берётся.** Первая найденная: `og_image` страницы, затем `image`, затем первая картинка во вводном блоке или в `hero` (блок первого экрана), затем `seo.og_default_image` сайта. Подпись к картинке - `og_image_alt`, иначе `image_alt`.
- **Размер.** Не меньше 1200 px по ширине. Меньшая картинка отдаётся как есть, а `heron check` предупредит: «обложка меньше 1200 px».
- **Композиция.** Лицо или главный предмет - в центральной трети кадра. Соцсети и выдача обрезают превью по-разному, края пропадают первыми.
- **Без прозрачности.** Подложку движок не добавляет: прозрачный PNG у поисковика окажется на чёрном или белом фоне.
- **Обложки нет вообще** - на странице не будет `og:image` и `primaryImageOfPage` (если тема его объявляла), `heron check` предупредит. Сборку это не остановит, но превью в мессенджере будет пустым.
- **Ваше значение главнее.** Если вы сами задали `primaryImageOfPage` или `entity.image` в блоке `schema`, движок не заменит их вычисленной обложкой.

### Как сайт называют люди

`site.alternate_names` - другие названия, по которым ищут сайт: старое имя, транслитерация, сокращение. Для отдельного языка - `alternate_names_ru` и так далее. В разметку они попадают, только если тема объявила `WebSite` для типа страницы:

```yaml
types:
  home:
    jsonld: [WebSite]
```

Иначе эти значения ни на что не влияют, и движок об этом не предупреждает.

```yaml
site:
  name: Workshop
  alternate_names: [Workshop Studio, Мастерская]
  alternate_names_ru: [Воркшоп]
```

Пустой список - ключа в разметке нет. Пишите сюда только то, как люди на самом деле называют и ищут сайт, а не ключевые запросы.

### Цены в разметке

По умолчанию запрещены (ошибка `E020`): если на страницах сайта цен нет, они не должны появиться и в JSON-LD. Разрешить - `seo.allow_prices: true`.

### Дата обновления

`lastmod` в карте сайта и `dateModified` в разметке берутся из `updated` в SEO-блоке страницы. Если его нет - из источника `build.updated_from`:

- `git` - дата последнего коммита файла;
- `file` - время изменения файла;
- `manual` - только то, что вписано руками.

Вписанное руками `updated` сильнее источника. Если при переносе сайта вписать его всем страницам, даты из git работать перестанут - отчёт после сборки покажет, у скольких страниц так вышло. Поисковику даты уходят полным ISO 8601 с часовым поясом: из git - время коммита (`2026-10-17T11:30:12+02:00`), день, вписанный руками, - полночь UTC (`2026-10-14T00:00:00+00:00`). На самой странице подпись остаётся просто датой. Дата из будущего и обновление раньше публикации - предупреждения, а при `--strict` - ошибки.

## Картинка и дополнительные ссылки в Google <a id="google-images-sitelinks"></a>

Честно о границах: движок готовит всё, что зависит от сайта, но что показать в выдаче, решает Google.

- **Картинка в выдаче.** Разметка и карта картинок дают поисковику право показать картинку, но не обязывают его. После выкладки обычно проходит 2-3 недели, пока картинка появится, а у части страниц она не появится вовсе.
- **Что проверить после выкладки:**
  1. Rich Results Test (отдельный инструмент Google для проверки расширенных результатов): вставьте адрес страницы и убедитесь, что разметка читается без ошибок и `primaryImageOfPage` на месте.
  2. В Search Console: «Проверка URL» -> «Запросить индексирование» - для главной и нескольких главных страниц после выкладки.
  3. В Search Console: отчёт «Картинки» (раздел эффективности поиска, тип поиска «Картинки»): через несколько недель там должны появиться показы.
- **Дополнительные ссылки (sitelinks) разметкой не включаются.** Специальной разметки для них нет, и движок её не придумывает - Google строит их сам. На это влияют: понятная навигация в HTML (меню из обычных ссылок), крошки, уникальные `title` у страниц, отсутствие дублей и брендовый спрос - сколько людей ищет сайт по названию. Первое в ваших руках, последнее приходит со временем.
- **Крупные превью** (`max-image-preview:large`) движок включает в `<head>` сам. Отключить можно только закрыв страницу от поиска: `noindex: true`.
- **Дев-сборка.** Без `--env prod` страницы закрыты `noindex, nofollow`, картинок в `sitemap.xml` нет, адреса ведут на дев-домен. Проверять на ней показ в Google бессмысленно.

## Проверка разметки schema.org <a id="schema-check"></a>

Внутри движка лежит словарь schema.org версии 29.3, и каждый узел вашей разметки сверяется с ним. Так ловится то, что поисковик потом молча проигнорирует: типа нет в словаре, свойство не подходит типу, значение не из перечисления, у значения не тот тип, использовано устаревшее, картинка из разметки не попала в сборку. Это коды `SCH001`-`SCH006`, полный список - [`21` §11](../spec/21-engine.md).

**Боевая и черновая сборка.** С `--env prod` находка - ошибка, и сборка останавливается. В остальных окружениях это предупреждение: сайт собирается, а в отчёте появляется строка с находкой. Чтобы заранее увидеть, что остановит боевую сборку, не собирая сайт:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check мой-сайт --env prod
```

**Как читать находку.** В отчёте строка вида `КОД файл:путь - причина (страниц: K)`:

- код - что не так;
- файл и путь - где поправить;
- число страниц - сколько страниц это затрагивает. Одинаковая находка с разных страниц и языков приходит одной строкой.

Под строкой - «ключ исключения»: готовая строка, которую можно скопировать (о нём ниже). С `--env prod` та же находка приходит ошибкой в короткой форме: `КОД файл: причина`, без пути и числа страниц; ключ исключения печатается и там.

**Сначала исправьте.** Исключение нужно, только когда исправить сейчас нельзя. Чаще всего исправление - замена свойства или типа, как в примере с врачом ниже.

**Как оформить исключение.** Это запись в `site.yaml`; причина обязательна, срок - по желанию:

```yaml
schema_exceptions:
  - key: "SCH002:site.yaml:schema.entity.worksFor"   # ключ скопирован из отчёта
    reason: "переход на practicesAt после смены темы"
    until: 2026-12-31                                  # необязательно
```

- без `reason` сборка остановится с `E011`; тот же ключ дважды - тоже `E011`;
- после даты `until` исключение перестаёт действовать: находка возвращается, а отчёт пишет «Исключение просрочено»;
- исключение, которое ничего не поймало, отчёт назовёт лишним - уберите его;
- пропустить находку один раз, не правя файл: `check мой-сайт --allow-schema "<ключ>"`, так же работает у `build`;
- исключение, записанное через конфигуратор, бессрочное: если такой ключ уже был (в том числе просроченный), причина заменяется, а срок `until` снимается. Нужен срок - поставьте его руками.

**Конфигуратор тоже проверяет.** Перед тем как записать `site.yaml`, `setup` проверяет сквозной узел и блоки `schema` и показывает три списка: действующие находки, исключённые и просроченные. Находку можно убрать из файла или записать исключением - тогда конфигуратор попросит причину.

### Пример: врач, было и стало

Все данные вымышленные. Раньше врача описывали как `Physician` и привязывали к клинике через `worksFor`:

```yaml
schema:
  entity:
    "@id": "#owner"
    "@type": Physician
    name: "Иван Образцов"
    worksFor:
      "@type": MedicalClinic
      name: "Клиника Образец"
    medicalSpecialty: "первичная помощь"
```

Начиная с релиза 24.0 конкретный врач в словаре - `IndividualPhysician`. Это организационный тип, поэтому `worksFor` у него недопустим (`SCH002`). Место работы задаётся свойством `practicesAt` с типом из списка словаря, а специальность - только значением `MedicalSpecialty`, адресом вида `https://schema.org/<имя>`:

```yaml
schema:
  entity:
    "@id": "#owner"
    "@type": IndividualPhysician
    name: "Иван Образцов"
    practicesAt:
      "@type": MedicalClinic
      name: "Клиника Образец"
    medicalSpecialty: https://schema.org/PrimaryCare
```

Свойство `practicesAt` в словаре пока числится в разделе pending: оно допустимо, и отчёт лишь упомянет его для сведения. Если специальность записана произвольной строкой, это `SCH003`: значение не из перечисления. → [`20` §5, «Блок schema»](../spec/20-data-contract.md#schema-block)

## Языки

- Перевод - это файл с тем же именем в папке другого языка. hreflang и переключатель языков появятся сами.
- У перевода может быть свой адрес (`slug`): переводы связаны по имени файла, а не по адресу.
- Язык один - нет ни hreflang, ни языковых карт сайта, ни `llms-<язык>.txt`: лишнее не генерируется.
- Перевода нет - в отчёте предупреждение, в переключателе этот язык неактивен, а ссылки на такую страницу с других языков ведут на версию на языке по умолчанию.
- Основной язык пуст - боевая сборка остановится (`E021`).

## Переезд со старого сайта <a id="migrate-from-old-site"></a>

Цель переезда: ни один адрес, который поисковик уже знает, не должен отдать 404. Каждый старый адрес либо перенаправляется (301) на новую страницу, либо честно отвечает «адреса больше нет» (410).

1. **Выгрузите старые адреса.** Откуда взять список:
   - Search Console -> «Страницы» -> экспорт (CSV; движок берёт первый столбец, похожий на адрес);
   - старая карта сайта (`sitemap.xml`) - выпишите адреса по одному на строку;
   - выгрузка WordPress или логи сервера.

   Сохраните список в файл `old-urls.txt` рядом с папкой сайта: по адресу на строку, строки с `#` и пустые пропускаются. Затем проверьте:

   ```bash
   docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod check мой-сайт --old-urls old-urls.txt
   ```

   Каждый адрес должен вести на страницу, быть в `redirect_from` или в `gone`. Остальные попадут в предупреждения - с подсказкой, куда, вероятно, их перенаправить:

   ```
   старый адрес /uslugi-dlya-primera/ никуда не ведёт; вероятно, поставить 301 на /ru/uslugi/: redirect_from: [/uslugi-dlya-primera/] во фронтматтере ru/uslugi.md
   старых адресов: 120, без пути: 7
   ```

   Чтобы закрыть предупреждение, добавьте адрес в `redirect_from` подсказанной страницы (или другой, если движок не угадал) либо в `gone`, и запустите проверку снова. Работа закончена, когда в сводке «без пути: 0».

   **Адрес без языкового префикса.** Старые адреса обычно без `/ru/`, а в новом сайте у неосновного языка префикс есть. Для сервера `/x/` и `/ru/x/` - разные адреса, поэтому перенаправление с `/ru/x/` старый `/x/` не обслужит. Пример: старая страница `/uslugi-dlya-primera/` (вымышленный адрес), новая живёт на `/ru/uslugi/`. Записывайте старый адрес ровно так, как он был, без префикса:

   ```yaml
   redirect_from:
     - /uslugi-dlya-primera/
   ```

   **Регистр.** `/About/` и `/about/` для сервера - разные адреса: записывайте как в выгрузке. Адреса сравниваются так же, как их видит nginx: `https://` и домен отбрасываются, закодированная кириллица (`%D0%BE…`) и обычная считаются одним адресом, со слешем на конце и без - тоже; параметры запроса учитываются только записями `gone` с параметром; повторы в файле считаются один раз.

   Куда перенаправить, движок угадывает по последней части адреса, похожей на слаг или заголовок страницы. Если ничего не нашлось, он предлагает главную этого языка - и тогда решаете вы: подходящая страница или `gone`.
2. **Адрес переехал** - впишите его в SEO-блок новой страницы:

   ```yaml
   redirect_from:
     - /старая-страница/
     - /%D1%81%D1%82%D0%B0%D1%80%D0%B0%D1%8F/
   ```

   Кириллица и percent-encoding приводятся к одному виду: обе формы выше - один адрес, и 301 сработает на любую из них, со слешем и без.
3. **Адреса больше нет** - впишите его в `gone` в `site.yaml`. Сервер ответит 410, и поисковик уберёт адрес из выдачи быстрее, чем после 404:

   ```yaml
   gone:
     - /sample-page/        # ровно этот адрес
     - /wp/*                # всё под /wp/
     - /?p=*                # главная с параметром p
   ```

4. **Соберите сайт.** Движок проверит, что старый адрес не совпадает с живой страницей, не ведёт в два места и не образует цепочку перенаправлений (`E009`), а 410 не пересекается со страницами и перенаправлениями (`E022`).
5. **Проверьте на образе.** Если у вас есть клон репозитория движка, `scripts/site.sh <сайт> smoke prod` поднимает nginx с сайтом и проверяет ответы 200, 404, каждый 301 и каждый 410 - подробнее в [06 · Сборка и выкладка](06-deploy.md).

Подробно: [`20` §2, «Старые адреса»](../spec/20-data-contract.md#old-addresses-cyrillic), [`22` §6](../spec/22-deploy.md#migrate-existing-site).

## Перед выкладкой

Последний шаг - боевая сборка в строгом режиме:

```bash
docker run --rm -v "$PWD:/site" -w /site --user "$(id -u):$(id -g)" ghcr.io/fmstm/heron:prod build мой-сайт --env prod --strict
```

`--strict` превращает предупреждения в ошибки: битая ссылка, картинка без `alt` или незаполненная обязательная связь не попадут на живой сайт. В отчёте сборки страницы посчитаны по типам разметки - так видно, что JSON-LD есть на всех.
